# Rebuntu 2 — Phase 0.0
# Repository Architecture, Project Skeleton & Evolution Contract

You are establishing the initial repository architecture of Rebuntu 2.

This is Phase 0.0.

The next phase, Phase 0.1, will implement the first real runtime
subsystem: a CPU-only native system LLM service based initially on
Microsoft BitNet b1.58 2B4T.

DO NOT implement Phase 0.1 in this task.

Phase 0.0 exists to create the structural, semantic, engineering, and
development foundation on which Rebuntu can evolve.

This is NOT merely:

    mkdir src tests docs

The repository structure itself should partially explain what Rebuntu is,
how it is engineered, how new functionality is discovered and integrated,
and how future contributors/agents should reason about the project.

At the same time:

    DO NOT PRETEND THAT THE FINAL REBUNTU ARCHITECTURE IS ALREADY KNOWN.

The complete functional scope of Rebuntu is intentionally open-ended.

======================================================================
0. REBUNTU IDENTITY
======================================================================

Rebuntu is a standalone, Python-first Linux system-management,
automation, monitoring, coordination, verification, recovery, security,
experimentation, and semantic-processing environment.

It lives ABOVE Linux while being deliberately grounded IN Linux.

Rebuntu should be capable of operating on the computer as a coherent
system rather than merely exposing wrappers for individual commands.

It should eventually be able to:

    observe system state
    operate on system state
    coordinate system mechanisms
    automate recurring/reactive behavior
    declare desired state
    detect divergence
    verify outcomes
    preserve evidence
    diagnose failures
    recover from failures
    enforce policies
    protect the system
    process unstructured system information
    expose coherent interfaces to humans and software

However, this list is NOT a closed specification.

Important functionality is expected to be discovered during development.

Rebuntu is also deliberately an educational systems project.

It should provide opportunities to learn:

    Linux internals
    kernel mechanisms
    process/service management
    IPC
    filesystems
    networking
    security
    resource management
    event systems
    observability
    system programming

without unnecessarily recreating mechanisms Linux already provides.

======================================================================
1. WHAT REBUNTU IS NOT
======================================================================

Rebuntu is NOT:

- a Linux distribution;
- a giant Bash framework;
- a collection of aliases;
- a collection of arbitrary shell wrappers;
- an inventory of Linux APIs;
- a directory tree containing every type of Linux object;
- a replacement for systemd;
- a replacement for the kernel;
- an unrestricted LLM-to-shell interface;
- an autonomous shell-command generator;
- a synthetic mind;
- a cognitive architecture;
- an AGI framework.

Do not anthropomorphize Rebuntu.

Do not structure it around psychological/cognitive categories such as:

    perception
    cognition
    consciousness
    thought
    executive function
    memory systems

Use systems/software terminology instead:

    observation
    state
    event
    condition
    policy
    coordination
    operation
    execution
    workflow
    scheduling
    verification
    evidence
    diagnosis
    recovery
    reconciliation
    semantic processing

2. CORE ENGINEERING PRINCIPLE
======================================================================

If Linux already provides the appropriate primitive, Rebuntu should use
that primitive instead of recreating it.

Before implementing any Linux-facing mechanism, future development should
ask:

    1. What Linux mechanism actually implements this?
    2. What is the appropriate interface to that mechanism?
    3. What does Rebuntu add above it?

Relevant native mechanisms may include:

    systemd
    D-Bus
    journald
    procfs
    sysfs
    udev
    cgroups v2
    namespaces
    Linux capabilities
    seccomp
    inotify
    fanotify
    netlink
    Unix sockets
    pipes
    signals
    epoll
    eventfd
    signalfd
    configfs
    eBPF
    tracepoints
    perf
    kernel audit facilities

Use the lowest APPROPRIATE native abstraction.

"Kernel-first" does NOT mean bypassing mature userspace abstractions merely
to call lower-level APIs directly.

Examples:

    service lifecycle
        -> systemd

    service control
        -> preferably supported systemd/D-Bus interfaces

    hardware/device state
        -> sysfs / udev where appropriate

    process observation
        -> procfs / appropriate kernel interfaces

    resource control
        -> cgroups v2

    filesystem events
        -> inotify/fanotify

    advanced observability
        -> tracepoints/perf/eBPF where justified

    network state/control
        -> netlink where appropriate

Document the kernel/native mechanism beneath significant Rebuntu
capabilities as they are implemented.

======================================================================
3. PYTHON-FIRST, NOT PYTHON-ONLY
======================================================================

Python is the primary implementation language of Rebuntu.

Python should normally implement:

    runtime logic
    state management
    registries
    contracts
    policies
    workflows
    automation
    orchestration
    semantic processing integration
    structured protocols
    validation
    testing
    higher-level Linux integration

But Rebuntu is explicitly multi-language where justified.

The initial repository MUST include dedicated space for:

    src/
    cpp/
    bin/

C++ exists for functionality where native implementation is justified,
for example:

    low-level/high-performance Linux interaction
    native libraries
    performance-sensitive processing
    inference/runtime integration
    system programming experiments
    bindings
    functionality where Python is demonstrably inappropriate

Do not implement C++ merely because cpp/ exists.

Bash/shell should primarily serve:

    shell integration
    thin command wrappers
    bootstrap helpers
    installation/deployment helpers
    interactive convenience

Do not move application architecture into Bash.

A useful principle:

    Python is the primary language of Rebuntu.
    C++ is available where native implementation is justified.
    Shell is an interface and integration tool, not the system runtime.

======================================================================
4. MAXIMALIST STRUCTURE, CONSERVATIVE IMPLEMENTATION
======================================================================

Phase 0.0 should create a reasonably broad repository skeleton.

The repository should have room for the kinds of artifacts and mechanisms
we already know Rebuntu is likely to need.

However:

    MAXIMALIST STRUCTURE != MAXIMALIST IMPLEMENTATION.

Empty directories and placeholder documentation are cheap.

Speculative runtime mechanisms are not.

Do not create hundreds of empty Python modules merely to populate the
tree.

Do not implement speculative subsystem APIs.

Do not invent interfaces whose requirements are not understood.

The Phase 0.0 tree is:

    an architectural hypothesis
    an organizational framework
    an ontological starting point
    an evolution scaffold

It is NOT:

    the final architecture
    the final ontology
    the complete feature inventory

======================================================================
5. FUNCTIONAL DISCOVERY
======================================================================

Rebuntu's functionality will partly be discovered while Rebuntu is built.

This is intentional.

During future implementation, developers/agents should notice:

    "what would be useful here?"

Examples of discoveries might include:

- several services require semantic coordination;
- several subsystems need combinations of assertions;
- a combination of individually normal events represents an abnormal
  system condition;
- multiple domains require known-good-state comparison;
- several operations need the same rollback mechanism;
- multiple automation mechanisms need arbitration;
- security, storage and service management independently require temporal
  event correlation;
- several subsystems need explicit resource ownership;
- an existing Linux primitive solves most of a newly encountered problem.

The expected reasoning pattern is:

    concrete need
        ->
    inspect existing Rebuntu
        ->
    inspect existing Linux/native facilities
        ->
    compose existing mechanisms if possible
        ->
    identify remaining abstraction gap
        ->
    record or implement the smallest coherent missing abstraction
        ->
    verify
        ->
    integrate
        ->
    reuse

Do not implement every interesting idea immediately.

6. ARCHITECTURAL DISCOVERY LIFECYCLE
======================================================================

Create a lightweight mechanism for recording architectural discoveries.

Use a vocabulary approximately equivalent to:

    DISCOVERY
    CANDIDATE
    ACCEPTED
    DEFERRED
    REJECTED
    SUPERSEDED

The exact storage format may be determined during this phase.

Do not build a database or runtime subsystem for this.

Documentation is sufficient.

A discovery should be able to record:

    identifier
    phase
    date
    observation/problem
    evidence
    related existing concepts
    possible abstraction
    native Linux mechanisms investigated
    current disposition
    rationale
    future trigger for reconsideration

Example:

    DISCOVERY:
        The semantic model requires explicit prohibition of GPU use.

    CANDIDATE:
        General ResourcePolicy abstraction.

    EVIDENCE:
        CPU-only system LLM requires resource ownership semantics.

    DISPOSITION:
        DEFERRED.

    RATIONALE:
        One concrete use case is insufficient to justify a global
        abstraction.

If a later subsystem independently needs the same concept, the candidate
can be reconsidered.

This allows architecture to emerge from evidence.

======================================================================
9. PRESERVE IMPORTANT HISTORICAL DISTINCTIONS
======================================================================

The following historical Rebuntu distinctions should be preserved as
starting hypotheses and documented clearly.

SETTINGS

    Qualities determining IF an action/functionality should occur.

OPTIONS

    Qualities determining WHAT alternative should be selected when
    multiple mutually exclusive scenarios exist.

PREFERENCES

    Qualities influencing HOW work should be performed when multiple
    valid methods or runtime strategies exist.

PROPERTIES

    Characteristics OF a code/component definition.

ATTRIBUTES

    Characteristics OF a concrete runtime object/instance.

SETUP

    Relatively non-variable installation/environment specification,
    generally established when Rebuntu or a component is installed.

CONFIGURATION

    Variable specification evaluated/applied when an instance or service
    is initialized and adjusted according to desired functionality.

POLICY

    Rules describing what MAY, MUST, SHOULD, or MUST NOT happen.

Useful shorthand:

    Setup          -> WHERE / under what environment
    Configuration  -> WITH WHAT parameters
    Settings       -> WHETHER
    Options        -> WHAT
    Preferences    -> HOW
    Policy         -> WHAT IS PERMITTED / REQUIRED

Treat these as initial semantics subject to refinement through actual use.

======================================================================
10. WORKFLOW SEMANTICS
======================================================================

Document the initial distinction:

    WORKFLOW
        -> PHASE
            -> STAGE
                -> STEP

Where:

STEP
    Smallest meaningful element of sequential workflow execution.

STAGE
    Group of steps accomplishing one immediate execution objective.

PHASE
    Larger logical portion of a workflow where the character/purpose of
    execution is meaningfully distinct.

WORKFLOW
    Composition describing execution flow toward an overall objective.

THREAD IS ORTHOGONAL.

Thread is not "a larger stage".

A thread represents an independently progressing execution flow that may
cross phases/stages and synchronize with other threads.

Topology/control concepts include:

    Branch
    Path
    Fork
    Join
    Barrier
    Gate

Iteration concepts include:

    Loop
    Cycle
    Retry

Do not implement a workflow engine in Phase 0.0.

======================================================================
11. OPERATION CONTRACT — INITIAL PRINCIPLE
======================================================================

Future mutating Rebuntu operations should generally follow a lifecycle
conceptually similar to:

    discover
        ->
    precheck
        ->
    plan
        ->
    execute
        ->
    verify
        ->
    report

Where appropriate:

    checkpoint
    rollback
    recovery

must be available.

The important principle is:

    COMMAND SUCCESS != OPERATION SUCCESS.

An exit code of zero is not sufficient evidence that desired state was
achieved.

Future operations should return explicit outcomes with evidence.

Do not build the complete operation framework in Phase 0.0.

Document the principle and reserve coherent architectural space for it.

======================================================================
12. OBSERVATION BEFORE MUTATION
======================================================================

A core Rebuntu engineering rule:

    ESTABLISH OBSERVABLE STATE AND EVIDENCE BEFORE MUTATION.

Rebuntu should know what it is changing, why, what state existed before
the change, and how success will be verified.

Future system changes should increasingly support:

    BEFORE STATE
    DESIRED STATE
    ACTION
    AFTER STATE
    VERIFICATION
    EVIDENCE

For destructive or difficult-to-reverse operations, future architecture
should support checkpoint/quarantine/rollback where appropriate.

13. ASSERTIONS, CONDITIONS AND COMBINED SYSTEM STATE
======================================================================

Reserve conceptual space for declarative relationships over system state.

Do NOT implement the engine in Phase 0.0.

Future Rebuntu may represent concepts such as:

    Fact
    Assertion
    AssertionSet
    Condition
    Constraint
    Invariant
    Rule
    Policy
    Violation
    Alert
    InternalAlert

An important expected capability is COMBINATION.

Example:

    service A active
    AND service B inactive
    AND mount X missing

may represent a condition that none of those facts represents
individually.

Likewise temporal relationships may eventually matter:

    A
    THEN B within T
    WHILE NOT C

This may become useful across:

    security
    service coordination
    storage
    recovery
    configuration drift
    hardware monitoring
    automation

Do not prematurely design the final assertion engine.

Document this as an architectural direction/candidate.

======================================================================
14. INTERNAL ALERTS AND SEMANTIC ESCALATION
======================================================================

Phase 0.1 will introduce a native system LLM.

One anticipated future pattern is:

    Linux/native events
        ->
    deterministic observation
        ->
    facts
        ->
    assertions/conditions
        ->
    deterministic correlation
        ->
    compact InternalAlert
        ->
    local semantic model
        ->
    structured Assessment / EvidenceRequest

The LLM should not normally receive enormous raw event streams.

Deterministic mechanisms should reduce data first.

"Internal Alert" means an internal structured system message.

It does NOT necessarily mean notifying the human user.

Do not implement this pipeline in Phase 0.0.

Ensure the repository does not make this direction awkward.

18. BIN POLICY
======================================================================

bin/ must remain thin.

Do not place major implementation logic in executable scripts.

Eventually user-facing commands may include concepts such as:

    rebuntu
    rebuntu-status
    rebuntu-doctor

but do NOT invent a huge command family in Phase 0.0.

Prefer one coherent CLI with subcommands unless future requirements
justify otherwise.

Entry points should eventually dispatch into Python/native implementation.

======================================================================
19. SYSTEMD POLICY
======================================================================

systemd/ exists because Rebuntu will contain real Linux services.

Future services must not reinvent:

    lifecycle
    PID management
    restart policy
    dependency ordering
    watchdog behavior
    timers
    socket activation
    path activation
    cgroup placement
    journald integration

when systemd already provides those mechanisms.

Do not create actual production services in Phase 0.0 merely to populate
the directory.

Phase 0.1 will introduce the first real service.

======================================================================
20. C++ POLICY
======================================================================

cpp/ is a first-class part of the repository but NOT a mandate to rewrite
Python in C++.

Native code should require justification.

Possible future reasons include:

    performance
    latency
    memory efficiency
    kernel-facing integration
    specialized native libraries
    inference runtime integration
    bindings
    low-level IPC
    high-volume event processing

C++ components must expose clean boundaries.

Do not let Python and C++ implementations duplicate the same logic without
a documented reason.

Establish a conventional build foundation, preferably CMake unless the
repository provides a compelling alternative.

Do not add heavy C++ dependencies in Phase 0.0.

======================================================================
21. CONFIGURATION POLICY
======================================================================

Configuration is not arbitrary scattered YAML/TOML.

Reserve coherent locations and document ownership.

Distinguish:

    project/development configuration
    installed-system configuration
    component configuration
    runtime state
    user preferences
    generated state
    secrets

These must not be mixed casually.

Do not store secrets in the repository.

Do not create runtime state inside the source tree during normal
operation.

Future Linux installation should eventually respect appropriate Linux
filesystem conventions.

Document likely mappings, but do not modify the host filesystem in
Phase 0.0.

30. SAFETY.md
======================================================================

Safety is foundational.

Encode at least:

- no unexpected deletion;
- no rm -rf cleanup of arbitrary trees;
- no filesystem reorganization outside explicit task scope;
- no modification of unrelated user data;
- no automatic "cleanup" of /tmp, caches, home directories, etc.;
- prefer quarantine/checkpoint/backup before destructive actions;
- inspect identity before operating on storage devices;
- mutations should become increasingly transactional/verifiable;
- privileged actions must be explicit;
- generated scripts must minimize system-wide effects;
- dry-run should be considered for significant mutations;
- preserve evidence during failure investigation;
- no raw LLM output directly becoming privileged execution.

Phase 0.0 itself MUST NOT perform system mutations outside the project
repository.
