# Rebuntu — Phase 0.1
# Structural Taxonomy Expansion
# System → Modules → Units and the Structural Grammar of Rebuntu

Phase 0.0 established the initial Rebuntu repository.

Phase 0.1 must now substantially expand and formalize the structural
taxonomy used inside src/.

This is not a cosmetic directory-creation task.

The objective is to answer:

    WHAT KINDS OF SOFTWARE ENTITIES EXIST INSIDE REBUNTU?

and:

    HOW DO THOSE ENTITIES RELATE TO EACH OTHER?

The result should establish a useful structural grammar that future
implementation phases can use without turning the repository into either:

    1. a flat collection of unrelated directories,
    2. an inventory of Linux objects,
    3. or an unnecessarily abstract taxonomy.

======================================================================
1. STARTING HYPOTHESIS
======================================================================

Begin from the following structural hypothesis:

    src/
    ├── system/
    │   ├── core/
    │   └── shell/
    │
    ├── modules/
    │   ├── services/
    │   └── daemons/
    │
    ├── units/
    │   ├── tasks/
    │   ├── jobs/
    │   └── schedules/
    │
    └── scripts/

This is NOT a mandatory final tree.

It is the starting point for architectural investigation.

Expand it where useful.

Merge or reject categories where their distinction cannot be justified.

Do not preserve a category merely because it appeared in the starting
hypothesis.

======================================================================
2. PRIMARY STRUCTURAL RELATION
======================================================================

Investigate whether the following relation is appropriate:

    SYSTEM
        ↓
    MODULE
        ↓
    UNIT

Do not assume that this necessarily means simple filesystem containment.

Determine what each level means.

Initial hypothesis:

SYSTEM
    A major coherent part of Rebuntu possessing broad responsibility,
    internal organization, lifecycle/state where appropriate, and
    potentially multiple modules.

MODULE
    A substantial reusable functional component belonging to or used by
    a system.

UNIT
    A smaller independently identifiable unit of work, behavior,
    execution, specification, or composition.

These definitions are intentionally incomplete.

Refine them.

======================================================================
3. SYSTEM
======================================================================

Investigate what belongs under:

    src/system/

Strong candidates include:

    core/
    shell/
    runtime/
    state/
    environment/

But do not add them mechanically.

For each candidate answer:

    What does it own?
    What may depend on it?
    What may it depend on?
    Is it actually part of System?
    Is it infrastructure instead?
    Is it cross-cutting support?
    Is the name precise?

Particularly define CORE.

"core" must not become:

    miscellaneous important code.

Core should contain only functionality whose absence would prevent the
basic Rebuntu runtime/model from existing coherently.

Likewise define SHELL.

Shell should not mean "all Bash code".

Investigate whether Rebuntu Shell represents:

    interactive command environment
    command-language integration
    shell-facing interface
    execution environment
    some combination of these

and place implementation accordingly.

======================================================================
4. MODULES
======================================================================

Expand the concept of Module.

Starting candidates:

    modules/
    ├── services/
    └── daemons/

Investigate additional module roles suggested by Rebuntu's historical
and current semantics.

Candidates worth evaluating include:

    managers
    controllers
    monitors
    schedulers
    coordinators
    organizers
    maintainers
    verifiers
    handlers
    builders
    publishers
    regulators

DO NOT simply create all of these directories.

For each candidate determine whether it is:

    a structural type,
    a functional role,
    an implementation pattern,
    a runtime role,
    a semantic label,
    or merely a verb/noun useful in naming.

This distinction is extremely important.

For example, it may turn out that:

    Monitor

is a role that a Service can perform rather than a structural kind of
Module.

If so, do not create:

    modules/monitors/

merely because the word exists.

The physical tree should encode strong structural distinctions.

Secondary roles can later exist as metadata/registries/classification.

======================================================================
5. SERVICE VS DAEMON
======================================================================

Formally distinguish Service and Daemon.

Initial hypothesis:

DAEMON

    A long-running background process/runtime characteristic.

SERVICE

    A managed functionality exposed or maintained by the system.

A Service may be implemented as:

    long-running daemon
    oneshot process
    socket-activated process
    timer-activated process
    path-activated process
    other managed execution

Therefore:

    SERVICE != DAEMON

and:

    service -> may use daemon

is likely more accurate than treating the terms as synonyms.

Determine whether this means both deserve parallel physical directories
under modules/, or whether another representation is more coherent.

Use Linux/systemd semantics as important evidence.

Do not redefine established Linux concepts gratuitously.

======================================================================
6. UNITS
======================================================================

Substantially investigate:

    units/

Starting categories:

    task
    job
    schedule

Candidate additional concepts:

    routine
    procedure
    operation
    action
    workflow
    step
    stage
    phase
    thread

DO NOT turn all vocabulary terms into directories.

Determine which are actual structural unit types and which describe
composition or execution.

======================================================================
7. TASK
======================================================================

Define Task precisely.

Initial hypothesis:

    Task = bounded specification of work to be performed.

A Task should not necessarily imply:

    scheduling
    execution instance
    process
    thread
    service

Determine its relationship to:

    Job
    Operation
    Procedure
    Workflow

======================================================================
8. JOB
======================================================================

Define Job separately from Task.

Candidate distinction:

    Task
        describes bounded work

    Job
        represents submitted/scheduled/executing realization of work

For example:

    Task specification
        ↓ submit
    Job
        ↓ execute
    Result

Determine whether this distinction is useful enough to encode
architecturally.

Do not preserve it if actual semantics cannot support it.

======================================================================
9. SCHEDULE
======================================================================

Use:

    schedules/

rather than:

    crons/

unless investigation produces a compelling reason otherwise.

Cron is a particular scheduling implementation.

Schedule is a Rebuntu-level concept.

Possible implementations may eventually include:

    systemd timer
    cron
    at
    internal scheduler
    external scheduler

Therefore preserve the distinction:

    Schedule != Cron

Do not implement scheduling backends in this phase.

======================================================================
10. OPERATION / PROCEDURE / ROUTINE / ACTION
======================================================================

This area requires careful semantic work.

Investigate whether Rebuntu needs all four terms.

Candidate semantics:

OPERATION

    Contractual system-level change/query performed against some target,
    generally possessing inputs, preconditions, result, verification and
    evidence.

PROCEDURE

    Reusable specification describing how an objective is accomplished.

ROUTINE

    Smaller reusable execution sequence used as part of procedures or
    implementation.

ACTION

    Individual act/effect occurring during execution.

Possible relation:

    Procedure
        contains/coordinates
            Routine
                produces
                    Action

while:

    Operation

describes the externally meaningful contractual system operation.

But DO NOT accept this model automatically.

Test it against real expected Rebuntu use cases.

======================================================================
11. WORKFLOW
======================================================================

Investigate whether Workflow belongs under units/ or deserves a separate
architectural area.

A Workflow is likely a composition rather than an atomic unit.

Initial hierarchy:

    Workflow
        ↓
    Phase
        ↓
    Stage
        ↓
    Step

Thread is orthogonal to this hierarchy.

Therefore do not mechanically create:

    units/phases/
    units/stages/
    units/steps/
    units/threads/

unless there is a compelling implementation reason.

Composition vocabulary does not automatically imply repository taxonomy.

======================================================================
12. SCRIPTS
======================================================================

Keep:

    src/scripts/

only if there is a clear distinction between runtime scripts inside the
Python package and top-level project/development:

    scripts/

Do not accidentally create two directories with identical purpose.

Possible distinction:

    /scripts/
        repository/development/bootstrap/deployment tooling

    /src/scripts/
        scripts that are actual Rebuntu-managed/runtime artifacts

If that distinction is not sufficiently strong, redesign it.

Scripts must remain subordinate artifacts.

Do not allow Rebuntu architecture to regress into a Bash-script
collection.

======================================================================
13. CONSIDER ADDITIONAL STRUCTURAL FAMILIES
======================================================================

Investigate whether src/ requires first-class structural areas such as:

    interfaces/
    adapters/
    support/

Potential interface categories:

    cli
    ipc
    api
    shell

Potential adapters:

    systemd
    dbus
    kernel/native
    shell
    external programs

Potential support:

    logging
    configuration
    validation
    serialization
    utilities

Again:

    DO NOT CREATE DIRECTORIES JUST BECAUSE THEY SOUND REASONABLE.

Ask whether they represent durable architectural boundaries.

======================================================================
14. STRUCTURE VS ROLE VS DOMAIN
======================================================================

This distinction is mandatory.

Every candidate concept should be evaluated along at least these axes:

STRUCTURE

    What kind of software entity is it?

ROLE

    What does it do?

DOMAIN

    What does it operate on?

Example:

    structure:
        Service

    role:
        Monitor

    domain:
        Storage

A storage monitoring service therefore does NOT necessarily imply:

    src/storage/monitor/service/

or:

    src/modules/monitors/storage/

The repository should avoid encoding every classification axis
simultaneously.

Establish one dominant structural organization.

Represent other axes later through metadata/registries/contracts where
useful.

======================================================================
15. DO NOT BUILD A LINUX ENCYCLOPEDIA
======================================================================

Do not structure src/ primarily as:

    cpu/
    memory/
    gpu/
    disk/
    filesystem/
    process/
    network/
    display/
    packages/
    users/

These are domains/targets.

They may eventually exist at an appropriate secondary level, but they are
not the primary ontology of Rebuntu.

The architecture should describe how Rebuntu manages systems, not merely
what Linux contains.

======================================================================
16. DO NOT PSYCHOLOGIZE
======================================================================

Do not introduce architecture based on:

    perception
    cognition
    reasoning
    consciousness
    memory
    executive function
    thought

Rebuntu is systems software.

Use terminology grounded in:

    system management
    execution
    automation
    coordination
    state
    policy
    monitoring
    verification
    recovery
    Linux mechanisms

======================================================================
17. DEPENDENCY RELATIONS
======================================================================

Define initial legal dependency directions between structural categories.

For example investigate relations such as:

    units
        should not own system lifecycle

    modules
        may compose/use units

    services
        may expose module functionality

    system/core
        must not depend arbitrarily on optional modules

    shell
        should call stable Rebuntu interfaces rather than contain
        implementation

    scripts
        should invoke stable functionality rather than duplicate it

    adapters
        should encapsulate mechanism-specific integration

Avoid circular architecture.

Do not impose rigid layering where it does not correspond to actual
semantics.

======================================================================
18. LIFECYCLE VS STRUCTURAL TYPE
======================================================================

Do not confuse:

    what something IS

with:

    what STATE it is in.

For example:

    Service
        is a structural/runtime concept.

    active
    inactive
    failed
    starting
    stopping

are states.

Likewise:

    Job

is not the same category of concept as:

    queued
    running
    completed
    failed

Keep ontology dimensions orthogonal.

======================================================================
19. EXECUTION VS SPECIFICATION
======================================================================

Investigate the important distinction between definitions and runtime
instances.

Examples:

    TaskDefinition
        vs
    TaskInstance / Job

    ServiceDefinition
        vs
    ServiceInstance

    WorkflowDefinition
        vs
    WorkflowRun

Do not necessarily use these exact names.

But avoid architectures where static specification and runtime state are
silently represented by the same object.

======================================================================
20. IDENTITY, STATE AND RESULT
======================================================================

Determine what common concepts structural entities are likely to require.

Candidates:

    identity
    specification
    configuration
    state
    lifecycle
    inputs
    outputs
    result
    status
    evidence

Do NOT immediately create one giant BaseRebuntuObject containing every
possible field.

Prefer composition and narrowly justified contracts.

This phase should define conceptual relationships before implementing
inheritance hierarchies.

======================================================================
21. NO GOD BASE CLASS
======================================================================

Do not implement:

    class RebuntuObject

with dozens of methods that every future entity must inherit.

The structural taxonomy is primarily semantic at this stage.

Future implementation evidence should determine shared protocols/base
classes.

Use typing/protocols/composition when appropriate later.

Do not freeze ontology into inheritance prematurely.

======================================================================
24. EXPAND ONTOLOGY.md
======================================================================

Represent relationships, not merely definitions.

Investigate and document relationships such as:

    System contains/coordinates Modules
    Module uses/composes Units
    Service exposes/maintains functionality
    Daemon may implement Service
    Task specifies work
    Job realizes submitted/executing work
    Schedule determines temporal activation
    Procedure specifies execution method
    Routine supports Procedure
    Workflow composes work
    Workflow contains Phases
    Phase contains Stages
    Stage contains Steps
    Thread crosses workflow hierarchy
    Adapter connects Rebuntu to native/external mechanism
    Interface exposes Rebuntu functionality

Do not force everything into one parent-child hierarchy.

Use multiple relation types.

======================================================================
26. UPDATE AGENTS.md
======================================================================

Add a placement procedure for future coding agents.

Before adding a new source component, the agent must determine:

    1. What kind of entity is this?
    2. Is it a System, Module, Unit, Interface, Adapter, Script, or
       something not yet represented?
    3. Is the proposed name actually a ROLE rather than a structural type?
    4. What domain does it operate on?
    5. Is that domain incorrectly influencing physical placement?
    6. Does an equivalent abstraction already exist?
    7. Is this specification or runtime realization?
    8. Is it implementation or integration?
    9. What may depend on it?
    10. What may it depend on?

If placement is unclear:

    DO NOT CREATE A CONVENIENT RANDOM DIRECTORY.

Investigate and document the ambiguity.

======================================================================
27. EXPANSION PROCEDURE
======================================================================

Perform this phase in four conceptual passes.

PASS A — STARTING TAXONOMY

Analyze:

    system
    modules
    units
    scripts

and their proposed children.

PASS B — SEMANTIC EXPANSION

Ask for each concept:

    What logically exists around it?
    What does it require?
    What does it produce?
    What controls it?
    What composes it?
    What is it composed of?
    What activates it?
    What verifies it?
    What state does it possess?
    What distinguishes its definition from its execution?

Generate candidate concepts.

PASS C — REDUCTION

Remove:

    synonyms
    redundant structural categories
    roles masquerading as types
    implementation details masquerading as architecture
    Linux domains masquerading as architecture
    premature abstractions

PASS D — MATERIALIZATION

Only after semantic reduction should the physical tree be changed.

This is:

    EXPAND FIRST
        ->
    CRITIQUE
        ->
    COMPRESS
        ->
    MATERIALIZE

not:

    brainstorm
        ->
    mkdir everything

======================================================================
28. EXPECTED DEPTH OF EXPLORATION
======================================================================

Be deliberately exploratory.

Phase 0.1 is allowed to discover considerably more vocabulary than it
physically implements.

For example, investigation may produce 50 useful concepts while only
five new directories are justified.

That is a successful result.

The purpose is to increase Rebuntu's conceptual resolution without
turning conceptual resolution into filesystem noise.

33. FINAL AUDIT
======================================================================

Before completion:

1. Inspect the final src/ tree.
2. Inspect every new structural category.
3. For every directory ask:

       "What semantic distinction justifies this directory?"

5. For every major vocabulary term ask:

       "Is this a type, role, domain, state, specification,
        runtime instance, or relationship?"

6. Search for synonyms accidentally represented as separate architecture.

7. Search for Linux domains accidentally promoted to top-level structure.

8. Search for role names unnecessarily promoted to structural categories.

9. Search for cognitive/psychological terminology.

======================================================================
CORE RULE
======================================================================

Rebuntu should have a rich vocabulary but a disciplined filesystem.

Do not confuse:

    HAVING A CONCEPT

with:

    NEEDING A DIRECTORY

or:

    NEEDING A CLASS

or:

    NEEDING A PROCESS.

Explore broadly.

Distinguish precisely.

Materialize conservatively.


# IMPLEMENTATION LANGUAGE OVERRIDE

INSTEAD OF PYTHON, USE C++20 AS THE PRIMARY IMPLEMENTATION LANGUAGE.

This instruction overrides all Python-specific implementation-language assumptions elsewhere in this task.

Preserve the task's semantic requirements, architecture, behavior, invariants, safety requirements, tests, acceptance criteria, and Linux integration, but implement them idiomatically in native C++20.

Translate Python-specific mechanisms to their appropriate C++20 equivalents by SEMANTIC PURPOSE, not by mechanical syntax substitution.

Use the existing Rebuntu C++ architecture, CMake/CTest infrastructure, Result/Evidence models, runtime, providers, Linux integrations, and other existing abstractions before creating new ones.

Do not recreate a Python architecture in C++ form.

Where the task explicitly concerns interoperability with an external Python component, Python may remain at that external boundary; Rebuntu itself remains C++20-first.

If any requirement in the task conflicts solely because it explicitly mandates Python for Rebuntu's own implementation, this IMPLEMENTATION LANGUAGE OVERRIDE takes precedence. Do not treat that conflict as an ambiguity requiring Python code.
