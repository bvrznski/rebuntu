# Rebuntu — Phase 0.10 — Operations
## System Actions, Queries, Contracts, Preconditions, Effects, Verification and Evidence

## Objective

Establish Rebuntu's canonical abstraction for an Operation.

Previous phases establish the structural and runtime grammar around:

    Unit
    Task
    Job
    Execution
    Attempt
    Schedule
    Activation
    Result

Phase 0.10 must now define the fundamental answer to:

    What does it mean for Rebuntu to DO something to, with, or about
    the operating environment?

The starting hypothesis is:

    Operation
        = a reusable, explicitly contracted system capability that
          observes, queries, changes, constructs, removes, transforms,
          controls, or otherwise acts upon a defined subject.

An Operation should normally expose enough semantics for Rebuntu to know:

    WHAT it intends to do
    WHAT it acts upon
    WHAT it requires
    WHAT it may change
    WHAT risks it carries
    HOW it executes
    WHAT success means
    HOW success is verified
    WHAT evidence supports the result
    WHETHER it is safe to retry
    WHETHER it can be reversed
    WHAT recovery is possible after failure

The central execution hypothesis is:

    DISCOVER
        ↓
    RESOLVE
        ↓
    PRECHECK
        ↓
    PLAN
        ↓
    EXECUTE
        ↓
    OBSERVE
        ↓
    VERIFY
        ↓
    EVIDENCE
        ↓
    RESULT

For mutating work, where appropriate:

    BEFORE STATE
        ↓
    PRECONDITIONS
        ↓
    PLAN
        ↓
    CHECKPOINT
        ↓
    EXECUTE
        ↓
    AFTER STATE
        ↓
    POSTCONDITIONS
        ↓
    VERIFY
        ↓
    RESULT

This is a conceptual starting point.

Do not force every trivial operation through a giant ceremonial
pipeline.

The purpose of this phase is to create a rigorous Operation contract
without turning Rebuntu into an enterprise transaction framework.

# 3. Recover the Original Rebuntu Strength

Historical Rebuntu already contained an important idea:

    install foo

should be semantically richer than:

    apt install foo

Likewise:

    create X
    configure X
    backup X
    restore X
    repair X
    verify X

should represent system-level intent rather than merely wrapping one
command.

A Rebuntu Operation may therefore perform something like:

    resolve target
        ↓
    inspect current state
        ↓
    determine whether action is necessary
        ↓
    validate prerequisites
        ↓
    choose provider
        ↓
    construct execution plan
        ↓
    execute
        ↓
    inspect resulting state
        ↓
    verify postconditions
        ↓
    report evidence

This is one of the foundational ideas of Rebuntu.

Formalize it properly.


# 4. Operation Definition

Determine the canonical definition.

Starting hypothesis:

    Operation
        = reusable contracted capability representing a bounded
          interaction with system state or a system resource.

An Operation may be:

    observational
    querying
    constructive
    mutating
    controlling
    administrative
    configurational
    maintenance-oriented
    recovery-oriented
    verification-oriented

Do not define Operation merely as:

    callable function

or:

    shell command.


# 5. Operation != Unit

Phase 0.7 defines Units.

Determine the relationship.

Possible interpretation:

    Unit
        structural/compositional executable artifact

    Operation
        semantic capability with an execution contract

A Unit may implement an Operation.

An Operation may compose Units.

A Unit may exist for purposes that do not constitute a system Operation.

Do not collapse them merely because both can execute.


# 6. Operation != Task

Phase 0.8 establishes bounded work.

Starting distinction:

    Operation
        reusable capability definition

    Task
        bounded work requested in a concrete context

Example:

    Operation:
        install software

    Task:
        install Firefox

Possible relation:

    Task
        ↓ invokes
    Operation

Do not require a Task object for every direct synchronous Operation
invocation if that adds no value.


# 7. Operation != Job

A Job is a managed realization of work.

An Operation describes capability.

For example:

    Operation:
        verify filesystem

    Job:
        concrete asynchronous verification of filesystem X

One Operation may produce many Jobs over time.


# 8. Operation != Execution

Operation describes semantics and contract.

Execution is runtime occurrence.

Therefore:

    Operation
        ↓ invoked as
    Execution

or, when managed:

    Operation
        ↓
    Task
        ↓
    Job
        ↓
    Execution

Do not store runtime state in the Operation definition itself unless the
Operation genuinely owns persistent state.


# 9. Operation != Attempt

Retrying an Operation does not create a new Operation.

It creates another Attempt associated with the same managed work.

Preserve this distinction.


# 10. Operation != Script

A Script is an executable artifact.

An Operation is semantic capability.

Possible implementation:

    Operation
        ↓
    Python function

or:

    Operation
        ↓
    native Linux API

or:

    Operation
        ↓
    D-Bus

or:

    Operation
        ↓
    systemd

or:

    Operation
        ↓
    external executable

or:

    Operation
        ↓
    Script

Do not make shell scripts the canonical Operation implementation model.


# 11. Operation != Shell Function

Historical Rebuntu often represented high-level behavior through shell
functions.

Preserve the user-facing composability where useful.

But modern architecture should permit:

    shell function
        ↓
    stable Rebuntu interface
        ↓
    Operation

rather than embedding all Operation semantics in Bash.


# 12. Operation != Procedure

Investigate the distinction.

Candidate:

    Operation
        defines WHAT system capability is performed and its contract

    Procedure
        defines HOW an objective is performed through reusable steps

Example:

    Operation:
        recover filesystem

    Procedure:
        inspect device
        unlock container
        verify filesystem
        mount
        verify mount

But avoid retaining both concepts if actual architecture cannot make
their distinction useful.


# 13. Operation != Routine

Candidate:

    Routine
        smaller reusable execution sequence

    Procedure
        reusable larger method

    Operation
        externally meaningful contracted system capability

Again:

    vocabulary richness != mandatory implementation richness


# 14. Operation != Action

Investigate Action as the smallest meaningful act/effect during
execution.

Possible hierarchy:

    Operation
        ↓
    Procedure
        ↓
    Actions

Example:

    Operation:
        install package

    Actions:
        refresh metadata
        invoke provider
        inspect package database

But do not create artificial Action objects for ordinary Python calls.


# 15. Operation != Workflow

A Workflow defines composed execution flow.

An Operation defines a capability contract.

An Operation may internally invoke a Workflow when complexity warrants.

A Workflow may invoke multiple Operations.

Example:

    Workflow:
        prepare gaming environment

    Operations:
        configure GPU
        configure CPU policy
        configure services
        verify environment

Do not turn every multi-step Operation into a Workflow automatically.

Use Workflow when execution topology itself becomes significant.


# 16. Operation != Automation

Automation determines:

    WHEN / WHY / UNDER WHAT CONDITIONS

Operation determines:

    WHAT SYSTEM ACTION OR QUERY IS AVAILABLE

Canonical relation:

    Event / Schedule / Condition
              ↓
          Automation
              ↓
          Operation

Do not put trigger policy inside Operation implementations.


# 17. Operation != Service

A Service provides managed functionality.

An Operation represents bounded capability.

A Service may expose Operations.

An Operation may interact with a Service.

Starting a Service may itself be represented through an Operation.

Do not collapse lifecycle-managed functionality with bounded action.


# 18. Operation != Daemon

A Daemon is a persistent process role.

An Operation is bounded semantic work.

A daemon may execute Operations.

An Operation should not become a daemon merely because it may take a
long time.


# 19. Operation != Command

This distinction is important for the future Rebuntu shell.

Candidate:

    Command
        user/interface-level invocation syntax

    Operation
        semantic capability behind the invocation

Example:

    install firefox

may be parsed as:

    Command
        verb = install
        target = firefox

which resolves to:

    Operation
        software.install

Do not bind semantic identity permanently to shell spelling.


# 20. Operation != Request

A Request asks Rebuntu to perform or provide something.

An Operation is the capability that may satisfy the Request.

Possible flow:

    Request
        ↓
    Resolve
        ↓
    Operation
        ↓
    Execution

One Request may potentially require multiple Operations.

Not every Operation invocation needs an externally visible Request
object.


# 21. Operation != Provider

This distinction is mandatory.

Example:

    Operation:
        software.install

Possible Providers:

    apt
    dpkg
    flatpak
    snap
    custom package source

Likewise:

    clipboard.write

may use:

    Wayland provider
    X11 provider

Therefore:

    WHAT
        Operation

    HOW THROUGH ENVIRONMENT-SPECIFIC IMPLEMENTATION
        Provider

This permits stable Rebuntu semantics over changing Linux mechanisms.


# 22. Operation != Adapter

Candidate distinction:

    Operation
        semantic capability

    Provider
        implementation capable of satisfying capability

    Adapter
        integration boundary translating Rebuntu semantics to an
        external/native interface

Example:

    Operation
        service.start

    Provider
        systemd

    Adapter
        systemd D-Bus adapter

Do not overformalize this if Phase 0.6 already established better
terminology.

Reuse existing decisions.


# 23. Operation Identity

Operations need stable semantic names.

Prefer names based on meaning rather than implementation.

Examples:

    software.install
    software.remove
    service.start
    service.stop
    service.restart
    filesystem.copy
    filesystem.move
    filesystem.verify
    storage.mount
    configuration.apply
    backup.create
    backup.restore

These are examples, not a mandatory namespace.

Do not encode:

    apt_install
    systemctl_start
    cp_file

as canonical semantic identities unless implementation specificity is
actually the intended capability.


# 24. Verb + Subject Grammar

Investigate whether Operation identity can generally follow:

    DOMAIN.SUBJECT.VERB

or:

    DOMAIN.VERB

or another consistent grammar.

Examples:

    package.install
    service.restart
    filesystem.copy
    configuration.apply

The shell may expose:

    install package
    restart service
    copy file

without requiring internal identifiers to mirror shell grammar exactly.

Do not freeze naming before examining actual use cases.

# 26. Imperative vs Predicate Grammar

Preserve the useful distinction between:

    install     → installed
    enable      → enabled
    disable     → disabled
    start       → running
    pause       → paused
    resume      → resumed
    lock        → locked
    unlock      → unlocked

Imperative Operation:

    install X

Predicate/query:

    installed X

This pattern is valuable.

But do not manufacture grammatical pairs where semantics are weak.


# 27. Operation Categories

Do not prematurely make categories into directories.

Investigate semantic categories such as:

    QUERY
    OBSERVATION
    VALIDATION
    VERIFICATION
    CONSTRUCTION
    MUTATION
    CONFIGURATION
    CONTROL
    MAINTENANCE
    ADMINISTRATION
    RECOVERY
    TRANSFER
    TRANSFORMATION

An Operation may potentially have multiple semantic properties.

Avoid a rigid single-category hierarchy if operations naturally span
multiple axes.


# 28. Side-Effect Classification

Every Operation should have explicit side-effect semantics where
relevant.

Candidate classification:

    PURE
    READ_ONLY
    MUTATING
    PRIVILEGED
    DESTRUCTIVE

These may be independent properties rather than one enum.

For example:

    filesystem.inspect
        READ_ONLY

    package.install
        MUTATING + PRIVILEGED

    filesystem.format
        MUTATING + PRIVILEGED + DESTRUCTIVE

Do not infer safety from the verb alone.


# 29. Risk Classification

Consider whether Operations require explicit risk metadata.

Potential dimensions:

    data loss
    availability impact
    security impact
    privilege
    irreversibility
    scope
    persistence
    external effects

Do not create fake numerical risk scores unless they have a consumer.

Simple semantic flags may be superior.


# 30. Scope

Operations should identify their scope where relevant.

Examples:

    process
    user session
    user
    filesystem path
    mount
    device
    service
    package
    network interface
    host
    system

Scope matters for:

    authorization
    locking
    conflict detection
    verification
    rollback
    evidence

Do not make "system-wide" the default.


# 31. Subject / Target

An Operation should have an explicit subject or target model where
appropriate.

Examples:

    install(package)
    restart(service)
    mount(filesystem)
    copy(source, destination)
    configure(component)
    verify(subject)

Do not pass opaque shell command strings as canonical targets.


# 32. Typed Inputs

Operations should accept structured inputs.

Prefer:

    operation:
        filesystem.copy

    input:
        source: Path
        destination: Path
        overwrite: false

over:

    command:
        "cp whatever whatever"

This is foundational for:

    validation
    planning
    security
    semantic shell
    verification
    retries
    auditing


# 33. Preconditions

A Precondition is something that must hold before execution is allowed or
meaningful.

Examples:

    source exists
    destination parent exists
    device is present
    package repository reachable
    service definition exists
    sufficient space available
    required privilege available

Precondition failure should normally prevent mutation.

Do not treat all precondition failures as execution failures.

Example:

    PRECONDITION_FAILED

may be more informative than:

    FAILED


# 34. Preconditions != Validation

Validation asks whether supplied data/specification is acceptable.

Preconditions ask whether the current environment permits meaningful
execution.

Example:

    destination path syntactically valid
        = validation

    destination filesystem writable
        = precondition

Keep these concepts separate.


# 35. Preconditions != Guards

A Guard may control whether an action is permitted based on policy,
runtime state or safety.

A Precondition describes required facts.

Example:

    filesystem mounted
        precondition

    destructive writes forbidden in current policy
        guard/policy constraint

Reuse earlier vocabulary if already defined differently.


# 36. Planning

Significant Operations should be able to determine intended actions
before mutation.

Candidate:

    plan(inputs, context, observed_state) -> Plan

The Plan may describe:

    provider
    actions
    expected effects
    affected resources
    required privilege
    checkpoints
    verification strategy
    rollback capability

Do not require a Plan object for trivial pure queries.

Planning complexity should be proportional to risk.


# 37. Dry Run

For significant mutating Operations, investigate explicit dry-run
semantics.

A dry run should answer:

    what WOULD be done?

without performing the mutation.

Do not claim dry-run support when the provider cannot reliably predict
effects.

Dry run is not verification.


# 38. Effects

An Operation contract should describe expected effects.

Examples:

    package becomes installed
    service becomes active
    file appears at destination
    configuration value changes
    mount becomes available

Expected effect is not evidence that the effect occurred.

This distinction is fundamental.


# 39. Observation Before Mutation

For important mutating Operations, inspect relevant current state first.

Example:

    install firefox

may first determine:

    already installed?
    installed through which provider?
    version?
    repository state?
    conflicting installation?
    desired version already present?

This enables:

    no-op
    repair
    update
    conflict detection
    provider selection

instead of blind mutation.


# 40. No-Op

No-op is a legitimate successful result.

Example:

    ensure service is enabled

when service is already enabled.

Possible result:

    SUCCESS
    changed = false

Do not execute unnecessary mutations merely so an Operation "did
something".


# 41. Ensure Semantics

"ensure" is a particularly important candidate verb.

Compare:

    start service
        perform explicit transition

with:

    ensure service running
        establish desired condition if necessary

This introduces desired-state semantics.

Investigate whether Ensure should be:

    an Operation
    an Operation modifier
    a reconciliation primitive
    a separate control concept

Do not casually define it before considering Phase 0.14 state and later
reconciliation architecture.


# 42. Execute

Execution should perform the approved Plan or direct bounded action.

Execution must not silently change the semantic intent established
during planning.

If the environment changes materially between Plan and Execute:

    revalidate
    reject
    replan

as appropriate.

This matters especially for destructive Operations.


# 43. TOCTOU

Explicitly consider time-of-check/time-of-use problems.

Example:

    verify path
        ↓
    attacker/process replaces path
        ↓
    destructive operation executes on different target

Use appropriate Linux primitives and safer handles where possible.

Do not pretend prechecks alone eliminate race conditions.


# 44. Postconditions

Postconditions describe what must be true after successful Operation
execution.

Examples:

    package is installed
    service is active
    file content matches source
    mount exists
    configuration has intended value

Postconditions define semantic success.

Exit status alone does not.


# 45. Verification

Verification evaluates whether required postconditions actually hold.

Canonical principle:

    EXECUTED != VERIFIED

and:

    EXIT 0 != VERIFIED SUCCESS

Example:

    apt exits 0
        ↓
    package database inspected
        ↓
    required package/version confirmed
        ↓
    VERIFIED

The verifier should use evidence independent enough to meaningfully test
the claim where practical.


# 46. Verification Strength

Not all verification is equally strong.

Investigate useful levels such as:

    NONE
    COMMAND_RESULT
    STATE_OBSERVATION
    FUNCTIONAL
    END_TO_END

Do not create arbitrary confidence percentages.

Document what was actually checked.


# 47. Independent Verification

Where practical, avoid verifying an Operation solely by asking the same
mechanism that claimed success.

Example:

    copy command says success

stronger verification may inspect:

    destination exists
    expected metadata
    size
    checksum where justified

Verification cost should be proportional to risk and importance.


# 48. Evidence

Verification must produce Evidence.

Potential evidence:

    observed state
    command result
    exit status
    filesystem metadata
    checksum
    package database state
    systemd state
    D-Bus response
    kernel state
    journal entries
    before/after values

Evidence supports claims.

Evidence is not merely debug logging.


# 49. Result

Operation Result should be semantic.

Potential information:

    operation identity
    subject
    outcome
    changed
    verification
    evidence references
    execution reference
    failure information

Do not create giant Result objects containing the entire runtime world.


# 50. Outcome

Do not reduce all outcomes to Boolean.

Potential outcomes may include:

    SUCCESS
    FAILED
    PARTIAL
    CANCELLED
    TIMED_OUT
    PRECONDITION_FAILED
    POLICY_DENIED
    UNSUPPORTED
    NOT_APPLICABLE

But do not create a giant enum prematurely.

Derive the smallest useful set from real Operations.


# 51. Error != Failure

An Error is information describing something that went wrong.

Failure is an outcome/state.

Multiple Errors may contribute to one Failure.

A recoverable warning need not imply Failure.

Preserve this distinction.


# 52. Partial Success

Some Operations affect multiple targets.

Example:

    configure 4 displays

Three succeed, one fails.

Determine whether Operation contracts can represent:

    PARTIAL

or structured per-subject Results.

Do not report global success when important sub-results failed.


# 53. Idempotency

Every mutating Operation should have explicit retry semantics where
relevant.

Candidate classification:

    IDEMPOTENT
    CONDITIONALLY_IDEMPOTENT
    NON_IDEMPOTENT
    UNKNOWN

Examples:

    ensure directory exists
        likely idempotent

    append line to arbitrary file
        potentially non-idempotent

    send external message
        potentially non-idempotent

UNKNOWN must never silently mean safe to retry.


# 54. Reentrancy

Idempotency and reentrancy are different.

An Operation may be idempotent but unsafe to run concurrently.

Example:

    ensure package installed

may produce the same desired final state but conflict with another
package manager execution.

Represent concurrency constraints separately.


# 55. Reversibility

Investigate whether an Operation can be reversed.

Candidate classifications:

    REVERSIBLE
    CONDITIONALLY_REVERSIBLE
    IRREVERSIBLE
    UNKNOWN

Do not assume:

    inverse verb = rollback

For example:

    install ↔ uninstall

does not guarantee restoration of the original state.


# 56. Inverse Operation

An inverse semantic Operation may exist:

    enable / disable
    attach / detach
    lock / unlock
    start / stop

But inverse Operation != rollback.

Rollback aims to restore prior state.

The inverse verb may establish a different state.


# 57. Checkpoint

For sufficiently risky Operations, capture enough prior state to support
safe recovery.

Examples:

    configuration backup
    filesystem snapshot
    previous value
    package version
    service state
    mount configuration

Checkpointing must be proportional.

Do not snapshot the universe before every mutation.


# 58. Rollback

Rollback should mean:

    restore relevant prior state after unsuccessful mutation

Do not promise rollback unless it is actually supported and verified.

Potential flow:

    PRECHECK
        ↓
    CHECKPOINT
        ↓
    EXECUTE
        ↓
    VERIFY FAILED
        ↓
    ROLLBACK
        ↓
    VERIFY ROLLBACK
        ↓
    REPORT

Rollback itself can fail.

Represent that honestly.


# 59. Compensation

Some Operations cannot be rolled back transactionally.

They may support compensation.

Example:

    external side effect occurred

A compensating action attempts to mitigate or counteract the effect but
does not literally restore history.

Therefore:

    ROLLBACK != COMPENSATION


# 60. Recovery

Recovery is broader than rollback.

Recovery may involve:

    retry
    restart
    rollback
    restore
    repair
    compensation
    alternate provider
    degraded mode
    manual intervention

Do not bury general recovery architecture inside Operation.execute().


# 61. Destructive Operations

Destructive Operations require explicit treatment.

Examples:

    delete
    format
    wipe
    overwrite
    remove package with dependencies
    destroy filesystem
    truncate data

Historical Rebuntu contains unsafe destructive helpers.

Do not execute historical code during archaeology.

For destructive Operations require appropriate combinations of:

    precise target identity
    validation
    scope
    preconditions
    authorization
    policy
    plan
    dry-run where meaningful
    checkpoint where possible
    explicit destructive classification
    verification
    evidence

Prefer quarantine/snapshot/reversible approaches where appropriate.


# 62. Filesystem Safety

Filesystem Operations deserve especially strong contracts.

For:

    copy
    move
    rename
    delete
    replace
    archive
    extract
    link
    mount
    format

consider:

    source identity
    destination identity
    symlinks
    mount boundaries
    permissions
    ownership
    free space
    atomicity
    overwrite behavior
    filesystem semantics
    partial failure
    verification
    rollback
    TOCTOU

Never normalize "cleanup" into unrestricted deletion.


# 63. Copy as a Reference Operation

Use filesystem copy as one pressure test.

A serious copy Operation may involve:

    validate source
    resolve destination
    inspect destination
    detect conflicts
    estimate required space
    determine overwrite policy
    execute using appropriate native mechanism
    verify destination
    preserve required metadata
    return evidence

But keep simple copy simple when advanced guarantees are not requested.


# 64. Install as a Reference Operation

Use installation as another pressure test.

Potential flow:

    resolve requested software
        ↓
    detect installed state
        ↓
    resolve provider
        ↓
    inspect availability
        ↓
    determine desired version/source
        ↓
    precheck
        ↓
    execute provider
        ↓
    inspect installed state
        ↓
    functional verification where appropriate
        ↓
    evidence/result

This is the modern formalization of the historical:

    install <target>

idea.


# 65. Service Operations

Pressure-test:

    service.start
    service.stop
    service.restart
    service.reload
    service.enable
    service.disable

Respect Phase 0.6:

    Rebuntu Service != systemd .service

If systemd is the provider, use its native interfaces.

Do not rebuild service supervision.


# 66. Configuration Operations

Pressure-test:

    configuration.apply
    configuration.validate
    configuration.restore

Configuration application should ideally distinguish:

    desired specification
    current state
    difference
    planned change
    resulting state
    verification

Do not treat writing a config file as sufficient proof that configuration
became effective.


# 67. Query Operations

Not every Operation mutates.

Examples:

    inspect
    query
    list
    get
    detect
    discover
    status

Read-only Operations still benefit from:

    typed inputs
    defined outputs
    error semantics
    evidence/provenance

But should not be burdened with rollback/checkpoint machinery.


# 68. Observation vs Query

Investigate:

    Query
        explicitly asks for information

    Observation
        acquires system state, potentially as part of ongoing monitoring

The same provider function may support both.

Do not create duplicate implementations merely to satisfy vocabulary.


# 69. Check vs Validate vs Verify

Formalize these distinctions.

Candidate semantics:

    CHECK
        generic inspection/test of a condition

    VALIDATE
        determine whether input/specification conforms to requirements

    VERIFY
        establish with evidence whether a claim/postcondition is true

Example:

    validate config syntax

before execution.

    verify service functionality

after execution.

Do not use the terms interchangeably.


# 70. Test

Distinguish:

    software test
    runtime system check
    validation
    verification
    diagnostic probe

The shell builtin `test` already exists.

Do not casually claim `test` as a Rebuntu top-level verb.


# 71. Diagnose

Diagnosis attempts to explain observed abnormal state.

It should normally remain separate from mutation.

Canonical:

    OBSERVE
        ↓
    DIAGNOSE
        ↓
    PLAN REPAIR
        ↓
    REPAIR
        ↓
    VERIFY

Do not let diagnostics silently repair the system.


# 72. Repair

Repair is a mutating Operation intended to restore acceptable state.

It requires stronger safety semantics than ordinary observation.

Repair should not mean:

    run arbitrary cleanup commands until problem disappears.


# 73. Reconcile

Reconciliation compares:

    desired state
        vs
    observed state

and attempts to reduce the difference.

This may compose Operations.

Do not collapse every Operation into reconciliation.

Phase 0.10 should establish compatibility with future reconciliation
without building a giant controller framework.


# 74. Provider Selection

An Operation may have multiple Providers.

Provider selection may depend on:

    availability
    environment
    compatibility
    configuration
    user preference
    policy
    capability
    safety
    current state

Example:

    software.install

could resolve differently depending on package source.

Provider selection should be observable and explainable.


# 75. Native Linux First

Before implementing an Operation, investigate whether Linux already
provides the mechanism.

Examples:

    systemd / D-Bus
    procfs
    sysfs
    netlink
    udev
    inotify/fanotify
    nftables
    mount APIs
    package-manager APIs
    libc/syscalls
    coreutils

Rebuntu adds:

    semantic intent
    contracts
    composition
    safety
    provider resolution
    verification
    evidence

It should not reimplement Linux.


# 76. Command Execution Boundary

External commands remain valid providers/tools.

But execute them safely.

Prefer:

    argv arrays
    explicit environment
    explicit cwd
    captured result
    timeout
    structured error handling

over:

    shell=True
    bash -c "<constructed string>"

unless shell semantics are genuinely required.


# 77. Shell Pipelines

Some Operations are naturally shell-shaped.

Historical Rebuntu's compositional style such as:

    some_command | clip

is valuable.

Do not destroy Unix composability by forcing every operation through
verbose structured output.

For shell-facing operations:

    stdout = primary data
    stderr = diagnostics
    exit status = machine-readable basic success/failure

while richer Operation metadata may travel through another interface.

Preserve clean pipelines.


# 78. Python-First Implementation

Python should be the primary language for:

    Operation contracts
    structured inputs/results
    validation
    provider selection
    planning
    state inspection
    verification
    evidence handling
    orchestration

Bash should remain appropriate for:

    shell-native behavior
    pipelines
    redirection
    tiny wrappers
    environment integration
    native command glue

Do not rewrite Python-shaped logic in Bash.


# 79. Privilege

Operations must declare privilege requirements where relevant.

Do not scatter:

    sudo

inside implementations.

Prefer deliberate elevation boundaries through:

    systemd
    polkit
    Linux capabilities
    privileged service/helper
    caller-controlled elevation

Authorization should occur before privileged mutation.


# 80. Authorization != Privilege

Privilege asks:

    what OS authority is required?

Authorization asks:

    is this requester permitted to perform this Operation on this
    subject?

Keep them separate.


# 81. Policy

Policy may constrain Operations.

Examples:

    destructive Operations forbidden automatically
    package removal requires explicit approval
    filesystem modifications limited to allowed scope
    network changes forbidden during protected workload
    recovery action limited to N attempts

Operation implementation should not contain scattered ad-hoc policy
rules.

Use explicit policy boundaries as architecture develops.


# 82. Locks and Resource Conflicts

Operations may require exclusive access.

Examples:

    package database
    filesystem target
    device
    configuration
    service lifecycle

Represent resource conflicts deliberately.

Prefer native locking and ownership mechanisms where possible.

Do not implement stale `.lock` marker files as runtime truth.


# 83. Concurrency

Ask whether an Operation supports:

    concurrent calls
    concurrent calls on different subjects
    only one global execution
    only one execution per subject

This may become contract metadata where useful.

Do not create a universal concurrency framework now.


# 84. Timeout

Operations may define or accept timeout constraints.

Reuse Phase 0.9 temporal grammar.

Do not implement a second timeout model inside Operations.


# 85. Retry

Operations expose enough semantics for execution machinery to determine
whether retry may be safe.

Reuse:

    Attempt
    Retry
    Backoff

from Phases 0.8–0.9.

Do not implement retry loops independently inside every Operation.


# 86. Cancellation

Operations should define cancellation behavior where relevant.

Possible:

    cancellable
    cancellable only before mutation
    cooperative cancellation
    non-cancellable critical section
    cancellation requires cleanup
    unsupported

Do not promise safe cancellation for irreversible work.


# 87. Progress

Long-running Operations may expose measurable progress.

Reuse Phase 0.8 semantics.

Do not fabricate percentages.

Possible progress evidence:

    bytes copied
    items processed
    stages completed
    provider-native progress

Progress reporting should remain optional.


# 88. Events

Operations may emit meaningful events.

Examples:

    operation.started
    operation.changed_state
    operation.completed
    operation.failed
    operation.verification_failed

Do not create an event for every internal function call.

Phase 0.15 will formalize communication/event semantics later.


# 89. Evidence Provenance

Evidence should record enough provenance to answer:

    where did this claim come from?

Examples:

    provider
    native subsystem
    command
    file metadata
    systemd
    kernel
    package database
    verifier

Do not let generated text become authoritative system evidence.


# 90. Semantic Model Boundary

Future BitNet integration may help interpret:

    user intent
    logs
    ambiguous textual state
    operation selection

But the semantic model must not directly perform privileged mutation.

Desired flow:

    text
      ↓
    semantic interpretation
      ↓
    typed Operation request
      ↓
    validation
      ↓
    authorization/policy
      ↓
    deterministic Operation
      ↓
    verification

Never:

    LLM text
      ↓
    sudo shell


# 91. Discovery

Operations should be discoverable.

Potential discovery questions:

    Is there already an Operation for this intent?

    What subjects does it support?

    What inputs are required?

    What provider is available?

    Is it read-only or mutating?

    Is it destructive?

    Can it verify success?

This supports the central Rebuntu principle:

    SEARCH BEFORE IMPLEMENTING.


# 92. Operation Registry

Evaluate whether an Operation Registry is justified.

Possible role:

    identity → definition/provider metadata

But:

    Registry != runtime state
    Registry != scheduler
    Registry != executor
    Registry != service manager

Do not create a registry without a concrete consumer.


# 93. Capability Discovery

An Operation may represent an implementation of a more general
Capability.

Investigate whether:

    Capability
        what Rebuntu knows how to do

    Operation
        contracted executable realization

is a useful distinction.

Do not force it if Phase 0.7 Units or existing ontology already provides
the necessary concept.


# 94. Missing Capability Path

Prepare the architecture for the future path:

    Request
        ↓
    capability search
        ↓
    operation search
        ↓
    NOT FOUND
        ↓
    implementation process
        ↓
    tests
        ↓
    verifier
        ↓
    acceptance
        ↓
    registration
        ↓
    deterministic reuse

Do not implement autonomous code generation in Phase 0.10.

Only ensure the Operation architecture can support later capability
growth.


# 95. Composition

Operations should compose cleanly.

Example:

    inspect
        ↓
    backup
        ↓
    modify
        ↓
    restart
        ↓
    verify

If composition becomes complex enough to involve:

    branching
    joins
    retries
    checkpoints
    phases
    stages
    compensation

then investigate promotion to Workflow rather than hiding an orchestration
engine inside one Operation.


# 96. Atomicity

Do not claim Operations are atomic unless the underlying mechanisms
actually provide atomicity.

Possible classifications:

    atomic
    externally atomic
    partially atomic
    multi-step
    non-atomic

Most system administration operations are not database transactions.

Be precise.


# 97. Transaction

Do not use "transaction" casually.

A Transaction should imply meaningful commit/rollback or equivalent
consistency semantics.

A sequence of commands is not automatically a Transaction.


# 98. Change Set

Investigate whether planning significant mutations benefits from a
ChangeSet concept:

    intended changes
    affected subjects
    before values
    desired after values

Do not implement it unless multiple Operations actually need it.

It may remain a candidate discovered during Phase 0.10.


# 99. Operation Specification

Determine the minimum useful Operation specification.

Potential fields:

    identity
    purpose
    inputs
    outputs
    subject type
    side effects
    privilege
    preconditions
    expected effects
    verification
    idempotency
    reversibility
    concurrency
    timeout
    provider requirements

Do not make every field mandatory.

Use proportional contracts.


# 100. Minimal Operations Must Stay Minimal

Example:

    hostname.get

may simply require:

    input: none
    output: hostname
    side_effects: none

It should not need:

    checkpoint
    rollback
    plan graph
    recovery policy
    transaction
    approval

The architecture must scale DOWN as well as up.


# 101. High-Risk Operations Scale Up

Conversely:

    filesystem.format

may justify:

    precise target resolution
    device identity verification
    mount-state inspection
    destructive classification
    authorization
    policy check
    explicit plan
    confirmation boundary
    execution isolation
    post-operation verification
    evidence

Contract strength should scale with consequence.


# 102. Physical Repository Placement

Do not automatically create:

    operations/
        queries/
        mutations/
        verification/
        administration/
        ...

because the ontology contains those concepts.

Explicitly evaluate:

A. centralized `operations/`;

B. Operations colocated with owning domain/module;

C. shared Operation contracts in core with implementations colocated with
   owners;

D. another structure already established by Phases 0.0–0.9.

Strongly consider:

    shared contract centrally
    concrete operation near semantic owner

if this best fits the current architecture.

But derive the answer from the repository.


# 103. Domain Axis

    filesystem

    display

    inspect

# 108. Architecture Pressure Tests

Test the architecture against realistic cases.


## Scenario A — Install

    install firefox

Can Rebuntu:

    resolve target
    determine provider
    inspect installed state
    avoid unnecessary work
    execute
    verify
    return evidence?


## Scenario B — Already Installed

    install firefox

when Firefox is already in the desired state.

Can the Operation return:

    success
    changed = false

without reinstalling it?


## Scenario C — Copy

    copy source destination

Can overwrite policy, path identity and verification be represented?


## Scenario D — Service Restart

    restart service X

Can Rebuntu use systemd rather than building its own process manager?


## Scenario E — Verification Failure

Provider returns success but desired state is absent.

Can:

    execution = successful
    verification = failed
    operation result = failed

coexist cleanly?


## Scenario F — Retry

First Attempt fails transiently.

Can retry machinery use Operation idempotency semantics rather than
blindly rerunning it?


## Scenario G — Destructive Action

    format device

Does the architecture demand substantially stronger safeguards than a
read-only query?


## Scenario H — Rollback Failure

Mutation fails verification.

Rollback is attempted.

Rollback also fails.

Can Rebuntu represent both failures honestly?


## Scenario I — Workflow Boundary

An Operation grows to 15 steps with branching and checkpoints.

Does the architecture recognize that it may actually be a Workflow?


## Scenario J — Shell Composition

    some_command | clip

Can simple Unix composition remain simple without being swallowed by a
heavy Operation framework?


## Scenario K — Semantic Shell

User writes:

    ensure ssh is stopped

Can this eventually resolve into deterministic typed semantics without
giving an LLM arbitrary shell authority?


## Scenario L — Concurrent Package Work

Two package installation Operations begin simultaneously.

Can the architecture recognize provider/resource serialization rather
than merely relying on eventual command failure?

# Core Operation Grammar

Rebuntu should ultimately be able to reason deterministically about:

    INTENT
       ↓
    OPERATION
       ↓
    SUBJECT
       ↓
    INPUT VALIDATION
       ↓
    CURRENT STATE
       ↓
    PRECONDITIONS
       ↓
    POLICY / AUTHORIZATION
       ↓
    PROVIDER RESOLUTION
       ↓
    PLAN
       ↓
    EXECUTION
       ↓
    OBSERVED RESULTING STATE
       ↓
    POSTCONDITIONS
       ↓
    VERIFICATION
       ↓
    EVIDENCE
       ↓
    RESULT

with optional branches for:

    NO-OP
    CANCELLATION
    RETRY
    CHECKPOINT
    ROLLBACK
    COMPENSATION
    RECOVERY

according to the Operation's actual requirements.


# Final Rule

AN OPERATION IS NOT A COMMAND STRING.

AN OPERATION IS NOT A SCRIPT.

AN OPERATION IS NOT A TASK.

AN OPERATION IS NOT A PROCESS.

AN OPERATION IS NOT A PROVIDER.

AN OPERATION IS A CONTRACTED SYSTEM CAPABILITY.

VALIDATE WHAT WAS REQUESTED.

OBSERVE BEFORE MUTATING.

KNOW THE SUBJECT.

KNOW THE SCOPE.

KNOW THE SIDE EFFECTS.

KNOW THE PRIVILEGE.

KNOW WHETHER RETRY IS SAFE.

KNOW WHETHER REVERSAL IS POSSIBLE.

PLAN IN PROPORTION TO RISK.

EXECUTE THROUGH THE APPROPRIATE NATIVE MECHANISM.

DO NOT CONFUSE EXIT STATUS WITH SUCCESS.

VERIFY THE RESULTING STATE.

PRESERVE EVIDENCE.

REPORT NO-OP HONESTLY.

DO NOT REIMPLEMENT LINUX.

DO NOT TURN EVERY FUNCTION INTO AN OPERATION.

SEARCH BEFORE IMPLEMENTING.

COMPOSE BEFORE DUPLICATING.

MAKE SIMPLE OPERATIONS SIMPLE.

MAKE DANGEROUS OPERATIONS EXPLICITLY SAFE.

MAKE CLAIMS PROVABLE.


# IMPLEMENTATION LANGUAGE OVERRIDE

INSTEAD OF PYTHON, USE C++20 AS THE PRIMARY IMPLEMENTATION LANGUAGE.

This instruction overrides all Python-specific implementation-language assumptions elsewhere in this task.

Preserve the task's semantic requirements, architecture, behavior, invariants, safety requirements, tests, acceptance criteria, and Linux integration, but implement them idiomatically in native C++20.

Translate Python-specific mechanisms to their appropriate C++20 equivalents by SEMANTIC PURPOSE, not by mechanical syntax substitution.

Use the existing Rebuntu C++ architecture, CMake/CTest infrastructure, Result/Evidence models, runtime, providers, Linux integrations, and other existing abstractions before creating new ones.

Do not recreate a Python architecture in C++ form.

Where the task explicitly concerns interoperability with an external Python component, Python may remain at that external boundary; Rebuntu itself remains C++20-first.

If any requirement in the task conflicts solely because it explicitly mandates Python for Rebuntu's own implementation, this IMPLEMENTATION LANGUAGE OVERRIDE takes precedence. Do not treat that conflict as an ambiguity requiring Python code.
