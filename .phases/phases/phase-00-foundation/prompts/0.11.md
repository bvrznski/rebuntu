# Phase 0.11 — Workflows — Composition, Phases, Stages & Steps

## Objective

Design and establish Rebuntu's Workflow architecture: the formal model for
composing multiple bounded operations into structured, inspectable,
controllable, resumable, and verifiable multi-step processes.

This phase must determine what a Workflow actually means in Rebuntu and
establish clean boundaries between:

- Workflow
- Operation
- Unit
- Task
- Job
- Execution
- Automation
- Schedule
- Script
- Service

Do not merely implement a generic workflow engine.

The purpose of this phase is to discover the smallest coherent abstraction
that lets Rebuntu express processes such as:

    prepare system
        ->
    inspect current state
        ->
    validate prerequisites
        ->
    apply several operations
        ->
    verify resulting state
        ->
    recover / compensate if necessary
        ->
    produce evidence and result

without turning every multi-function procedure into a Workflow.

## 2. Define Workflow Precisely

Begin from the working hypothesis:

    WORKFLOW =
        A STRUCTURED COMPOSITION OF MULTIPLE BOUNDED ACTIONS OR OPERATIONS
        WITH EXPLICIT CONTROL FLOW AND AN OVERALL PURPOSE.

Treat this as a hypothesis, not an unquestionable definition.

A Workflow should normally exist because the overall process requires
coordination across multiple independently meaningful pieces of work.

A Workflow should NOT simply mean:

- a Python function calling another function;
- several shell commands written next to each other;
- every Operation containing multiple internal implementation steps;
- every Unit with more than one function;
- every Script with multiple commands;
- every Service startup sequence;
- every dependency chain;
- every Automation;
- every Schedule.

Determine the minimum characteristics that justify promotion to Workflow.


## 3. Workflow vs Operation

Resolve this boundary explicitly.

Candidate distinction:

    Operation
        = one semantically bounded system change/query/action

    Workflow
        = coordinated composition of multiple Operations or other
          bounded executable definitions toward a larger objective

Example:

    Operation:
        package.install("foo")

    Workflow:
        prepare_development_environment

            inspect host
            ensure repositories
            install packages
            configure environment
            install tools
            verify toolchain
            produce report

But do not enforce this example mechanically.

An Operation may internally contain implementation steps without becoming
a Workflow.

The distinction should be semantic rather than based on line count.

Ask:

    Can this thing be understood as one system operation?

If yes, it may remain an Operation even if its implementation is internally
complex.

Ask:

    Does this thing coordinate several independently meaningful operations,
    with explicit sequencing, conditions, branching, recovery, or shared
    objective?

If yes, Workflow is probably appropriate.


## 4. Workflow vs Unit

Reconcile this phase with Phase 0.7.

Determine whether:

    Workflow contains Units

or:

    Workflow contains Operations

or:

    Workflow Steps reference executable targets that may resolve to Units,
    Operations, other Workflows, or carefully constrained primitives.

Avoid making Workflow dependent on an unresolved Unit ontology.

Do not create redundant abstractions simply to make the hierarchy look neat.

Possible model:

    WorkflowDefinition
        |
        +-- Step
              |
              +-- target -> Operation / Unit / Workflow

but validate this against the architecture already established in 0.7-0.10.


## 5. Workflow vs Task / Job / Execution

Preserve the distinction between reusable definition and runtime realization.

Candidate model:

    WorkflowDefinition
        |
        v
    WorkflowRequest / Task
        |
        v
    Job
        |
        v
    WorkflowExecution
        |
        +-- StepExecution
        +-- StepExecution
        +-- StepExecution
        |
        v
    WorkflowResult

Do not introduce all of these layers automatically.

Use only the abstractions justified by Phases 0.8-0.10.

At minimum distinguish:

    Workflow definition

from:

    a particular execution of that Workflow.

Runtime state must not be stored inside the static Workflow definition.


## 6. Workflow vs Automation

This distinction is mandatory.

Use the working distinction:

    Workflow:
        WHAT coordinated process should execute.

    Automation:
        WHEN / WHY execution should be initiated.

Example:

    Workflow:
        backup_and_verify

    Automation:
        when external backup disk appears,
        invoke backup_and_verify

Therefore:

    Event / Condition / Schedule
                |
                v
            Automation
                |
                v
            Workflow
                |
                v
            Operations

Do not bury triggers and scheduling inside Workflow definitions unless there
is a compelling architectural reason.

Workflow should generally be independently invokable.


## 7. Workflow vs Schedule

Schedule is temporal specification.

Workflow is executable composition.

Therefore:

    Schedule != Workflow

A Schedule may activate:

- Automation;
- Task;
- Operation;
- Workflow;

depending on the final activation architecture.

Do not make time a Workflow property merely because a Workflow can be
scheduled.


## 8. Workflow vs Script

A Script is an executable artifact.

A Workflow is a semantic execution/composition definition.

A Script may:

- invoke a Workflow;
- implement a simple Operation;
- serve as an adapter;
- bootstrap Workflow execution.

A Script must not become the canonical representation of Workflow state,
dependency graphs, retries, checkpoints, or recovery semantics merely
because Bash can express sequencing.

Prefer Python for Workflow runtime and structured orchestration.


## 9. Workflow Structure

Evaluate the hierarchy:

    Workflow
        -> Phase
            -> Stage
                -> Step

Do NOT blindly implement all four levels.

Historical Rebuntu explored rich hierarchies such as:

    systems
        -> modules
            -> units
                -> stages
                    -> tasks
                        -> streams
                            -> steps

Treat this as archaeological evidence rather than architecture.

Determine whether Phase and Stage are actually useful structural concepts.

Possible semantics:

    Workflow
        overall coordinated process

    Phase
        major semantic segment of the Workflow

    Stage
        execution grouping within a Phase

    Step
        smallest explicit orchestration node

But if Phase and Stage cannot be given meaningfully different contracts,
collapse them.

The filesystem must not encode distinctions that exist only because they
sound architecturally elegant.


## 10. Step Semantics

Define Step carefully.

A Step should represent an orchestration node, not necessarily implementation
code.

Candidate Step fields:

    id
    name
    target
    inputs
    outputs
    dependencies
    condition
    timeout
    retry_policy
    failure_policy
    verification
    compensation
    resource_requirements

Keep the required core much smaller if possible.

A Step should generally reference an existing executable capability rather
than embed arbitrary code.

Prefer:

    Step(
        target="package.install",
        inputs={"package": "foo"}
    )

over:

    Step(
        shell="sudo apt install foo"
    )

Arbitrary shell execution must not become the Workflow universal escape hatch.


## 11. Sequential Composition

Support explicit sequential relationships.

Example:

    A -> B -> C

Meaning:

    B cannot begin until the required completion condition of A is satisfied.
    C cannot begin until the required completion condition of B is satisfied.

Do not confuse:

    execution order

with:

    dependency.

Sometimes A must execute before B without B semantically depending on A.

Represent this distinction if it proves useful.


## 12. Dependency Graph

Workflows should be capable of representing a directed dependency graph where
needed.

Example:

          A
         / \
        B   C
         \ /
          D

Do not force all Workflows into linear chains.

Determine whether the canonical representation should be:

- ordered steps;
- DAG;
- graph with constrained cycles;
- another simpler model.

Prefer the simplest representation supporting real Rebuntu use cases.

Cycles should not be permitted accidentally.


## 13. Parallel Composition

Support parallel execution where:

- dependencies permit it;
- resource constraints permit it;
- concurrency is safe;
- ordering is not semantically required.

Example:

          inspect_network
         /
    START
         \
          inspect_storage

               |
               v

          correlate_results

Parallelism belongs to runtime execution policy and Workflow topology.

Do not automatically spawn threads/processes for every independent Step.


## 14. Branching

Workflows must be able to represent conditional control flow.

Example:

    inspect package

        installed?
        /       \
      yes        no
       |          |
    verify      install
       |          |
       +-----> verify

Conditions should operate on typed state/results rather than parsing
human-readable output.


## 15. Joins

Define semantics for branches converging.

Possible join policies:

    ALL
    ANY
    FIRST_SUCCESS
    FIRST_COMPLETION
    QUORUM

Do not implement policies without real use cases.

At minimum ensure that parallel branches can converge deterministically.


## 16. Gates

A Gate controls whether execution may proceed.

Examples:

- precondition satisfied;
- authorization granted;
- required device present;
- sufficient disk space;
- maintenance window active;
- previous verification succeeded.

Gate != Step if it does not itself perform work.

Determine whether Gate deserves a first-class type or whether it is simply
a Step condition / dependency predicate.


## 17. Preconditions

A Workflow may define preconditions for starting.

Example:

    target filesystem mounted
    network reachable
    required privilege available
    sufficient free space

Preconditions should fail before mutation begins whenever possible.

Do not partially execute a Workflow that was impossible from the start.


## 18. Postconditions

A Workflow may define expected final conditions.

Example:

    package installed
    service enabled
    service running
    endpoint reachable

Workflow completion must not be inferred merely from all subprocesses exiting
with status 0.

This principle remains fundamental:

    EXECUTION SUCCESS != VERIFIED SUCCESS


## 19. Verification

Verification must be first-class.

Support verification at appropriate levels:

    Step verification
    Operation verification
    Phase verification
    Workflow verification

Do not duplicate verification unnecessarily.

Prefer functional verification over implementation verification.

Example:

Weak:

    systemctl returned 0

Better:

    service is active

Stronger where relevant:

    expected service functionality is actually available


## 20. Results

Workflow execution must produce a structured result.

Candidate:

    WorkflowResult
        workflow_id
        execution_id
        outcome
        started_at
        finished_at
        step_results
        verification
        evidence
        errors

Do not treat console output as the result contract.

Human-readable rendering should be derived from structured results.


## 21. Output vs Result

Preserve the distinction:

    Output
        data produced by execution

    Result
        structured statement describing execution outcome

Example:

    Step output:
        discovered package version

    Step result:
        SUCCESS / FAILED / VERIFIED / etc.

A Workflow may pass outputs between Steps while independently tracking their
execution results.


## 22. Data Flow

Determine how outputs from one Step become inputs to another.

Example:

    discover_device
        |
        | output.device_id
        v
    inspect_device
        |
        | output.health
        v
    decide_action

Avoid global mutable dictionaries as the implicit Workflow communication
mechanism.

Prefer explicit typed bindings.


## 23. Workflow Context

Determine whether executions need a WorkflowContext containing runtime
information such as:

    execution identity
    caller
    scope
    environment
    configuration
    cancellation state
    deadlines
    evidence references
    runtime services

Keep context bounded.

Do not turn WorkflowContext into a global dependency container.


## 24. Failure Semantics

Define failure propagation.

Possible policies:

    FAIL_FAST
    CONTINUE
    SKIP_DEPENDENTS
    COMPENSATE
    ROLLBACK
    DEGRADE

Do not create a giant policy enum without demonstrated use.

Determine sensible defaults.

Failures should preserve:

- failing Step;
- cause;
- input context where safe;
- relevant output;
- evidence;
- dependent Steps affected;
- recovery actions attempted.


## 25. Retry

Retry should be explicit policy.

A Step must not silently retry indefinitely.

Potential policy fields:

    max_attempts
    delay
    backoff
    retryable_failures

Reuse temporal semantics from Phase 0.9.

Retry should normally create another Attempt rather than erase the failed
execution history.


## 26. Timeout and Deadline

Support bounded execution where relevant.

Distinguish:

    timeout
        maximum allowed duration

    deadline
        absolute temporal boundary

Use monotonic time for elapsed-duration decisions.

Timeout must propagate through the execution runtime cleanly.


## 27. Cancellation

Workflow execution should support cooperative cancellation.

Define:

    cancellation requested
    cancellation acknowledged
    currently running Steps
    pending Steps
    cleanup requirements
    final outcome

Cancellation != failure.

Do not kill arbitrary processes without understanding ownership and cleanup
requirements.


## 28. Checkpoints

Investigate checkpoint semantics.

A checkpoint may represent:

- known recoverable execution point;
- persisted progress boundary;
- state snapshot reference;
- point from which execution may resume.

Do not implement checkpointing merely as "last step number".

A useful checkpoint must contain enough information to determine whether
resumption is safe.


## 29. Resume

Resumption must not blindly continue from the next Step.

Before resume:

    load execution state
        ->
    inspect current system state
        ->
    verify previous assumptions
        ->
    validate checkpoint
        ->
    determine remaining valid plan
        ->
    resume

The external system may have changed while execution was interrupted.


## 30. Rollback

Do not pretend every Workflow is transactional.

Rollback is valid only where reverse operations or snapshots actually provide
the required guarantees.

Distinguish:

    rollback
        restore a previous state where a real reversible mechanism exists

from:

    compensation
        perform additional actions intended to mitigate/reverse effects

Do not label compensation as rollback.


## 31. Compensation

Support compensating actions where useful.

Example:

    create temporary mount
        ->
    perform operation
        ->
    failure
        ->
    unmount temporary mount

Compensation may itself fail.

Record compensation results independently.


## 32. Planning

Significant mutating Workflows should support a planning stage.

Conceptual lifecycle:

    RESOLVE
        ->
    VALIDATE
        ->
    PLAN
        ->
    AUTHORIZE
        ->
    EXECUTE
        ->
    VERIFY
        ->
    EVIDENCE
        ->
    RESULT

Planning should expose intended changes before destructive or privileged
execution where appropriate.


## 33. Dry Run

Determine whether Workflow dry-run can be derived from Operation planning.

Do not implement fake dry-run by simply skipping command execution.

A meaningful dry-run should answer:

- which Steps would execute;
- which would be skipped;
- which Operations would be invoked;
- expected mutations;
- privilege requirements;
- unresolved dependencies;
- potentially destructive actions;
- verification plan.


## 34. Idempotency

Workflow idempotency cannot be assumed from Step idempotency alone.

Record whether a Workflow is:

    IDEMPOTENT
    CONDITIONALLY_IDEMPOTENT
    NON_IDEMPOTENT
    UNKNOWN

only if such classification has an actual consumer.

Prefer designing mutating Workflows toward safe repeated invocation where
reasonable.


## 35. Side Effects

Workflow metadata should be able to summarize relevant effects inherited
from contained Operations.

Examples:

    READ_ONLY
    MUTATING
    PRIVILEGED
    DESTRUCTIVE

Do not let a Workflow hide dangerous effects behind a harmless-looking name.


## 36. Authorization

Authorization must happen before privileged or destructive execution.

A Workflow should not acquire broad privilege merely because one Step needs it.

Prefer least privilege at the Operation/Step boundary where practical.

Do not put `sudo` inside arbitrary Workflow definitions.


## 37. Resource Requirements

Workflows may coordinate resource-sensitive Operations.

Examples:

    filesystem locks
    exclusive device access
    network availability
    CPU limits
    GPU ownership
    disk capacity

Reuse the resource/locking concepts established elsewhere.

Do not build a second resource manager inside Workflow.


## 38. Locks

Workflow-wide locks should exist only where required.

Prefer narrow locks around the resource and duration that actually require
exclusivity.

Locks must have explicit ownership and release semantics.

Crash recovery for locks must be considered.


## 39. Workflow State

Do not use one giant state enum.

Potential orthogonal dimensions include:

    lifecycle
    activity
    control
    health
    readiness
    outcome

Reuse the state grammar established in Phase 0.14 rather than inventing a
Workflow-specific competing vocabulary.

For now identify requirements and integration points.


## 40. Persistence

Determine which Workflow execution state must survive:

- process restart;
- service restart;
- user logout;
- system reboot.

Not every Workflow needs persistence.

Candidate classes:

    EPHEMERAL
    RESUMABLE
    PERSISTENT

Do not persist everything merely because persistence is possible.


## 41. Workflow Identity

Every reusable Workflow definition should have a stable semantic identity.

Examples:

    system.backup.verify
    development.environment.prepare
    storage.device.inspect

These are examples, not mandatory namespace conventions.

IDs should describe semantics rather than implementation.

Avoid names such as:

    bash_backup_script
    python_workflow_3


## 42. Workflow Versioning

Determine how execution records remain interpretable when Workflow definitions
change.

Do not create a heavy versioning framework yet.

At minimum consider recording enough definition identity/hash/version
information to know what was actually executed.


## 43. Workflow Discovery

A Workflow should be discoverable through the architecture established in
Phase 0.19.

Do not implement a global magical registry prematurely.

Prefer deterministic, explicit discovery.

Search before implementing:

    NAME BEFORE CREATE
    SEARCH BEFORE IMPLEMENT


## 44. Composition

A Workflow may invoke another Workflow only where hierarchical composition
actually simplifies the model.

Avoid arbitrary deep nesting.

Prevent:

    Workflow A -> Workflow B -> Workflow C -> Workflow D

when the structure merely hides simple Operations.

Nested Workflow execution must preserve traceability.


## 45. Recursion

Workflow recursion should be forbidden by default.

If recursive workflows ever become useful, they require explicit bounds and
strong justification.

Detect accidental cycles during validation.


## 46. Dynamic Workflows

Investigate whether Rebuntu needs runtime-generated Workflow topology.

Prefer static/declared topology where possible.

Dynamic generation may be justified for discovered sets such as:

    for each detected disk:
        inspect disk

Even then, prefer deterministic expansion from typed input rather than
arbitrary runtime code generation.


## 47. Fan-Out / Fan-In

Support the conceptual pattern:

          item A -> operation
         /
    SET - item B -> operation -> aggregate
         \
          item C -> operation

This may be useful for:

- disks;
- packages;
- services;
- GPUs;
- network interfaces;
- files.

Do not create a separate abstraction if normal Workflow graph expansion is
sufficient.


## 48. Loops

Do not introduce general unrestricted loops into declarative Workflow
definitions unless necessary.

Prefer bounded iteration over explicit collections.

Unbounded continuous behavior probably belongs to:

    Automation
    Service
    Daemon
    reconciliation loop

rather than Workflow.


## 49. Workflow vs Reconciliation

A Workflow has a bounded execution objective.

Reconciliation continuously or repeatedly drives observed state toward desired
state.

Therefore:

    Workflow != Reconciliation Loop

A reconciliation mechanism may invoke Workflows or Operations.


## 50. Workflow vs Recovery

Recovery may be:

- an Operation;
- a Workflow;
- a compensation branch;
- an external stability mechanism.

Do not automatically embed every recovery strategy into the original
Workflow.

Separate normal execution logic from system-level resilience where
appropriate.


## 51. Workflow vs Pipeline / Stream

Distinguish control-flow orchestration from continuous data flow.

Workflow:

    bounded coordinated execution

Pipeline:

    transformation / transfer of data through connected stages

Stream:

    potentially ongoing sequence of data

Do not call every Unix pipe a Workflow.

Historical Rebuntu's interest in pipes and streams should be preserved as
communication architecture, not collapsed into workflow semantics.


## 52. Native Linux Integration

Before implementing custom orchestration mechanisms, inspect what Linux and
systemd already provide:

- systemd dependencies;
- targets;
- Wants / Requires;
- Before / After;
- OnFailure;
- timers;
- path activation;
- socket activation;
- transient units;
- D-Bus activation;
- udev activation.

Use native mechanisms where they naturally solve the problem.

But do not force high-level Rebuntu semantic Workflows into systemd dependency
graphs when systemd lacks the required workflow semantics.


## 53. Python-First Implementation

Workflow definitions and runtime orchestration should primarily be implemented
in Python.

Bash may:

- invoke Workflows;
- provide thin interactive wrappers;
- integrate shell-native streams;
- bridge native commands.

Do not build a complex Workflow engine in Bash.

Python is the language of Rebuntu.

Bash is one language users can speak to Rebuntu and one adapter to Linux.


## 54. Structured Definitions

Evaluate a structured declarative representation for Workflow definitions.

Possible representations include:

- Python objects;
- dataclasses;
- typed schemas;
- TOML/YAML/JSON manifests where useful.

Do not introduce configuration DSLs merely for aesthetics.

A Python definition may be preferable initially if it provides stronger typing,
composition and testing.

If external manifests are introduced, validate them into the same internal
typed representation.


## 55. Typed Internal Representation

Workflow execution should operate on validated internal structures.

Conceptually:

    user / shell / config / API
            |
            v
        Workflow request
            |
            v
        validation
            |
            v
      typed Workflow IR
            |
            v
      execution runtime

Do not allow unvalidated textual instructions to become privileged execution.


## 56. Shell Integration

Eventually Rebuntu Shell should support concise semantic invocations.

Example:

    run backup.verify

or another syntax selected by the Shell architecture.

Do not consume the valuable top-level `run` verb casually before Phase 6
finalizes the command language.

The Workflow system should expose structured functionality that the Shell can
later map onto cleanly.


## 57. Observability

Workflow execution should emit enough structured information to answer:

    What is running?
    Why is it running?
    Who/what initiated it?
    Which Step is active?
    What already succeeded?
    What failed?
    What is waiting?
    What resources are held?
    What will execute next?
    Was verification successful?

Avoid noisy event emission for trivial internal implementation details.


## 58. Journald Integration

Use journald for operational logs where appropriate.

Structured execution state should not exist only in logs.

Logs are evidence and diagnostics.

They are not the authoritative Workflow state store.


## 59. Evidence

Important Workflow actions should preserve evidence sufficient to justify the
reported outcome.

Examples:

    command exit status
    observed service state
    file checksum
    package version
    mount state
    device identity
    relevant journal records
    verification result

Evidence collection must be proportional to operation importance.


## 60. Provenance

Record where execution originated when useful:

    user
    shell
    API
    Automation
    Schedule
    Service
    Recovery
    another Workflow

This enables later auditability and debugging.


## 61. Testing

Add architecture-level and representative implementation tests covering:

- simple sequential Workflow;
- failed Step;
- skipped Step;
- conditional branch;
- parallel independent Steps;
- dependency join;
- timeout;
- cancellation;
- retry;
- verification failure after execution success;
- compensation;
- checkpoint/resume where implemented;
- invalid graph;
- dependency cycle;
- missing target;
- invalid input binding;
- privilege rejection;
- dry-run/plan behavior;
- structured result generation.

Do not require all advanced runtime capabilities to be fully implemented in
Phase 0.11 if doing so would prematurely build Phase 4/10 functionality.

The purpose here is architecture plus enough executable proof to validate it.


## 62. Representative Validation Scenarios

Validate the model against realistic Rebuntu scenarios.

### Scenario A — Package installation

    inspect package
        ->
    resolve provider
        ->
    install
        ->
    verify binary/package
        ->
    report

Question:

Should this remain one Operation rather than a Workflow?

The likely answer may be yes.

Use this to prevent Workflow overuse.


### Scenario B — Development environment setup

    inspect host
        ->
    validate repositories
        ->
    install package group
        ->
    configure environment
        ->
    install developer tools
        ->
    verify toolchain

This is a stronger Workflow candidate.


### Scenario C — Backup

    discover destination
        ->
    verify destination
        ->
    snapshot/source preparation
        ->
    transfer
        ->
    verify transferred data
        ->
    record evidence

Evaluate checkpointing, recovery and verification.


### Scenario D — System diagnostic collection

Parallel:

    kernel evidence
    journal evidence
    storage evidence
    GPU evidence
    memory evidence

Then:

    aggregate
        ->
    correlate
        ->
    report

Validate fan-out/fan-in.


### Scenario E — Device arrival

    udev event
        ->
    Automation
        ->
    Workflow
        ->
    inspect device
        ->
    apply policy
        ->
    verify

Validate the boundary between Event, Automation and Workflow.


### Scenario F — Scheduled maintenance

    Schedule
        ->
    Automation
        ->
    maintenance Workflow
        ->
    Operations

Validate that Schedule does not become part of Workflow semantics.


### Scenario G — Failure with compensation

    mount temporary filesystem
        ->
    copy data
        ->
    verification fails
        ->
    compensation:
        unmount
        clean temporary state safely
        preserve evidence

Validate failure propagation and compensation.


## 63. Avoid the "Workflow Engine" Trap

Do not begin by implementing:

    WorkflowManager
    WorkflowEngine
    WorkflowController
    WorkflowRegistry
    WorkflowScheduler
    WorkflowExecutor
    WorkflowCoordinator

as a forest of abstractions.

First determine actual responsibilities.

A possible minimal architecture may require only:

    WorkflowDefinition
    StepDefinition
    WorkflowExecution
    WorkflowRunner

or even less.

Only introduce separate Controller/Executor/Registry/Coordinator objects when
they have distinct consumers, lifecycle or responsibilities.


## 64. Avoid Manager Proliferation

Do not create `*Manager` classes merely to hold methods.

Prefer names reflecting actual semantics:

    Resolver
    Runner
    Executor
    Store
    Registry
    Planner
    Validator

only when those responsibilities genuinely exist.

A module with functions may be better than a class.


## 65. Avoid Directory Proliferation

Do not automatically create:

    workflows/
        phases/
        stages/
        steps/
        gates/
        branches/
        joins/
        retries/
        checkpoints/
        compensation/

The conceptual vocabulary does not need a one-to-one filesystem mapping.

Remember:

    HAVING A CONCEPT != NEEDING A DIRECTORY

    HAVING A DIRECTORY != NEEDING A CLASS

    HAVING A CLASS != NEEDING A PROCESS


## 66. Architectural Ownership

Determine where Workflow infrastructure belongs physically.

Consider:

    src/...

based on the package structure established in earlier phases.

Do not create a new top-level architecture silo without justification.

Concrete Workflows may eventually live near their owning domains rather than
inside one giant central `workflows/` catalog.

Separate:

    Workflow infrastructure

from:

    concrete domain Workflows.


## 67. Domain Ownership

## Core Architectural Principle

A Workflow is not "some code that does several things".

It exists when Rebuntu needs to explicitly represent and control the
relationship between multiple bounded pieces of work.

Prefer:

    Operation
        when one semantic system action is sufficient.

Use:

    Workflow
        when coordination itself becomes part of the semantics.

The target architecture is:

    INTENT / REQUEST
           |
           v
       WORKFLOW
           |
           +--> STEP --> OPERATION
           |
           +--> STEP --> OPERATION
           |
           +--> CONDITION / BRANCH
           |
           +--> STEP --> OPERATION
           |
           v
       VERIFICATION
           |
           v
        EVIDENCE
           |
           v
         RESULT

while initiation remains orthogonal:

    EVENT / CONDITION / SCHEDULE
                |
                v
            AUTOMATION
                |
                v
            WORKFLOW

Do not make Workflow the place where unclear concepts go.

Workflow should make multi-step execution more explicit, more observable,
more controllable, more recoverable and more verifiable than ordinary code,
or it should not exist as a separate abstraction.
