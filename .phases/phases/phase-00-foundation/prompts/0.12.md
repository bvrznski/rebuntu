## Mission

Establish the canonical architecture for **Automation** and determine the
modern meaning of **Automaton** in Rebuntu.

Historical Rebuntu used automatons heavily. Preserve the valuable idea:
the system can notice circumstances and cause appropriate work to happen
without the user manually issuing every command.

Do not preserve accidental historical mechanisms merely because they existed.

The central candidate relationship is:

    EVENT / CONDITION / SCHEDULE / REQUEST
                    |
                    v
              AUTOMATION
                    |
          activation decision
                    |
                    v
        OPERATION / WORKFLOW
                    |
                    v
              EXECUTION
                    |
                    v
        VERIFICATION + EVIDENCE
                    |
                    v
                 RESULT

The key architectural principle to test is:

    Automation decides WHEN and WHY work should happen.
    Workflow defines HOW coordinated work proceeds.
    Operation defines WHAT bounded system action is performed.

## Define Automation

Start from:

    AUTOMATION =
        A DECLARED RELATION BETWEEN AN ACTIVATION CONDITION
        AND BOUNDED REBUNTU WORK, GOVERNED BY POLICY.

Validate or improve it.

An Automation should answer:

- what circumstance matters?
- what evidence establishes it?
- what policy permits reaction?
- what target work becomes eligible?
- under what scope?
- with what concurrency behavior?
- what happens if the condition repeats?
- how is the activation explained afterward?

Automation must not mean "anything automatic".

## Define Automaton

Resolve whether `Automaton` should mean:

A. durable Automation definition;
B. runtime instance of an Automation;
C. long-lived evaluator of automation rules;
D. historical term to retire;
E. another precisely defined concept.

Do not keep both `Automation` and `Automaton` if they are synonyms.

If both survive, document the difference strongly enough that an engineer can
classify a new object without guessing.

## Mandatory distinctions

Explicitly resolve:

    Automation != Workflow
    Automation != Operation
    Automation != Schedule
    Automation != Timer
    Automation != Event
    Automation != Condition
    Automation != Rule
    Automation != Policy
    Automation != Service
    Automation != Daemon
    Automation != Event Handler
    Automation != Reconciliation

A Schedule can activate work but does not describe the work.

A Workflow can be invoked manually and remain the same Workflow.

A Daemon may host an automation evaluator but process persistence does not
define Automation.

A Service may expose functionality continuously without being an Automation.

Reconciliation repeatedly drives observed state toward desired state; an
Automation may activate reconciliation but is not automatically reconciliation.

## Trigger sources

Model only sources justified by real cases:

- explicit request;
- event;
- state transition;
- condition becoming true;
- schedule;
- systemd timer;
- path activation;
- socket activation;
- device/udev event;
- D-Bus event;
- journald event;
- inotify/fanotify event;
- netlink event;
- boot/session lifecycle event.

Prefer events over polling.

Polling requires explicit justification, interval, cost, timeout/stop behavior
and stale-observation semantics.

## Condition semantics

Conditions must operate on typed facts/state where possible.

Avoid:

    grep output -> if string -> privileged mutation

Prefer:

    Observation
        -> typed Fact
        -> Condition evaluation
        -> policy
        -> Activation

Define edge-triggered vs level-triggered semantics where relevant.

For:

    disk.free < threshold

decide whether repeated observations continuously activate work or whether
activation occurs on threshold crossing.

## Repeated triggers

Define policies such as only when real cases require them:

- ALLOW_CONCURRENT
- SUPPRESS_WHILE_RUNNING
- COALESCE
- REPLACE
- DEFER
- REJECT

Do not invent a queue merely to implement these words.

Document defaults.

## Event storms

Design protection against:

- bursty udev events;
- repeated journal records;
- filesystem storms;
- feedback loops where Rebuntu's own action generates the triggering event;
- repeated failing recovery attempts.

Investigate:

- debounce;
- coalescing;
- cooldown;
- rate limiting;
- causal/correlation IDs;
- suppression windows;
- state-transition triggering.

Keep these concepts distinct.

## Activation provenance

Every meaningful activation should be explainable:

    automation_id
    trigger kind
    source
    observed fact/event
    timestamp
    scope
    policy decision
    target
    correlation/causation identity

Do not require all fields for trivial in-process use.

## Enabled vs running

An Automation being enabled is administrative desired state.

It does not imply:

- evaluator process running;
- target currently executing;
- condition currently true;
- automation healthy;
- last execution successful.

Integrate Phase 0.14 vocabulary rather than inventing an automation state blob.

## Failure model

Distinguish:

- trigger-source failure;
- observation failure;
- condition-evaluation failure;
- policy rejection;
- activation failure;
- target execution failure;
- verification failure;
- automation-host failure.

Do not flatten these into `automation failed`.

## Retry

Retry belongs to failed bounded work or failed activation according to an
explicit policy.

Reuse Phase 0.8 attempts and Phase 0.9 temporal semantics.

Every retry must preserve previous attempt evidence.

Never silently retry forever.

## Missed activations

For persistent scheduling/events determine whether missed activation matters.

Examples:

- missed nightly maintenance may be catch-up eligible;
- missed transient USB insertion may no longer be meaningful.

Do not implement one universal "run missed jobs" policy.

## Cancellation / disable

Define what happens when an Automation is disabled while its target is already
running.

Default candidate:

    disable prevents future activations;
    it does not automatically kill already-running work.

Validate this.

Cancellation of current work must be a separate explicit action/policy.

## Persistence

Persist only what must survive:

- enabled/disabled desired state;
- durable schedule/trigger definitions;
- last processed cursor if required for correctness;
- cooldown/retry state if restart semantics require it.

Do not persist rediscoverable runtime truth unnecessarily.

## Native Linux mapping

Explicitly map use cases to:

- systemd timers;
- systemd path units;
- systemd socket activation;
- systemd device units;
- udev rules;
- D-Bus signals;
- journald;
- inotify/fanotify;
- netlink;
- process-local event loops.

Do not build a generic polling daemon when a native activation mechanism is
better.

      -> Automation
      -> policy
      -> Workflow
      -> verify

### Disk-space threshold

### Service crash

      -> automation

Do not duplicate systemd restart policy when systemd itself is sufficient.

### File organizer

Revisit the historical automatic organizer. Determine which pieces are:

- filesystem observation;
- classification;
- policy;
- Automation;
- Workflow/Operation;
- verification.

### Event storm

Prove repeated identical events do not create unbounded work.

### Reboot

Determine which automation state must survive and which should be
reconstructed.
