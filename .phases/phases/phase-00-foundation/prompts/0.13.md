## Resolve the runtime roles

Explicitly decide whether these survive:

### Runner

Candidate meaning:

    progresses one bounded execution according to an executable definition.

### Executor

Candidate meaning:

    invokes a concrete implementation/provider and returns structured runtime
    observations/results.

### Dispatcher

Candidate meaning:

    routes eligible work to an appropriate execution mechanism/provider.

### Activation

Candidate meaning:

    a concrete occurrence making a definition eligible to become runtime work.

Do not retain three classes when one function/module has the actual
responsibility.

## Definition vs runtime

Enforce:

    OperationDefinition != OperationExecution
    WorkflowDefinition != WorkflowExecution
    Task != Job
    Job != Execution
    Execution != Attempt
    Execution != Process

A Python function call can be an Execution without an OS child process.

A systemd unit may realize an Execution while systemd owns the process.

A daemon RPC may realize an Execution without spawning anything.

## Execution mechanisms

Map at least:

- direct Python callable;
- coroutine;
- native executable;
- subprocess;
- systemd transient/managed unit;
- D-Bus method;
- Unix-socket RPC;
- request to existing daemon/service.

Do not normalize them so aggressively that native semantics disappear.

## Execution identity

Define semantic execution identity separately from:

- PID;
- thread ID;
- systemd MainPID;
- cgroup;
- subprocess handle.

When OS process correlation matters, prefer robust primitives such as pidfd,
start time, cgroup/systemd unit identity rather than PID alone.

## Execution context

Determine the minimum bounded context required:

- execution ID;
- parent/correlation ID;
- caller/origin;
- scope;
- typed inputs;
- selected provider;
- cwd;
- explicit environment subset;
- timeout/deadline;
- cancellation;
- resource claims;
- evidence sink/reference.

Do not create a global dependency container disguised as `ExecutionContext`.

## Environment

Ambient environment is not trustworthy configuration.

For consequential subprocess execution:

- explicit argv;
- explicit cwd;
- controlled env;
- no accidental secret copying;
- explicit timeout;
- explicit stdin policy;
- captured/streamed stdout/stderr policy.

## Sync vs async

Synchronous means caller waits for completion.

Asynchronous means caller does not synchronously block for final completion.

Async does not automatically mean:

- queue;
- worker pool;
- daemon;
- separate process;
- distributed execution.

## Dispatch

Dispatch should exist only if actual routing decisions exist.

Potential routing dimensions:

- provider;
- implementation kind;
- resource availability;
- scope;
- privilege;
- target service;
- local execution mechanism.

Do not build a scheduler here.

## Privilege

No hidden `sudo`.

The runtime must know whether a target requires privilege and use the
authorization/elevation architecture established elsewhere.

A generic root Executor accepting arbitrary commands is forbidden.

## Cancellation

Define:

    cancellation requested
    cancellation propagated
    cancellation acknowledged
    termination attempted
    cleanup
    final outcome

Cancellation != failure.

For subprocesses define process-group/ownership semantics before killing.

For systemd-backed work use systemd lifecycle mechanisms.

For RPC work use protocol cancellation only where supported.

## Timeout / deadline

Reuse Phase 0.9.

Timeout expiry is a condition requiring a termination/cancellation policy.

It is not synonymous with SIGKILL.

Use monotonic time for elapsed duration.

## Attempts / retries

Reuse Phase 0.8:

    Execution
        -> Attempt 1
        -> Attempt 2
        -> ...

Never overwrite prior failed-attempt evidence.

The runtime should not invent retry policy when the caller/definition has none.

## Resources / locks

Execution may acquire resources only through established ownership/locking
semantics.

Record ownership.

Release resources in success, failure and cancellation paths.

Do not create stale `.lock` files as truth.

## Streams

stdout/stderr are streams.

They may become evidence.

They are not the structured Result contract.

Support bounded capture or streaming to avoid unbounded memory use.

## Errors

Preserve native diagnostics:

- errno;
- exit code;
- terminating signal;
- systemd result;
- D-Bus error;
- provider-specific error.

Normalization may add structure but must not erase native evidence.

## Crash recovery

After controller/runtime restart, classify known work where possible:

    COMPLETED
    STILL_RUNNING
    INTERRUPTED
    UNKNOWN
    ORPHANED
    REQUIRES_VERIFICATION

Do not infer failure merely because in-memory state disappeared.

Observe authoritative native state.

## Backpressure

If runtime consumers can submit faster than work can execute, define bounded
behavior.

Do not automatically build a queue.

Possible behavior can include immediate rejection, caller waiting, or
resource-specific concurrency limits.

## Observability

It must be possible to answer:

- what is executing?
- what definition caused it?
- who/what activated it?
- which attempt?
- through which provider?
- which resources?
- what is it waiting for?
- has cancellation been requested?
- what evidence exists?

Use structured journald correlation where appropriate.
