## Mission

Historical Rebuntu contains a rich state vocabulary. Preserve useful semantic
distinctions while eliminating ambiguous synonyms and giant state enums.

## Core problem

A single object can simultaneously be:

    lifecycle = RUNNING
    activity = WAITING
    control = ENABLED
    readiness = NOT_READY
    health = HEALTHY
    outcome = NONE

Therefore one flat enum is usually wrong.

## Candidate orthogonal axes

Evaluate:

### Lifecycle

Progress through existence/execution:

    CREATED
    INITIALIZING
    RUNNING
    STOPPING
    COMPLETED / TERMINATED
    FAILED

Do not add states merely for symmetry.

### Activity

What it is doing now:

    BUSY
    WAITING
    IDLE
    SLEEPING

Determine whether `RESTING` has a distinct systems meaning or is historical
synonym/noise.

### Control

Administrative imposed state:

    ENABLED / DISABLED
    PAUSED
    FROZEN
    LOCKED

Determine whether locked belongs to resource ownership rather than generic
control.

### Availability

Can consumers access the capability/service/resource?

### Readiness

Can it correctly accept/perform work now?

### Health

Is it operating within its expected correctness envelope?

### Outcome

What terminal semantic result occurred?

Do not implement all axes for all objects.

## State vs Status

Define both or eliminate one.

Candidate:

    state = structured machine-readable condition
    status = human/query-oriented projection/report

But do not keep this distinction unless it improves actual architecture.

## Desired / observed / persisted / derived

Explicitly distinguish:

- desired state;
- observed state;
- persisted state;
- derived state;
- reported state.

Example:

    desired service state = running
    observed service state = stopped
    persisted last observation = running

These are not contradictory once provenance/time is explicit.

## Provenance and freshness

Observed state should support, where needed:

- source;
- observed_at;
- freshness/staleness;
- confidence only if genuinely inferred;
- evidence reference.

Do not attach elaborate metadata to every boolean.

## UNKNOWN

UNKNOWN is first-class whenever authoritative observation is unavailable.

Never convert:

    query failed -> false
    missing file -> stopped
    no evidence -> healthy
    stale cache -> current truth

## Enabled / running / ready / available / healthy

Make these distinctions explicit.

A service can be:

- enabled but stopped;
- running but not ready;
- ready but degraded;
- running but unhealthy;
- disabled yet currently running.

Tests must demonstrate these cases.

## Waiting

`WAITING` requires a reason rather than dozens of states.

Candidate:

    activity = WAITING
    reason.kind = RESOURCE / DEPENDENCY / EVENT / TIME / INPUT / LOCK

Do not invent `WAITING_FOR_NETWORK`, `WAITING_FOR_DISK`, etc. as global enums
unless domain contracts require them.

## Jammed

Investigate and define `jammed`.

Candidate:

    alive/running but failing to make expected forward progress.

This is useful for hangs/stalls and is distinct from:

- dead;
- blocked normally;
- waiting intentionally;
- failed;
- zombie.

Define how jammed can be established from evidence. Never infer it from one
slow observation.

## Zombie

For OS processes, `zombie` must correspond to Linux process state Z.

Do not reuse `zombie` for stale registry entries or orphaned runtime records.

Use terms such as stale/orphaned if those concepts are needed.

## Done / completed / finished

Do not collapse blindly.

Investigate historical semantics.

Possible outcome:

- `done` becomes a predicate/UX word;
- `completed` means semantic completion;
- `finished` means runtime execution ended regardless of semantic success.

Or reject this if evidence suggests a cleaner grammar.

## Transitions

Separate state from transition/action:

    start
    stop
    pause
    resume
    freeze
    thaw/unfreeze
    release
    continue
    exit
    complete
    finish
    fail

Do not store `resumed` as a durable current state if it is really an event.

## Progress

Progress is separate from state.

Possible representations:

- indeterminate;
- current/total;
- units;
- current stage;
- last_progress_at.

Never fabricate percentages.

Progress evidence is especially relevant to `jammed`.

## Native mappings

Map carefully:

- systemd ActiveState/SubState/UnitFileState;
- process states from procfs;
- package installed state;
- mount state;
- device availability;
- socket/service readiness.

Do not force all native states into one lossy universal enum.

Use adapters/projections where necessary.

## Persistence

Ask for every state value:

- can it be rediscovered?
- does it need to survive restart?
- is it desired state or observation?
- who owns it?
- what invalidates it?

Do not persist current runtime truth unnecessarily.

## Invalid transitions

Where lifecycle transitions are controlled by Rebuntu, define valid transition
rules.

Where state is merely observed from Linux, do not pretend Rebuntu controls the
transition graph.

## Predicates

Support clean predicates for later shell semantics where justified:

    running
    enabled
    installed
    ready
    healthy
    reachable
    readable
    writable
    executable
    locked

Predicates should have typed subjects and evidence.
