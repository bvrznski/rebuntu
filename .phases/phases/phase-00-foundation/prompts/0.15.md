## Canonical semantic candidates

### Event

A statement that something relevant was observed to have happened.

An Event is not necessarily a log record.

### Request

A structured expression asking a capability/component to perform or query
something.

### Response

Communication replying to a Request.

Response is not automatically the final semantic Result.

### Message

A transport-neutral communication envelope/payload.

A Message may carry a Request, Event, Response or other typed payload.

### Signal

Define carefully.

Distinguish semantic Rebuntu Signal from POSIX signals such as SIGTERM.

If a separate semantic Signal adds no value, reject it.

### Command

If retained, define as an imperative semantic request, not a shell command
string.

### Trigger

Trigger is activation semantics, not a transport packet.

## Transport independence

Do not make:

    Event == D-Bus signal
    Request == socket packet
    Command == shell string
    Message == JSON

Semantic types must survive transport changes.

## In-process communication

Prefer ordinary typed Python calls when components live in the same process
and no isolation/lifecycle reason requires IPC.

Do not create IPC because modules are conceptually separate.

## IPC decision

Evaluate:

- Unix domain sockets;
- D-Bus;
- pipes/FIFOs;
- inherited file descriptors;
- subprocess stdin/stdout;
- shared memory only where justified;
- existing service-native APIs.

Do not expose network TCP by default.

## Historical FIFOs

Historical dedicated pipes may have provided:

- addressability;
- control;
- request delivery;
- state transitions.

Separate those semantics.

Do not preserve FIFO-per-component merely for nostalgia.

Use FIFO only if FIFO semantics themselves are appropriate.

## Correlation and causation

Where multi-step activity crosses boundaries, support:

    message/request ID
    correlation ID
    causation ID
    origin
    timestamp

Do not require distributed-tracing bureaucracy for simple local calls.

## Time semantics

For Events distinguish where relevant:

- event occurrence time;
- observation time;
- processing time.

Do not pretend they are identical.

## Schemas

Durable/public IPC contracts require typed schemas.

Define:

- message kind;
- version if compatibility requires it;
- typed payload;
- required fields;
- bounds;
- unknown-field policy;
- validation errors.

Never deserialize untrusted pickle.

## Validation

External input is untrusted.

Validation must occur before:

- provider selection;
- privilege;
- filesystem mutation;
- shell execution.

## Delivery guarantees

State guarantees honestly.

Possible:

- best effort;
- at-most-once;
- retryable request;
- durable delivery if actually implemented.

Do not claim exactly-once semantics.

Idempotency and deduplication are often better tools than fictional
exactly-once delivery.

## Ordering

Do not promise global ordering.

Define ordering only within a concrete channel/source when supported.

## Duplicates

Events/messages may be duplicated.

Consumers that require deduplication need explicit identity/window semantics.

## Backpressure

Streams and queues require bounded behavior.

Define:

- bounded buffers;
- producer blocking;
- dropping policy;
- coalescing;
- rejection.

Never allow unbounded memory growth.

## Request timeout and cancellation

Reuse Phase 0.9/0.13.

A disconnected caller does not automatically imply safe cancellation of the
requested work.

Define ownership.

## Security

For privileged IPC determine:

- peer identity;
- authorization;
- socket permissions;
- D-Bus policy;
- capability scope.

A local socket is not automatically trusted.

## Logs vs events

journald is excellent for logs and can be an observation source.

Do not turn every log line into a semantic Event.

Normalize only records that matter to Rebuntu semantics.

## Internal vs user notifications

An internal alert/event is not a desktop/user notification.

Keep presentation/notification policy separate.

## Stream semantics

Define Stream as ongoing/ordered data sequence where useful.

Stream != Workflow.

Pipeline != Workflow.

Unix pipe topology is communication/data flow, not automatically orchestration.

## Representative scenarios

1. shell sends typed Operation request;
2. Workflow invokes in-process Operation;
3. semantic service receives local request;
4. daemon publishes a device event;
5. journald record becomes normalized Event;
6. malformed privileged request;
7. duplicate event;
8. caller disconnects;
9. large stdout stream;
10. backpressure;
11. D-Bus signal;
12. historical FIFO migration.

## Anti-patterns

Reject:

- universal EventBus without demonstrated consumers;
- generic broker;
- arbitrary JSON blobs;
- pickle IPC;
- network listener by default;
- semantic types tied to transport;
- global ordering promises;
- unbounded queues;
- logs as authoritative state;
- shell strings as commands.
