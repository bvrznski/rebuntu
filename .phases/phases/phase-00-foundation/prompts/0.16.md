## Definitions

### Interface

Candidate:

    an explicit behavioral/contract boundary visible to consumers.

Interface does not necessarily mean Python ABC.

### Adapter

Candidate:

    translation between Rebuntu semantics/contracts and an external or
    incompatible mechanism.

### Provider

Candidate:

    one concrete implementation/source capable of satisfying a semantic
    capability.

Validate all three.

## Example: package installation

Desired semantic level:

    package.install(target)

Possible providers:

    apt
    snap
    flatpak
    pipx
    cargo
    npm
    go

But these do not necessarily have identical semantics.

Provider abstraction must not lie.

Record provider-specific constraints.

## Example: clipboard

Semantic capability:

    clipboard.write(data)

Possible adapters/providers may depend on:

- Wayland;
- X11;
- desktop/session tooling.

Preserve the elegant historical `clip` UX while making mechanism selection
explicit and verifiable.

## Interface != ABC

Do not create abstract base classes merely to say an interface exists.

Use Protocols, typed call contracts, modules/functions or ABCs according to
actual needs.

## Provider selection

Selection must be:

- deterministic;
- policy-aware;
- observable;
- explainable;
- testable.

Inputs may include:

- explicit caller choice;
- user preference;
- platform availability;
- semantic capability;
- security policy;
- scope.

Do not silently fall back to a provider with materially different semantics.

## Availability

Provider installed != provider available != provider usable.

Model only distinctions needed.

Verification may include:

- executable exists;
- service available;
- permissions sufficient;
- target environment compatible.

## Errors

Preserve native provider errors.

Add normalized categories only when consumers benefit.

Do not replace useful native diagnostics with `ProviderError("failed")`.

## Native Linux boundaries

Map concrete system boundaries:

- systemd;
- D-Bus;
- udev;
- procfs;
- sysfs;
- package managers;
- filesystem;
- mount APIs/tools;
- network stack;
- nftables;
- desktop/session;
- GPU/vendor APIs;
- hardware/device interfaces.

Prefer structured/native APIs over parsing human-oriented output when
practical.

CLI adapters are acceptable when the CLI is the stable practical interface.

## Anti-corruption boundary

Where Linux/provider semantics differ from Rebuntu semantics, translate at the
boundary.

Do not leak apt-specific flags into `package.install` unless the semantic
operation intentionally exposes provider-specific options.

## Dependency direction

Core semantic contracts should not import concrete provider implementation.

Concrete providers may depend on semantic contracts.

Avoid circular imports.

## Discovery vs registration

Provider discovery asks what exists/is usable.

Registration maps a provider implementation into Rebuntu where a registry is
actually needed.

Do not create a dynamic plugin ecosystem merely because providers exist.

## Lifecycle

Most providers should not have lifecycle.

A provider backed by a persistent service may have availability/readiness.

Do not give every adapter start/stop methods.

## Security

Each boundary must document:

- trust level;
- input validation;
- privilege requirements;
- filesystem/network exposure;
- secrets;
- cleanup ownership.

## Time/cancellation

Translate timeout and cancellation semantics honestly.

If underlying provider cannot cancel safely, expose that limitation.

## Structured normalization

Normalize enough to give consumers stable typed data.

Do not normalize away meaningful provider distinctions.

This instruction overrides all Python-specific implementation-language assumptions elsewhere in this task.

Preserve the task's semantic requirements, architecture, behavior, invariants, safety requirements, tests, acceptance criteria, and Linux integration, but implement them idiomatically in native C++20.

Translate Python-specific mechanisms to their appropriate C++20 equivalents by SEMANTIC PURPOSE, not by mechanical syntax substitution.

If any requirement in the task conflicts solely because it explicitly mandates Python for Rebuntu's own implementation, this IMPLEMENTATION LANGUAGE OVERRIDE takes precedence. Do not treat that conflict as an ambiguity requiring Python code.
