### Safe modification policy

Do not use `rm -rf`, broad recursive `chown`, broad recursive `chmod`, or
similar destructive commands as a convenient architecture tool.

If useful code is misplaced:

    DISCOVER
        -> UNDERSTAND
        -> FIND CORRECT OWNER
        -> MOVE / REFACTOR
        -> UPDATE IMPORTS
        -> TEST
        -> VERIFY

Do not delete it merely because its current directory is wrong.

For filesystem mutation prefer:

    DISCOVER
        -> RESOLVE EXACT TARGET
        -> PRECHECK

## Definitions

### Result

Structured report of an invocation/execution.

### Outcome

Semantic classification of what ultimately happened.

### Error

Structured information describing a problem encountered.

### Failure

Failure to satisfy a required contract.

### Verification

Evaluation of whether expected semantic postconditions hold in observed
reality.

### Evidence

Observations/artifacts supporting claims.

### Report

Human or aggregate presentation derived from structured facts/results.

Validate these definitions.

## Validation vs verification

Validation happens before/around execution:

    Is input/schema/plan acceptable?

Verification happens after effect/observation:

    Is the intended state actually true?

Do not use these interchangeably.

## Native execution evidence

Preserve:

- return/exit status;
- stdout;
- stderr;
- errno;
- signal;
- systemd result;
- D-Bus error;
- provider diagnostics;
- timestamps.

These are evidence about execution, not automatically proof of semantic
postconditions.

## Verification

A mutating Operation should define meaningful postconditions where feasible.

Examples:

Package install:

    weak: apt returned 0
    better: package manager reports package installed
    stronger where required: expected executable/version is available

Service start:

    weak: systemctl start returned 0
    better: systemd reports active
    stronger: functional readiness probe succeeds

## Verification statuses

Design a minimal vocabulary.

Candidates:

    VERIFIED
    NOT_VERIFIED
    VERIFICATION_FAILED
    UNKNOWN

Do not create false certainty.

If no verifier exists, report that fact.

## UNKNOWN

Examples:

- verifier unavailable;
- permission prevents observation;
- observation timed out;
- evidence stale.

UNKNOWN is not FAILED.

## Output vs Result

Output is data produced.

Result describes execution/outcome.

A query may output a package version and have a successful Result.

A command may produce useful stdout while its Operation fails verification.

## Error chains

Preserve causality:

    verification failed
      caused by
    endpoint unreachable
      caused by
    connection refused

Do not stringify away structured causes.

## Partial success

Define only where useful.

Workflow aggregation must preserve child results.

Do not label a Workflow `SUCCESS` if a required child failed simply because
later cleanup succeeded.

## Cancellation / timeout

Treat cancellation and timeout distinctly when consumers need to reason about
them.

Timeout is not necessarily failure of the underlying semantic target; final
state may require observation.

## Retry

A final successful retry must not erase earlier failed Attempts.

Result aggregation should make history inspectable.

## Evidence model

Evidence may include:

- state observation;
- file stat;
- checksum;
- package metadata;
- service state;
- readiness probe;
- journal cursor/record reference;
- device identity;
- command execution record;
- before/after state.

Evidence should have provenance and observation time where meaningful.

## Evidence storage

Do not embed enormous logs into every Result.

Use references/structured summaries and durable evidence storage only where
required.

Define ownership and retention.

## Secrets / redaction

Results/evidence/logs must not accidentally include:

- passwords;
- tokens;
- secret environment variables;
- credentials;
- private key material.

Redaction belongs at trusted boundaries, not only human rendering.

## Human rendering

Machine result and human report are separate.

A shell may render:

    Installed foo ✓

while the structured Result retains provider, version, verification and
evidence.

## Immutability/finalization

Determine whether finalized Results should be immutable.

Do not let later code silently rewrite history.

This instruction overrides all Python-specific implementation-language assumptions elsewhere in this task.

Preserve the task's semantic requirements, architecture, behavior, invariants, safety requirements, tests, acceptance criteria, and Linux integration, but implement them idiomatically in native C++20.

If any requirement in the task conflicts solely because it explicitly mandates Python for Rebuntu's own implementation, this IMPLEMENTATION LANGUAGE OVERRIDE takes precedence. Do not treat that conflict as an ambiguity requiring Python code.
