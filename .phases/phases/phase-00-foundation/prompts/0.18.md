2. Inspect the current tree.

4. Search for existing names and semantic equivalents, not only exact names.

10. Write down evidence for the proposed architectural decision.

### Safe modification policy

Do not use `rm -rf`, broad recursive `chown`, broad recursive `chmod`, or
similar destructive commands as a convenient architecture tool.

If useful code is misplaced:

    DISCOVER
        -> UNDERSTAND
        -> FIND CORRECT OWNER
        -> MOVE / REFACTOR
        -> UPDATE IMPORTS
        -> TEST
        -> VERIFY

Do not delete it merely because its current directory is wrong.

For filesystem mutation prefer:

    DISCOVER
        -> RESOLVE EXACT TARGET
        -> PRECHECK
        -> PLAN
        -> AUTHORIZE
        -> CHECKPOINT / BACKUP WHEN WARRANTED
        -> EXECUTE
        -> OBSERVE
        -> VERIFY
        -> EVIDENCE
        -> RESULT

## Mission

Establish Rebuntu's canonical grammar for configuration and declarative
specifications.

Historical Rebuntu used:

    Settings
    Options
    Preferences
    Properties
    Attributes
    Setup
    Configuration

Do not preserve these merely because the words exist. Determine whether each
has a distinct engineering meaning.

## Archaeology

Search:

- configuration files;
- settings files;
- defaults;
- env vars;
- shell variables;
- setup scripts;
- templates;
- properties;
- attributes;
- options;
- preferences;
- schemas;
- manifests;
- command-line overrides;
- historical forms.

For every historical concept identify actual consumers and semantics.

## Candidate distinctions

Test these hypotheses:

    Settings
        stable behavioral selections/toggles

    Options
        bounded alternatives available for a choice

    Preferences
        soft user choices that may be unsatisfied

    Setup
        specification/process establishing an environment/installation

    Configuration
        parameters consumed by installed components

    Properties
        characteristics of a definition/component

    Attributes
        characteristics of an instance/runtime object

These are hypotheses.

Collapse concepts that cannot be distinguished by contract and consumer.

## Configuration != state

Never store runtime truth as configuration merely because it is convenient.

Examples:

    configured desired GPU = configuration
    currently active GPU = observed state

    configured service enabled = desired configuration
    current service state = observation

## Specification != instance

A WorkflowSpec is not a WorkflowExecution.

An Operation definition is not its current Result.

Do not allow runtime fields to leak into declarative specs.

## Sources and precedence

Discover actual needs before fixing an order.

Candidate sources:

1. built-in defaults;
2. system configuration;
3. host configuration/profile;
4. user configuration;
5. user preferences;
6. environment;
7. invocation overrides.

Define precedence explicitly.

Do not allow every source to override every field.

Policy/security constraints may be non-overridable.

## Provenance

For effective configuration, it should be possible where useful to answer:

    value = X
    source = user config
    default = Y
    constrained by = policy Z

Do not attach heavy provenance objects to every local variable.

## Defaults

Defaults are not detected values.

A default should be deterministic and documented.

Detected host facts belong to observation/discovery.

## Preferences

A preference may fail to be satisfiable.

Example:

    preferred clipboard provider = Wayland tool
    current session = X11

The system should explain fallback rather than pretending the preference
changed.

## Options

Determine whether `Option` needs any runtime type at all.

Often an option is simply an enum/schema constraint.

Prefer schema semantics over ontology proliferation.

## Properties / attributes

Determine whether these are necessary Rebuntu terms or ordinary programming
language vocabulary.

Do not create `Properties` and `Attributes` frameworks unless distinct
architecture requires them.

## Schemas

Structured durable configuration should have:

- types;
- required/optional fields;
- defaults;
- validation;
- unknown-field policy;
- constraints;
- migration/version only when necessary.

Prefer standard formats and typed Python models.

## Formats

Evaluate:

- TOML;
- JSON;
- typed Python;
- environment variables;
- shell config.

YAML should require a concrete reason.

Do not create a custom configuration language.

## Secrets

Secret values require separate handling.

Do not:

- log them;
- put them in normal result/evidence;
- serialize them casually;
- store them world-readable.

Prefer references/native credential facilities where appropriate.

## Reload

Not every configuration is reloadable.

Define:

- startup-only;
- reloadable;
- per-request.

Do not implement reload watchers without consumers.

## Atomic writes

For managed durable configuration use safe write/replace patterns where
appropriate.

Preserve ownership/mode.

Never overwrite user-authored files without an explicit ownership/merge
contract.

## Configuration application

Separate:

    parse
      -> validate
      -> resolve effective config
      -> plan changes
      -> authorize
      -> apply
      -> observe
      -> verify

A valid config does not prove successful application.

## Shared specification grammar

Investigate common fields across:

- Unit;
- Operation;
- Workflow;
- Automation;
- Schedule.

Possible shared concepts:

- identity;
- description;
- inputs;
- policy references;
- timeout;
- resource requirements.

Do not create a giant universal `BaseSpec`.

Composition/protocols are preferable when commonality is small.

## Introspection

Users/agents should be able to inspect effective configuration without
exposing secrets.

Support provenance/diff where useful.

# IMPLEMENTATION LANGUAGE OVERRIDE

INSTEAD OF PYTHON, USE C++20 AS THE PRIMARY IMPLEMENTATION LANGUAGE.

This instruction overrides all Python-specific implementation-language assumptions elsewhere in this task.

Preserve the task's semantic requirements, architecture, behavior, invariants, safety requirements, tests, acceptance criteria, and Linux integration, but implement them idiomatically in native C++20.

Translate Python-specific mechanisms to their appropriate C++20 equivalents by SEMANTIC PURPOSE, not by mechanical syntax substitution.

Use the existing Rebuntu C++ architecture, CMake/CTest infrastructure, Result/Evidence models, runtime, providers, Linux integrations, and other existing abstractions before creating new ones.

Do not recreate a Python architecture in C++ form.

Where the task explicitly concerns interoperability with an external Python component, Python may remain at that external boundary; Rebuntu itself remains C++20-first.

If any requirement in the task conflicts solely because it explicitly mandates Python for Rebuntu's own implementation, this IMPLEMENTATION LANGUAGE OVERRIDE takes precedence. Do not treat that conflict as an ambiguity requiring Python code.
