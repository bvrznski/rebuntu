### Repository-first procedure

Before changing code:

1. Read every applicable `AGENTS.md`.
2. Inspect the current tree.
3. Read relevant architecture, ontology, vocabulary, safety, archaeology and
   roadmap documents.
4. Search for existing names and semantic equivalents, not only exact names.
5. Search tests.
6. Search current implementation.
7. Search historical Rebuntu material when available.
8. Search for native Linux mechanisms already solving the lower-level problem.
9. Identify consumers before creating abstractions.
10. Write down evidence for the proposed architectural decision.

Search broadly enough to find implementations hidden under old terminology.

Do not assume a missing exact class name means the capability is absent.

### Safe modification policy

Do not use `rm -rf`, broad recursive `chown`, broad recursive `chmod`, or
similar destructive commands as a convenient architecture tool.

If useful code is misplaced:

    DISCOVER
        -> UNDERSTAND
        -> FIND CORRECT OWNER
        -> MOVE / REFACTOR
        -> UPDATE IMPORTS
        -> TEST
        -> VERIFY

Do not delete it merely because its current directory is wrong.

For filesystem mutation prefer:

    DISCOVER
        -> RESOLVE EXACT TARGET
        -> PRECHECK
        -> PLAN
        -> AUTHORIZE
        -> CHECKPOINT / BACKUP WHEN WARRANTED
        -> EXECUTE
        -> OBSERVE
        -> VERIFY
        -> EVIDENCE
        -> RESULT

without building registry bureaucracy or magical plugin loading.

## Name categories

Distinguish:

### Human name

Presentation label.

### Semantic ID

Stable identity describing what capability/object means.

### Filesystem path

Storage location.

### Python import path

Implementation location.

### systemd unit name

Native lifecycle artifact identity.

### Shell verb/command

User-language surface.

These must not be assumed identical.

## Semantic IDs

Evaluate semantic IDs such as:

    package.install
    service.restart
    storage.inspect

Do not enforce a naming style without checking existing architecture.

IDs should describe semantics, not implementation:

Bad:

    apt_installer
    python_workflow_3
    bash_backup_script

when the semantic capability is provider-independent.

## Namespace design

Use namespaces to:

- avoid collisions;
- communicate semantic ownership;
- support discovery.

Do not create deeply nested namespaces for aesthetic taxonomy.

Domain may be one axis, structural kind another; do not force both into every
identifier.

## Aliases

Aliases are alternate names resolving to a canonical identity.

Define collision behavior.

Aliases must not silently change meaning over time.

## Rename / deprecation

If stable IDs change, define:

- canonical replacement;
- deprecation;
- compatibility only if required;
- migration of persisted references where relevant.

Do not preserve every historical typo forever.

## Registry

Candidate:

    authoritative mapping used by runtime consumers to resolve known
    definitions/implementations.

A Registry requires a consumer.

Do not create one merely to list files.

## Catalog

Candidate:

    discoverable descriptive inventory, potentially broader than runtime
    resolution.

Catalog may support search/documentation without becoming authoritative
runtime truth.

## Discovery

Discovery is the process of finding what exists/is available.

Distinguish:

- source-code discovery;
- installed capability discovery;
- provider discovery;
- native-system discovery;
- runtime availability.

Do not conflate these.

## Deterministic loading

Avoid import-time magic.

Prefer:

- explicit modules;
- manifests where justified;
- entry points only when needed;
- deterministic filesystem conventions;
- explicit registration.

Do not execute arbitrary files merely because they appeared in a directory.

## Search before implement

Make the project's core engineering rule practical.

An agent/engineer should be able to search:

- semantic ID;
- aliases;
- vocabulary;
- implementation symbols;
- docs;
- providers;
- tests.

Do not require a sophisticated semantic index in Phase 0.19.

A good tree/catalog and explicit IDs may be enough.

## Provider registration

One semantic capability may have multiple providers.

Keep:

    capability identity

separate from:

    provider identity

and:

    implementation path.

## Ownership locality

Concrete domain capabilities should remain near their domain owner when that
improves cohesion.

Do not move everything into central:

    operations/
    workflows/
    providers/

merely to make discovery easy.

Discovery should accommodate locality.

## Staleness

If catalogs are generated/cached, define invalidation.

A stale catalog must not become more authoritative than repository/runtime
reality.

## Security

Discovery must not create execution authority.

An untrusted file copied into a scanned directory must not automatically
become a privileged capability.

Validation/trust/registration are separate.

## Shell verb dictionary

Formalize the shell collision process before assigning a top-level verb:

    command -v <verb>
    type -a <verb>

Classify:

    FREE
    REBUNTU
    SHELL_BUILTIN
    SYSTEM_COMMAND
    USER_DEFINED
    AMBIGUOUS

Do not shadow builtins/system commands accidentally.

Preserve the known high-value historical UX where appropriate:

    install
    uninstall
    installed
    declared
    download
    extract
    catdir

but inspect collisions and semantics.

Reserve valuable free verbs such as `run` until deliberately assigned by the
shell architecture.

## Naming quality

Avoid generic dumping-ground names:

    misc
    helpers
    utils
    common

when a clear semantic owner exists.

Use ordinary helper modules when they truly are local implementation details;
the rule is not a ban on the English word "utility", but a ban on hiding
architecture.

# IMPLEMENTATION LANGUAGE OVERRIDE

INSTEAD OF PYTHON, USE C++20 AS THE PRIMARY IMPLEMENTATION LANGUAGE.

This instruction overrides all Python-specific implementation-language assumptions elsewhere in this task.

Preserve the task's semantic requirements, architecture, behavior, invariants, safety requirements, tests, acceptance criteria, and Linux integration, but implement them idiomatically in native C++20.

Translate Python-specific mechanisms to their appropriate C++20 equivalents by SEMANTIC PURPOSE, not by mechanical syntax substitution.

Use the existing Rebuntu C++ architecture, CMake/CTest infrastructure, Result/Evidence models, runtime, providers, Linux integrations, and other existing abstractions before creating new ones.

Do not recreate a Python architecture in C++ form.

Where the task explicitly concerns interoperability with an external Python component, Python may remain at that external boundary; Rebuntu itself remains C++20-first.

If any requirement in the task conflicts solely because it explicitly mandates Python for Rebuntu's own implementation, this IMPLEMENTATION LANGUAGE OVERRIDE takes precedence. Do not treat that conflict as an ambiguity requiring Python code.
