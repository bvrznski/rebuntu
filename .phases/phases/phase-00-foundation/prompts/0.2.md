# Rebuntu — Phase 0.2
# Runtime, Execution, Control & Coordination Architecture
# Expanding the Operational Grammar of Rebuntu

Phase 0.0 established the repository foundation.

Phase 0.1 established and expanded Rebuntu's structural grammar,
including the distinction between structural entities such as:

    System
    Module
    Unit
    Service
    Daemon
    Task
    Job
    Schedule
    Script

and broader distinctions such as:

    structural type
    operational role
    target domain
    specification
    runtime instance
    lifecycle state

Phase 0.2 must now answer the next architectural question:

    HOW DO REBUNTU ENTITIES ACTUALLY LIVE, EXECUTE,
    COMMUNICATE, COORDINATE, CHANGE STATE, AND PRODUCE RESULTS?

This is primarily an architectural expansion phase.

Do not implement a giant runtime framework.

Do not implement the native system LLM yet.

Instead, establish the operational grammar required for future runtime
implementation.

======================================================================
1. PRIMARY OBJECTIVE
======================================================================

Phase 0.1 primarily answered:

    WHAT KINDS OF THINGS EXIST IN REBUNTU?

Phase 0.2 should investigate:

    How are they instantiated?

    How are they activated?

    How are they executed?

    How are they controlled?

    How do they communicate?

    How are they coordinated?

    How is work submitted?

    How does work progress?

    How is state represented?

    How are lifecycle and health represented?

    How are dependencies represented?

    How are results returned?

    How are failures represented?

    How is execution verified?

    How do persistent and ephemeral entities differ?

    How does asynchronous activity differ from synchronous execution?

    How do events differ from requests and signals?

    How does scheduling relate to triggering?

    How do Rebuntu components interact with native Linux facilities?

The result should be a coherent operational architecture, not a pile of
manager classes.

4. OPERATIONAL GRAMMAR
======================================================================

Attempt to derive a compact grammar describing execution in Rebuntu.

For example, investigate whether a useful generalized relation resembles:

    REQUEST / EVENT / SIGNAL / SCHEDULE
                    |
                    v
                ACTIVATION
                    |
                    v
                 UNIT
                    |
                    v
               EXECUTION
                    |
                    v
                RESULT
                    |
                    v
              VERIFICATION
                    |
                    v
               EVIDENCE

For persistent entities:

    DEFINITION
        |
        v
    INSTANTIATION
        |
        v
    INITIALIZATION
        |
        v
    ACTIVATION
        |
        v
    RUNNING
        |
        v
    OBSERVATION
        |
        v
    CONTROL
        |
        v
    TERMINATION

Do not adopt these diagrams blindly.

Test them against:

    Task
    Job
    Service
    Daemon
    Schedule
    Workflow
    Operation

A good operational grammar should explain several entity types without
forcing them into identical lifecycle models.

======================================================================
5. RUNTIME
======================================================================

Define Runtime precisely.

Do not let:

    runtime/

become "everything that happens while Rebuntu is running."

Investigate whether Runtime should mean:

    the infrastructure required to instantiate and execute Rebuntu
    entities

and potentially own concepts such as:

    lifecycle
    execution context
    dispatch
    active instances
    coordination
    shutdown
    runtime state

Determine what belongs in:

    system/runtime/

versus:

    modules/
    units/
    interfaces/
    adapters/
    support/

Do not create a second Core under Runtime.

======================================================================
6. INSTANCE
======================================================================

Formalize the distinction between:

    definition/specification

and:

    runtime instance

Examples:

    ServiceDefinition
        ->
    ServiceInstance

    Task
        ->
    Job / TaskRun

    Workflow
        ->
    WorkflowRun

    Schedule
        ->
    scheduled activation

Do not necessarily use these exact class names.

The important architectural requirement is that Rebuntu must not confuse:

    what something IS DEFINED TO BE

with:

    what currently EXISTS IN EXECUTION.

Investigate identity rules for runtime instances.

Possible concerns include:

    instance ID
    parent/origin
    creation time
    lifecycle state
    execution context
    associated configuration
    result
    evidence

Do not create a universal giant runtime-object class.

======================================================================
7. EXECUTION
======================================================================

Define Execution as a first-class concept.

Investigate:

    Execution
    Runner
    Executor

Do not assume these are synonyms.

Possible distinction:

RUNNER

    Maintains the mechanics/lifecycle of running work.

EXECUTOR

    Performs or dispatches a concrete executable operation.

EXECUTION

    Concrete runtime occurrence of work being performed.

This is only a candidate distinction.

Test it.

For example:

    Job
        submitted to
    Runner
        creates
    Execution
        uses
    Executor
        performs
    Operation

may or may not be useful.

Reject unnecessary intermediaries.

======================================================================
8. DISPATCH
======================================================================

Investigate whether Dispatch deserves an explicit concept.

Potential flow:

    Request
        ->
    Resolve target
        ->
    Validate
        ->
    Dispatch
        ->
    Execute

Dispatch may need to choose between:

    local Python implementation
    C++ implementation
    systemd service
    subprocess
    D-Bus call
    Unix socket
    native Linux operation
    external provider

Do not implement the dispatcher yet.

Determine whether dispatch is:

    runtime infrastructure
    interface infrastructure
    execution infrastructure

and document the decision.

======================================================================
9. REQUEST
======================================================================

Define Request carefully.

A Request should probably represent an explicit request for Rebuntu to
perform or evaluate something.

Investigate fields/concepts such as:

    identity
    operation
    target
    parameters
    origin
    context
    constraints
    timeout
    priority

Do not freeze a schema yet unless enough evidence exists.

Distinguish Request from:

    Call
    Command
    Event
    Signal
    Task

Candidate distinction:

    Request = semantic/system request for something to happen
    Call    = invocation mechanism between components
    Command = user/interface representation or imperative
    Event   = statement that something happened
    Signal  = lightweight notification/control indication

Test these distinctions.

======================================================================
10. COMMAND
======================================================================

Rebuntu historically has command-oriented shell roots.

Determine where Command belongs in the modern vocabulary.

Potential relation:

    human/shell command
        ->
    parser
        ->
    Request
        ->
    Operation

Thus:

    Command != Operation

and:

    Command != Request

may be useful distinctions.

Do not make command strings the internal language of Rebuntu.

======================================================================
11. EVENT
======================================================================

Define Event as:

    an immutable or effectively immutable statement that something
    occurred or was observed

subject to refinement.

Events may originate from:

    Rebuntu
    systemd
    journald
    udev
    kernel
    filesystem
    network
    timers
    services
    users
    external applications

Events should not automatically imply actions.

Potential flow:

    Event
        ->
    Observation / state update
        ->
    Condition evaluation
        ->
    optional Trigger
        ->
    activation

Keep:

    EVENT

distinct from:

    RESPONSE

and:

    COMMAND.

======================================================================
12. SIGNAL
======================================================================

Signal requires special care because Linux already has a precise concept
of process signals.

Determine whether Rebuntu needs:

    Signal

as a broader internal concept.

If so, distinguish explicitly:

    Rebuntu Signal
    Linux process signal

Do not overload terminology ambiguously.

Candidate Rebuntu meaning:

    lightweight control/notification indication without the semantic
    payload expected from an Event or Request

But investigate whether Message/Event already cover this.

It is acceptable to reject a generic Rebuntu Signal concept and reserve
"signal" for native Linux signals.

======================================================================
13. TRIGGER
======================================================================

Define Trigger separately from Event.

Candidate:

    Event = something happened.
    Condition = some proposition is true.
    Trigger = activation decision produced because activation criteria
              were satisfied.

For example:

    udev event
        +
    condition: device matches X
        ->
    trigger: activate workflow Y

This distinction could become important.

Investigate it.

======================================================================
14. SCHEDULE
======================================================================

Phase 0.1 established Schedule as a Rebuntu concept rather than Cron.

Now investigate Schedule operationally.

A Schedule may produce activation based on:

    absolute time
    interval
    recurrence
    calendar expression
    delay
    deadline
    temporal window

Potential backend mechanisms:

    systemd timers
    cron
    at
    internal scheduler

Prefer native facilities where sufficient.

Do not implement a scheduling framework in this phase.

======================================================================
15. CONDITION
======================================================================

Define Condition as something evaluated over facts/state/context.

Examples:

    service.active == true

    mount.available == false

    temperature > threshold

    event_count >= N within T

Conditions may participate in:

    activation
    verification
    policy
    diagnostics
    security
    recovery

Do not implement the general condition engine yet.

But establish its likely architectural relationships.

======================================================================
16. STATE
======================================================================

State must be treated carefully.

Distinguish at minimum:

    observed state
    desired state
    runtime state
    persisted state
    derived state

Do not put all of these into one global dictionary.

Investigate ownership.

Example:

    system observed state
        should come from evidence/native mechanisms

    service runtime state
        may be maintained by systemd

    Rebuntu workflow runtime state
        may be owned by Rebuntu

    desired state
        may come from configuration/profile/policy

Avoid shadow state when Linux already owns authoritative state.

======================================================================
17. STATUS
======================================================================

Define Status separately from State.

Potential distinction:

    State
        actual structured condition of an entity

    Status
        summarized/exposed assessment of that state

For example:

    state:
        process exists
        socket bound
        model loaded

    status:
        READY

Determine whether this distinction is useful.

======================================================================
18. LIFECYCLE
======================================================================

Historical Rebuntu explored very detailed daemon lifecycle models.

Preserve the problem, not the old state explosion.

Do not construct one universal lifecycle containing dozens of states.

Investigate orthogonal dimensions such as:

    LifecycleState
    WorkState
    HealthState
    RecoveryState

Example:

    lifecycle = RUNNING
    work      = IDLE
    health    = DEGRADED
    recovery  = NONE

is more expressive than:

    running_idle_degraded

Do not necessarily implement these enums now.

Document the model.

======================================================================
19. INITIAL LIFECYCLE STATES
======================================================================

Determine whether a minimal generic lifecycle vocabulary is useful.

Candidates:

    CREATED
    INITIALIZING
    READY
    ACTIVE
    STOPPING
    STOPPED
    FAILED

But recognize that:

    Service
    Job
    Workflow
    Daemon

may require different lifecycle vocabularies.

Prefer shared semantics only where truly shared.

======================================================================
20. HEALTH
======================================================================

Health is NOT lifecycle.

An entity can be:

    running + healthy
    running + degraded
    running + unhealthy

Potential health states:

    UNKNOWN
    HEALTHY
    DEGRADED
    UNHEALTHY

Do not confuse:

    process exists

with:

    component works correctly.

======================================================================
21. READINESS
======================================================================

Readiness is also distinct.

Example:

    process running
    model loading
    health normal
    readiness false

then:

    model loaded
    readiness true

Document:

    Lifecycle != Health != Readiness.

This distinction will become immediately useful when Phase 0.3 introduces
the native semantic model service.

======================================================================
22. RESULT
======================================================================

Define Result.

A Result should represent the structured result of completed work.

Possible components:

    outcome
    output
    status
    evidence
    diagnostics
    timing
    error

Do not require all results to contain all fields.

Avoid using raw exit code as the universal result representation.

======================================================================
23. OUTCOME
======================================================================

Investigate Outcome as a semantic conclusion distinct from process status.

Candidate outcomes:

    SUCCESS
    FAILURE
    PARTIAL
    SKIPPED
    CANCELLED
    TIMED_OUT
    BLOCKED

Potentially:

    VERIFIED
    UNVERIFIED

should be a separate verification dimension rather than Outcome.

For example:

    execution outcome = SUCCESS
    verification      = FAILED

must be representable.

This is extremely important.

======================================================================
24. ERROR VS FAILURE
======================================================================

Distinguish:

ERROR

    information describing something that went wrong.

FAILURE

    an unsuccessful system/work outcome.

An operation may fail with one or more errors.

An error may be recoverable and therefore not cause final failure.

Do not make Python exceptions the system's complete failure ontology.

======================================================================
25. VERIFICATION
======================================================================

Connect Phase 0.2 runtime semantics to the future verification system.

Candidate execution pattern:

    PRECHECK
        ->
    EXECUTION
        ->
    RESULT
        ->
    VERIFICATION
        ->
    EVIDENCE

Important:

    execution succeeded

does NOT imply:

    desired state achieved.

Represent this distinction explicitly in architecture and vocabulary.

======================================================================
26. EVIDENCE
======================================================================

Treat Evidence as a first-class architectural concept.

Evidence may include:

    observed values
    command/API results
    systemd state
    file metadata
    kernel state
    timestamps
    hashes
    before/after snapshots
    verification measurements

Evidence should support claims made by Rebuntu.

Potential principle:

    CLAIMS SHOULD BE TRACEABLE TO EVIDENCE.

Do not implement an evidence database yet.

======================================================================
27. REGISTRY
======================================================================

Historical Rebuntu relied heavily on registries.

Re-evaluate the concept professionally.

Potential Registry responsibilities:

    discover known components
    map identifiers to definitions/providers
    expose capabilities
    resolve implementations
    enumerate available units/modules

Registry should NOT automatically become:

    global mutable application state.

Distinguish:

    Registry
    Catalog
    RuntimeState
    Configuration

Investigate whether multiple specialized registries are preferable to one
global registry.

Do not implement a giant service locator.

======================================================================
28. CATALOG
======================================================================

Determine whether Catalog is distinct from Registry.

Possible distinction:

    Catalog
        descriptive collection/index of known definitions/capabilities

    Registry
        runtime mapping/resolution mechanism

Example:

    Capability Catalog
        says filesystem.copy exists

    Provider Registry
        resolves filesystem.copy to implementation X

This distinction may prove useful.

Do not force it if unnecessary.

======================================================================
29. DISCOVERY
======================================================================

Discovery is one of Rebuntu's important future mechanisms.

Future behavior should increasingly follow:

    request capability
        ->
    search existing capabilities
        ->
    resolve existing implementation
        ->
    compose existing primitives
        ->
    only then consider extension/new implementation

Investigate architectural requirements for:

    capability discovery
    provider discovery
    service discovery
    runtime instance discovery

Do not implement all of them.

======================================================================
30. RESOLUTION
======================================================================

Define Resolver/Resolution if justified.

Potential uses:

    operation -> implementation
    service name -> service definition
    capability -> provider
    command intent -> operation
    dependency -> instance

Determine whether Resolver is a reusable structural concept or simply
behavior implemented by registries/providers.

Do not create `resolvers/` automatically.

======================================================================
31. LOADER
======================================================================

Historical Rebuntu used Loader heavily.

Determine what Loader should mean now.

Possible responsibilities:

    loading configuration
    loading definitions
    loading plugins/providers
    loading runtime resources

These may be different concepts.

Avoid one magical Loader that imports the entire system.

If multiple kinds of loading exist, use precise naming.

======================================================================
32. COORDINATION
======================================================================

Define Coordination.

Coordination is not execution itself.

Coordination may manage relationships between independently meaningful
entities.

Examples:

    start B after A is ready
    prevent C while D is active
    activate E when A and B satisfy conditions
    synchronize workflow threads
    arbitrate competing resource requests

Prefer Linux/systemd dependency mechanisms when they already express the
required relationship.

Rebuntu coordination should add semantics that native mechanisms do not
already provide.

======================================================================
33. DEPENDENCY
======================================================================

Distinguish different dependency kinds.

Possible categories:

    structural dependency
    implementation dependency
    runtime dependency
    ordering dependency
    readiness dependency
    resource dependency
    data dependency

Do not represent all dependencies as:

    depends_on = ["foo"]

without semantics.

Do not implement a dependency engine yet.

======================================================================
34. CHAIN
======================================================================

Historical Rebuntu used Chain to connect units and activation states.

Investigate whether Chain remains useful.

Possible modern meaning:

    declared ordered/conditional relationship among multiple Units

But compare it with:

    Workflow
    Pipeline
    Dependency graph
    Route

If Chain adds no unique semantics, retire it.

If it does, define exactly what those semantics are.

======================================================================
35. PIPELINE
======================================================================

Investigate Pipeline.

Possible distinction:

    Workflow
        general orchestration/composition

    Pipeline
        data/output from one stage flows into another

This would connect naturally with Rebuntu's historical Unix pipe/FD
influence.

Potential relation:

    Source -> Transform -> Transform -> Sink

Do not make every workflow a pipeline.

======================================================================
36. CHANNEL
======================================================================

Define Channel as an abstract communication relationship if useful.

A Channel may be implemented through:

    Unix socket
    pipe
    queue
    shared memory
    D-Bus
    internal Python queue

Do not confuse Channel with the transport implementation.

But do not abstract transports unnecessarily.

======================================================================
37. STREAM
======================================================================

Distinguish Stream from Channel.

Possible:

    Channel = communication path
    Stream  = ordered flow of data through a channel

Likewise:

    Pipe = specific topology/mechanism
    Route = selected path through components

Test these semantics.

======================================================================
38. MESSAGE
======================================================================

Determine whether Message is the common envelope for:

    Request
    Response
    Event

or whether these should remain independent protocols.

Do not create an enterprise messaging framework.

A small common protocol concept may eventually be useful for IPC.

======================================================================
39. SOURCE AND SINK
======================================================================

Preserve useful Unix/dataflow vocabulary.

Source:

    producer/origin of data/events/messages.

Sink:

    consumer/destination.

These may be roles rather than structural categories.

Do not create `sources/` and `sinks/` merely because the terms are useful.

======================================================================
40. SYNCHRONOUS VS ASYNCHRONOUS EXECUTION
======================================================================

Document this distinction explicitly.

Rebuntu will need both.

Synchronous:

    caller waits for completion/result.

Asynchronous:

    execution continues independently and result/status is observed later.

Do not encode asynchronous execution as "daemon".

A Job can be asynchronous without being a Daemon.

A Service can be persistent without representing a Job.

======================================================================
41. QUEUES
======================================================================

Investigate Queue as a runtime primitive.

Potential use:

    pending Jobs
    events
    requests
    internal work

Before implementing any queue, ask whether:

    asyncio
    Unix sockets
    systemd
    existing message infrastructure
    kernel facilities

already solve the concrete requirement.

Do not introduce Redis/RabbitMQ/etc. without an actual requirement.

======================================================================
42. CONCURRENCY
======================================================================

Reserve architectural language for:

    concurrency
    parallelism
    synchronization
    exclusion
    serialization

Do not assume Thread means Python thread.

Rebuntu's conceptual Thread from workflow semantics is distinct from:

    OS thread
    Python threading.Thread
    asyncio Task

Document naming carefully.

======================================================================
43. LOCK
======================================================================

Historical Rebuntu used files extensively as locks.

Preserve the requirement for mutual exclusion, not the implementation.

Different lock scopes may require:

    in-process lock
    inter-process lock
    filesystem lock
    systemd coordination
    database transaction
    kernel primitive

Do not create `.lock` files as a universal coordination mechanism.

Define Lock as a synchronization/control concept.

======================================================================
44. GUARD
======================================================================

Investigate Guard.

Possible meaning:

    evaluates whether an operation/activation is currently permitted.

A Guard might evaluate:

    policy
    conditions
    dependencies
    safety
    resources

Compare with:

    Gate
    Policy
    Precondition
    Constraint

Avoid synonyms.

======================================================================
45. GATE
======================================================================

Potential distinction:

    Guard
        evaluates permission/eligibility.

    Gate
        controls progression through an execution/workflow boundary.

Example:

    Step A
       |
    [Gate: verification passed?]
       |
    Step B

Determine whether both concepts are necessary.

======================================================================
46. CONTROL
======================================================================

Control must not become a vague mega-category.

Investigate sub-concepts such as:

    activation control
    execution control
    lifecycle control
    resource control
    policy control
    coordination

Determine whether `control/` deserves a physical architectural location or
whether these responsibilities belong with their owners.

======================================================================
47. CONTROLLER
======================================================================

Controller is likely a ROLE more often than a structural type.

Example:

    DisplayProfileService
        role = controller

rather than:

    modules/controllers/display_profile

Test this assumption.

Do not create controller classes simply because MVC/software tradition
uses the word.

======================================================================
48. MANAGER
======================================================================

Likewise investigate Manager critically.

"Manager" often means:

    class containing unrelated methods because naming was difficult.

Do not permit that.

If Manager is retained, define a precise Rebuntu meaning.

Otherwise classify it as discouraged generic naming.

This should be recorded in VOCABULARY.md/AGENTS.md.

======================================================================
49. HANDLER
======================================================================

Handler may be useful as a role:

    handles Event X
    handles Request Y
    handles Failure Z

But it may not deserve structural status.

Define naming rules.

Prefer:

    ServiceFailureHandler

over:

    SystemManager

when behavior is narrow and explicit.

======================================================================
50. SCHEDULER
======================================================================

Distinguish:

    Schedule = specification

from:

    Scheduler = mechanism evaluating/managing schedules

and:

    scheduled Job = runtime work resulting from schedule activation.

This is a useful example of:

    specification
    mechanism
    runtime realization

being three separate concepts.

======================================================================
51. AUTOMATION
======================================================================

Phase 0.2 should begin formalizing Automation without implementing the
automation engine.

Candidate definition:

    persistent or reusable rule/mechanism that observes events/state/time
    and activates Rebuntu work when declared conditions are satisfied.

Potential relation:

    Observation
        ->
    Condition
        ->
    Trigger
        ->
    Task/Workflow/Operation

Automation differs from Workflow:

    Workflow
        describes how work progresses after activation.

    Automation
        describes when/why work becomes activated.

This distinction is important.

======================================================================
52. AUTOMATON
======================================================================

Historical Rebuntu used "automaton" extensively.

Re-evaluate and preserve it if useful.

Possible modern distinction:

    Automation
        specification/rule

    Automaton
        active runtime realization of automation

or:

    Automaton
        persistent system component implementing an automation policy

Investigate both.

Do not make every daemon an Automaton.

Do not make every automation a daemon.

Native systemd timers/path/socket activation may implement some automations
without a persistent Rebuntu process.

======================================================================
53. RECONCILIATION
======================================================================

Introduce Reconciliation as an architectural candidate.

Potential pattern:

    observed state
        +
    desired state
        ->
    difference
        ->
    corrective plan
        ->
    operation
        ->
    verification

This is likely fundamental to future stability/homeostasis behavior.

But keep terminology firmly systems-oriented.

Do not implement the reconciler yet.

======================================================================
54. DESIRED STATE
======================================================================

Formalize DesiredState as distinct from Configuration.

Configuration may influence how a component operates.

Desired state says what system condition should hold.

Example:

    configuration:
        ssh port = 22

    desired state:
        ssh service active

    policy:
        SSH permitted only on LAN interface

    invariant:
        public ingress must remain unavailable

These are different concepts.

======================================================================
55. OBSERVED STATE
======================================================================

Observed state should be evidence-backed.

Do not assume Rebuntu should mirror the entire system in an internal state
store.

Native authority should remain authoritative where possible.

Example:

    systemd owns service state.

Rebuntu should query/subscribe to systemd rather than maintain an
independent competing truth.

======================================================================
56. RECONCILIATION VS RECOVERY
======================================================================

Distinguish:

RECONCILIATION

    moves observed state toward desired state.

RECOVERY

    responds to failure/degradation and attempts to restore acceptable
    operation.

They overlap but are not identical.

A configuration drift correction is reconciliation.

Recovering a failed filesystem may require a recovery procedure.

======================================================================
57. RECOVERY
======================================================================

Reserve semantics for:

    Retry
    Restart
    Rollback
    Restore
    Repair
    Failover
    Degrade

Do not treat them as synonyms.

Examples:

Retry:
    attempt the same operation again.

Rollback:
    return to a prior known state.

Restore:
    recreate desired/known-good state from preserved source.

Repair:
    modify damaged/inconsistent state to become valid.

Failover:
    switch to alternate implementation/resource.

Degrade:
    continue with reduced functionality.

Document these distinctions.

======================================================================
58. RETRY
======================================================================

Retry policy should eventually consider:

    maximum attempts
    delay
    backoff
    retryable errors
    idempotency
    deadline

Do not create blind infinite retry loops.

Historical self-repair semantics should evolve into bounded,
evidence-driven recovery.

======================================================================
59. CANCELLATION
======================================================================

Define cancellation as a first-class runtime concern.

Potential distinction:

    Cancel requested
    Cancellation in progress
    Cancelled

Cancellation must not necessarily mean process kill.

A unit may support cooperative cancellation.

Linux signals may be one implementation mechanism.

======================================================================
60. TIMEOUT
======================================================================

Timeout should be explicit.

A timeout is not automatically a failure cause identical to all others.

It may produce:

    TIMED_OUT outcome

and trigger:

    cancellation
    retry
    recovery
    escalation

depending on policy.

======================================================================
61. PRIORITY
======================================================================

71. BUS
======================================================================

    Unix sockets
    D-Bus

    pipes

    Unix sockets
    D-Bus

======================================================================
73. PROCESS MODEL
======================================================================

Document the principle:

    SEMANTIC MODULARITY != PROCESS MODULARITY.

A Module does not automatically require its own process.

A Unit does not automatically require its own process.

A Service may or may not involve a persistent process.

Multiple Rebuntu components may coexist in one runtime process when
appropriate.

Conversely, isolation may justify separate processes.

Process boundaries should follow:

    lifecycle
    isolation
    privilege
    resource ownership
    failure containment
    performance
    native integration

not directory boundaries.

======================================================================
74. SYSTEMD RELATIONSHIP
======================================================================

Formalize the division of responsibility.

systemd should own where appropriate:

    process/service lifecycle
    dependencies
    restart behavior
    watchdogs
    timers
    path activation
    socket activation
    cgroups
    resource limits
    credentials
    sandboxing
    journald integration

Rebuntu should own higher-level semantics such as:

    intent
    configuration
    policy
    composition
    coordination
    verification
    evidence
    reconciliation

Concise principle:

    systemd manages processes/services;
    Rebuntu manages higher-level system semantics around them.

Do not duplicate systemd.

75. KERNEL / NATIVE MECHANISM MAPPING
======================================================================

    Event

        -> systemd timer where appropriate

    Process lifecycle

    IPC

    Filesystem observation
        -> inotify/fanotify

This mapping should remain educational and practical.

Do not implement every mapping.

78. CHECK / TEST / VALIDATE / VERIFY
======================================================================

Clarify these words.

Possible initial distinctions:

    lightweight evaluation of a condition.

TEST

    deliberate procedure intended to determine behavior/correctness.

VALIDATE

    determine whether data/specification satisfies expected structure or
    constraints.

VERIFY

    determine whether a claim/postcondition/result is actually true.

These distinctions will matter heavily later.

Refine them and add them to vocabulary.

    preconditions
    postconditions

    destination exists and satisfies required equivalence

Do not implement the full contract engine yet.

Introduce Idempotency as an operation property.

    retry
    reconciliation
    recovery
    automation

Do not assume every operation is idempotent.

Introduce Reversibility as another operation characteristic.

    naturally reversible

    compensatable
    irreversible

    runtime progress checkpoint

84. ROLLBACK VS COMPENSATION
======================================================================

Distinguish:

Rollback:
    restore prior state.

Compensation:
    perform another action that semantically counteracts the effect.

Example:

    package install
        compensation may be uninstall

but this is not necessarily exact rollback because dependencies/state may
have changed.

This distinction should be documented.
