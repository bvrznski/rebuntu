# Rebuntu — Phase 0.3
# Shell Sources Architecture, Categorization & Source Library

Phase 0.3 establishes the architecture of Rebuntu's Shell Sources.

The canonical location is:

    src/system/shell/sources/

This phase must investigate, define, organize and prepare the reusable
source library used by the Rebuntu shell environment.

This is NOT permission to recreate historical Rebuntu as a giant Bash
framework.

The objective is to preserve one of the strongest ideas of historical
Rebuntu:

    reusable, composable, semantically organized shell capabilities

while redesigning it according to the architecture, vocabulary, safety
rules and Linux-native engineering principles established in Phases
0.0–0.2.

======================================================================
1. PURPOSE OF SHELL SOURCES
======================================================================

Define precisely what a Shell Source is.

Initial hypothesis:

    A Shell Source is a shell-native reusable implementation artifact
    intended to be sourced into, or otherwise made available to, the
    Rebuntu shell environment.

It may provide:

    shell functions
    shell-specific composition primitives
    shell environment integration
    command wrappers
    shell-native transformations
    shell-native convenience operations

It should NOT automatically contain:

    general Rebuntu business logic
    Python functionality rewritten in Bash
    daemon implementations
    service lifecycle management
    large state-management frameworks
    functionality better implemented through stable Python/native APIs

The shell source library exists because some functionality is naturally
expressed at the shell boundary.

It is not the implementation language of the entire project.

======================================================================
2. CANONICAL LOCATION
======================================================================

Use:

    src/system/shell/sources/

as the canonical source-library root unless repository evidence discovered
during this phase proves that this placement creates a serious
architectural contradiction.

Do not create a competing top-level:

    src/sources/

for the same purpose.

Do not confuse Shell Sources with:

    repository source code in general
    data sources
    event sources
    package sources
    external software repositories

The term "source" here has a specific Shell meaning.

Document that meaning.

======================================================================
3. HISTORICAL ARCHAEOLOGY IS IMPORTANT
======================================================================

Historical Rebuntu contained extensive source libraries organized into
semantic categories.

Search all historical Rebuntu material available to the repository.

Do not inspect only one historical snapshot.

Historical copies may represent different branches/eras and may contain
unique functionality.

Search especially for historical directories/categories resembling:

    auth
    data
    flow
    functions
    info
    math
    methods
    path
    structures
    text
    time

and later categories such as:

    administration
    configuration
    connectivity
    construction
    containment
    coordination

as well as any other categories discovered during archaeology.

Create an inventory of historical Shell Source categories.

For every historical category determine:

    what semantic purpose it expressed;
    what functions/artifacts belonged to it;
    whether the category remains useful;
    whether it overlaps another category;
    whether the name remains precise;
    whether Linux/Python/current Rebuntu supersedes it;
    whether it should be retained, renamed, split, merged or rejected.

Historical organization is evidence.

It is not automatically the new architecture.

======================================================================
4. INVENTORY BEFORE MIGRATION
======================================================================

Before moving or recreating historical functionality, build a conceptual
inventory.

For each discovered source artifact classify:

    historical location
    name
    purpose
    inputs
    outputs
    side effects
    dependencies
    privilege requirements
    safety characteristics
    composability
    implementation completeness
    apparent test status
    modern equivalent if any

Also classify implementation status:

    IDEA
    STUB
    PARTIAL
    IMPLEMENTED
    VERIFIED
    UNSAFE
    OBSOLETE
    SUPERSEDED
    UNKNOWN

Do not equate existence of a function with a working capability.

5. CATEGORY DESIGN
======================================================================

Design a coherent category taxonomy under:

    src/system/shell/sources/

Potential categories worth investigating include:

    administration/
    configuration/
    construction/
    containment/
    coordination/
    execution/
    filesystem/
    flow/
    information/
    input/
    output/
    parsing/
    paths/
    processes/
    requests/
    security/
    state/
    structures/
    text/
    time/
    verification/

These are candidates.

They are NOT a mandatory directory list.

Expand the candidate set through archaeology and architectural reasoning.

Then reduce it.

Use:

    DISCOVER
        ->
    INVENTORY
        ->
    CLASSIFY
        ->
    EXPAND
        ->
    FIND OVERLAPS
        ->
    NORMALIZE VOCABULARY
        ->
    COMPRESS
        ->
    MATERIALIZE

======================================================================
6. CATEGORY QUALITY
======================================================================

A source category should have:

    a clear semantic boundary;
    enough expected content to justify existence;
    low overlap with sibling categories;
    a stable meaning;
    useful discoverability.

Avoid categories such as:

    misc/
    other/
    helpers/
    utils/
    common/

unless their semantics are exceptionally well defined.

A category should answer:

    What kind of shell capability belongs here?

without requiring knowledge of individual filenames.

======================================================================
7. FUNCTIONAL CLASSIFICATION IS ALLOWED HERE
======================================================================

The general Rebuntu repository must not become a Linux encyclopedia.

However, shell/sources is a specialized operational library.

Therefore categories such as:

    filesystem
    processes
    paths
    text

may legitimately exist here if they improve discovery and composition.

Do not mechanically apply top-level architectural placement rules to a
specialized library taxonomy.

Distinguish:

    REBUNTU ARCHITECTURE

from:

    SHELL SOURCE LIBRARY CLASSIFICATION.

These are different classification problems.

======================================================================
8. CATEGORY AXES
======================================================================

Investigate whether candidate categories accidentally mix multiple axes.

Examples:

    text
        target/data domain

    parsing
        operation

    security
        concern

    administration
        broad role

    output
        flow position

    filesystem
        system domain

Mixing axes is not automatically forbidden in a practical source library.

But it creates ambiguity.

Test real functions against the proposed taxonomy.

If a function could reasonably belong to five categories, improve the
taxonomy or establish a primary-placement rule.

======================================================================
9. ONE CANONICAL HOME
======================================================================

Every Shell Source artifact should normally have one canonical home.

Do not duplicate implementation across categories merely because a function
belongs semantically to several domains.

Use metadata, documentation, indexing, aliases or registry mechanisms later
if multi-axis discoverability is required.

Physical duplication is not classification.

======================================================================
10. CATEGORY GRANULARITY
======================================================================

Avoid both extremes.

Too broad:

    sources/system.sh
    sources/functions.sh
    sources/helpers.sh

Too narrow:

    sources/files/copy/single/local/verified/

Prefer categories that remain useful at repository scale.

Do not predict hundreds of directories before content exists.

======================================================================
11. SHELL SOURCES SHOULD BE COMPOSABLE
======================================================================

Preserve the historical Rebuntu strength of compositional operations.

Historical style included ideas analogous to:

    some_command | clip

and high-level operations such as:

    install <something>

whose implementation could include more than a trivial package-manager
alias.

Modern Shell Sources should preserve useful composition while improving:

    typing/validation where possible
    error semantics
    quoting
    safety
    observability
    deterministic behavior
    integration with Python Rebuntu
    verification

Do not turn convenience wrappers into opaque magic.

======================================================================
12. PIPE-FRIENDLY DESIGN
======================================================================

Shell Sources should respect Unix composition where appropriate.

Functions intended for pipelines should have disciplined behavior:

    stdout
        primary data output

    stderr
        diagnostics

    exit status
        machine-readable success/failure indication

Avoid mixing decorative messages with pipeline data.

If structured output is required, define it explicitly.

Do not break standard Unix composition merely to make functions visually
friendly.

======================================================================
13. INPUT / OUTPUT CONTRACTS
======================================================================

For reusable source functions determine:

    accepted arguments
    stdin behavior
    stdout behavior
    stderr behavior
    exit status
    side effects
    environment dependencies

Where appropriate also document:

    idempotency
    reversibility
    privilege
    verification

Shell functions should not depend on undocumented global variables.

======================================================================
14. SOURCEABILITY
======================================================================

Files intended to be sourced must behave correctly when sourced.

They must not unexpectedly:

    execute operations
    mutate the filesystem
    start processes
    print output
    change directories
    alter shell options globally
    exit the caller
    install packages

merely because the file was sourced.

Loading definitions and executing behavior are separate operations.

======================================================================
15. IMPORT / EXPORT SEMANTICS
======================================================================

Historical Rebuntu explored:

    imports()
    exports()
    sources()

Re-evaluate the underlying requirement.

Determine how modern Shell Sources declare:

    dependencies
    exported functions
    internal functions
    required commands
    optional capabilities

Do not reproduce historical implementation mechanically.

A lightweight convention may be sufficient.

Avoid building a package manager in Bash.

======================================================================
16. PUBLIC VS INTERNAL FUNCTIONS
======================================================================

Establish a convention distinguishing:

    public shell API

from:

    internal implementation helpers.

Possible mechanisms include naming conventions or explicit metadata.

Do not expose every helper function globally after sourcing.

Avoid shell namespace pollution.

Consider a consistent Rebuntu prefix if appropriate.

But inspect existing repository naming conventions first.

======================================================================
17. NAMESPACE
======================================================================

Investigate shell namespace conventions.

Potential approaches:

    rebuntu_<function>
    rebuntu::<function>
    rb_<function>

or another convention already established by the repository.

Consider:

    Bash compatibility
    readability
    tab completion
    collision avoidance
    historical usability

Do not choose aesthetic cleverness over reliable shell behavior.

Document the selected convention.

======================================================================
18. SOURCE LOADING
======================================================================

Design, but do not overbuild, the future loading mechanism.

Questions:

    How are source categories discovered?

    How are individual source files loaded?

    Is loading eager or lazy?

    Can categories be loaded independently?

    How are dependencies handled?

    How are duplicate function definitions detected?

    How are load failures reported?

    How are optional external commands handled?

    Can source loading be inspected?

Do not implement a giant dynamic loader unless required.

A simple deterministic loader is preferable initially.

======================================================================
19. LOAD ORDER
======================================================================

Avoid hidden correctness dependence on alphabetical source order.

If dependencies exist, make them explicit.

Prefer:

    dependency declaration

over:

    rename file to 00_base.sh so it loads first.

If deterministic ordering is required, document why.

======================================================================
20. COLLISION DETECTION
======================================================================

Historical Rebuntu contained ideas related to determining whether a name
was already used as:

    Bash function
    executable
    command

Preserve this requirement where useful.

Before exporting a public shell function, consider collisions with:

    shell builtins
    aliases
    functions
    PATH executables
    Rebuntu exports

Do not silently shadow important native commands.

======================================================================
21. NATIVE COMMAND WRAPPERS
======================================================================

A wrapper around a Linux command must provide actual Rebuntu value.

Good reasons may include:

    stable Rebuntu semantics
    safer defaults
    structured validation
    provider abstraction
    composability
    verification
    normalization across environments

Bad reason:

    replacing `cp` with a function that simply calls `cp "$@"`.

Do not wrap Linux for the sake of wrapping Linux.

======================================================================
22. PYTHON BOUNDARY
======================================================================

Determine what belongs in Bash and what belongs in Python.

Prefer Bash for:

    shell environment manipulation
    pipelines
    redirection
    shell-native composition
    aliases/functions/completion
    lightweight invocation glue

Prefer Python for:

    complex parsing
    structured state
    persistent state
    orchestration
    non-trivial validation
    registries
    complex configuration
    concurrency
    higher-level operations
    semantic processing

A Shell Source may call stable Rebuntu Python functionality.

It should not duplicate that functionality.

======================================================================
23. NATIVE LINUX BOUNDARY
======================================================================

Before implementing shell logic, determine whether an established native
interface already provides the functionality.

Examples:

    systemctl / systemd D-Bus
    journalctl / journald APIs
    find
    stat
    readlink
    realpath
    grep
    sed
    awk
    coreutils
    procfs
    sysfs

Using standard utilities is acceptable.

But do not build brittle pipelines around human-formatted output when a
stable machine-readable/native interface exists.

======================================================================
24. SAFETY CLASSIFICATION
======================================================================

Classify source functions by side-effect/safety characteristics.

Possible conceptual classes:

    PURE
        transforms input without system mutation.

    READ_ONLY
        observes system state.

    MUTATING
        changes state.

    PRIVILEGED
        requires elevated/system privilege.

    DESTRUCTIVE
        can cause irreversible or difficult-to-reverse change.

Do not necessarily encode these exact names in filenames.

But the information should become available in documentation/metadata where
useful.

======================================================================
25. DESTRUCTIVE SOURCES
======================================================================

Historical source libraries may contain destructive helpers.

Do not migrate destructive behavior blindly.

Particularly inspect functions containing:

    rm
    rm -rf
    mv
    dd
    mkfs
    wipefs
    mount
    umount
    chmod
    chown
    sudo
    package removal
    process killing

Treat them as archaeology until individually reviewed.

Do not execute them during archaeology.

======================================================================
26. VERIFICATION
======================================================================

Historical Rebuntu's `Verifier` concept should be investigated.

Shell functions performing meaningful mutation should increasingly connect
to Rebuntu's verification semantics.

Do not assume:

    command exit status == verified result.

For simple shell-native functions exit status may be sufficient.

For system mutations, explicit postcondition verification may be required.

======================================================================
27. REQUESTS
======================================================================

Historical Rebuntu had concepts such as:

    Command
    Request
    Query

Investigate whether any shell-native request primitives belong in:

    shell/sources/requests/

or whether Request is now represented by the Python/IR boundary.

Do not preserve a category solely because it historically existed.

If the shell now creates structured Rebuntu requests through a stable CLI
or API, source functions should use that mechanism.

======================================================================
28. FLOW
======================================================================

Historical `flow` concepts are potentially important because Rebuntu grew
from Unix shell composition.

Investigate concepts such as:

    Pipe
    Channel
    Route
    Source
    Sink
    Transfer
    Link
    Stream

Determine which are useful shell primitives versus broader Rebuntu
architecture.

Do not create abstractions that merely rename `|`, `<`, `>` and file
descriptors.

Preserve abstractions only when they add useful semantics.

======================================================================
29. PATHS
======================================================================

A dedicated:

    paths/

category may be justified because safe path manipulation is foundational in
shell programming.

Potential concerns:

    normalization
    canonicalization
    existence
    type
    parent
    basename
    extension
    relative/absolute conversion
    safe joining
    symlink handling

Do not duplicate Python pathlib functionality unless shell-native use
justifies it.

Path functions must handle:

    spaces
    tabs
    newlines where realistically possible
    leading dashes
    symlinks
    missing paths

carefully.

======================================================================
30. TEXT
======================================================================

Investigate a:

    text/

category for reusable shell-native transformations.

Distinguish it from:

    parsing/
    input/
    output/
    structures/

Do not recreate awk/sed/grep as Bash functions.

Use wrappers only where Rebuntu semantics add value.

======================================================================
31. INFORMATION
======================================================================

Historical `info` concepts may map to:

    information/

or:

    inspection/
    query/
    observation/

Investigate actual historical contents before deciding.

A category should not exist merely for functions named:

    get_*
    show_*
    print_*

Determine the underlying semantic boundary.

======================================================================
32. CONFIGURATION
======================================================================

Investigate shell-native configuration sources.

Do not put the primary Rebuntu configuration system in Bash.

Shell Sources may provide:

    environment integration
    shell-facing configuration access
    conversion/export helpers

but should consume the canonical configuration system rather than create a
second one.

======================================================================
33. ADMINISTRATION
======================================================================

Be suspicious of broad:

    administration/

because almost all Rebuntu system functionality could be described as
administration.

Retain it only if archaeology demonstrates a coherent narrower meaning.

Otherwise split/reclassify its contents.

======================================================================
34. CONSTRUCTION
======================================================================

Historical Rebuntu used construction concepts extensively.

Investigate whether Shell Sources need construction primitives for:

    command construction
    shell artifact construction
    templates
    source generation
    argument construction

Do not mix repository/code generators with runtime shell primitives.

======================================================================
35. STRUCTURES
======================================================================

Historical:

    structures/

may contain shell representations of:

    arrays
    maps
    lists
    records
    stacks
    queues

Investigate actual content.

Modern Bash associative arrays may make some helpers unnecessary.

Complex structured data should usually move toward Python rather than
building an object system in Bash.

======================================================================
36. MATH
======================================================================

Historical:

    math/

must be evaluated critically.

If it merely wraps shell arithmetic or standard tools, it may not deserve a
category.

If actual reusable shell-domain numeric operations exist, preserve only
those with demonstrated use.

Do not create categories merely for symmetry.

======================================================================
37. AUTH / SECURITY
======================================================================

Historical:

    auth/

should be examined carefully.

Do not implement custom authentication in shell.

Modern security-related shell sources may include safe wrappers or
inspection helpers, but authentication/authorization should use established
Linux mechanisms.

Potential category:

    security/

must have a clearly bounded purpose.

======================================================================
38. TIME
======================================================================

A:

    time/

category may legitimately contain shell-native helpers for:

    timestamps
    durations
    elapsed time
    formatting
    deadlines

Distinguish:

    wall clock
    monotonic duration

where relevant.

Do not build scheduling itself into time helpers.

======================================================================
39. PROCESS / EXECUTION
======================================================================

Investigate whether:

    processes/
    execution/

are separate useful categories.

Potential distinction:

processes:
    observation/control of process entities.

execution:
    invoking commands/programs and managing invocation semantics.

Do not duplicate functionality owned by Rebuntu runtime/systemd.

======================================================================
40. INPUT AND OUTPUT
======================================================================

Investigate whether separate:

    input/
    output/

categories are justified.

Possible shell-native functionality:

    stdin handling
    prompts
    terminal detection
    output formatting
    clipboard integration
    pager integration

Keep presentation output separate from machine/pipeline output.

The historical `clip` composition idea is particularly relevant.

======================================================================
41. CLIPBOARD
======================================================================

Preserve the abstraction demonstrated by:

    some_command | clip

The purpose of `clip` is not merely to invoke one clipboard binary.

It expresses:

    "send this stream to the current environment's clipboard"

while hiding implementation details such as:

    Wayland provider
    X11 provider
    desktop-specific implementation

This is a good example of a shell-native Rebuntu abstraction.

Implement only if within current phase scope and safely testable.

Otherwise document it as a reference use case for the architecture.

======================================================================
42. HIGH-LEVEL SHELL OPERATIONS
======================================================================

Historical commands such as:

    install <target>

could represent much more than aliases.

Potential semantics include:

    resolve installation method
    precheck
    execute installation
    inspect logs/status
    verify package/application state
    report result

However, substantial operation logic should belong to the main Rebuntu
operation/runtime layer.

The shell function should ideally be a thin human-facing entry point.

Preserve the high-level UX without duplicating the operation engine.

======================================================================
43. FUNCTION SIZE
======================================================================

Do not recreate historical giant shell files containing hundreds of
unrelated functions.

Prefer cohesive source files.

But do not create one file per trivial three-line helper automatically.

Choose boundaries based on:

    semantic cohesion
    dependency
    independent loading
    testability
    discoverability

======================================================================
44. FILE NAMING
======================================================================

Establish consistent naming.

Prefer names describing provided semantics rather than historical numbering
or load order.

Avoid:

    functions.sh
    helpers.sh
    misc.sh
    stuff.sh

unless the file genuinely represents a specifically defined concept.

Do not encode dependency order into filenames unless absolutely necessary.

======================================================================
45. SOURCE FILE CONTRACT
======================================================================

Investigate whether sourced files should follow a lightweight standard
structure.

Historical Rebuntu experimented with:

    imports()
    exports()
    sources()
    configs()
    default()
    logging()
    init()
    main()
    quit()

Do NOT reproduce this template blindly.

A sourced library normally should not require application-style lifecycle
functions.

Extract useful concepts:

    metadata
    dependencies
    exports
    initialization where genuinely required
    cleanup where genuinely required

Keep the contract lightweight.

======================================================================
46. SHELLCHECK
======================================================================

Use ShellCheck for shell source files where available/configured.

Do not silence warnings globally.

When suppressing a warning:

    understand it;
    scope the suppression narrowly;
    document non-obvious reasoning.

Use modern safe Bash practices.

======================================================================
47. FORMATTING
======================================================================

Use the repository's configured shell formatter if one exists.

Do not introduce a formatter solely for this phase without evaluating
project-wide implications.

Keep style consistent.

======================================================================
48. TESTING SHELL SOURCES
======================================================================

Establish a testing strategy.

At minimum investigate tests for:

    sourceability
    namespace collisions
    expected exports
    argument handling
    stdin/stdout behavior
    exit codes
    paths with spaces
    missing dependencies
    invalid arguments
    safe failure
    no unexpected side effects during sourcing

For mutating functions, use isolated temporary environments where possible.

Never test destructive historical functions against the real user
filesystem.

======================================================================
49. SOURCEABILITY TEST
======================================================================

Every source file should be testable with a pattern equivalent to:

    source file

and verify that loading it:

    succeeds;
    does not unexpectedly print;
    does not unexpectedly mutate system state;
    does not exit the parent shell;
    exports only intended functions.

Build suitable automated checks if justified.

======================================================================
50. DEPENDENCY TEST
======================================================================

Where a source requires external commands, determine whether dependencies
are:

    mandatory
    optional
    provider-specific

Failure should be clear.

Do not produce:

    command not found

deep inside execution when a dependency could have been checked earlier.

======================================================================
51. INDEX / CATALOG
======================================================================

Investigate creating a machine-readable or generated index of Shell Sources.

Possible information:

    category
    source file
    exported functions
    description
    dependencies
    side-effect class
    privilege
    stability
    historical provenance

Do not manually duplicate information across many documents if it can be
generated reliably.

Do not implement a complex registry unless useful.

======================================================================
52. DISCOVERABILITY
======================================================================

A major purpose of categorization is discoverability by:

    humans
    shell tooling
    Rebuntu itself
    coding agents

It should be possible to answer:

    "Do we already have a shell primitive for X?"

without grep archaeology across thousands of lines.

Design with future capability search in mind.

======================================================================
53. DOCUMENTATION
======================================================================

Document:

    what Shell Sources are;
    what they are not;
    category taxonomy;
    public API convention;
    source-loading rules;
    dependency rules;
    Bash/Python boundary;
    safety rules;
    testing rules;
    historical migration policy.

Consider a local:

    src/system/shell/sources/README.md

and/or:

    src/system/shell/sources/AGENTS.md

if consistent with repository conventions.

A local AGENTS.md is strongly justified if future coding agents will
frequently modify this library.

======================================================================
54. LOCAL AGENTS.md
======================================================================

If created, the local instructions should state at minimum:

    search existing sources before adding functions;

    choose one canonical category;

    do not duplicate Python functionality;

    do not reimplement native Linux utilities without added semantics;

    keep sourced files side-effect-free at load time;

    preserve pipeline semantics;

    stdout is data, stderr is diagnostics;

    quote safely;

    avoid undocumented globals;

    do not shadow native commands casually;

    test sourceability;

    classify dangerous/mutating behavior;

    never migrate historical destructive code without review;

    do not turn the shell library into the Rebuntu runtime.

======================================================================
55. ARCHAEOLOGY MAPPING
======================================================================

Produce a mapping such as:

    historical category
        ->
    modern category
        ->
    disposition

Possible dispositions:

    RETAIN
    RENAME
    MERGE
    SPLIT
    MOVE_TO_PYTHON
    REPLACE_WITH_NATIVE
    DEFER
    REJECT

For important functions, record similar mappings.

This should prevent useful historical ideas from disappearing during
cleanup.

======================================================================
56. DO NOT MASS-MIGRATE
======================================================================

Do not copy thousands of historical functions into the new source tree in
this phase.

The immediate goal is:

    architecture
    taxonomy
    inventory
    migration rules
    infrastructure
    representative validation

not:

    resurrect every historical function.

Historical functionality should later be migrated selectively.

======================================================================
57. REPRESENTATIVE MIGRATION
======================================================================

If useful, select only a very small number of representative,
non-destructive historical concepts to validate the architecture.

Ideal candidates are:

    pure
    read-only
    composable
    easy to test
    clearly useful

For example a pipeline/clipboard/path/text primitive may be suitable.

Do not choose package management, storage recovery or destructive
filesystem operations merely to prove the structure works.

======================================================================
58. CATEGORY EVOLUTION
======================================================================

The category taxonomy is expected to evolve.

Do not treat Phase 0.3 categories as eternal.

When future implementation shows:

    one category is too broad;
    two categories overlap;
    a new recurring semantic family exists;

update the taxonomy deliberately.

Do not preserve bad placement for compatibility with an internal directory
layout unless compatibility actually matters.

======================================================================

Phase 0.3 is complete when:

[ ] src/system/shell/sources/ has a clearly defined purpose.

[ ] historical Shell Source trees were investigated.

[ ] historical categories were inventoried.

[ ] unique historical category ideas were not silently lost.

[ ] candidate modern categories were generated.

[ ] overlapping/redundant categories were analyzed.

[ ] final initial category taxonomy was justified.

[ ] each physical category has a documented semantic boundary.

[ ] Shell Source is distinguished from general Rebuntu implementation.

[ ] Bash/Python responsibility boundary is documented.

[ ] Shell/native-Linux responsibility boundary is documented.

[ ] public/internal shell API convention is established.

[ ] namespace/collision strategy is established.

[ ] sourceability rules are established.

[ ] loading/dependency semantics are analyzed.

[ ] pipeline stdin/stdout/stderr conventions are established.

[ ] safety classification is established or explicitly deferred.

[ ] destructive historical sources were identified and NOT blindly run.

[ ] source testing strategy exists.

[ ] representative safe sources were migrated only if useful.

[ ] no mass migration occurred.

[ ] no giant Bash runtime was introduced.

[ ] relevant architecture/vocabulary documentation was updated.

[ ] __tree__.txt was regenerated.

[ ] existing tests still pass.
