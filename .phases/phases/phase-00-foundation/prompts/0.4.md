# Rebuntu — Phase 0.4
# Scripts Architecture, Classification, Contracts & Execution Model

Phase 0.4 establishes the architecture, taxonomy, contracts and engineering
rules for scripts in Rebuntu.

The central distinction of this phase is:

    SHELL SOURCE != SCRIPT

A Shell Source is primarily a reusable artifact loaded into the shell
environment and composed with other shell functionality.

A Script is primarily a standalone executable artifact with an invocation
boundary, lifecycle, inputs, outputs, result and explicit purpose.

This phase must establish what scripts mean in Rebuntu, where different
kinds of scripts belong, how they interact with Python and native Linux
facilities, and how historical Rebuntu scripts should be classified and
selectively migrated.

Do not turn this phase into mass implementation.

======================================================================
1. INSPECT BEFORE DESIGNING
======================================================================

Before changing the repository:

1. inspect the complete current tree;
2. read all applicable AGENTS.md files;
3. read ARCHITECTURE.md, VOCABULARY.md and ONTOLOGY.md;
4. inspect Phase 0.3 Shell Sources architecture;
5. search for all current scripts;
6. search historical Rebuntu material for script-related structures;
7. inspect current bin/, systemd/, tools/, tests/ and development scripts;
8. determine whether current terminology already defines Script.

Do not design scripts in isolation from the architecture already created
in Phases 0.0–0.3.

======================================================================
2. DEFINE SCRIPT PRECISELY
======================================================================

Establish a canonical Rebuntu definition.

Initial hypothesis:

    SCRIPT

    A standalone executable artifact implementing a bounded operation,
    procedure, utility, integration, maintenance activity or other
    explicitly invokable behavior.

A script normally has:

    invocation boundary
    inputs
    outputs
    exit/result semantics
    dependencies
    side-effect characteristics
    execution environment
    lifecycle
    ownership

A script MAY be implemented in:

    Bash
    Python
    another justified scripting language

but implementation language does not define the concept.

A `.py` file is not automatically a Script.

A `.sh` file is not automatically a Script.

Classification is semantic.

======================================================================
3. SCRIPT != SHELL SOURCE
======================================================================

Make this distinction explicit in documentation.

Shell Source:

    intended primarily to be sourced;
    exposes reusable shell functionality;
    normally performs no work merely by being loaded;
    participates in interactive/compositional shell behavior.

Script:

    intended primarily to be executed;
    has an explicit entry point;
    performs bounded work;
    has process-level invocation semantics.

Examples:

    shell/sources/output/clipboard.sh

may expose:

    clip()

while:

    scripts/maintenance/rebuild_index

may execute an entire maintenance procedure.

Do not duplicate implementation merely to provide both forms.

A Shell Source may invoke a Script.

A Script may use stable Rebuntu APIs.

Shared substantial logic should normally live in the appropriate Python or
native implementation layer.

======================================================================
4. SCRIPT != BIN ENTRY POINT
======================================================================

Also distinguish:

    SCRIPT

from:

    BIN / USER-FACING COMMAND.

bin/ represents Rebuntu's executable/public command surface.

A bin entry point should normally be thin:

    parse invocation
        ->
    call stable Rebuntu functionality
        ->
    render result
        ->
    exit

Not every internal script belongs in bin/.

Not every script should become a user-facing command.

Do not duplicate the complete script implementation into bin/.

======================================================================
5. SCRIPT != OPERATION
======================================================================

A Script is an implementation/execution artifact.

An Operation is a semantic system capability.

Therefore:

    one Operation may use a Script;

    one Script may invoke several Operations;

    an Operation may have no Script at all;

    a Script may implement repository/development work rather than a
    runtime Operation.

Do not collapse operational ontology into executable-file organization.

======================================================================
6. SCRIPT != TASK != JOB
======================================================================

Preserve the structural distinctions.

SCRIPT
    executable artifact.

TASK
    bounded specification of work.

JOB
    concrete submitted/scheduled execution of work.

A Job may execute a Script.

A Script may implement a Task.

These concepts are related but not interchangeable.

Use repository vocabulary as authoritative where Phase 0.0–0.3 has refined
these definitions.

======================================================================
7. SCRIPT != SERVICE != DAEMON
======================================================================

A Script is not automatically:

    a Service
    a Daemon
    a systemd Unit

A script may serve as ExecStart for a legitimate service when appropriate.

But do not create long-running Bash loops merely because a script needs
periodic execution.

Investigate:

    systemd service
    timer
    path activation
    socket activation
    udev
    native event mechanisms

before implementing persistent script loops.

======================================================================
8. DETERMINE THE PHYSICAL SCRIPT SPACES
======================================================================

Investigate whether Rebuntu needs two distinct script spaces.

Candidate distinction:

    scripts/

        repository/development/bootstrap/maintenance scripts for working
        on Rebuntu itself

versus:

    src/scripts/

        scripts that are actual runtime-managed Rebuntu artifacts

Do NOT blindly create both.

Determine whether both concepts genuinely exist.

If they do, document the boundary rigorously.

Possible interpretation:

    /scripts
        PROJECT TOOLING

    /src/scripts
        REBUNTU RUNTIME SCRIPT ARTIFACTS

If only one is justified, use one.

Do not allow two ambiguous script junk drawers.

======================================================================
9. PROJECT TOOLING SCRIPTS
======================================================================

Top-level scripts/, if retained, may contain things such as:

    bootstrap
    development
    repository maintenance
    generation
    migration
    packaging
    validation
    release support
    environment preparation

These scripts operate primarily ON THE PROJECT.

They are not automatically part of Rebuntu runtime semantics.

Possible categories to investigate:

    scripts/
    ├── bootstrap/
    ├── development/
    ├── generation/
    ├── maintenance/
    ├── migration/
    ├── packaging/
    ├── validation/
    └── testing/

This is a candidate taxonomy only.

Derive the final taxonomy from actual repository needs.

======================================================================
10. RUNTIME SCRIPTS
======================================================================

If runtime scripts are justified, investigate a structure conceptually like:

    src/scripts/
    ├── administration/
    ├── configuration/
    ├── diagnostics/
    ├── maintenance/
    ├── recovery/
    ├── setup/
    ├── support/
    └── verification/

Again:

    candidate taxonomy != mandatory taxonomy.

Do not merely mirror every top-level Rebuntu subsystem.

A runtime script category must exist because executable artifacts genuinely
need that classification.

======================================================================
11. CLASSIFY BY PURPOSE, NOT LANGUAGE
======================================================================

Do not organize:

    scripts/bash/
    scripts/python/

as the primary semantic taxonomy.

Implementation language is metadata.

Purpose is architecture.

Prefer:

    scripts/maintenance/foo.sh
    scripts/maintenance/bar.py

over:

    scripts/bash/foo.sh
    scripts/python/bar.py

when both perform the same conceptual category of work.

Language-specific directories are justified only if the language itself
defines the integration boundary.

======================================================================
12. SCRIPT CATEGORIES
======================================================================

Explore categories based on actual script semantics.

Candidate categories include:

    administration
    bootstrap
    configuration
    construction
    diagnostics
    generation
    installation
    maintenance
    migration
    packaging
    recovery
    setup
    support
    testing
    validation
    verification

Do not create all of these merely because the names are useful.

For every category answer:

    What belongs here?

    What explicitly does not belong here?

    Why is this not another category?

======================================================================
13. AVOID GENERIC SCRIPT JUNK DRAWERS
======================================================================

Do not create:

    scripts/misc/
    scripts/helpers/
    scripts/utils/
    scripts/other/
    scripts/common/

as escape hatches.

If an artifact cannot be classified, investigate why.

It may reveal:

    incorrect taxonomy
    incorrect artifact type
    misplaced code
    missing architectural concept

Use ambiguity as architectural evidence.

======================================================================
14. HISTORICAL ARCHAEOLOGY
======================================================================

Search historical Rebuntu artifacts extensively.

Historical code contained many standalone Bash/Python files and experiments.

Do not assume every historical executable file is conceptually a Script.

Classify historical artifacts according to their actual behavior.

For each useful artifact determine:

    historical name
    historical location
    implementation language
    purpose
    execution model
    dependencies
    inputs
    outputs
    side effects
    privilege
    safety
    state ownership
    whether sourceable
    whether standalone
    whether daemon-like
    whether scheduled
    whether interactive
    whether complete
    whether tested
    modern native equivalent
    current architectural destination

======================================================================
15. HISTORICAL SCRIPT DISPOSITION
======================================================================

Use dispositions such as:

    RETAIN_AS_SCRIPT
    MOVE_TO_SHELL_SOURCE
    MOVE_TO_PYTHON_MODULE
    MOVE_TO_OPERATION
    MOVE_TO_TOOL
    MOVE_TO_EXPERIMENT
    REPLACE_WITH_NATIVE_LINUX
    SPLIT
    MERGE
    DEFER
    REJECT
    OBSOLETE
    UNSAFE

Do not preserve file type merely because historical implementation used
that file type.

A 2000-line historical Bash script may actually contain:

    reusable sources
    operations
    configuration
    state
    daemon behavior
    UI
    helpers

and therefore need conceptual decomposition rather than migration.

======================================================================
16. PRESERVE HISTORICAL INTENT
======================================================================

Historical scripts are requirements fossils.

For each significant script ask:

    What problem was Wojciech trying to solve?

    What reusable concept exists underneath the implementation?

    Does modern Linux solve part of it?

    Does current Rebuntu already contain the abstraction?

    What remains genuinely useful?

Preserve the idea.

Do not worship the implementation.

======================================================================
17. SCRIPT CONTRACT
======================================================================

Define a lightweight common script contract.

A script should have a knowable:

    identity
    purpose
    invocation
    inputs
    outputs
    dependencies
    side effects
    privilege requirement
    result
    failure behavior

For significant scripts also consider:

    idempotency
    reversibility
    timeout
    verification
    evidence
    supported environment

Do not build a gigantic metadata framework merely to describe a ten-line
script.

Use proportional engineering.

======================================================================
18. ENTRY POINT
======================================================================

Every standalone script should have an obvious execution entry point.

For Bash, prefer a clear:

    main()

pattern where useful.

For Python, prefer:

    def main() -> int:
        ...

    if __name__ == "__main__":
        raise SystemExit(main())

or the repository-established equivalent.

Importing a Python script/module should not accidentally execute its work.

Sourcing a Bash library should not accidentally execute its work.

======================================================================
19. EXIT STATUS
======================================================================

Scripts must use exit status deliberately.

At minimum:

    0
        requested script execution succeeded

    non-zero
        execution failed or could not satisfy its contract

Do not invent dozens of undocumented magic exit codes.

If differentiated codes are useful, define and document them.

Remember:

    exit 0 != verified system state

for mutating system operations.

======================================================================
20. STDOUT / STDERR
======================================================================

Establish consistent output semantics.

Prefer:

    stdout
        intended primary output/result

    stderr
        diagnostics/errors

Do not mix banners, debug logs and machine-readable output on stdout.

Scripts intended for composition should be pipeline-friendly.

If structured output is supported, define an explicit mode such as JSON
through the repository's interface conventions.

======================================================================
21. HUMAN OUTPUT != MACHINE OUTPUT
======================================================================

A script may need:

    human-readable output

and:

    machine-readable output.

Do not attempt to make one ambiguous format serve both.

Where justified, support an explicit output format.

Example conceptual interface:

    --output human
    --output json

Do not require this option for every trivial script.

======================================================================
22. ARGUMENT PARSING
======================================================================

Use appropriate argument parsing.

For Python, prefer argparse or the project's established CLI mechanism
unless another dependency is justified.

For Bash, use disciplined parsing appropriate to complexity.

Do not build a custom CLI parser repeatedly in every script.

When script interfaces become substantial, consider whether the behavior
belongs in the canonical Rebuntu CLI instead.

======================================================================
23. CONFIGURATION
======================================================================

Scripts should consume canonical Rebuntu configuration where appropriate.

Do not create independent:

    ~/.foo-script.conf

files for every script.

Do not scatter configuration semantics across environment variables,
hard-coded constants and positional arguments without reason.

Configuration ownership must be explicit.

======================================================================
24. ENVIRONMENT VARIABLES
======================================================================

Environment variables are useful for:

    process environment
    shell integration
    conventional overrides
    secrets supplied by controlled execution environments

but should not become an undocumented global configuration bus.

Document variables that affect behavior.

Never trust environment input automatically.

======================================================================
25. WORKING DIRECTORY
======================================================================

Scripts must not assume they are invoked from the repository root unless
that is explicitly part of their contract.

Resolve repository-relative resources robustly.

Do not:

    cd somewhere

and leave the caller's shell environment altered when sourced behavior is
involved.

Standalone scripts may change their own process working directory when
necessary, but the behavior should be deliberate.

======================================================================
26. PATH SAFETY
======================================================================

Scripts manipulating paths must correctly handle:

    spaces
    leading dashes
    symlinks
    relative paths
    absolute paths
    missing targets

and other relevant edge cases.

Always quote shell path variables unless deliberate word splitting is
required.

Do not parse `ls`.

Do not use unsafe temporary-file patterns.

======================================================================
27. TEMPORARY DATA
======================================================================

Use secure temporary files/directories.

Prefer:

    mktemp

or Python tempfile facilities.

Ensure cleanup where appropriate.

Do not use predictable paths such as:

    /tmp/rebuntu.tmp

for security-sensitive operations.

======================================================================
28. PRIVILEGE
======================================================================

A script should not invoke sudo internally merely because some action may
require privilege.

Determine the privilege boundary explicitly.

Prefer:

    caller-controlled elevation
    systemd service privilege
    polkit
    Linux capabilities
    narrowly privileged helper

where appropriate.

Never run an entire complex script as root when only one small operation
requires privilege without considering a better boundary.

======================================================================
29. NATIVE LINUX FIRST
======================================================================

Before implementing script infrastructure, investigate native facilities.

Do not implement scripts that manually reproduce:

    systemd lifecycle
    timers
    service restart policy
    log rotation
    filesystem watching
    device event handling
    process supervision
    cgroup management

when native Linux mechanisms provide them.

A Script should perform bounded work.

Linux should provide Linux infrastructure.

======================================================================
30. SCHEDULING
======================================================================

A script that must run periodically does not become its own scheduler.

Represent:

    Script
        = work

    Schedule
        = when work should activate

Possible providers include:

    systemd timer
    cron
    internal Rebuntu scheduler

Prefer native mechanisms where appropriate.

Do not put:

    while true; sleep 60

inside a script to emulate scheduling.

======================================================================
31. EVENT ACTIVATION
======================================================================

Similarly, scripts responding to system events should not necessarily poll.

Investigate:

    systemd path activation
    udev
    inotify/fanotify
    D-Bus
    netlink
    socket activation
    journald/event interfaces

Use event-driven native mechanisms where they fit.

======================================================================
32. DAEMONIZATION
======================================================================

Do not implement classic self-daemonization by default.

Do not casually use:

    nohup
    disown
    &
    double fork
    custom PID files

for service management.

If persistent execution is required, prefer systemd ownership.

The script remains foreground work.

The service manager manages its lifecycle.

======================================================================
33. LOCKING
======================================================================

If concurrent script execution would be unsafe, define the concurrency
contract.

Investigate:

    flock
    systemd serialization/dependencies
    Rebuntu execution locking

before inventing `.lock` state files.

Historical lock files may reveal a valid mutual-exclusion requirement, but
not necessarily the correct modern implementation.

======================================================================
34. STATE
======================================================================

Scripts should not create arbitrary state files throughout the filesystem.

Persistent state must have:

    owner
    schema/meaning
    lifecycle
    canonical location

Temporary runtime state should use appropriate runtime locations.

Do not confuse:

    lock
    state
    cache
    configuration
    checkpoint
    evidence

because all happen to be files.

======================================================================
35. LOGGING
======================================================================

Do not give every script its own ad-hoc logfile.

For system-managed execution, prefer journald where appropriate.

For interactive tools, stderr may be sufficient.

If structured logging exists in Rebuntu, integrate with it.

Do not log secrets.

======================================================================
36. SCRIPT -> REBUNTU API
======================================================================

When a script needs substantial Rebuntu behavior, prefer:

    script
        ->
    stable Rebuntu CLI/API/Python interface
        ->
    operation/runtime

rather than reimplementing behavior inside the script.

Scripts should become increasingly thin as stable Rebuntu capabilities
grow.

This is desirable.

======================================================================
37. PYTHON SCRIPT OR PYTHON MODULE?
======================================================================

Before creating a Python script ask:

    Is this actually reusable Python functionality?

If yes:

    implement the functionality in src/... or the current canonical
    Python source area

and make the script a thin entry point.

Avoid substantial reusable implementation under scripts/ merely because it
is invoked from the command line.

======================================================================
38. BASH SCRIPT OR SHELL SOURCE?
======================================================================

Before creating a Bash script ask:

    Does this need standalone execution semantics?

If no, and its purpose is reusable shell composition:

    shell/sources/

may be the correct location.

If yes:

    scripts/

may be correct.

Do not copy the same Bash function into both.

======================================================================
39. SCRIPT OR TOOL?
======================================================================

Distinguish scripts required by Rebuntu/runtime from engineering tools.

A repository analyzer, tree generator or release helper may belong under:

    tools/

rather than:

    scripts/

Define the distinction during this phase.

A useful hypothesis:

    Script
        executes a bounded established procedure.

    Tool
        provides a reusable engineering/development capability.

But test this against current repository semantics.

======================================================================
40. SCRIPT OR EXPERIMENT?
======================================================================

Experimental executable code belongs in:

    experiments/

until promoted.

Do not place speculative scripts into production script categories merely
because they run.

Promotion should require:

    useful result
    defined ownership
    safety review
    tests
    appropriate integration

======================================================================
41. SCRIPT OR INSTALLER?
======================================================================

Installation/bootstrap deserves special attention.

Determine whether:

    install
    setup
    bootstrap
    migration

are separate concepts.

Suggested distinction:

BOOTSTRAP
    prepares enough environment to start using/developing Rebuntu.

SETUP
    establishes relatively stable environment-specific requirements.

INSTALLATION
    deploys Rebuntu artifacts into their intended locations.

MIGRATION
    transforms an existing Rebuntu state/layout/schema to another.

Do not use these words interchangeably.

======================================================================
42. MAINTENANCE
======================================================================

Maintenance scripts should perform explicit bounded maintenance.

Avoid vague:

    cleanup.sh

that deletes whatever appears old.

Prefer precise purposes such as:

    regenerate_tree
    validate_units
    prune_known_cache

and require strong safety for destructive behavior.

"Maintenance" is not permission for cleanup.

======================================================================
43. GENERATION
======================================================================

Historical Rebuntu contained constructor/code-generation ideas.

Investigate a:

    generation/

category for deterministic artifact generation.

Potential outputs:

    configuration
    documentation
    manifests
    templates
    source indexes
    systemd units

Generated files should have identifiable provenance.

Do not overwrite hand-maintained files silently.

======================================================================
44. VALIDATION VS VERIFICATION
======================================================================

Preserve the distinction.

VALIDATION

    checks whether an input/artifact/configuration satisfies expected
    structure/rules before or independently of execution.

VERIFICATION

    checks whether a claimed result/postcondition is actually true.

Example:

    validate systemd unit syntax

versus:

    verify installed service is running with intended configuration.

Do not use these terms interchangeably.

======================================================================
45. DIAGNOSTICS
======================================================================

Diagnostic scripts should normally be:

    observational
    evidence-producing
    non-mutating

unless explicitly documented otherwise.

Do not silently repair the system from a diagnostic script.

Preserve:

    OBSERVATION != RECOVERY.

======================================================================
46. RECOVERY
======================================================================

Recovery scripts deserve strict safety rules.

Before mutation:

    identify target
    collect current state
    validate assumptions
    create checkpoint/backup where appropriate
    plan action

After mutation:

    verify result
    report evidence

Do not create "repair everything" scripts.

======================================================================
47. DRY RUN
======================================================================

For scripts with significant/destructive mutation, investigate:

    --dry-run

or equivalent planning support.

Dry-run must not merely print:

    "would execute..."

after already performing half the side effects.

Planning and execution should be structurally separated where practical.

Do not force dry-run onto pure/read-only scripts.

======================================================================
48. CONFIRMATION
======================================================================

Interactive confirmation may be appropriate for destructive manual
operations.

But do not use interactive prompts as the primary safety mechanism for
automation.

Automated execution requires explicit policy/authorization.

A `yes | script` scenario must not accidentally bypass carefully intended
safety semantics.

======================================================================
49. IDEMPOTENCY
======================================================================

Determine whether each mutating script is:

    IDEMPOTENT
    CONDITIONALLY IDEMPOTENT
    NON-IDEMPOTENT

where this matters.

Do not blindly retry non-idempotent scripts.

Document retry behavior for automation-facing scripts.

======================================================================
50. REVERSIBILITY
======================================================================

Determine whether script actions are:

    REVERSIBLE
    COMPENSATABLE
    IRREVERSIBLE

where relevant.

Do not advertise:

    --rollback

unless previous state can genuinely be restored.

A compensating action is not necessarily rollback.

======================================================================
51. SCRIPT MANIFEST / METADATA
======================================================================

Investigate whether a lightweight machine-readable script catalog is useful.

Potential metadata:

    name
    purpose
    category
    language
    invocation
    dependencies
    side_effects
    privilege
    idempotency
    reversibility
    automation_safe
    stability

Do not build an elaborate manifest framework before real consumers exist.

If metadata can be derived reliably from a simple convention, prefer that.

======================================================================
52. DISCOVERABILITY
======================================================================

It should eventually be easy for a human or coding agent to answer:

    What scripts exist?

    What does this script do?

    Is it safe?

    Does it mutate the system?

    Does it require root?

    Can it be automated?

    Is there already a script for X?

Design the organization with search/discovery in mind.

======================================================================
53. NAMING
======================================================================

Script names should describe the bounded action or purpose.

Prefer:

    regenerate_tree
    validate_repository
    migrate_configuration

over:

    manager
    helper
    do_stuff
    utility

Use repository naming conventions for separators/extensions.

Do not encode historical sequence numbers into production names.

======================================================================
54. EXTENSIONS
======================================================================

Decide whether executable scripts retain language extensions.

For internal/project scripts, extensions may improve clarity:

    foo.sh
    foo.py

For public installed commands, extensionless entry points may be more
appropriate.

Do not remove extensions merely for aesthetics.

======================================================================
55. SHEBANGS
======================================================================

Use appropriate portable shebangs according to deployment assumptions.

Examples may include:

    #!/usr/bin/env bash

or an explicit interpreter path where environment control requires it.

For Python, prefer installed package entry points when that is the proper
deployment model.

Do not assume arbitrary virtualenv paths.

======================================================================
56. BASH MODE
======================================================================

For Bash scripts, establish an error-handling policy deliberately.

Do not blindly paste:

    set -euo pipefail

into every historical script without understanding consequences.

Use strict modes where appropriate and code correctly for their semantics.

Understand pipelines, subshells, conditionals and expected non-zero
commands.

======================================================================
57. SIGNAL HANDLING
======================================================================

Longer-running scripts should consider relevant signals.

Where cleanup is necessary, use disciplined traps.

Do not trap every signal automatically.

Do not swallow termination requests.

Systemd-managed scripts should terminate predictably.

======================================================================
58. CLEANUP
======================================================================

Cleanup handlers should only remove resources owned by the current
execution.

Never use broad wildcard deletion in cleanup.

Track temporary resources explicitly.

Cleanup failure should be observable where important.

======================================================================
59. TIMEOUTS
======================================================================

Potentially blocking external operations should have a timeout strategy
where necessary.

Do not assume every command eventually returns.

Use native/process-level timeout mechanisms appropriately.

Distinguish timeout from failure.

======================================================================
60. EXTERNAL COMMAND DEPENDENCIES
======================================================================

Scripts should know which external commands they require.

Check important dependencies early where useful.

Do not fail halfway through destructive work because a predictable command
dependency was missing.

Prefer feature/capability detection over brittle version assumptions where
appropriate.

======================================================================
61. PORTABILITY
======================================================================

Rebuntu is Linux-first.

Do not weaken good Linux integration for hypothetical cross-platform
portability.

But distinguish:

    Linux-generic
    distribution-specific
    Ubuntu-specific
    desktop-specific

scripts where relevant.

Use providers/adapters rather than scattered distro conditionals when the
difference becomes architectural.

======================================================================
62. TESTING
======================================================================

Establish script testing infrastructure.

Test where relevant:

    invocation
    help
    argument parsing
    exit status
    stdout/stderr separation
    invalid inputs
    dependency failure
    path edge cases
    idempotency
    dry-run
    cleanup
    signal handling
    timeout
    safe failure

Use isolated temporary directories/environments.

Do not test destructive scripts against the user's real system.

======================================================================
63. SHELLCHECK
======================================================================

Run ShellCheck on Bash scripts where available.

Understand warnings.

Do not globally suppress diagnostics to obtain a green result.

Use narrow justified suppression where necessary.

======================================================================
64. PYTHON QUALITY
======================================================================

Python scripts must follow project linting, formatting, typing and testing
rules.

Do not create a lower-quality Python coding standard merely because a file
lives under scripts/.

Reusable Python logic should migrate into the canonical Python source tree.

======================================================================
65. SCRIPT TESTABILITY
======================================================================

Avoid scripts whose entire implementation exists as top-level statements.

Separate:

    parsing
    planning
    execution
    verification
    rendering

where complexity justifies it.

This makes behavior testable without spawning the complete script for every
test.

Do not over-engineer trivial scripts.

======================================================================
66. SCRIPT COMPOSITION
======================================================================

Scripts may compose other capabilities.

Prefer:

    stable interfaces
    explicit inputs/outputs
    structured results where needed

over scraping human output from another Rebuntu script.

If two scripts need substantial shared behavior, extract the common
capability rather than creating a fragile script-to-script dependency
network.

======================================================================
67. SCRIPT CHAINS
======================================================================

Do not create opaque chains such as:

    A.sh -> B.sh -> C.sh -> D.sh

without explicit reason.

At some complexity threshold this is a Workflow, not merely chained scripts.

Recognize when orchestration belongs in the workflow/runtime layer.

======================================================================
68. WORKFLOW BOUNDARY
======================================================================

A useful heuristic:

    SCRIPT
        bounded executable procedure

    WORKFLOW
        explicit composition and progression across multiple pieces of work

If a script begins implementing:

    phases
    stages
    checkpoints
    branching
    retries
    rollback
    parallel threads

investigate whether it should become a Workflow using stable operations.

Do not build workflow engines inside Bash scripts.

======================================================================
69. AUTOMATION BOUNDARY
======================================================================

A Script describes executable work.

Automation determines when/why work should happen.

Therefore avoid embedding:

    event loops
    scheduling loops
    continuous monitoring
    trigger engines

inside scripts unless the artifact is explicitly and correctly classified
as something else.

======================================================================
70. SYSTEMD INTEGRATION
======================================================================

If a script is invoked by systemd:

    keep it foreground;
    use meaningful exit status;
    write appropriate diagnostics;
    avoid self-daemonization;
    understand stop/timeout semantics;
    document required privilege;
    document environment assumptions.

The unit owns lifecycle.

The script owns its bounded work.

======================================================================
71. SCRIPT INSTALLATION
======================================================================

Determine which scripts are:

    repository-only
    development-only
    installed internal
    installed public

Do not install every repository script onto the host.

Installation policy should be explicit.

Public executable commands should normally be surfaced deliberately through
bin/package entry points.

======================================================================
72. VERSION CONTROL
======================================================================

Generated runtime state does not belong in source-controlled scripts/.

Do not commit:

    logs
    temporary output
