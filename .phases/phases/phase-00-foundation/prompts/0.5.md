# Rebuntu — Phase 0.5
# Daemons Architecture, Lifecycle, Supervision & Native Linux Integration

Phase 0.5 establishes the architecture, taxonomy, lifecycle model,
engineering contracts and Linux-native execution model for Daemons in
Rebuntu.

This phase must define precisely what a Daemon is, what it is not, when
Rebuntu genuinely needs one, how daemons are supervised, how they expose
state and health, and how historical daemon/automaton experiments should
map onto modern Linux facilities.

The central principle is:

    DAEMON = RUNTIME / PROCESS CHARACTERISTIC

not:

    DAEMON = EVERY BACKGROUND FEATURE

and not:

    DAEMON = SERVICE

and not:

    DAEMON = AUTOMATION.

Rebuntu must not recreate process supervision already provided by Linux
and systemd.

======================================================================
1. INSPECT BEFORE DESIGNING
======================================================================

Before modifying the repository:

1. inspect the complete current tree;
2. read all applicable AGENTS.md files;
3. read ARCHITECTURE.md, VOCABULARY.md and ONTOLOGY.md;
4. inspect the structural taxonomy established in previous phases;
5. inspect shell/sources architecture;
6. inspect scripts architecture;
7. inspect existing service/unit/runtime abstractions;
8. search for daemon-related implementation;
9. search for:
       daemon
       service
       worker
       monitor
       watcher
       loop
       background
       supervisor
       process
       lifecycle
       watchdog
       automaton
10. inspect relevant tests;
11. inspect historical Rebuntu daemon/automaton implementations.

Do not create a parallel daemon architecture if equivalent lifecycle
infrastructure already exists.

======================================================================
2. DEFINE DAEMON PRECISELY
======================================================================

Establish a canonical Rebuntu definition.

Initial hypothesis:

    DAEMON

    A long-lived background process that continuously or repeatedly
    provides functionality, observes events, processes work, maintains
    runtime state, or serves requests.

The defining property is primarily its runtime/process behavior:

    long-lived
    background/non-interactive
    independently supervised
    explicit lifecycle

A daemon is not defined merely by:

    having a loop;
    running from systemd;
    being called a service;
    doing automation;
    periodically executing;
    monitoring something.

Document the final definition.

======================================================================
3. DAEMON != SERVICE
======================================================================

This distinction is mandatory.

SERVICE

    managed functionality exposed or maintained by the system.

DAEMON

    long-lived process that may implement some or all of that
    functionality.

Therefore:

    a Service may be daemon-backed;

    a Service may be oneshot;

    a Service may be socket-activated;

    a Service may consist of multiple processes;

    a Daemon may participate in implementing a Service;

    not every Service requires a Daemon.

Do not use the terms interchangeably.

======================================================================
4. DAEMON != AUTOMATION
======================================================================

Also mandatory:

    AUTOMATION

describes logic deciding:

    WHEN
    WHY
    UNDER WHAT CONDITION

work should occur.

A Daemon describes:

    HOW A PROCESS REMAINS AVAILABLE/RUNNING

when persistent process execution is actually required.

An Automation may use:

    systemd timer
    path activation
    udev
    D-Bus
    event subscription
    one-shot service
    daemon

depending on its needs.

Do not create a daemon merely because something is automated.

======================================================================
5. DAEMON != SCRIPT
======================================================================

A Script is a standalone executable artifact.

A Daemon is a runtime execution mode/process role.

A script MAY implement a daemon process.

But:

    Script != Daemon

and long-lived behavior should not automatically be implemented as Bash.

Prefer Python or justified native code for substantial Rebuntu daemons.

======================================================================
6. DAEMON != UNIT
======================================================================

A systemd Unit is a systemd configuration object.

A Rebuntu Unit, if separately defined by the repository, follows the
repository's own structural definition.

Neither concept is automatically synonymous with Daemon.

A daemon may be launched by:

    foo.service

but:

    foo.service != daemon.

Keep configuration, semantic entity and runtime process distinct.

======================================================================
7. DAEMON != PROCESS
======================================================================

Every daemon is implemented through one or more processes.

Not every process is a daemon.

A short-lived command is a process.

A one-shot worker is a process.

An interactive shell is a process.

Daemon describes a particular lifecycle/runtime role.

======================================================================
8. DAEMON != WORKER
======================================================================

Investigate the distinction between:

    Daemon
    Worker

A useful hypothesis:

DAEMON

    persistent runtime process responsible for maintaining availability
    of functionality.

WORKER

    execution participant responsible for processing bounded work.

A daemon may host workers.

Workers may be ephemeral.

Workers may be separate processes.

Do not introduce Worker as a formal architecture category unless actual
requirements justify it.

======================================================================
9. DAEMON != MONITOR
======================================================================

Monitor describes responsibility.

Daemon describes execution form.

A Monitor may be implemented as:

    daemon
    timer-triggered job
    event subscription
    eBPF program + consumer
    systemd activation
    direct query

Do not create one daemon per monitoring concern.

Remember:

    STRUCTURE != ROLE != DOMAIN.

======================================================================
10. DAEMON != SCHEDULER
======================================================================

Do not implement:

    while true:
        sleep(...)
        do_work()

merely to execute periodic work.

Investigate:

    systemd timers
    scheduler infrastructure
    event activation

first.

A daemon is justified when persistent process state, low-latency event
handling, serving, continuous stream processing or similar requirements
actually require persistence.

======================================================================
11. WHEN IS A DAEMON JUSTIFIED?
======================================================================

Explicitly define daemon admission criteria.

Potential valid reasons include:

    persistent IPC endpoint
    persistent in-memory state
    continuous event stream consumption
    low-latency event response
    expensive initialization worth retaining
    persistent connection/session
    continuous aggregation
    queue consumption
    long-running coordination
    long-lived model/runtime
    kernel/event subscription requiring persistent consumer
    resource ownership requiring persistent process

Potential INVALID reasons include:

    "needs to run every minute"
    "needs to check a file occasionally"
    "it runs in the background"
    "historical Rebuntu called it a daemon"
    "a while loop is easy"

Document this distinction.

======================================================================
12. DAEMON ADMISSION TEST
======================================================================

Before creating a daemon, ask:

    Can this be a direct operation?

    Can this be a Script?

    Can this be a Task/Job?

    Can this be a systemd oneshot service?

    Can this be timer activated?

    Can this be path activated?

    Can this be socket activated?

    Can udev activate it?

    Can D-Bus activation handle it?

    Can an existing daemon provide the functionality?

Only after these alternatives are evaluated should a new persistent
daemon be introduced.

======================================================================
13. SYSTEMD IS THE DEFAULT SUPERVISOR
======================================================================

Rebuntu must not build its own generic process supervisor.

On the target Linux environment, systemd should normally own:

    daemon startup
    shutdown
    restart
    dependency ordering
    process tracking
    cgroups
    resource controls
    stdout/stderr capture
    journald integration
    watchdog integration
    startup timeout
    shutdown timeout
    credentials
    sandboxing
    service activation

Rebuntu may provide higher-level semantics around those facilities.

Do not duplicate them.

======================================================================
14. FOREGROUND PROCESS MODEL
======================================================================

Rebuntu daemons managed by systemd should normally run in the foreground.

Do NOT self-daemonize using:

    fork + exit parent
    double fork
    setsid
    nohup
    disown
    background '&'

unless a specific integration absolutely requires it.

Preferred model:

    systemd
        owns process lifecycle

    Rebuntu daemon
        runs foreground event loop

This improves:

    supervision
    logging
    shutdown
    cgroup tracking
    failure detection
    resource control.

======================================================================
15. NO PID FILES BY DEFAULT
======================================================================

Do not create custom PID files for systemd-managed daemons.

systemd already tracks processes.

Historical `.pid` or equivalent files should be treated as evidence that
process identity was once needed, not as implementation requirements.

Use PID files only when integrating with software whose protocol genuinely
requires them.

======================================================================
16. NO CUSTOM DAEMONIZER
======================================================================

Historical Rebuntu experimented with daemonizers.

Investigate them archaeologically.

Do not resurrect a generic:

    daemonize(command)

framework if systemd already solves the problem.

Extract useful requirements such as:

    lifecycle
    state
    restart
    health
    communication
    dependency
    activation

and map them to modern facilities.

======================================================================
17. HISTORICAL AUTOMATONS
======================================================================

Historical Rebuntu contained "automatons" implemented partly as
semi-daemons with:

    loops
    pipes
    state files
    marker files
    activation flags
    stop files
    hold files
    lock files
    channels
    triggers

Study these carefully.

For each historical automaton determine:

    Was persistence actually necessary?

    Was it polling because better event mechanisms were unknown?

    Was it really a Service?

    Was it really an Automation?

    Was it a Schedule?

    Was it a Workflow?

    Was it a Worker?

    Was it a Script?

    Was it genuinely a Daemon?

Do not map:

    historical automaton -> modern daemon

automatically.

======================================================================
18. HISTORICAL STATE FILES
======================================================================

Historical mechanisms such as:

    .lock
    .stop
    .hold
    .on
    .en

express requirements.

Analyze the semantic requirement behind each.

Possible modern mappings:

    .lock
        -> flock / execution lock / systemd serialization

    .stop
        -> service lifecycle / policy state

    .hold
        -> pause/suspend semantic state

    .on
        -> desired enabled state

    .en
        -> configuration/policy

Do not preserve accidental filesystem protocols when stronger native
mechanisms exist.

======================================================================
19. HISTORICAL PIPES
======================================================================

Historical dedicated pipes may express legitimate IPC requirements.

Investigate whether modern equivalents should use:

    Unix domain socket
    D-Bus
    pipe/FIFO
    systemd socket activation
    eventfd
    direct process communication

Do not reject FIFOs merely because they are old.

Use them when FIFO semantics are genuinely appropriate.

But do not make filesystem pipes the universal Rebuntu bus.

======================================================================
20. DAEMON CATEGORIES
======================================================================

Investigate whether daemon categorization is useful.

Possible runtime roles include:

    server
    watcher
    consumer
    coordinator
    aggregator
    bridge
    worker-host
    model-host
    event-processor

These are ROLE classifications.

They do not automatically justify physical directories.

Avoid creating:

    daemons/watchers/
    daemons/coordinators/
    daemons/managers/

without evidence.

======================================================================
21. PHYSICAL LOCATION
======================================================================

Determine the canonical physical location of daemon implementations.

Do not assume:

    src/daemons/

is automatically correct.

Possible architectures include:

A)

    daemon implementation lives with the Module/Service it implements.

B)

    dedicated daemon runtime area contains reusable daemon infrastructure,
    while concrete daemons live with their owning modules.

C)

    dedicated daemons/ area contains concrete daemon applications.

Evaluate the existing structural taxonomy before deciding.

Prefer ownership locality unless a dedicated category has genuine semantic
value.

======================================================================
22. DAEMON INFRASTRUCTURE VS CONCRETE DAEMONS
======================================================================

This distinction is important.

Reusable daemon infrastructure might include:

    lifecycle hooks
    shutdown coordination
    readiness
    health protocol
    watchdog integration
    signal handling
    common service bootstrap

Concrete daemon functionality should remain owned by its subsystem/module.

Do not create a central directory that accumulates unrelated background
processes.

======================================================================
23. ONE DAEMON PER CONCERN?
======================================================================

No.

Do not create one daemon for every semantic responsibility.

Process boundaries should follow:

    failure isolation
    privilege separation
    lifecycle independence
    resource ownership
    performance
    persistent state ownership
    security
    deployment
    activation requirements

not directory taxonomy.

Several responsibilities may correctly live in one process.

One conceptual subsystem may correctly use multiple processes.

Reason explicitly.

======================================================================
24. PROCESS OWNERSHIP
======================================================================

Every daemon must have an architectural owner.

It should be possible to answer:

    Which Module/System owns this daemon?

    What functionality does it implement?

    Who starts it?

    Who stops it?

    What resources does it own?

    What state does it own?

    What interfaces does it expose?

    What happens if it dies?

Avoid orphan background processes.

======================================================================
25. LIFECYCLE MODEL
======================================================================

Define a minimal daemon lifecycle.

Candidate lifecycle:

    CREATED
        ->
    STARTING
        ->
    RUNNING
        ->
    STOPPING
        ->
    STOPPED

with:

    FAILED

where appropriate.

Do not create an enormous lifecycle state machine prematurely.

Lifecycle should describe process/runtime progression only.

======================================================================
26. LIFECYCLE != HEALTH
======================================================================

Keep separate:

    lifecycle
    health

Example:

    lifecycle = RUNNING
    health    = DEGRADED

or:

    lifecycle = RUNNING
    health    = UNHEALTHY

Do not encode:

    RUNNING_DEGRADED

as a lifecycle state.

======================================================================
27. LIFECYCLE != READINESS
======================================================================

Also distinguish:

    alive
    ready
    healthy

A daemon may be:

    process alive = yes
    readiness     = no
    health        = healthy

during initialization.

Define these concepts explicitly.

======================================================================
28. STARTED != READY
======================================================================

A successfully spawned process does not prove functionality is available.

Where relevant, provide readiness semantics.

Potential mechanisms:

    sd_notify READY=1
    successful IPC health endpoint
    explicit initialization completion
    service-specific readiness probe

Do not add readiness machinery to trivial daemons that do not need it.

======================================================================
29. HEALTH
======================================================================

Health should represent whether the daemon can correctly perform its
responsibility.

Potential states:

    UNKNOWN
    HEALTHY
    DEGRADED
    UNHEALTHY

Keep the model small initially.

Do not infer health solely from:

    process exists.

======================================================================
30. HEARTBEAT != HEALTH
======================================================================

A heartbeat proves some code is executing.

It does not necessarily prove useful functionality.

Distinguish:

    liveness
    readiness
    health
    functional verification

where necessary.

======================================================================
31. SYSTEMD WATCHDOG
======================================================================

For daemons where failure/hang detection matters, investigate:

    WatchdogSec=
    sd_notify WATCHDOG=1

Use systemd watchdog support instead of implementing an independent
supervisor heartbeat daemon.

Do not enable watchdog mechanically for every process.

======================================================================
32. STARTUP
======================================================================

Daemon startup should have explicit phases where complexity justifies it:

    load configuration
    validate configuration
    initialize dependencies
    acquire resources
    establish IPC
    subscribe to events
    establish readiness
    enter main loop

If startup fails:

    fail visibly.

Do not remain alive in a broken pseudo-running state merely to avoid
systemd restart.

======================================================================
33. SHUTDOWN
======================================================================

Daemon shutdown should be deliberate.

Typical sequence:

    receive termination
        ->
    stop accepting new work
        ->
    cancel/finish active work according to policy
        ->
    flush required state
        ->
    release owned resources
        ->
    close IPC
        ->
    exit

Do not make shutdown indefinitely block.

Respect systemd timeout semantics.

======================================================================
34. SIGNALS
======================================================================

Define signal behavior only where useful.

Normally:

    SIGTERM
        graceful shutdown

Potentially:

    SIGHUP
        configuration reload

but do not assume historical Unix conventions are automatically required.

Do not overload signals with complex application protocols.

Use IPC for structured requests.

======================================================================
35. SIGNAL HANDLING IN PYTHON
======================================================================

For Python daemons, integrate signals cleanly with the selected runtime
model.

If asyncio is used, coordinate termination through the event loop rather
than scattered global flags.

Avoid unsafe signal-handler work.

Keep handlers minimal.

======================================================================
36. ASYNCIO
======================================================================

Python asyncio is a candidate for I/O-heavy daemons.

Use it when concurrency model benefits from:

    sockets
    IPC
    multiple event streams
    timers
    asynchronous subprocesses

Do not use asyncio merely because the component is called a daemon.

A simple blocking event loop may be more appropriate for simple cases.

======================================================================
37. THREADS
======================================================================

Do not introduce threads casually.

Use threads when required by:

    blocking APIs
    libraries
    CPU/native integration
    appropriate concurrency model

Document ownership and shutdown behavior.

Do not confuse:

    OS thread
    Python thread
    asyncio Task
    workflow Thread.

======================================================================
38. MULTIPROCESS
======================================================================

Do not use multiprocessing as generic isolation.

Use separate processes when justified by:

    fault isolation
    privilege separation
    resource ownership
    CPU parallelism
    incompatible runtimes
    independent lifecycle

systemd may manage separate services/processes more cleanly than a parent
daemon spawning everything itself.

======================================================================
39. CHILD PROCESSES
======================================================================

If a daemon launches child processes:

    define ownership;
    define timeout;
    define cancellation;
    define stdout/stderr handling;
    define failure semantics;
    avoid orphaning.

Prefer systemd-managed peer services where independent lifecycle is more
appropriate.

======================================================================
40. STATE OWNERSHIP
======================================================================

Every daemon must explicitly distinguish:

    authoritative native state
    daemon-owned runtime state
    persisted state
    cache
    derived state
    desired state

Do not mirror systemd/kernel truth into mutable daemon state unnecessarily.

Query or subscribe to authoritative state.

======================================================================
41. PERSISTENCE
======================================================================

A daemon should not persist state merely because it has memory.

Persist only what must survive restart.

Examples might include:

    checkpoints
    durable queue position
    learned configuration
    pending durable work

Do not persist transient caches without reason.

Define persistence ownership and schema.

======================================================================
42. RESTART SEMANTICS
======================================================================

For each daemon determine:

    Is restart safe?

    What state is lost?

    What work may be repeated?

    Can duplicate work occur?

    How is interrupted work reconciled?

    Is initialization idempotent?

Do not configure:

    Restart=always

blindly.

Choose restart policy based on failure semantics.

======================================================================
43. CRASH RECOVERY
======================================================================

Distinguish:

    daemon restart

from:

    system recovery.

Restarting the process may restore availability.

It may not repair external state.

Do not assume:

    daemon restarted == problem solved.

Verify post-restart functionality where necessary.

======================================================================
44. CRASH LOOP
======================================================================

Avoid infinite high-frequency restart loops.

Use systemd controls such as appropriate:

    RestartSec=
    StartLimitIntervalSec=
    StartLimitBurst=

or current equivalents.

Surface repeated failure as diagnostic evidence.

Do not hide crashes through aggressive restarting.

======================================================================
45. FAILURE CLASSIFICATION
======================================================================

Where useful distinguish:

    configuration failure
    dependency unavailable
    transient external failure
    internal software error
    permission failure
    resource exhaustion
    protocol failure
    corrupted state

Different failure classes may justify different recovery behavior.

Do not retry every exception.

======================================================================
46. RESOURCE OWNERSHIP
======================================================================

Daemons often own long-lived resources.

Explicitly identify:

    sockets
    file descriptors
    connections
    subscriptions
    model runtimes
    devices
    locks
    queues
    memory caches

Ensure acquisition and release are deterministic.

Avoid leaking resources across reload/reconnect cycles.

======================================================================
47. RESOURCE LIMITS
======================================================================

Use systemd/cgroups where appropriate for:

    CPU
    memory
    process count
    file descriptors
    I/O
    device access

Do not build an internal generic resource limiter when the kernel already
provides one.

Resource policy belongs near service deployment/configuration, not buried
inside arbitrary application code.

======================================================================
48. CPU/GPU OWNERSHIP
======================================================================

Do not assume accelerator access.

A daemon using significant compute resources must declare its resource
requirements explicitly.

CPU-only daemons must not opportunistically initialize CUDA.

GPU ownership must be explicit if ever introduced.

Resource isolation should use established Linux mechanisms where practical.

======================================================================
49. IPC
======================================================================

A daemon exposing functionality requires an explicit communication model.

Potential mechanisms:

    Unix domain sockets
    D-Bus
    systemd socket activation
    pipes/FIFOs
    direct local sockets
    shared memory
    native protocol-specific interfaces

Choose based on requirements.

Do not create one universal Rebuntu daemon protocol prematurely.

======================================================================
50. UNIX DOMAIN SOCKETS
======================================================================

Unix domain sockets are a strong default candidate for local structured
IPC where:

    request/response semantics
    local-only communication
    filesystem permissions
    stream/datagram semantics

fit the requirement.

But investigate D-Bus/systemd/native mechanisms first where those are more
appropriate.

======================================================================
51. SOCKET OWNERSHIP
======================================================================

If a daemon owns a Unix socket:

    define path
    permissions
    ownership
    cleanup
    stale-socket behavior
    protocol
    versioning
    concurrency behavior

Prefer appropriate runtime directories such as:

    /run/...

for system runtime sockets where deployment requires it.

Do not scatter sockets through arbitrary project directories.

======================================================================
52. SYSTEMD SOCKET ACTIVATION
======================================================================

Investigate socket activation for request-driven services.

Benefits may include:

    daemon starts only when needed
    socket exists before daemon
    restart without losing listener
    reduced idle resource use

Do not keep a daemon permanently alive merely because it exposes a socket
if socket activation provides a cleaner model.

======================================================================
53. D-BUS
======================================================================

Use D-Bus where the semantics fit:

    system integration
    structured methods/signals
    desktop/service integration
    established Linux APIs

Do not introduce D-Bus solely to appear Linux-native.

Choose it when it genuinely improves integration.

======================================================================
54. EVENT SOURCES
======================================================================

For event-driven daemons investigate native sources such as:

    inotify
    fanotify
    netlink
    udev
    D-Bus signals
    journald
    systemd
    sockets
    eBPF/perf where justified

Avoid polling when reliable native event mechanisms exist.

======================================================================
55. POLLING
======================================================================

Polling is not forbidden.

Use it when:

    no suitable event source exists;
    state must periodically be reconciled anyway;
    event loss is possible and periodic verification is needed;
    simplicity outweighs negligible cost.

If polling is used define:

    interval
    jitter where relevant
    cost
    timeout
    failure behavior

Do not poll at high frequency without evidence.

======================================================================
56. EVENT LOSS
======================================================================

Event-driven architecture does not automatically guarantee correctness.

Consider:

    daemon downtime
    buffer overflow
    missed events
    reconnect
    startup race

where relevant.

For important state, combine:

    events for responsiveness

with:

    authoritative state reconciliation

for correctness.

======================================================================
57. BACKPRESSURE
======================================================================

For high-rate event processing, define overload behavior.

Potential strategies:

    bounded queues
    coalescing
    deduplication
    batching
    dropping low-value events
    prioritization
    producer backpressure

Do not allow unbounded in-memory queues.

======================================================================
58. QUEUES
======================================================================

Do not create a generic queue subsystem unless needed.

For in-process work:

    asyncio.Queue

or equivalent may suffice.

For durable cross-process work:

    investigate actual durability requirements before choosing technology.

Do not use files as an accidental queue protocol.

======================================================================
59. TIMERS INSIDE DAEMONS
======================================================================

A persistent daemon may legitimately use internal timers for:

    timeout
    housekeeping
    cache expiration
    connection maintenance
    periodic reconciliation

This differs from creating an entire daemon merely to perform scheduled
work.

Make that distinction explicit.

======================================================================
60. CONFIGURATION
======================================================================

Daemon configuration should use canonical Rebuntu configuration semantics.

Do not create bespoke configuration loaders for every daemon.

Configuration should be:

    validated
    explicit
    safe by default
    observable

Invalid critical configuration should normally fail startup clearly.

======================================================================
61. CONFIGURATION RELOAD
======================================================================

Do not implement hot reload automatically.

First determine:

    Is reload actually needed?

    Which fields are reloadable?

    What happens to active work?

    What happens if new configuration is invalid?

A restart may be simpler and safer.

If reload exists, make its semantics explicit.

======================================================================
62. DESIRED STATE
======================================================================

Distinguish:

    service enabled
    daemon process running
    daemon ready
    daemon healthy
    functionality desired

These are not the same state.

Rebuntu higher-level control may decide desired functionality.

systemd may manage actual process lifecycle.

Do not collapse the layers.

======================================================================
63. LOGGING
======================================================================

System-managed daemons should normally log through stdout/stderr into
journald or use appropriate native journal integration.

Do not create private rotating log infrastructure by default.

Logs should contain useful structured context where practical:

    daemon/component
    event
    request/job identifier
    severity
    relevant state

Do not log secrets.

======================================================================
64. LOG LEVELS
======================================================================

Use log levels consistently.

Potential:

    DEBUG
    INFO
    WARNING
    ERROR
    CRITICAL

Do not log routine healthy loop iterations at INFO.

Avoid journal flooding.

High-frequency telemetry may need aggregation rather than logging.

======================================================================
65. OBSERVABILITY
======================================================================

A daemon should make important runtime behavior inspectable.

Depending on complexity:

    lifecycle
    readiness
    health
    errors
    queue depth
    active work
    resource consumption
    restart count
    dependency status

may be useful.

Do not implement a metrics platform in Phase 0.5.

Establish extensible conventions.

======================================================================
66. STATUS
======================================================================

Define how Rebuntu can obtain daemon status.

Do not rely solely on:

    ps | grep.

Potential sources:

    systemd state
    IPC health/status
    daemon-owned diagnostics
    cgroup/process state

The authoritative source depends on what is being asked.

======================================================================
67. SERVICE STATUS != DAEMON STATUS
======================================================================

Example:

    systemd service state:
        active

    daemon readiness:
        false

    daemon health:
        degraded

These observations can coexist.

Preserve them rather than compressing them into one boolean.

======================================================================
68. SECURITY
======================================================================

Daemon security deserves special attention because daemons are persistent
attack surfaces.

Consider:

    privilege
    IPC permissions
    input validation
    credentials
    filesystem access
    device access
    network exposure
    resource exhaustion
    dependency trust
    unsafe deserialization
    command injection
    path traversal
    symlink attacks

Use least privilege.

======================================================================
69. SYSTEMD HARDENING
======================================================================

Investigate appropriate systemd hardening options for concrete daemons.

Potential mechanisms include:

    NoNewPrivileges=
    ProtectSystem=
    ProtectHome=
    PrivateTmp=
    PrivateDevices=
    RestrictAddressFamilies=
    CapabilityBoundingSet=
    RestrictNamespaces=
    SystemCallFilter=
    ProtectKernelTunables=
    ProtectKernelModules=

Do NOT blindly enable every hardening option.

Determine what the daemon actually requires.

Test resulting functionality.

======================================================================
70. USER VS SYSTEM DAEMONS
======================================================================

Determine whether a daemon belongs to:

    system service

or:

    user service.

Do not run user-session functionality as root.

Do not force machine-wide functionality into a user session.

Document ownership.

======================================================================
71. SESSION DEPENDENCY
======================================================================

Some daemons may depend on:

    graphical session
    Wayland
    X11
    user D-Bus
    audio session
    user environment

Such components should normally be user services rather than system
services.

Do not assume desktop environment variables exist in system daemons.

======================================================================
72. PRIVILEGE SEPARATION
======================================================================

If a daemon needs both:

    untrusted/high-level processing

and:

    small privileged operations

investigate splitting privilege boundaries.

Prefer a narrow privileged interface over running the entire daemon as
root.

Use:

    systemd
    polkit
    capabilities
    dedicated helper/service

where appropriate.

======================================================================
73. FILESYSTEM ACCESS
======================================================================

Explicitly define daemon filesystem access.

Persistent background software must not roam through user data without a
clear reason.

For systemd services use sandboxing/access controls where practical.

Do not grant broad `/home` access by default.

======================================================================
74. NETWORK
======================================================================

A daemon should not listen on TCP merely because IPC is needed.

For local Rebuntu components prefer local IPC.

If network access is required:

    bind deliberately;
    authenticate where required;
    authorize;
    validate input;
    document exposure.

Do not accidentally expose Rebuntu control interfaces on LAN/WAN.

======================================================================
75. AUTHENTICATION / AUTHORIZATION
======================================================================

Do not invent custom authentication protocols in Phase 0.5.

For local system functionality investigate:

    Unix socket ownership/mode
    peer credentials
    polkit
    D-Bus policy
    systemd credentials
    OS user/group identity

Use Linux identity and authorization mechanisms where appropriate.

======================================================================
76. PROTOCOLS
======================================================================

If a daemon exposes structured IPC:

    define framing;
    define schema;
    validate input;
    bound message size;
    define errors;
    consider versioning.

Do not use arbitrary pickle/deserialization across trust boundaries.

Do not use ad-hoc line parsing for complex protocols without reason.

======================================================================
77. REQUEST IDs
======================================================================

For request-serving daemons, request IDs may improve:

    tracing
    cancellation
    diagnostics
    correlation

Introduce them only where useful.

Do not impose distributed-systems complexity on trivial local IPC.

======================================================================
78. TIMEOUTS
======================================================================

Daemon operations interacting with external resources must consider
timeouts.

Do not allow:

    subprocess
    socket
    device
    filesystem/network operation

to block the entire daemon indefinitely where failure is plausible.

Use monotonic time for duration mechanics.

======================================================================
79. CANCELLATION
======================================================================

If work can outlive a request or shutdown begins, define cancellation
semantics.

Do not abandon partially mutating operations without considering resulting
state.

Cancellation and rollback are different concepts.

======================================================================
80. VERIFICATION
======================================================================

Daemon verification has several levels:

PROCESS

    process is alive.

READINESS

    daemon completed initialization.

HEALTH

    daemon believes it can perform responsibility.

FUNCTIONAL

    an actual representative operation succeeds.

Do not confuse them.

Acceptance tests should use the strongest reasonable level.

======================================================================
81. SELF-REPORTING IS NOT ENOUGH
======================================================================

A daemon reporting:

    "healthy": true

is evidence, not proof.

For important functionality use external verification where practical.

Example:

    start daemon
    wait for readiness
    send real IPC request
    validate response
    stop daemon
    verify clean shutdown

======================================================================
82. TESTING
======================================================================

Establish reusable daemon test patterns.

Potential tests:

    clean startup
    invalid configuration
    dependency unavailable
    readiness
    health
    IPC
    malformed request
    concurrent requests
    graceful SIGTERM
    forced failure
    restart behavior
    stale socket
    resource cleanup
    timeout
    cancellation
    repeated start/stop
    crash loop controls
    privilege restrictions
    service sandboxing

Do not implement all tests for every trivial daemon.

Create proportional expectations.

======================================================================
83. INTEGRATION TESTS
======================================================================

Where safe, test actual Linux mechanisms rather than mocking everything.

Examples:

    Unix sockets
    signal shutdown
    temporary systemd user unit
    journald integration

Do not modify persistent host configuration merely to run tests.

Prefer isolated/user-level/test fixtures.

======================================================================
84. TEST PROCESS CLEANUP
======================================================================

Daemon tests must never leave background processes behind.

After tests verify:

    child processes terminated
    sockets removed/released
    temp files cleaned
    resources closed

Failure paths must also clean up.

======================================================================
85. SYSTEMD UNIT TESTING
======================================================================

Validate generated/provided systemd units with appropriate native tools.

Where possible test:

    syntax
    dependency model
    startup
    readiness
    shutdown
    restart
    hardening compatibility

Do not assume a syntactically valid unit is behaviorally correct.

======================================================================
86. DAEMON DEVELOPMENT MODE
======================================================================

Concrete daemons should be runnable in foreground development mode without
requiring system-wide installation where practical.

This improves:

    debugging
    tests
    profiling

Do not create a separate daemon implementation for development.

Same executable, different supervisor/environment.

======================================================================
87. DEBUGGING
======================================================================

Do not hide daemon exceptions behind generic:

    daemon failed

messages.

Preserve:

    traceback where appropriate
    failure category
    operation
    dependency
    relevant state

while protecting secrets.

Let journald provide chronological system context.

======================================================================
88. RELOAD / RESTART / REEXEC
======================================================================

Keep these distinct:

RELOAD
    update configuration/state without replacing process.

RESTART
    stop and start process/service.

REEXEC
    replace executable/process image while preserving selected external
    resources where architecture supports it.

Do not introduce advanced reexec semantics without a real requirement.

======================================================================
89. UPDATE BEHAVIOR
======================================================================

Do not make daemons self-update.

Package/deployment/update mechanisms should own software updates.

A daemon may detect incompatible versions and fail safely.

It should not fetch arbitrary code and replace itself.

======================================================================
90. DEPENDENCY AVAILABILITY
======================================================================

For daemon dependencies distinguish:

    hard startup dependency
    soft dependency
    runtime dependency
    optional provider

A missing optional capability should not necessarily kill unrelated daemon
functionality.

Expose degraded state honestly.

======================================================================
91. DEPENDENCY RECOVERY
======================================================================

When a runtime dependency disappears:

    do not necessarily crash;
    do not necessarily retry forever.

Choose based on semantics.

Potential responses:

    reconnect with bounded backoff
    enter degraded state
    fail and let systemd restart
    disable affected capability
    surface alert

Document behavior.

======================================================================
92. BACKOFF
======================================================================

Repeated connection/recovery attempts should use bounded backoff where
appropriate.

Avoid tight retry loops.

Consider:

    minimum delay
    maximum delay
    jitter
    reset after stable success

Do not add sophisticated algorithms without need.

======================================================================
93. DAEMON AND INTERNAL ALERTS
======================================================================

Daemons may become producers or consumers of Rebuntu Internal Alerts.

Do not make every daemon send raw logs/events to the semantic model.

Preferred:

    native event
        ->
    deterministic processing
        ->
    state/fact/assertion
        ->
    meaningful condition
        ->
    InternalAlert

Only escalate when semantic processing adds value.

======================================================================
94. DAEMON AND SEMANTIC MODEL
======================================================================

A semantic-model runtime may itself legitimately be daemon-backed because
it can have:

    expensive model initialization
    persistent memory allocation
    local IPC
    repeated inference requests

This is a good example of a potentially justified daemon.

But Phase 0.5 must NOT implement the BitNet model yet.

Instead, daemon architecture should make the later semantic service a
natural consumer of the established lifecycle and service conventions.

Do not overfit the entire daemon abstraction to model serving.

======================================================================
95. DAEMON AND VERIFICATION
======================================================================

If a daemon performs mutating operations, it must not bypass Rebuntu
operation verification merely because it is trusted internal software.

Persistent execution is not an exemption from:

    preconditions
    policy
    verification
    evidence
    safety

Use stable operation interfaces.

======================================================================
96. DAEMON AND WORKFLOWS
======================================================================

Do not implement complex workflows inside daemon event loops.

A daemon may:

    receive request
    trigger workflow
    observe workflow
    return/result

where architecture supports it.

Workflow semantics belong to the workflow layer.

======================================================================
97. DAEMON AND AUTOMATION
======================================================================

A daemon may host automation evaluation if architecture later justifies
persistent evaluation.

But do not assume:

    automation engine = daemon

before analyzing activation/event requirements.

systemd/native event mechanisms may eliminate the need for persistence in
many cases.

======================================================================
98. DAEMON AND SCHEDULES
======================================================================

A daemon may contain internal housekeeping timers.

But externally meaningful schedules should normally remain Schedule
entities/providers rather than hidden timers in daemon code.

This preserves inspectability.

======================================================================
99. DAEMON AND SHELL
======================================================================

The interactive shell should not need to source daemon implementation.

Shell Sources may provide commands/functions that communicate with daemon
services through stable interfaces.

Do not couple shell lifecycle to daemon internals.

======================================================================
100. DAEMON AND SCRIPTS
======================================================================

Scripts may:

    inspect daemon status
    invoke daemon functionality
    perform installation/deployment support

but should not become alternate daemon supervisors.

Do not create:

    start-daemon.sh
    stop-daemon.sh
    restart-daemon.sh

when systemd/service interfaces already provide those semantics unless the
scripts add genuine Rebuntu-level behavior.

======================================================================
101. INSTALLATION
======================================================================

Distinguish:

    daemon executable
    service unit
    configuration
    runtime state
    persistent state
    IPC endpoint

Installation should place each in the appropriate Linux location according
to deployment strategy.

Do not hard-code development-repository paths into production units.

======================================================================
102. DEVELOPMENT VS INSTALLED PATHS
======================================================================

Design so the same daemon code can be:

    run from development environment

and:

    installed correctly

without source modifications.

Do not embed:

    /home/<user>/Rebuntu/...

in production code or service units.

======================================================================
103. PACKAGING
======================================================================

Do not solve full packaging in Phase 0.5 unless repository architecture
already requires it.

But daemon design must not prevent future packaging.

Avoid assumptions that only work from a Git checkout.

======================================================================
104. LOCAL AGENTS.md
======================================================================

If a dedicated daemon infrastructure directory is created, add a local
AGENTS.md if consistent with repository conventions.

It should state at minimum:

    Daemon != Service.
    Daemon != Automation.
    Daemon != Schedule.
    Daemon != Script.
    Daemon != Monitor.
    systemd is the default supervisor.
    do not self-daemonize.
    do not create PID files by default.
    do not create persistent processes without admission justification.
    use native event mechanisms.
    separate lifecycle/readiness/health.
    define state/resource ownership.
    support graceful shutdown.
    use least privilege.
    test real lifecycle behavior.
    do not recreate historical daemonizers blindly.

The purpose is to prove:

    foreground execution
    systemd supervision model
    readiness
    graceful shutdown
    health/status
    IPC if justified
    logging
    testability

Do not create meaningless production architecture merely for a demo.

A test fixture may be preferable to a permanent production daemon.

======================================================================
109. DAEMON BASE CLASS?
======================================================================

Explicitly investigate whether Rebuntu needs a:

    DaemonBase

or equivalent abstraction.

Do NOT assume yes.

A common base class is justified only if multiple concrete daemons share
meaningful implementation behavior.

Potential shared concerns:

    startup/shutdown coordination
    readiness
    signal handling
    health
    structured logging

But composition/protocols may be better than inheritance.

Do not create inheritance architecture based on hypothetical future
daemons.

======================================================================
110. DAEMON RUNTIME?
======================================================================

    daemon runtime

is justified.

Possible outcome:

    NO — systemd + small per-service bootstrap is sufficient.

Possible outcome:

    YES — a narrow reusable Python lifecycle helper is justified.

Either is acceptable.

Do not build a second systemd.

======================================================================
111. CENTRAL DAEMON MANAGER?
======================================================================

Strong default:

    DO NOT CREATE ONE.

A `DaemonManager` that starts/stops/tracks every daemon risks duplicating
systemd.

If Rebuntu needs higher-level daemon/service coordination, it should query
and command the authoritative service manager through appropriate adapters.

Do not maintain shadow process truth.

======================================================================
112. DAEMON REGISTRY?
======================================================================

Investigate carefully.

A catalog of known Rebuntu daemon definitions may eventually be useful.

But:

    catalog != supervisor
    registry != runtime truth

If introduced, it should describe Rebuntu-known components, not duplicate
systemd process state.

Do not create it without a consumer.

======================================================================
113. SYSTEMD ADAPTER
======================================================================

If current architecture already has an adapter/provider layer, daemon/service
integration should reuse it.

Do not scatter:

    subprocess.run(["systemctl", ...])

through daemon-related modules.

But do not implement a massive systemd abstraction solely for Phase 0.5.

======================================================================
114. PROCESS IDENTITY
======================================================================

When process identity is needed, use authoritative mechanisms.

Do not identify daemons through:

    ps | grep daemon_name

or process-name substring matching.

Prefer:

    systemd unit/cgroup identity
    explicit PID from supervisor/API
    IPC identity

according to the requirement.

115. START/STOP IDEMPOTENCY
======================================================================

Higher-level requests such as:

    ensure daemon running
    ensure daemon stopped

should favor desired-state semantics where appropriate.

This differs from:

    start exactly once
    stop exactly once.

Do not create errors merely because desired state is already satisfied
unless API semantics require it.

    manually invoked for development;
    systemd-managed in deployment;
    enabled according to configuration/profile/policy.

Do not hard-wire user-facing policy into daemon implementation.

The daemon should perform its responsibility.

Higher layers decide whether it should exist.

CORE PRINCIPLE
======================================================================

A Rebuntu Daemon exists because some functionality genuinely benefits from
a persistent process.

It must NOT exist merely because background execution is convenient.

Before creating a daemon:

    OPERATION?
    SCRIPT?
    TASK/JOB?
    ONESHOT SERVICE?
    TIMER?
    PATH ACTIVATION?
    SOCKET ACTIVATION?
    UDEV?
    D-BUS ACTIVATION?
    EXISTING SERVICE?

Only then:

    DAEMON.

When a daemon is justified:

    KEEP IT FOREGROUND.
    LET SYSTEMD SUPERVISE IT.
    DEFINE OWNERSHIP.
    DEFINE LIFECYCLE.
    DEFINE READINESS.
    DEFINE HEALTH.
    DEFINE FAILURE SEMANTICS.
    DEFINE SHUTDOWN.
    DEFINE RESOURCES.
    DEFINE IPC.
    USE NATIVE EVENTS.
    USE LEAST PRIVILEGE.
    VERIFY FUNCTIONALITY.

DO NOT BUILD ANOTHER SYSTEMD.

DO NOT RESURRECT HOMEMADE DAEMONIZATION FOR NOSTALGIA.

PRESERVE THE REQUIREMENTS DISCOVERED BY HISTORICAL REBUNTU.

REPLACE ACCIDENTAL MECHANISMS WITH MODERN LINUX FACILITIES.

A DAEMON IS A PROCESS ROLE.

A SERVICE IS MANAGED FUNCTIONALITY.

AN AUTOMATION DECIDES WHEN/WHY WORK HAPPENS.

A WORKFLOW DEFINES HOW COMPOSED WORK PROGRESSES.

A SCHEDULE DEFINES WHEN WORK SHOULD BE ACTIVATED.

KEEP THESE CONCEPTS SEPARATE.
