# Rebuntu — Phase 0.6
# Services Architecture, Contracts, Activation, Dependencies & Native Linux Integration

Phase 0.6 establishes the canonical Service model for Rebuntu.

Previous phases established the repository structure, structural taxonomy,
Shell Sources, Scripts and Daemons.

This phase now answers:

    WHAT IS A SERVICE IN REBUNTU?

    WHEN SHOULD FUNCTIONALITY BECOME A SERVICE?

    WHO OWNS A SERVICE?

    HOW IS IT ACTIVATED?

    HOW IS ITS AVAILABILITY DETERMINED?

    HOW DOES IT DEPEND ON OTHER FUNCTIONALITY?

    HOW DOES IT MAP TO SYSTEMD AND OTHER NATIVE LINUX FACILITIES?

    HOW DOES A SERVICE DIFFER FROM A DAEMON, UNIT, MODULE, OPERATION,
    SCRIPT, TASK, JOB, SCHEDULE AND AUTOMATION?

The central principle is:

    SERVICE = MANAGED FUNCTIONALITY WITH AN EXPLICIT AVAILABILITY,
              LIFECYCLE AND INTERFACE CONTRACT

not:

    SERVICE = DAEMON

not:

    SERVICE = SYSTEMD .service FILE

not:

    SERVICE = BACKGROUND SCRIPT

not:

    SERVICE = ANY REBUNTU MODULE.

A Service describes functionality.

Its implementation and activation model may vary.

Examples:

    persistent daemon-backed service
    socket-activated service
    D-Bus-activated service
    one-shot service
    event-triggered service
    timer-triggered service
    service composed from multiple processes

The architecture must preserve these distinctions.

======================================================================
2. DEFINE SERVICE PRECISELY
======================================================================

Establish a canonical definition.

Initial hypothesis:

    SERVICE

    A managed Rebuntu functionality with an explicit identity,
    availability contract, interface, ownership and lifecycle semantics.

A Service answers:

    WHAT FUNCTIONALITY IS PROVIDED?

    HOW CAN IT BE ACCESSED?

    WHEN SHOULD IT BE AVAILABLE?

    HOW DO WE DETERMINE WHETHER IT IS AVAILABLE?

    WHAT DOES IT DEPEND ON?

    WHAT OWNS IT?

A Service does NOT inherently answer:

    which process implements it;
    whether a process is permanently running;
    which activation mechanism is used;
    whether systemd uses Type=simple/notify/oneshot/etc.;
    whether implementation is Python, C++, Bash or external software.

Those are implementation/deployment concerns.

======================================================================
3. SERVICE != DAEMON
======================================================================

Mandatory distinction:

    SERVICE
        managed functionality.

    DAEMON
        persistent process/runtime role.

A daemon may implement a Service.

But a Service may instead be:

    one-shot
    socket-activated
    D-Bus-activated
    timer-triggered
    event-triggered
    externally provided
    composed from multiple processes.

Therefore:

    Service -> may use Daemon

but:

    Service != Daemon.

Never organize the architecture as though:

    services/ == daemons/.

======================================================================
4. SERVICE != SYSTEMD SERVICE UNIT
======================================================================

This distinction is equally important.

A systemd:

    foo.service

is a native Linux service-manager Unit.

A Rebuntu Service is a semantic/system architecture concept.

A Rebuntu Service may map to:

    one .service unit

or:

    .socket + .service

or:

    .timer + .service

or:

    .path + .service

or:

    D-Bus activation

or:

    multiple units

or:

    an external existing Linux service

or potentially:

    no dedicated systemd service unit at all.

Therefore:

    REBUNTU SERVICE
        !=
    SYSTEMD SERVICE UNIT

Document this explicitly.

======================================================================
5. SERVICE != MODULE
======================================================================

A Module is a reusable structural/software boundary.

A Service is managed functionality.

A Module may implement:

    zero services
    one service
    multiple services.

A Service may use multiple modules.

Do not create one Service per Module automatically.

======================================================================
6. SERVICE != SYSTEM
======================================================================

A System is a larger coherent architectural area or foundational runtime
according to the structural taxonomy.

A Service is narrower managed functionality.

A System may contain or depend on several Services.

Do not use Service as a generic synonym for subsystem.

======================================================================
7. SERVICE != OPERATION
======================================================================

An Operation represents bounded system capability/action.

A Service represents available functionality with management/lifecycle
semantics.

Example:

    service:
        semantic processing service

    operations:
        classify_log
        parse_request
        summarize_alert

A Service may expose Operations.

An Operation may exist without a Service.

Do not create persistent service semantics around every Operation.

======================================================================
8. SERVICE != SCRIPT
======================================================================

A Script is an executable artifact.

A Service is functionality.

A Script may participate in implementing:

    one-shot service
    setup action
    service helper

but:

    Script != Service.

Do not classify something as a Service merely because systemd executes a
script.

======================================================================
9. SERVICE != TASK
======================================================================

A Task is bounded work/specification.

A Service provides functionality capable of accepting or performing work.

A Service may receive Tasks.

A Task may be executed without any persistent Service.

Keep them distinct.

======================================================================
10. SERVICE != JOB
======================================================================

A Job is a concrete execution/submission of work.

A Service may process Jobs.

A Job is not a Service.

A Service should not be created merely because a Job must execute.

======================================================================
11. SERVICE != SCHEDULE
======================================================================

A Schedule determines WHEN work/functionality should activate.

A Service determines WHAT managed functionality exists.

A Schedule may activate a Service or Job.

Do not encode scheduling semantics inside Service identity.

======================================================================
12. SERVICE != AUTOMATION
======================================================================

Automation determines:

    WHEN
    WHY
    UNDER WHAT CONDITIONS

something should happen.

Service defines:

    WHAT FUNCTIONALITY IS AVAILABLE.

An Automation may:

    activate a Service
    invoke a Service
    change desired availability
    respond to Service failure
    request an Operation exposed by a Service.

Do not merge automation policy into Service implementation.

======================================================================
13. SERVICE != INTERFACE
======================================================================

A Service may expose one or more interfaces.

Examples:

    Unix socket
    D-Bus
    CLI facade
    local API
    filesystem endpoint
    native kernel interface

The interface is how functionality is accessed.

The Service is the managed functionality itself.

======================================================================
14. SERVICE != PROVIDER
======================================================================

A Provider implements or supplies some capability behind an abstraction.

A Service may use Providers.

A Service itself may also serve as a Provider from another component's
perspective.

But these are different classification dimensions.

Do not force them into the same taxonomy.

======================================================================
15. SERVICE ADMISSION TEST
======================================================================

Before creating a new Service ask:

    Is this merely a Python Module?

    Is this merely an Operation?

    Is this merely a Script?

    Is this merely a Task?

    Is this merely a Workflow?

    Is this merely scheduled work?

    Is this merely Automation?

    Is this functionality already provided by Linux?

    Is this functionality already provided by an existing system service?

    Does this functionality genuinely need independent management,
    availability or lifecycle semantics?

Only then introduce a Service.

======================================================================
16. WHEN IS A SERVICE JUSTIFIED?
======================================================================

Potential legitimate reasons:

    functionality has independent availability;

    multiple clients consume it;

    functionality has expensive initialization;

    functionality owns persistent resources;

    functionality has independent lifecycle;

    functionality exposes stable IPC/API;

    functionality needs privilege isolation;

    functionality needs fault isolation;

    functionality represents a persistent external integration;

    functionality must be activated independently;

    functionality has meaningful readiness/health;

    functionality needs resource governance;

    functionality benefits from service-manager supervision.

Invalid reasons include:

    "there is a module for it";

    "it runs code";

    "it needs a command";

    "systemd can run it";

    "services/ is a convenient directory";

    "microservices sound professional".

======================================================================
17. DO NOT MICROSERVICE REBUNTU
======================================================================

Rebuntu is a local operating environment.

Do not fragment it into dozens of tiny services.

Every process/service boundary introduces:

    lifecycle
    IPC
    serialization
    failure modes
    deployment
    permissions
    observability
    synchronization
    testing

cost.

Prefer in-process modularity unless an independent service boundary has a
real systems reason.

======================================================================
18. SERVICE OWNERSHIP
======================================================================

Every Service must have a clear architectural owner.

Answer:

    Which System/Module owns this Service?

    What functionality does it provide?

    Who consumes it?

    What state does it own?

    What resources does it own?

    What interfaces does it expose?

    What native facilities implement it?

    What happens when it is unavailable?

Avoid orphan services.

======================================================================
19. SERVICE IDENTITY
======================================================================

A Service should have stable semantic identity independent of:

    PID
    executable filename
    implementation language
    systemd unit filename
    temporary socket path.

Example conceptual identity:

    semantic

or:

    semantic.processing

rather than:

    python_server_1.

Do not prematurely invent globally elaborate naming schemes.

Use existing Rebuntu naming conventions.

======================================================================
20. SERVICE CONTRACT
======================================================================

Define a lightweight Service contract.

Potential fields:

    identity
    purpose
    owner
    interface
    activation
    dependencies
    availability
    readiness
    health
    state ownership
    resource ownership
    privilege
    failure behavior
    verification

Not every trivial Service needs a giant manifest.

Use proportional engineering.

======================================================================
21. AVAILABILITY
======================================================================

Define availability independently from process existence.

Potential conceptual states:

    UNAVAILABLE
    ACTIVATING
    AVAILABLE
    DEGRADED
    DEACTIVATING
    FAILED

But do not create a large state machine unless required.

Investigate whether some of these belong instead to:

    lifecycle
    readiness
    health.

Avoid duplicating Phase 0.5 state concepts.

======================================================================
22. SERVICE LIFECYCLE VS DAEMON LIFECYCLE
======================================================================

A daemon process may:

    start
    run
    stop.

Service functionality may:

    become available
    become unavailable
    degrade
    switch provider
    survive process replacement.

Therefore:

    PROCESS LIFECYCLE
        !=
    SERVICE AVAILABILITY.

Preserve this distinction.

======================================================================
23. ENABLED != RUNNING != AVAILABLE
======================================================================

These concepts must remain distinct.

ENABLED

    deployment/configuration says service should normally activate.

RUNNING

    implementation process currently exists.

READY

    implementation finished initialization.

AVAILABLE

    clients can actually use functionality.

HEALTHY

    functionality behaves correctly.

DESIRED

    higher-level configuration/policy currently wants functionality.

Example:

    enabled = true
    running = true
    ready = true
    available = true
    healthy = degraded

is possible.

Do not reduce Service state to one boolean.

======================================================================
24. DESIRED SERVICE STATE
======================================================================

Rebuntu may eventually manage desired functionality state.

Potential conceptual form:

    desired:
        enabled: true
        availability: required

Actual state may differ.

This creates a useful control relation:

    DESIRED STATE
        ->
    OBSERVED STATE
        ->
    DIFFERENCE
        ->
    RECONCILIATION

Do not build a full reconciliation engine solely for Phase 0.6.

But design Service contracts so it remains possible.

======================================================================
25. ACTIVATION MODEL
======================================================================

Service activation must be explicit.

Potential activation modes:

    persistent
    manual
    boot
    on-demand
    socket
    D-Bus
    path
    device/event
    timer
    dependency
    policy-driven

These are activation characteristics, not necessarily Service categories.

Avoid one directory per activation type.

======================================================================
26. PERSISTENT ACTIVATION
======================================================================

Persistent activation is appropriate where continuous availability is
required.

Usually:

    systemd
        ->
    daemon
        ->
    Service.

But do not make persistence the default merely because it is familiar.

======================================================================
27. ON-DEMAND ACTIVATION
======================================================================

If functionality is rarely used, investigate on-demand activation.

Benefits:

    lower idle resource use
    fewer persistent processes
    simpler resource ownership
    smaller attack surface

Possible mechanisms:

    socket activation
    D-Bus activation
    direct oneshot invocation.

======================================================================
28. SOCKET ACTIVATION
======================================================================

Investigate systemd socket activation where appropriate.

Conceptually:

    client
        ->
    socket
        ->
    systemd activation
        ->
    service implementation.

This can preserve stable availability semantics without requiring a
permanently running daemon.

Do not create a daemon simply to keep a socket open if systemd can own the
socket.

======================================================================
29. D-BUS ACTIVATION
======================================================================

For functionality naturally integrated with system/user bus semantics,
investigate D-Bus activation.

Use it when its object/method/signal model fits.

Do not use D-Bus merely for architectural fashion.

======================================================================
30. ONESHOT SERVICES
======================================================================

Some managed functionality may correctly use:

    Type=oneshot

or equivalent native semantics.

Examples might include:

    controlled initialization
    synchronization
    migration
    system preparation

Do not create a fake persistent daemon around bounded work.

======================================================================
31. TIMER-TRIGGERED SERVICES
======================================================================

Periodic functionality may use:

    .timer
        ->
    .service

without a persistent daemon.

Preserve:

    Schedule = temporal policy
    Service = managed functionality
    systemd timer = native activation provider.

Do not hide periodicity in endless loops.

======================================================================
32. PATH-TRIGGERED SERVICES
======================================================================

Investigate:

    systemd.path
    inotify/fanotify
    appropriate native mechanisms

for filesystem-triggered functionality.

Do not poll directories unnecessarily.

======================================================================
33. DEVICE/EVENT ACTIVATION
======================================================================

Hardware/device-driven functionality may use:

    udev
    systemd device dependencies
    netlink
    native kernel event sources.

Do not create polling services for events Linux already exposes.

======================================================================
34. SERVICE DEPENDENCIES
======================================================================

Define dependency semantics explicitly.

Potential distinctions:

    REQUIRED
    OPTIONAL
    ORDERING
    RUNTIME
    PROVIDER
    ACTIVATION
    SOFT

Do not immediately encode all of these as a giant dependency framework.

First establish conceptual distinctions.

======================================================================
35. DEPENDENCY != ORDERING
======================================================================

A classic systemd lesson must be preserved:

    "A requires B"

and:

    "A should start after B"

are different statements.

Do not collapse:

    dependency
    ordering.

Use native systemd dependency semantics correctly where deployment maps to
systemd.

======================================================================
36. HARD DEPENDENCIES
======================================================================

A hard dependency means functionality cannot correctly exist without the
dependency.

Failure should be explicit.

Do not pretend availability when required dependencies are absent.

======================================================================
37. OPTIONAL DEPENDENCIES
======================================================================

Optional dependencies may enrich functionality without making the entire
Service unavailable.

The Service may expose:

    reduced capability
    degraded health
    unavailable optional operation.

Do not kill unrelated functionality unnecessarily.

======================================================================
38. SERVICE GRAPH
======================================================================

Service dependencies naturally form a graph.

Do not assume a tree.

Detect or prevent invalid cycles where they create impossible activation.

Do not implement a huge graph framework before actual Service count
justifies it.

But preserve graph semantics in the model.

======================================================================
39. DEPENDENCY CYCLES
======================================================================

Explicitly consider:

    A requires B
    B requires A.

Differentiate:

    genuine logical cycle
    ordering cycle
    optional mutual integration
    startup coordination.

Do not solve cycles with arbitrary sleep delays.

======================================================================
40. SERVICE COMPOSITION
======================================================================

A higher-level Service may be composed from several lower-level
functionalities.

Do not necessarily create another process for the composed Service.

Composition is semantic.

Process topology is an implementation decision.

======================================================================
41. SERVICE GROUPS / TARGETS
======================================================================

Investigate whether Rebuntu needs logical Service groups.

Where systemd targets naturally fit, use them.

Potential examples:

    profile-level functionality
    session-level functionality
    development environment functionality.

Do not invent groups without consumers.

======================================================================
42. SYSTEMD TARGETS
======================================================================

systemd targets may express:

    grouping
    synchronization
    activation topology.

Do not reproduce them with homemade marker files.

But Rebuntu's higher-level Profile/System concepts should not be blindly
equated to `.target` units.

Map semantics deliberately.

======================================================================
43. PROVIDER MODEL
======================================================================

Some Service functionality may have multiple providers.

Example conceptual structure:

    service capability
        ->
    provider A
    provider B

Provider selection may depend on:

    platform
    environment
    availability
    configuration
    policy.

Do not build dynamic provider switching unless required.

But keep Service identity independent of implementation where useful.

======================================================================
44. EXTERNAL SERVICES
======================================================================

Rebuntu may manage or consume services it did not implement.

Examples include native Linux/system software.

Do not wrap every external service in a custom daemon.

Represent external service integration through adapters/providers/contracts
where useful.

======================================================================
45. AUTHORITATIVE STATE
======================================================================

Do not create shadow truth.

For systemd-managed service state:

    systemd is authoritative for process/unit state.

For kernel state:

    kernel/native interface is authoritative.

For Rebuntu semantic desired state:

    Rebuntu may be authoritative.

Clearly document which layer owns which truth.

======================================================================
46. SYSTEMD ADAPTER
======================================================================

Service management should not scatter:

    subprocess.run(["systemctl", ...])

through the repository.

Use or extend the appropriate adapter/integration boundary.

Investigate:

    systemd D-Bus API

where it gives stronger structured semantics.

CLI invocation may still be appropriate for bounded tooling.

Choose the lowest appropriate native abstraction.

======================================================================
47. START / STOP / RESTART / RELOAD
======================================================================

Define these separately.

START
    request activation.

STOP
    request deactivation.

RESTART
    stop and activate again.

RELOAD
    ask existing implementation to apply reloadable configuration.

Do not assume every Service supports all four.

Expose only meaningful operations.

======================================================================
48. ENABLE / DISABLE
======================================================================

Keep:

    enable
    disable

distinct from:

    start
    stop.

Enablement concerns future/default activation.

Running concerns current runtime state.

Do not create user interfaces that confuse them.

======================================================================
49. MASKING
======================================================================

Where systemd masking is relevant, preserve its stronger meaning:

    activation prohibited

rather than treating it as another synonym for:

    disabled.

Do not expose systemd-specific concepts as universal Service ontology
unless Rebuntu genuinely needs them.

======================================================================
50. ENSURE SEMANTICS
======================================================================

Rebuntu service operations may benefit from desired-state verbs:

    ensure_available
    ensure_unavailable

rather than imperative-only:

    start
    stop.

Example:

    ensure_available()

should succeed when functionality is already correctly available.

This is useful for idempotent automation.

Do not replace all native lifecycle verbs; preserve both semantics where
useful.

======================================================================
51. READINESS
======================================================================

Reuse the Phase 0.5 distinction.

A Service is not available merely because its implementation process
started.

Potential readiness evidence:

    sd_notify READY=1
    IPC endpoint functioning
    dependency initialization complete
    representative request succeeds.

Do not invent duplicate readiness frameworks.

======================================================================
52. HEALTH
======================================================================

Service health describes whether functionality behaves correctly.

Possible minimal states:

    UNKNOWN
    HEALTHY
    DEGRADED
    UNHEALTHY

Reuse established health semantics.

Do not create a second incompatible health ontology.

======================================================================
53. HEALTH AGGREGATION
======================================================================

A composed Service may derive health from:

    implementation process
    dependencies
    providers
    functional verification.

Do not simply calculate:

    all processes running => healthy.

Define meaningful aggregation only when composition requires it.

======================================================================
54. FUNCTIONAL VERIFICATION
======================================================================

The strongest Service verification often means:

    invoke representative functionality
        ->
    validate result.

For an IPC service:

    connect
    request
    receive
    validate.

For a storage service:

    verify actual intended state.

For an external integration:

    perform safe health operation.

Self-reported health is useful but not sufficient for critical guarantees.

======================================================================
55. SERVICE CONTRACT VERIFICATION
======================================================================

A Service contract should make it possible to verify:

    identity
    activation
    availability
    interface
    dependencies
    readiness
    health
    permissions
    expected functionality.

Do not require every Service to implement bespoke verification logic.

Reuse verification infrastructure.

======================================================================
56. FAILURE MODEL
======================================================================

Classify failures where useful:

    activation failure
    implementation crash
    readiness failure
    dependency failure
    provider failure
    interface failure
    degraded functionality
    authorization failure
    resource exhaustion
    configuration failure.

Different failures imply different responses.

Do not reduce everything to:

    service failed.

======================================================================
57. RECOVERY
======================================================================

Possible recovery actions include:

    restart implementation
    reinitialize provider
    restore configuration
    reacquire dependency
    switch provider
    reconcile desired state
    escalate diagnostic evidence.

Do not automatically restart every failed Service forever.

Recovery belongs to explicit policy/mechanism.

======================================================================
58. SERVICE RECONCILIATION
======================================================================

Design Service representation so future reconciliation can express:

    desired availability
        !=
    observed availability.

Potential flow:

    observe
        ->
    compare
        ->
    determine permitted correction
        ->
    activate/deactivate/reconfigure
        ->
    verify
        ->
    record evidence.

Do not implement a Kubernetes clone.

This is a local Linux control problem.

======================================================================
59. RESTART POLICY
======================================================================

Restart policy belongs primarily to the supervisor/deployment layer.

Use systemd facilities.

Do not implement:

    while service_failed:
        restart()

inside Rebuntu runtime unless a higher-level recovery policy has a genuinely
different semantic purpose.

======================================================================
60. RESOURCE POLICY
======================================================================

Service resource constraints may include:

    CPU
    memory
    I/O
    processes
    devices
    file descriptors.

Use:

    systemd
    cgroups

rather than application-level imitation.

Keep resource requirements/limits inspectable.

======================================================================
61. CPU/GPU REQUIREMENTS
======================================================================

Services requiring accelerators must declare this explicitly.

Do not opportunistically initialize GPUs.

A CPU-only Service must remain CPU-only when configured as such.

Resource ownership should be compatible with future machine-wide resource
coordination.

Do not build that entire system in Phase 0.6.

======================================================================
62. PRIVILEGE MODEL
======================================================================

Each Service must have an explicit privilege model.

Ask:

    system service or user service?
    which Unix user?
    which groups?
    which capabilities?
    which files?
    which devices?
    which sockets?
    which network access?

Use least privilege.

Do not run a Service as root merely because one operation requires elevated
privilege.

======================================================================
63. PRIVILEGE SEPARATION
======================================================================

When appropriate:

    unprivileged service
        ->
    narrow privileged helper/interface.

Potential native mechanisms:

    polkit
    capabilities
    dedicated system service
    Unix socket permissions
    D-Bus policy.

Do not invent a universal privileged broker without evidence.

======================================================================
64. SYSTEM SERVICE VS USER SERVICE
======================================================================

Define placement rules.

SYSTEM SERVICE

    machine-wide functionality independent of interactive login.

USER SERVICE

    functionality owned by user/session/environment.

Examples of user-dependent context:

    desktop session
    Wayland
    X11
    user D-Bus
    user audio session.

Do not run session-bound functionality as a root system daemon.

======================================================================
65. IPC
======================================================================

A Service may expose IPC.

Potential mechanisms:

    Unix domain socket
    D-Bus
    systemd socket activation
    pipe/FIFO
    direct library interface
    native protocol.

Do not impose one universal IPC protocol.

Choose based on Service requirements.

======================================================================
66. LOCAL-FIRST COMMUNICATION
======================================================================

Rebuntu Services are local by default.

Do not expose TCP/network listeners unless remote access is an explicit
requirement.

Prefer:

    Unix sockets
    D-Bus
    native local facilities.

Reduce attack surface.

======================================================================
67. INTERFACE CONTRACT
======================================================================

For structured Service interfaces define where relevant:

    operations/methods
    request schema
    response schema
    error semantics
    timeout
    cancellation
    authorization
    protocol version.

Do not create informal text protocols for structured control surfaces.

======================================================================
68. PROTOCOL VERSIONING
======================================================================

Version local IPC protocols when evolution risk justifies it.

Do not over-engineer compatibility for interfaces that do not yet exist.

But avoid protocols that cannot evolve safely.

======================================================================
69. REQUEST VALIDATION
======================================================================

Service boundaries are trust boundaries.

Validate:

    message size
    schema
    path arguments
    identifiers
    enum values
    ranges
    authorization.

Do not trust callers merely because they are local.

======================================================================
70. SERVICE DISCOVERY
======================================================================

Eventually Rebuntu should be able to answer:

    What Services exist?

    Who owns them?

    What functionality do they provide?

    How are they activated?

    Are they desired?

    Are they available?

    Are they healthy?

    What do they depend on?

Design for discoverability.

Do not implement a large registry until real consumers justify it.

======================================================================
71. SERVICE CATALOG != RUNTIME TRUTH
======================================================================

If a Service catalog/registry is introduced:

    catalog
        describes known Services.

It must not duplicate:

    systemd's actual process/unit state.

Runtime truth should be obtained from authoritative sources.

======================================================================
72. STATIC DEFINITION VS RUNTIME INSTANCE
======================================================================

Distinguish:

    ServiceDefinition

from:

    ServiceInstance

only if multiple runtime instances genuinely exist.

Do not create enterprise-style object models prematurely.

But preserve the conceptual difference:

    definition != runtime realization.

======================================================================
73. TEMPLATE / INSTANCE SERVICES
======================================================================

systemd template units may be useful for repeated instances:

    foo@.service
    foo@bar.service.

Investigate when actual requirements appear.

Do not create custom templating if native instance units fit.

======================================================================
74. SERVICE INSTANCE IDENTITY
======================================================================

If multiple instances exist, identity must be stable and validated.

Do not embed arbitrary user strings into unit names or paths unsafely.

Use proper escaping/native mechanisms.

======================================================================
75. SERVICE GROUPING
======================================================================

Investigate semantic grouping separately from dependencies.

A group may mean:

    profile membership
    operational category
    deployment bundle
    lifecycle cohort.

Do not overload dependency edges to represent every relationship.

======================================================================
76. PROFILES
======================================================================

Profiles may eventually express desired Service state.

Example conceptual profile:

    workstation:
        services:
            display_support: required
            gaming_support: optional
            semantic: enabled

Do not implement profile orchestration in Phase 0.6 unless existing
architecture already requires it.

Ensure the Service model can support it later.

======================================================================
77. CONTEXT
======================================================================

Service desired state may depend on machine context.

Examples:

    hardware present
    graphical session active
    network available
    storage mounted
    power state
    active profile.

Context determines policy/desired state.

Service implementation should not independently invent machine-wide policy.

======================================================================
78. AUTOMATION INTEGRATION
======================================================================

Automation may observe:

    ServiceUnavailable
    ServiceDegraded
    ServiceRecovered

and request appropriate actions.

Services should expose structured state/events where useful.

Establish the model.

84. SERVICE INSTALLATION
======================================================================

Separate:

    implementation
    systemd units
    configuration
    IPC endpoints
    runtime state
    persistent state.

    manual files must not be overwritten silently.

the Service implementation itself.

======================================================================
92. EXTERNAL LINUX SERVICES
======================================================================

Rebuntu should understand that many useful Services already exist outside
Rebuntu.

Examples may include:

    systemd-resolved
    NetworkManager
    sshd
    PipeWire
    Docker daemon

depending on host configuration.

Do not replace mature native services.

Integrate with them through appropriate interfaces.

======================================================================
93. SERVICE WRAPPERS
======================================================================

Do not create wrapper Services merely to rename external Linux services.

A Rebuntu abstraction is justified when it adds:

    stable cross-provider semantics
    verification
    policy
    composition
    structured evidence
    meaningful higher-level capability.

Otherwise use the native service directly through an adapter.

======================================================================
94. SERVICE MANAGER?
======================================================================

Explicitly evaluate whether Rebuntu needs a `ServiceManager`.

Strong default:

    probably not as a process supervisor.

systemd already performs service management at the native lifecycle level.

Rebuntu may need a higher-level:

    ServiceController
    ServiceRegistry
    ServiceResolver
    ServiceReconciler

eventually.

But introduce only the smallest abstraction justified by current
requirements.

Never create a shadow systemd.

======================================================================
95. SERVICE CONTROLLER
======================================================================

If a controller abstraction is justified, it should express Rebuntu-level
intent such as:

    inspect
    ensure_available
    ensure_unavailable
    verify
    resolve_provider

and delegate native lifecycle operations through adapters.

It should not independently track process truth.

======================================================================
96. SERVICE REGISTRY
======================================================================

Explicitly evaluate whether a Service registry is justified now.

Potential purpose:

    discover known Rebuntu Services
    resolve identity
    inspect contracts
    map providers/deployment.

Do not introduce it merely because "registries are architectural".

If created:

    registry = definitions/catalog

not:

    registry = authoritative runtime process table.

======================================================================
97. SERVICE RESOLUTION
======================================================================

Future functionality may request:

    semantic processing

without knowing whether implementation is:

    local BitNet
    another local model
    external provider.

This suggests possible separation:

    requested Service capability
        ->
    provider resolution
        ->
    concrete implementation.

Do not build generalized dynamic resolution before real multiple providers
exist.

Keep the architecture capable of it.

======================================================================
98. SERVICE BOUNDARY TEST
======================================================================

For every proposed Service boundary ask:

    Does it need independent lifecycle?

    Does it need independent failure isolation?

    Does it need independent privilege?

    Does it need independent resource ownership?

    Does it have multiple clients?

    Does it expose a stable interface?

    Does it need activation independent of caller?

    Does deployment benefit from process isolation?

If most answers are no:

    it probably should remain a Module/Operation.

======================================================================
99. SERVICE COHESION
======================================================================

A Service should provide a coherent functionality set.

Do not create giant:

    rebuntu-everything.service

that owns unrelated responsibilities.

But also do not create:

    rebuntu-parse-one-line.service
    rebuntu-format-one-result.service
    rebuntu-check-one-flag.service.

Find meaningful system boundaries.

======================================================================
100. PROCESS TOPOLOGY
======================================================================

Do not infer process topology from semantic decomposition.

A Service may use:

    zero persistent processes
    one daemon
    several workers
    external native services.

Likewise, one daemon may potentially support multiple closely related
service interfaces if ownership/lifecycle justify it.

Architecture first.

Process topology second.

======================================================================
101. FAILURE ISOLATION
======================================================================

Service boundaries may be justified by failure isolation.

But process isolation has cost.

Use it for actual risk:

    unstable integration
    native library crash
    model runtime
    privilege boundary
    device ownership
    expensive state.

Do not isolate trivial pure Python modules into services.

======================================================================
102. RESOURCE ISOLATION
======================================================================

Similarly, a Service boundary may allow independent:

    CPU limits
    memory limits
    I/O limits
    device access.

Use systemd/cgroups.

Do not create services solely to imitate container architecture.

======================================================================
103. SERVICE AND CONTAINERS
======================================================================

Containers may eventually host some providers.

Container != Service.

Service identity should remain independent of whether implementation runs:

    directly
    under systemd
    inside container
    through external software.

Do not containerize local functionality without a concrete reason.

======================================================================
104. SERVICE AND NATIVE CODE
======================================================================

A Service may be implemented in:

    Python
    C++
    external executable
    mixed stack.

Language does not determine Service semantics.

Use C++ only where native/performance requirements justify it.

Python remains Rebuntu's primary higher-level implementation language.

======================================================================
105. SERVICE AND SHELL
======================================================================

Shell Sources may provide ergonomic functions for interacting with
Services.

Example conceptual flow:

    shell command
        ->
    stable Rebuntu CLI/API
        ->
    Service interface.

Do not source service implementation into the interactive shell.

======================================================================
106. SERVICE AND BIN
======================================================================

Public commands may act as Service clients.

Keep bin entry points thin.

Do not duplicate Service implementation in command wrappers.

======================================================================
107. SERVICE AND SCRIPTS
======================================================================

Scripts may:

    install
    validate
    migrate
    inspect
    invoke

Services.

They must not become alternate process supervisors.

Do not create shell scripts duplicating:

    systemctl start/stop/restart

without adding meaningful Rebuntu semantics.

======================================================================
108. SERVICE AND OPERATIONS
======================================================================

Services should expose canonical Operations where the operation model
already exists.

Example:

    Service
        Semantic Processing

    Operations
        classify
        extract
        summarize

This preserves discoverability and verification.

Do not make every RPC method a globally registered Operation unless the
operation ontology requires it.

======================================================================
109. SERVICE AND WORKFLOWS
======================================================================

A Workflow may invoke several Services.

A Service should not silently become a workflow engine.

If a request requires:

    multiple stages
    branching
    rollback
    checkpoints
    coordination

use the workflow architecture where appropriate.

======================================================================
110. SERVICE AND VERIFICATION
======================================================================

Every important Service should eventually have an answer to:

    How do we prove this functionality currently works?

Possible evidence:

    native unit state
    readiness
    IPC response
    representative operation
    dependency verification
    resource verification.

Do not equate "systemctl says active" with functional correctness.

======================================================================
111. SERVICE AND EVIDENCE
======================================================================

Where significant, verification should produce structured evidence.

Potential evidence:

    provider
    implementation
    unit state
    PID/cgroup
    interface endpoint
    readiness
    representative test
    timestamp.

Do not produce giant evidence bundles for routine trivial checks.

======================================================================
112. SERVICE AND SECURITY
======================================================================

Every Service boundary is potentially an attack surface.

Review:

    callers
    IPC permissions
    input validation
    privilege
    filesystem access
    network
    device access
    secrets
    resource exhaustion
    deserialization
    subprocess execution.

Security should be part of Service design, not a later wrapper.

======================================================================
113. SERVICE AND SECRETS
======================================================================

Do not put secrets directly into:

    systemd unit files
    command-line arguments
    environment files committed to Git
    logs.

Use appropriate credential/secret mechanisms.

Investigate systemd credentials where relevant.

======================================================================
114. SERVICE TIMEOUTS
======================================================================

Service operations must not block callers forever.

Define timeout semantics at the appropriate interface.

Distinguish:

    activation timeout
    readiness timeout
    request timeout
    shutdown timeout.

Use monotonic timing for durations.

======================================================================
115. SERVICE CANCELLATION
======================================================================

Where requests may be long-running, investigate cancellation semantics.

Cancellation does not automatically imply:

    rollback.

Do not introduce asynchronous job protocols unless actual Service behavior
needs them.

======================================================================
116. SERVICE CONCURRENCY
======================================================================

Define concurrency based on Service responsibility.

Potential models:

    serial
    bounded parallel
    concurrent async
    worker pool.

Do not allow unbounded request/task creation.

Do not make a universal concurrency framework in this phase.

======================================================================
117. BACKPRESSURE
======================================================================

If a Service accepts work faster than it can process it:

    bound queues
    reject appropriately
    apply backpressure
    aggregate/coalesce where semantically valid.

Do not allow memory growth without bound.

======================================================================
118. IDEMPOTENCY
======================================================================

Service lifecycle/control requests such as:

    ensure_available

should normally be idempotent.

Individual exposed Operations may or may not be.

Document important differences.

Do not blindly retry non-idempotent work after connection failures.

======================================================================
119. STARTUP ORDER
======================================================================

Do not solve startup order with:

    sleep 5.

Use:

    native dependencies
    readiness
    socket activation
    explicit synchronization

where appropriate.

Timing is not dependency semantics.

======================================================================
120. BOOT
======================================================================

Do not enable every Rebuntu Service at boot.

Choose activation according to actual availability requirements.

On-demand activation should be preferred when it reduces unnecessary
persistent state without harming functionality.

======================================================================
121. SHUTDOWN
======================================================================

Service shutdown should account for dependency ordering and active work.

Use systemd's lifecycle model where applicable.

Do not create global custom shutdown scripts unless a real orchestration
requirement exists.

======================================================================
122. DEVELOPMENT MODE
======================================================================

Concrete Service implementations should be testable/developable without
requiring permanent system installation where practical.

Support:

    foreground execution
    temporary socket/config
    isolated state
    test clients.

The production supervisor remains systemd.

CORE PRINCIPLE
======================================================================

A Rebuntu Service is managed functionality.

A Daemon is one possible persistent process implementation of that
functionality.

A systemd .service file is one possible native deployment/lifecycle
mechanism.

A Module is a software structure.

An Operation is bounded capability.

A Script is an executable artifact.

A Task is bounded work.

A Job is a concrete execution.

A Schedule determines when work activates.

Automation determines when and why action should occur.

A Provider supplies an implementation.

An Interface defines how functionality is accessed.

DO NOT COLLAPSE THESE CONCEPTS.
