# Rebuntu — Phase 0.7
# Units Architecture, Taxonomy, Contracts, Composition & Execution Semantics

Phase 0.7 establishes the canonical Unit model for Rebuntu.

Earlier phases established:

    repository architecture
    structural taxonomy
    operational grammar
    Shell Sources
    Scripts
    Daemons
    Services

The concept of Unit has already appeared in the structural grammar, but it
must now be defined precisely enough to support future implementation.

This phase answers:

    WHAT IS A UNIT IN REBUNTU?

    WHAT MAKES SOMETHING A UNIT RATHER THAN A MODULE, OPERATION,
    TASK, JOB, SERVICE, SCRIPT OR WORKFLOW?

    WHICH UNIT TYPES ACTUALLY EXIST?

    WHAT IS A UNIT DEFINITION?

    WHAT IS A UNIT INSTANCE / EXECUTION?

    HOW ARE UNITS COMPOSED?

    HOW ARE THEY ACTIVATED?

    HOW ARE THEY VERIFIED?

    WHAT STATE MAY THEY OWN?

    HOW ARE THEY DISCOVERED?

    HOW SHOULD HISTORICAL REBUNTU "UNITS" MAP INTO THE MODERN SYSTEM?

The central principle is:

    UNIT = A BOUNDED, ADDRESSABLE, COMPOSABLE REBUNTU EXECUTION /
           OPERATIONAL DEFINITION WITH AN EXPLICIT CONTRACT

but this is only an initial hypothesis.

The phase must validate, refine or reject it.

Do not make Unit a generic synonym for "component".

======================================================================
2. DEFINE UNIT PRECISELY
======================================================================

Establish a canonical Rebuntu definition.

Initial hypothesis:

    UNIT

    A bounded, independently identifiable Rebuntu definition representing
    a discrete piece of executable or operational functionality that may
    be invoked, activated, composed, scheduled, inspected and verified.

A Unit should normally have:

    identity
    purpose
    inputs
    outputs
    contract
    execution semantics
    dependencies
    result semantics

Potentially:

    preconditions
    postconditions
    verification
    resource requirements
    safety characteristics
    idempotency
    reversibility

A Unit should NOT simply mean:

    any class
    any function
    any file
    any directory
    any process
    any systemd unit
    any Service.

======================================================================
3. UNIT != SYSTEMD UNIT
======================================================================

This distinction is mandatory.

A systemd Unit is a systemd-native configuration object such as:

    .service
    .socket
    .timer
    .path
    .mount
    .target

A Rebuntu Unit is part of Rebuntu's own operational ontology.

A Rebuntu Unit may be implemented or activated through systemd.

But:

    REBUNTU UNIT != SYSTEMD UNIT.

Use qualified terminology whenever ambiguity exists:

    Rebuntu Unit
    systemd Unit

Do not import systemd's complete Unit ontology into Rebuntu.

======================================================================
4. UNIT != MODULE
======================================================================

MODULE

    reusable structural software boundary.

UNIT

    bounded operational/executable definition.

A Module may contain or implement multiple Units.

A Unit may depend on several Modules.

Example:

    filesystem module
        may implement

            copy unit
            move unit
            inspect unit

if the architecture ultimately adopts such a model.

Do not create one Unit per Module automatically.

======================================================================
5. UNIT != SERVICE
======================================================================

A Service provides managed functionality with availability/lifecycle
semantics.

A Unit represents bounded executable/operational functionality.

A Service may expose Units.

A Unit may invoke a Service.

A Unit may execute entirely in-process with no Service.

Do not turn every Unit into a Service.

======================================================================
6. UNIT != DAEMON
======================================================================

A Daemon is a persistent process role.

A Unit is an operational definition.

A daemon may execute Units.

A Unit may be executed by a daemon-backed Service.

A Unit may also execute:

    directly
    in-process
    via Script
    via subprocess
    through systemd
    through an Adapter.

Process persistence is irrelevant to Unit identity.

======================================================================
7. UNIT != SCRIPT
======================================================================

A Script is an executable artifact.

A Unit is a semantic/operational entity.

Possible relations:

    Unit -> implemented by Python function
    Unit -> implemented by Script
    Unit -> implemented by native call
    Unit -> implemented through Service
    Unit -> composed from other Units

Do not classify Unit identity by file type.

======================================================================
8. UNIT != OPERATION
======================================================================

This distinction must be explicitly investigated.

Possible model A:

    Operation is one subtype of Unit.

Possible model B:

    Unit is the executable container/definition;
    Operation describes the semantic action exposed by it.

Possible model C:

    Operation and Unit are redundant concepts and one should disappear.

Do not assume the answer.

Test against real expected Rebuntu use cases.

A likely useful relation may be:

    Unit
        structural/execution definition

    Operation
        contract describing a system action/query

but this must be validated.

======================================================================
9. UNIT != TASK
======================================================================

Investigate carefully.

Candidate distinction:

    UNIT
        reusable executable definition

    TASK
        bounded specification of work to be performed

Example:

    Unit:
        filesystem.copy

    Task:
        copy /foo to /bar

This makes Task a parameterized work specification referring to a Unit.

But another model may be more coherent.

Do not freeze the distinction without testing.

======================================================================
10. UNIT != JOB
======================================================================

Candidate model:

    Unit
        reusable definition

    Task
        requested work specification

    Job
        concrete submitted/executing realization

Potential chain:

    Unit
        +
    parameters
        ->
    Task
        ->
    submit
        ->
    Job
        ->
    Execution
        ->
    Result

This is a hypothesis.

Evaluate whether all intermediate concepts are actually necessary.

Remove redundant layers.

======================================================================
11. UNIT != WORKFLOW
======================================================================

A Workflow represents composed execution.

A Unit may:

    be invoked by a Workflow;
    form a Step within a Workflow;
    potentially wrap a reusable Workflow if architecture explicitly
    supports composite Units.

Do not automatically make every Workflow a Unit.

Investigate whether:

    atomic Unit
    composite Unit

is useful terminology.

======================================================================
12. UNIT != PROCEDURE
======================================================================

Procedure likely describes:

    reusable method for accomplishing something.

A Unit may implement a Procedure.

A Procedure may describe multiple Units.

Or Procedure may be unnecessary in the runtime ontology.

Investigate.

Do not create parallel concepts without distinct semantics.

======================================================================
13. UNIT != ROUTINE
======================================================================

Routine may describe a reusable implementation-level sequence.

It may belong below Unit abstraction.

Potential relation:

    Unit
        public operational contract

    Routine
        implementation helper

If so, Routine should not become a first-class runtime Unit type.

Test historical Rebuntu usage.

======================================================================
14. UNIT != ACTION
======================================================================

Action may represent an individual effect occurring during execution.

Potential model:

    Unit
        ->
    Execution
        ->
    Actions
        ->
    Result

Do not expose every implementation action as a Unit.

Keep runtime detail separate from stable operational identity.

======================================================================
15. UNIT AS ADDRESSABLE CAPABILITY
======================================================================

Investigate whether one defining property of Unit should be:

    addressability.

Meaning:

    a Unit has a stable semantic identifier that can be referenced by:

        CLI
        Workflow
        Automation
        Schedule
        Service
        API
        configuration
        tests
        capability discovery

Example:

    filesystem.copy

rather than:

    call function copy_file_v2() in foo.py.

This could make Units a powerful boundary between architecture and
implementation.

Do not impose this if it conflicts with existing capability architecture.

======================================================================
16. UNIT AS COMPOSITION PRIMITIVE
======================================================================

A Unit should potentially be reusable inside larger execution structures.

Example:

    filesystem.copy
    filesystem.verify
    service.ensure_available

may be composed into a Workflow.

Therefore Unit contracts should avoid unnecessary dependence on:

    interactive shell
    global process state
    presentation layer
    implicit cwd
    hidden configuration
    mutable globals.

Design for composition.

======================================================================
17. UNIT TYPES
======================================================================

Investigate whether Unit has meaningful subtypes.

Candidates include:

    OperationUnit
    TaskUnit
    JobUnit
    ScheduleUnit
    CheckUnit
    VerificationUnit
    TransformationUnit
    QueryUnit
    CompositeUnit

Do NOT create these classes/directories automatically.

First determine whether Unit subtype taxonomy adds information.

A Unit type must correspond to genuinely different semantics, not naming
taste.

======================================================================
18. QUERY UNIT?
======================================================================

Read-only system inspection may deserve different semantics from mutation.

Potential distinction:

    Query
        returns information without intended system mutation.

    Operation
        may change system state.

If this distinction already exists elsewhere, integrate with it.

Do not introduce QueryUnit merely for symmetry.

======================================================================
19. CHECK UNIT?
======================================================================

A Check may evaluate a condition.

Example:

    service.active?
    path.exists?
    mount.writable?

Investigate whether Checks should be ordinary Operations with read-only
semantics, or a specialized Unit category.

Prefer minimal ontology.

======================================================================
20. VERIFICATION UNIT?
======================================================================

Verification is fundamental to Rebuntu.

But determine whether verification should be:

    Unit type

or:

    contract/function associated with another Unit.

Example:

    filesystem.copy
        execute
        then
        verify copy postcondition.

Creating a separate verification Unit may aid composition in some cases,
but may also fragment simple operations.

Investigate actual use cases.

======================================================================
21. TRANSFORMATION UNIT?
======================================================================

Pure transformations may be useful for:

    parsing
    text
    structured data
    conversion.

They may not need system-state semantics.

Determine whether Unit abstraction should support pure computation or only
system operations.

A general Unit model may support both while distinguishing side-effect
class.

Do not over-generalize prematurely.

======================================================================
22. UNIT SIDE-EFFECT MODEL
======================================================================

Define or reuse side-effect classification.

Potential classes:

    PURE
    READ_ONLY
    MUTATING
    PRIVILEGED
    DESTRUCTIVE

Do not necessarily make them mutually exclusive if semantics require
orthogonal attributes.

For example:

    privileged + read-only

is possible.

Prefer attributes over a rigid single enum if dimensions differ.

======================================================================
23. UNIT SAFETY CHARACTERISTICS
======================================================================

A Unit contract may eventually declare:

    mutates_system
    requires_privilege
    destructive
    reversible
    idempotent
    automation_safe
    interactive_only

Do not add metadata with no consumer.

But ensure the architecture can represent safety-relevant properties.

======================================================================
24. UNIT DEFINITION
======================================================================

Formalize UnitDefinition conceptually.

Possible components:

    identity
    description
    inputs
    outputs
    preconditions
    postconditions
    implementation/provider
    dependencies
    side effects
    resources
    timeout
    verification
    failure semantics

Do not create a giant mandatory schema.

Start with the smallest useful common contract.

======================================================================
25. UNIT INSTANCE / EXECUTION
======================================================================

Distinguish:

    UnitDefinition
        reusable definition

from:

    UnitExecution
        concrete execution of that Unit.

Possible execution data:

    execution ID
    unit ID
    parameters
    context
    start time
    end time
    state
    result
    evidence.

Do not store runtime execution state inside the static Unit definition.

======================================================================
26. UNIT INSTANCE != JOB
======================================================================

Explicitly resolve whether:

    UnitExecution

and:

    Job

are the same concept or distinct.

Possible model:

    Job
        scheduler/queue-facing submitted work

    Execution
        actual attempt to execute work.

Thus one Job might theoretically have multiple Execution attempts after
retry.

Example:

    Job 123
        Execution attempt 1 -> transient failure
        Execution attempt 2 -> success.

If this distinction adds value, preserve it.

If not, simplify.

======================================================================
27. EXECUTION ATTEMPT
======================================================================

Investigate whether retries require explicit Attempt semantics.

Potential:

    Job
        ->
    Attempt 1
        ->
    Attempt 2.

Do not create this abstraction until retry behavior requires it.

But avoid data models where retry silently overwrites previous evidence.

======================================================================
28. UNIT INPUTS
======================================================================

Unit input contracts should be explicit enough for:

    validation
    CLI/API use
    Workflow composition
    automation
    testing.

Prefer structured inputs.

Avoid undocumented `**kwargs` dictionaries as stable contracts.

Do not over-wrap trivial scalar values.

======================================================================
29. UNIT OUTPUTS
======================================================================

Distinguish:

    output data

from:

    execution result/status.

Example:

    filesystem.inspect

output:
    filesystem metadata.

result:
    SUCCESS.

verification:
    VERIFIED / not applicable.

evidence:
    native observations.

Do not collapse all output into stdout strings.

======================================================================
30. RESULT MODEL
======================================================================

Reuse Phase 0.2 semantics.

A Unit result may include:

    outcome
    output
    error
    verification
    evidence
    timing.

Do not create a second incompatible Result abstraction.

======================================================================
31. SUCCESS != VERIFIED
======================================================================

Maintain the fundamental distinction:

    execution succeeded

does not mean:

    intended postcondition was verified.

A mutating Unit should support states such as:

    outcome = SUCCESS
    verification = VERIFIED

or:

    outcome = SUCCESS
    verification = FAILED

or:

    outcome = SUCCESS
    verification = UNVERIFIED.

Do not collapse these into one boolean.

======================================================================
32. PRECONDITIONS
======================================================================

Unit contracts may define preconditions.

Examples:

    source exists
    service dependency available
    target device identity verified
    privilege available
    required provider present.

Preconditions should be evaluated before dangerous work where practical.

Do not confuse precondition failure with execution failure.

======================================================================
33. POSTCONDITIONS
======================================================================

Postconditions define what should be true after successful execution.

Examples:

    destination exists
    service available
    configuration validates
    mount established.

Verification should evaluate postconditions where appropriate.

This is stronger than checking exit status.

======================================================================
34. INVARIANTS
======================================================================

A Unit may need to preserve invariants.

Example:

    operation modifies firewall rule

while invariant:

    LAN SSH access remains available.

Do not implement global invariant machinery in Phase 0.7.

But Unit contracts should not prevent future invariant-aware execution.

======================================================================
35. IDEMPOTENCY
======================================================================

Unit definitions should be able to express whether repeating execution is:

    safe
    conditionally safe
    unsafe.

Potential categories:

    IDEMPOTENT
    CONDITIONALLY_IDEMPOTENT
    NON_IDEMPOTENT

Do not blindly retry Units without this knowledge.

======================================================================
36. REVERSIBILITY
======================================================================

A Unit may be:

    naturally reversible
    rollback-supported
    compensatable
    irreversible.

Do not pretend compensation is exact rollback.

This characteristic should influence automation and recovery.

======================================================================
37. DRY RUN / PLAN
======================================================================

For significant mutating Units, investigate separation:

    plan
        ->
    execute.

A plan may describe:

    intended changes
    affected resources
    preconditions
    risk
    required privilege.

Do not force a dry-run API onto trivial Units.

But destructive work should not require execution merely to discover what
would happen.

======================================================================
38. UNIT RESOURCES
======================================================================

A Unit may require resources:

    CPU
    memory
    GPU
    device
    filesystem path
    network
    Service
    lock
    privilege.

Resource requirements should be explicit where they affect execution.

Do not implement a full resource scheduler in this phase.

======================================================================
39. UNIT LOCKING
======================================================================

Some Units may require mutual exclusion.

Example:

    modifying the same package database
    mounting/unmounting same resource
    changing same configuration.

Do not encode locks as arbitrary marker files.

Use appropriate runtime/native synchronization.

Investigate whether lock requirements belong in Unit contracts.

======================================================================
40. UNIT DEPENDENCIES
======================================================================

Define dependency types carefully.

Potential examples:

    implementation dependency
    capability dependency
    Service dependency
    ordering dependency
    resource dependency
    data dependency.

Do not represent everything as a flat:

    depends_on = [...]

without semantics.

======================================================================
41. UNIT DEPENDENCY != WORKFLOW ORDER
======================================================================

Example:

    Unit B requires capability A

is different from:

    Step B occurs after Step A.

Dependency semantics and Workflow sequencing are separate.

Do not conflate them.

======================================================================
42. UNIT COMPOSITION
======================================================================

Investigate composition.

Possible patterns:

    Unit A output -> Unit B input

    Unit A + Unit B -> Composite Unit

    Workflow orchestrates A then B.

Determine when composition itself becomes:

    another Unit

versus:

    a Workflow.

A useful rule may be:

    simple reusable functional composition
        may become composite Unit

    execution topology / branching / retries / checkpoints
        belongs to Workflow.

Test this distinction.

======================================================================
43. ATOMIC VS COMPOSITE UNITS
======================================================================

Investigate terminology:

    Atomic Unit
    Composite Unit

Do not interpret "atomic" as transactionally atomic unless explicitly
defined.

Perhaps use:

    Primitive Unit
    Composite Unit

if clearer.

Avoid terminology likely to imply guarantees that do not exist.

======================================================================
44. UNIT GRANULARITY
======================================================================

Units should be neither enormous nor microscopic.

Too large:

    system_maintenance

containing 50 unrelated actions.

Too small:

    convert_one_string_to_lowercase

unless that really is a reusable domain capability.

A Unit should represent a meaningful reusable operational boundary.

Use actual consumers to validate granularity.

======================================================================
45. UNIT OWNERSHIP
======================================================================

Every Unit must have an architectural owner.

Ask:

    Which System/Module owns this Unit?

    Who exposes it?

    Who implements it?

    Who may call it?

    What domain does it affect?

Do not create a giant unrelated global Units dump.

======================================================================
46. PHYSICAL PLACEMENT
======================================================================

Explicitly decide where Units belong physically.

Earlier structural hypothesis may include:

    src/.../units/

with categories such as:

    tasks/
    jobs/
    schedules/

But Phase 0.7 must reevaluate this.

Possible models:

A)

    units/ is a first-class global structural area.

B)

    reusable Unit infrastructure lives in units/,
    concrete Units live near owning Modules.

C)

    concrete Units live entirely with owning Modules,
    and no central units/ implementation directory is needed.

D)

    units/ contains definitions/catalog only.

Evaluate and document.

Do not keep a central directory merely because Phase 0.1 proposed it.

======================================================================
47. OWNERSHIP LOCALITY
======================================================================

Strongly consider:

    shared Unit protocol/contracts
        central

    concrete Unit implementation
        near functional owner.

Example:

    units/
        contracts.py

but:

    filesystem/
        operations/
            copy.py

if this better preserves cohesion.

Do not centralize all functionality into:

    units/operations/

without considering domain ownership.

======================================================================
48. UNIT REGISTRY
======================================================================

Evaluate whether Unit discovery requires a registry.

Potential purposes:

    lookup stable Unit ID
    inspect contract
    discover capabilities
    resolve implementation/provider.

Do not introduce a registry without consumers.

If created:

    registry describes known definitions.

It must not become:

    global runtime state
    execution queue
    dependency injector
    service locator for everything.

======================================================================
49. UNIT CATALOG
======================================================================

Investigate whether Catalog differs from Registry.

Potential distinction:

    Catalog
        descriptive/searchable Unit definitions.

    Registry
        runtime mapping from Unit identity to executable implementation.

This may support future agent/capability discovery.

But retain only if actual distinction proves useful.

======================================================================
50. UNIT DISCOVERY
======================================================================

A future coding agent/runtime should be able to answer:

    Does Rebuntu already have a Unit that performs X?

Unit organization should therefore support:

    semantic search
    identifier search
    capability search
    contract inspection.

This directly supports:

    SEARCH BEFORE IMPLEMENTING.

Design discoverability deliberately.

======================================================================
51. UNIT IDENTIFIERS
======================================================================

Investigate stable names such as:

    filesystem.copy
    filesystem.inspect
    service.ensure_available
    text.normalize

or whatever namespace architecture ultimately establishes.

Identifiers should describe semantic capability, not implementation.

Avoid:

    copy_py_v2
    foo_handler
    unit_0042.

Do not over-design namespace depth.

======================================================================
52. UNIT VERSIONING
======================================================================

Do not version Unit identity casually.

During early Rebuntu development, fix bad internal contracts directly.

Version only when:

    compatibility
    persistence
    IPC
    external consumers

actually require it.

Do not create:

    filesystem.copy.v2

just because implementation changes.

======================================================================
53. UNIT PROVIDERS
======================================================================

A Unit may potentially have multiple implementations/providers.

Example:

    clipboard.copy

provider may depend on:

    Wayland
    X11
    desktop environment.

Or:

    package.install

may depend on package ecosystem.

Distinguish:

    stable Unit semantics

from:

    provider-specific execution.

Do not build a giant provider framework before concrete alternatives exist.

======================================================================
54. UNIT ADAPTERS
======================================================================

Adapters translate between stable Rebuntu semantics and native/external
interfaces.

A Unit may use:

    SystemdAdapter
    UdevAdapter
    PackageAdapter
    ClipboardAdapter

without exposing those details to callers.

Do not embed mechanism-specific shell pipelines directly into generic Unit
contracts when an adapter boundary already exists.

======================================================================
55. UNIT ACTIVATION
======================================================================

A Unit may be activated by:

    direct invocation
    Request
    Workflow
    Automation
    Schedule
    Service
    CLI
    Shell
    API
    event-derived Trigger.

Activation source should not change Unit semantics.

Do not create different Unit implementations for each caller.

======================================================================
56. DIRECT INVOCATION
======================================================================

Simple Units should be directly invokable where practical.

This improves:

    testing
    composition
    reuse
    debugging.

Do not require the full Rebuntu runtime for every pure/read-only Unit if a
clean direct call is sufficient.

======================================================================
57. ASYNC EXECUTION
======================================================================

Some Units may execute asynchronously.

Do not make async behavior part of Unit identity unless semantics require
it.

A caller may submit a Unit as a Job.

The same Unit might also support synchronous direct execution.

Separate:

    Unit semantics

from:

    execution mode.

======================================================================
58. TIMEOUT
======================================================================

Units interacting with:

    network
    device
    service
    subprocess
    filesystem

may require timeout semantics.

Define timeout at the correct layer.

Do not allow indefinite blocking where failure is plausible.

Use monotonic time for duration mechanics.

======================================================================
59. CANCELLATION
======================================================================

Investigate cancellation.

Some Units can be cancelled safely.

Some cannot.

Some may leave partial state.

Unit contracts should eventually be able to describe cancellation
semantics where relevant.

Do not promise safe cancellation universally.

======================================================================
60. RETRY
======================================================================

Retry belongs to execution policy, not necessarily Unit implementation.

A Unit may declare:

    retry-safe
    retry conditions
    idempotency characteristics.

Workflow/Job/Recovery logic may then decide whether to retry.

Do not hide uncontrolled retries inside arbitrary Units.

======================================================================
61. UNIT ERROR MODEL
======================================================================

Reuse the shared error/failure architecture.

Unit execution may fail because of:

    invalid input
    failed precondition
    unavailable dependency
    permission
    timeout
    external system failure
    implementation error
    verification failure.

Do not reduce all failures to generic exception strings.

======================================================================
62. ERROR != OUTCOME
======================================================================

Preserve:

    Error
        diagnostic information.

    Outcome
        semantic execution result.

One failed execution may contain several errors/evidence items.

A recoverable error may not result in final failure.

======================================================================
63. UNIT STATE
======================================================================

Avoid stateful Unit definitions.

Static Unit definition should normally be immutable or effectively
immutable.

Runtime state belongs to:

    Execution
    Job
    WorkflowRun
    Service
    authoritative native source.

Do not use Unit objects as global mutable runtime containers.

======================================================================
64. UNIT CONTEXT
======================================================================

Execution may receive Context.

Potential Context:

    machine
    environment
    active profile
    caller
    current resources
    execution identity.

Do not make Unit behavior depend on invisible global Context.

Pass required context explicitly where practical.

======================================================================
65. UNIT CONFIGURATION
======================================================================

Distinguish:

    Unit definition
    Unit parameters
    Configuration
    Context.

Example:

    configuration:
        default copy verification mode

    parameters:
        source=/a
        destination=/b

    context:
        active machine/session environment.

Do not merge these into one untyped dictionary.

======================================================================
66. UNIT SECURITY
======================================================================

Units may become a central execution boundary.

Therefore consider:

    authorization
    privilege
    path validation
    command injection
    target identity
    destructive effects
    resource access.

Do not assume internal callers are automatically authorized for every Unit.

======================================================================
67. PRIVILEGED UNITS
======================================================================

Do not run all Unit execution with root privileges because some Units need
privilege.

Prefer:

    unprivileged main runtime

plus:

    native permissions
    polkit
    Linux capabilities
    narrow privileged Service/helper

where justified.

Privilege should be explicit in Unit metadata/contract where useful.

======================================================================
68. DESTRUCTIVE UNITS
======================================================================

A destructive Unit must require stronger safety.

Potential requirements:

    target verification
    explicit authorization
    plan/dry-run
    backup/checkpoint
    invariant checks
    postcondition verification.

Do not provide generic:

    execute_any_shell_command_as_root

as a Unit.

======================================================================
69. SHELL UNIT BOUNDARY
======================================================================

Shell Sources may expose ergonomic functions that invoke Units.

Example:

    install foo

may map to:

    package.install(target="foo")

Unit semantics belong below the shell UX.

Do not implement canonical Units as shell-only functions if structured
Python/runtime implementation is more appropriate.

======================================================================
70. SCRIPT UNIT BOUNDARY
======================================================================

A Script may implement a Unit.

But substantial Unit logic should not automatically live in scripts/.

If reusable structured behavior dominates:

    move it into canonical Python/native implementation

and keep Script thin.

======================================================================
71. SERVICE UNIT BOUNDARY
======================================================================

A Service may expose Units through IPC.

Example:

    Semantic Service
        exposes Units:
            semantic.classify
            semantic.extract
            semantic.summarize

or those may instead be Service methods/Operations.

Phase 0.7 must determine the cleaner model.

Do not globally register every Service RPC as a Unit without reason.

======================================================================
72. DAEMON UNIT BOUNDARY
======================================================================

Daemons execute behavior.

They do not own Unit ontology automatically.

A daemon-backed Service may resolve incoming requests to Units.

But Unit implementation should not depend on being hosted in one specific
daemon unless unavoidable.

======================================================================
73. SCHEDULED UNITS
======================================================================

A Schedule may reference:

    Unit
    Task
    Workflow
    Service activation

depending on the final ontology.

Phase 0.7 should clarify the preferred scheduling target.

A clean model may be:

    Schedule
        creates/submits
    Task/Job
        targeting
    Unit

CORE PRINCIPLE
======================================================================

A Rebuntu Unit must represent a meaningful bounded operational abstraction.

It must NOT mean:

    arbitrary function
    arbitrary file
    arbitrary class
    arbitrary process
    arbitrary system component.

A good Unit is:

    IDENTIFIABLE
    BOUNDED
    COMPOSABLE
    DISCOVERABLE
    CONTRACTUAL
    TESTABLE
    VERIFIABLE

where those properties are relevant to its behavior.

Do not preserve the historical Unit model merely because the name existed.

Use historical Rebuntu to discover requirements.

Use modern architecture to separate concerns.

If Task, Job and Schedule do not actually belong under Unit:

    MOVE THEM.

If Unit and Operation are redundant:

    SIMPLIFY.

If Unit and Capability overlap:

    RESOLVE THE OVERLAP.

If a function does not need architectural identity:

    LEAVE IT AS A FUNCTION.

If functionality requires availability/lifecycle:

    IT MAY BE A SERVICE.

If it represents composed control flow:

    IT MAY BE A WORKFLOW.

If it is standalone executable packaging:

    IT MAY BE A SCRIPT.

If it is concrete submitted work:

    IT MAY BE A JOB.

DO NOT MAKE UNIT THE PLACE WHERE UNCLEAR CONCEPTS GO.

UNIT SHOULD REDUCE AMBIGUITY, NOT ABSORB IT.
