# Rebuntu — Phase 0.8 — Tasks, Jobs, Executions & Attempts
## Work Identity and Runtime Realization

## Objective

Establish Rebuntu's canonical model for bounded work and its runtime
realization.

Phase 0.7 defines Units. Phase 0.8 must determine what happens when
reusable system functionality becomes concrete work.

Starting hypothesis:

    Unit
      ↓
    Task
      ↓
    Job
      ↓
    Execution
      ↓
    Attempt
      ↓
    Result

This is a hypothesis to investigate, not an architecture to enforce.

The central question is:

    What is the difference between:

        - something Rebuntu can execute,
        - work Rebuntu has been asked to perform,
        - a concrete submitted or scheduled realization of that work,
        - an actual runtime execution,
        - one particular attempt to execute it?

The phase must prevent the following concepts from becoming interchangeable:

    Unit
    Task
    Job
    Execution
    Attempt
    Instance
    Process
    Operation
    Procedure
    Routine
    Action
    Workflow
    Script
    Service
    Daemon
    Request
    Schedule
    Result

This is primarily an architecture, archaeology, vocabulary, contracts,
and skeleton phase.

Do not build a large task scheduler, job server, queue framework,
workflow engine, distributed execution system, or generic orchestration
platform.

# 3. Establish the Work Ontology

Investigate and define the smallest useful ontology for work.

The following are candidate definitions.


## Unit

A reusable identifiable executable or compositional definition.

A Unit should describe something that CAN participate in execution.

A Unit is not necessarily currently requested or running.


## Task

A bounded specification of work to be performed.

A Task answers approximately:

    WHAT work is requested?

It may reference one or more Units, Operations, Procedures or other
capabilities.

A Task should not automatically mean:

    process
    thread
    shell script
    scheduled item
    running work


## Job

A concrete submitted, accepted, queued, scheduled or otherwise managed
realization of work.

A Job answers approximately:

    WHICH concrete piece of requested work is being managed?

Candidate relation:

    Task = work specification
    Job  = managed realization of that work

But test whether this distinction actually earns its complexity.


## Execution

The runtime occurrence of performing work.

An Execution answers:

    WHAT is happening or happened at runtime?

Do not confuse the execution record with the operating-system process
used to implement it.


## Attempt

One attempt to perform an Execution or Job.

This distinction becomes useful when retry exists.

For example:

    Task T
        ↓
    Job J
        ↓
    Attempt 1 → FAILED
        ↓
    Attempt 2 → FAILED
        ↓
    Attempt 3 → SUCCESS

Determine whether Execution contains Attempts, whether Attempt is itself
an Execution, or whether another model is cleaner.

Do not force the example above if implementation evidence suggests a
better model.


# 4. Task != Job

Resolve this distinction explicitly.

Potential model:

    Task
        declarative specification of bounded work

    Job
        managed realization of a Task

Example:

    Task:
        verify filesystem integrity

    Job:
        verification requested for /dev/nvme0n1p2 at 03:14

A Task may therefore be reusable while Jobs are concrete.

But investigate whether Rebuntu actually requires both abstractions.

Do not retain two nouns merely because conventional software systems
often have both.


# 5. Job != Execution

A Job may exist before execution begins.

Possible lifecycle:

    CREATED
      ↓
    ACCEPTED
      ↓
    QUEUED
      ↓
    READY
      ↓
    RUNNING
      ↓
    COMPLETED

while Execution represents actual runtime activity.

This potentially allows:

    job exists
    execution does not yet exist

or:

    one job
    multiple execution attempts

Determine whether this is useful for Rebuntu.


# 6. Execution != Process

This distinction is mandatory.

A Rebuntu execution may be implemented by:

    Python function call
    coroutine
    thread
    subprocess
    external command
    systemd unit
    daemon request
    D-Bus call
    Unix socket request
    native Linux operation
    combination of the above

Therefore:

    EXECUTION != PROCESS

A process is an operating-system runtime entity.

An Execution is a Rebuntu semantic/runtime entity.

Do not create unnecessary processes merely because work has a separate
semantic identity.


# 7. Task != Operation

Phase 0.10 will define Operations in detail, but Phase 0.8 must establish
the boundary.

Starting hypothesis:

    Task
        describes bounded work requested in a particular context

    Operation
        describes a reusable contractual capability for querying or
        changing system state

Example:

    Operation:
        install software

    Task:
        install package X

Possible realization:

    Task
        ↓
    Operation invocation
        ↓
    Job
        ↓
    Execution

Again, investigate rather than enforce.


# 8. Task != Workflow

A Task may invoke a Workflow.

A Workflow may contain Tasks.

Neither relationship should automatically make them equivalent.

Potential example:

    Task:
        prepare machine for gaming

    Workflow:
        Phase 1 — inspect
        Phase 2 — configure
        Phase 3 — activate
        Phase 4 — verify

The workflow describes HOW composed work progresses.

The task describes WHAT bounded work has been requested.


# 9. Task != Script

A Script is an executable artifact.

A Task is a work specification.

Possible relation:

    Task
        ↓
    Executor
        ↓
    Script

but a Task may equally invoke:

    Python
    native API
    D-Bus
    systemd
    kernel interface
    Service
    Operation
    Workflow

Never classify Tasks by implementation language or file extension.


# 10. Task != Service / Daemon

A Service represents managed functionality.

A Daemon represents a persistent process role.

A Task represents bounded work.

A service may accept Tasks.

A daemon may execute Tasks.

A Task may request a Service.

These facts do not collapse the concepts.


# 11. Task != Request

Investigate:

    Request
        asks something of a system/interface

    Task
        represents work accepted or formulated for execution

Potential flow:

    Request
        ↓
    validation / normalization
        ↓
    Task
        ↓
    Job
        ↓
    Execution

But not every Request needs to create a Task.

For example, a simple state query may be served immediately.

Do not create Task objects for every function call merely for conceptual
purity.


# 12. Task != Schedule

A Task describes work.

A Schedule describes temporal activation.

Therefore prefer composition:

    Task + Schedule

rather than making scheduled work a special kind of Task.

Potential flow:

    Schedule
       ↓
    Activation
       ↓
    Task
       ↓
    Job

Phase 0.9 will define temporal semantics in detail.


# 13. Specification vs Runtime Instance

Apply the Phase 0.x rule:

    SPECIFICATION != INSTANCE

Candidate relationships:

    UnitDefinition
        ↓
    TaskSpecification
        ↓
    Job
        ↓
    Execution
        ↓
    Attempt

But avoid suffix-heavy enterprise vocabulary unless it genuinely improves
precision.

The public vocabulary should remain compact.

Prefer:

    Task
    Job
    Execution

over gratuitous names such as:

    TaskDefinitionDescriptor
    JobExecutionContextObject
    RuntimeExecutionSpecification

unless a real technical distinction requires them.


# 14. Identity

Determine what requires stable identity.

Potential identifiers:

    unit_id
    task_id
    job_id
    execution_id
    attempt_id

Do not create IDs merely because an object exists.

Ask:

    Does another component need to refer to it later?
    Can it outlive the current call?
    Can it be queried?
    Can it be cancelled?
    Can it be retried?
    Is evidence associated with it?
    Does it require correlation across logs/events?
    Can multiple instances coexist?

Use stable semantic identifiers where useful.

Do not use PID as Rebuntu identity.


# 15. Parentage and Correlation

Work may form relationships such as:

    parent
    child
    origin
    requested_by
    triggered_by
    scheduled_by
    retry_of
    continuation_of
    dependency
    produces
    consumes

Do not turn all relationships into one generic "parent".

Preserve causal meaning where useful.

Example:

    event
      ↓ triggered_by
    automation
      ↓ creates
    task
      ↓ realizes
    job
      ↓ executes_as
    execution
      ↓ attempt
    attempt

The exact relation vocabulary must be derived and normalized.


# 16. Lifecycle

Do not define one giant lifecycle shared by every concept.

Task lifecycle, Job lifecycle and Execution lifecycle may differ.

Candidate Task lifecycle:

    CREATED
    ACCEPTED
    CANCELLED
    COMPLETED

Candidate Job lifecycle:

    CREATED
    QUEUED
    READY
    RUNNING
    COMPLETED
    FAILED
    CANCELLED

Candidate Attempt lifecycle:

    CREATED
    STARTING
    RUNNING
    FINISHING
    FINISHED

These are examples only.

Derive the minimum meaningful lifecycle for each abstraction.

    state = "..."

Historical Rebuntu vocabulary includes concepts such as:

    start
    stop
    wait
    pause
    resume
    freeze

    done
    busy
    ready
    unlocked
    locked
    released
    waiting
    running
    sleeping
    resting
    idling
    zombie
    failed
    jammed
    enabled
    disabled
    paused
    resumed
    escaped
    exited
    continued
    completed
    finished

Treat "exitted" in historical material as a spelling error and normalize
it to:

    exited

Do not assume all terms belong to one enum.

Investigate orthogonal axes such as:

    LifecycleState
    ActivityState
    ControlState
    AvailabilityState
    ReadinessState
    HealthState
    OutcomeState

For example, a runtime entity could simultaneously be:

    lifecycle = RUNNING

    ENABLED_RUNNING_WAITING_READY_HEALTHY


# 18. Jammed

Preserve and formally investigate the historical concept:

    jammed

It may represent an important distinction:

    FAILED
        work has reached a failure outcome

    JAMMED
        work remains nominally alive but measurable forward progress
        has ceased

Determine whether this belongs to:

    ActivityState
    HealthState
    ProgressState
    ExecutionCondition

or another appropriate axis.

Do not equate:

    jammed
    waiting
    blocked
    failed

without analysis.


# 19. Zombie

Linux already has a precise process concept:

    zombie process / process state Z

Do not casually redefine "zombie".

If Rebuntu uses ZOMBIE for process state, align it with Linux semantics.

If historical Rebuntu used "zombie" for a broader concept such as
"registered but no longer functioning", either:

    - define the broader concept under another name, or
    - explicitly distinguish it from Linux ProcessState.ZOMBIE.


# 20. Progress

Investigate whether bounded work needs explicit progress semantics.

Possible forms:

    unknown
    indeterminate
    current / total
    percentage
    stage
    units completed
    last_progress_at

Do not assume every Task supports progress.

Progress must reflect real evidence.

Never fabricate percentages for work whose progress cannot be measured.


# 21. Waiting and Blocking

Distinguish reasons why execution is not currently progressing.

Candidates:

    waiting_for_input
    waiting_for_dependency
    waiting_for_resource
    waiting_for_lock
    waiting_for_event
    waiting_for_time
    rate_limited
    paused
    blocked
    jammed

Avoid creating dozens of states if structured metadata can represent the
reason more cleanly.

For example:

    activity = WAITING
    waiting_for = RESOURCE
    resource = "storage:nvme0"


# 22. Pause / Resume / Freeze / Continue

Define these carefully.

They are not necessarily synonyms.

Potential distinctions:

    pause
        cooperative suspension at a safe boundary

    resume
        continue previously paused work

    freeze
        externally prevent execution/progress

    continue
        resume forward progression after interruption

Investigate native Linux mappings where appropriate:

    SIGSTOP
    SIGCONT
    cgroup freezer
    systemd controls

Do not expose native mechanisms as universal semantics if their behavior
does not match Rebuntu's contract.


# 23. Cancellation

Cancellation must be explicit.

Distinguish:

    request cancellation
    cancellation accepted
    cancellation in progress
    cancelled
    force terminated

Cancellation is not automatically failure.

Investigate cooperative cancellation first.

For destructive or state-changing work, cancellation may require:

    checkpoint
    cleanup
    compensation
    rollback
    verification

Do not promise safe cancellation when the underlying operation cannot
provide it.


# 24. Timeout

Timeout is a control condition, not necessarily an outcome by itself.

Possible semantics:

    timeout detected
        ↓
    cancellation requested
        ↓
    grace period
        ↓
    termination
        ↓
    resulting outcome

Distinguish:

    execution timeout
    inactivity timeout
    startup timeout
    dependency timeout
    IPC timeout

Phase 0.9 will generalize temporal semantics.


# 25. Retry and Attempts

Retry is a major reason to distinguish Job/Execution/Attempt.

Example:

    Job J42
        Attempt 1 → timeout
        Attempt 2 → dependency failure
        Attempt 3 → verified success

The final Job result should preserve attempt history.

Do not overwrite previous failure evidence merely because a later retry
succeeds.

Determine:

    retry eligibility
    maximum attempts
    backoff ownership
    retry reason
    attempt correlation
    final outcome

Do not implement a generic retry engine unless needed for the skeleton.


# 26. Idempotency

Tasks and Jobs should not pretend to be idempotent merely because they
can be retried.

Idempotency belongs primarily to the underlying Operation/capability
contract.

Before automatic retry, Rebuntu must be able to determine whether retry
is safe.

Possible classifications:

    IDEMPOTENT
    CONDITIONALLY_IDEMPOTENT
    NON_IDEMPOTENT
    UNKNOWN

UNKNOWN must not silently mean safe.


# 27. Result and Outcome

Phase 0.17 will formalize Results and Evidence in depth, but Phase 0.8
needs a minimal execution result contract.

Distinguish:

    runtime completion
    operation success
    verification success

For example:

    process_exit = 0
    execution = FINISHED
    operation_result = SUCCESS
    verification = FAILED

These facts can coexist.

Therefore:

    EXIT 0 != VERIFIED SUCCESS


# 28. Evidence

Every meaningful managed execution should be able to associate evidence
with its result.

Potential evidence:

    exit status
    stdout/stderr references
    journal entries
    timestamps
    verification results
    changed state
    before/after observations
    generated artifacts
    native subsystem state

Do not stuff all evidence into the Job object itself.

Define relationships and ownership.


# 29. Logs and Correlation

Logs for managed work should support correlation using semantic IDs where
appropriate.

For example:

    task_id
    job_id
    execution_id
    attempt_id

But avoid noisy metadata proliferation.

Use journald structured fields where appropriate.

Do not invent a parallel logging infrastructure when journald already
provides the required transport/storage.


# 30. Queue Semantics

Investigate whether Queue is required as a foundational abstraction.

Do not assume:

    Jobs → Queue

Some work can execute immediately.

Some work may be activated by systemd.

Some services may maintain their own bounded queues.

Some operations should reject rather than queue.

If a common queue abstraction is not currently justified, document it as
a candidate rather than implementing it.


# 31. Priority

Likewise, do not create an elaborate priority system prematurely.

Investigate possible need for:

    priority
    urgency
    importance
    fairness
    resource priority

Do not collapse them automatically.

Native Linux mechanisms may include:

    nice
    scheduler policy
    ionice
    cgroup weights

Semantic Rebuntu priority should not simply mirror one kernel number.


# 32. Dependencies

A Task or Job may depend on other work.

Distinguish at least conceptually:

    data dependency
    completion dependency
    success dependency
    readiness dependency
    resource dependency
    ordering dependency

Do not create dependency graphs where a simple sequential call suffices.

Do not encode ordering using sleeps.


# 33. Concurrency

Determine where concurrency belongs.

Possible forms:

    multiple Jobs concurrently
    multiple Executions for one Workflow
    multiple Attempts prohibited
    shared resource serialization
    parallel independent work

Concurrency policy must respect:

    locks
    resources
    safety
    operation contracts
    system limits

Do not build a generic concurrency framework in this phase.


# 34. Locks

Work may need locking, but:

    LOCK != STATE FILE

Prefer native mechanisms where appropriate:

    flock
    systemd serialization/dependencies
    filesystem locks
    database transaction
    application-level synchronization

Historical .lock files are archaeology evidence, not a default modern
implementation.

A stale marker file must not permanently define runtime truth.


# 35. Persistence

Determine which work concepts need persistence.

Possible policy:

    Task definition
        persistent if reusable/configured

    Job
        persistent if asynchronous, scheduled, inspectable or recoverable

    Execution
        runtime record

    Attempt
        retained as evidence/history where useful

Do not persist everything automatically.

Persistence creates lifecycle, migration, cleanup and consistency
obligations.


# 36. Crash Recovery

Ask what happens when Rebuntu itself crashes while work is running.

Possible classifications after restart:

    completed
    still_running
    interrupted
    unknown
    orphaned
    recoverable
    requires_verification

Never infer success merely because the controlling process disappeared.

Native process/service state should be inspected where applicable.


# 37. Orphaned Work

Investigate the concept of orphaned managed work.

Examples:

    Rebuntu crashed but child process survived
    systemd unit continues running
    external command completed but result was not recorded
    daemon accepted work before controller restarted

Reconciliation may be preferable to blindly restarting work.


# 38. Resource Requirements

Tasks/Jobs may declare requirements such as:

    CPU
    memory
    storage
    network
    GPU
    device
    service
    privilege
    lock

Do not build a cluster resource scheduler.

The immediate goal is to make resource requirements representable and
inspectable.

Use systemd/cgroups/native Linux resource controls where appropriate.


# 39. Privilege

Privilege belongs to the work contract.

A Task should not casually call sudo internally.

Determine:

    required privilege
    requesting identity
    executing identity
    authorization
    elevation mechanism

Prefer:

    systemd
    polkit
    Linux capabilities
    narrow privileged helpers

over broad hidden sudo.


# 40. Environment and Context

An Execution may require:

    environment variables
    working directory
    user/session
    host
    profile
    configuration
    filesystem namespace
    service context

Distinguish execution Context from global Environment.

Do not capture the entire process environment blindly as persistent
state, especially secrets.


# 41. Inputs and Outputs

Task/Job contracts should support explicit inputs and outputs.

Inputs may include:

    arguments
    structured payload
    paths
    references
    stdin
    artifacts
    context

Outputs may include:

    Result
    structured data
    artifacts
    stdout
    state changes
    Evidence

Do not use stdout as the only universal result representation.


# 42. Shell Integration

Eventually the Rebuntu Shell should be able to express bounded work
naturally.

Examples:

    install firefox
    backup home
    verify mount
    inspect gpu

The shell should not need to expose Task/Job/Execution vocabulary for
ordinary synchronous use.

Advanced usage may eventually support:

    submit
    jobs
    status
    wait
    cancel

but do not consume valuable top-level shell verbs without checking the
Shell Verb Dictionary and native command namespace first.

Before proposing any shell verb:

    command -v <verb>
    type -a <verb>

Respect native shell/Linux commands.


# 43. "run" Is a High-Value Verb

Historical namespace inspection showed that:

    run

is currently free in the user's shell environment.

Treat it as a high-value reserved candidate.

Do not casually assign "run" to an arbitrary helper during this phase.

Investigate whether it should eventually represent Rebuntu's generic
explicit execution entry point.

Do not implement that decision prematurely.


# 44. Predicate Vocabulary

Preserve the emerging distinction between imperative verbs and state
predicates.

Examples:

    start       → running
    install     → installed
    enable      → enabled
    pause       → paused
    resume      → resumed
    lock        → locked
    unlock      → unlocked

Do not force grammatical symmetry where semantics do not justify it.

Do not create meaningless predicates merely to complete naming pairs.


# 45. Native Linux Mapping

For every runtime concept, investigate the relevant Linux mechanism.

Examples:

    Process identity       → PID / pidfd
    Process observation    → procfs
    Process supervision    → systemd
    Signals                → signal / signalfd
    Waiting                → waitpid / pidfd / event loop
    Stop/continue          → SIGSTOP / SIGCONT
    Freeze                 → cgroup freezer
    Resource control       → cgroups
    Scheduling             → systemd timers / kernel clocks
    Locking                → flock / native synchronization
    Logging                → journald
    Service execution      → systemd
    Async IPC              → Unix sockets / D-Bus / native IPC

Use the lowest appropriate native abstraction.

Understand what lies beneath it.

Do not emulate Linux unnecessarily.


# 46. PID Safety

Never use PID alone as durable identity.

PIDs are reused.

Where process identity matters across time, investigate:

    pidfd
    systemd unit identity
    process start time
    cgroup identity
    execution correlation metadata

Do not build fragile ps|grep process ownership logic.


# 47. Runtime Records

If runtime record structures are introduced, keep them small and useful.

Potential information:

    identity
    originating task/job
    timestamps
    lifecycle
    current activity
    implementation reference
    result
    evidence references

Do not create giant universal context objects.


# 48. Serialization

If Task/Job structures need serialization:

    use explicit schemas
    validate inputs
    version durable formats where necessary
    avoid Python pickle for untrusted or durable IPC/state

Do not introduce schema complexity without a consumer.


# 49. Public vs Internal Concepts

Not every internal runtime distinction belongs in the public shell/API.

For example:

    install firefox

may internally create:

    Request
    Task
    Job
    Execution
    Attempt
    Result
    Evidence

without forcing the user to know any of those nouns.

Architecture precision should reduce user complexity, not export it.


# 50. Physical Repository Placement

Do not assume that because Task and Job are concepts they need:

    src/tasks/
    src/jobs/
    src/executions/
    src/attempts/

Explicitly evaluate placement.

Possible outcomes include:

A. dedicated runtime/work package;

B. contracts/types near core runtime;

C. definitions owned by Units/Operations and runtime records owned by
   execution infrastructure;

D. no dedicated directories until concrete implementations justify them.

Prefer semantic ownership and discoverability over ontology-shaped
directory proliferation.

HAVING A CONCEPT != NEEDING A DIRECTORY.


# 51. Class Proliferation

Likewise:

    Task
    Job
    Execution
    Attempt

do not automatically require four Python classes.

A dataclass, protocol, enum, record, schema or ordinary function may be
sufficient.

Use the smallest representation that preserves the required semantics.

HAVING A NOUN != NEEDING A CLASS.


# 52. Manager Proliferation

Do not automatically create:

    TaskManager
    JobManager
    ExecutionManager
    AttemptManager
    QueueManager

Determine the actual responsibility first.

A generic "Manager" often hides unclear ownership.

Prefer precise responsibilities such as:

    Executor
    Dispatcher
    Registry
    Resolver
    Store
    Scheduler

only where those responsibilities genuinely exist.


# 53. No Shadow systemd

Do not build a generic process supervisor.

systemd already handles:

    process lifecycle
    service supervision
    restart policy
    dependencies
    resource control
    timers
    activation
    cgroups
    logging integration

Rebuntu should add semantic work identity, composition, contracts,
verification and evidence where useful.

It must not become another init system.


# 54. No Premature Distributed Architecture

Rebuntu is currently a local operating environment.

Do not introduce:

    distributed queues
    worker clusters
    consensus
    leases
    remote orchestration
    service mesh
    Kubernetes-style controllers
    distributed tracing infrastructure

unless a concrete current requirement proves their necessity.

Design clean local contracts that could evolve later without implementing
distributed machinery now.

    historical .stop
        → desired control state / cancellation request / obsolete

Do not preserve historical names merely because they existed.


# 59. Architecture Pressure Tests

Before finishing, test the ontology against realistic scenarios.


## Scenario A — synchronous shell command

    install firefox

Can Rebuntu execute this without forcing unnecessary Job persistence?


## Scenario B — asynchronous work

    start a long filesystem verification and return control to the user

Can it be queried and cancelled later?


## Scenario C — retry

An operation fails twice and succeeds on the third attempt.

Can Rebuntu preserve all three attempts and final verification?


## Scenario D — system restart

Rebuntu restarts while a systemd-backed Job is still running.

Can runtime truth be rediscovered without trusting stale state?


## Scenario E — workflow

A workflow contains several pieces of bounded work.

Are Workflow, Task and Job still clearly distinct?


## Scenario F — daemon request

A persistent Service receives a request and performs bounded work.

Does that work require a new process? It should not automatically.


## Scenario G — jammed execution

The process remains alive but no measurable progress occurs.

Can Rebuntu represent this without calling it FAILED?


## Scenario H — paused work

Work is paused and later resumed.

Can lifecycle, activity and control state remain distinct?


## Scenario I — verified failure

Execution exits successfully but postcondition verification fails.

Can the result represent this honestly?


## Scenario J — native systemd work

A systemd unit performs the actual execution.

Can Rebuntu track semantic work without replacing systemd supervision?

# 61. Completion Criteria

Phase 0.8 is complete when:

1. Unit, Task, Job, Execution and Attempt have explicit meanings.

2. Their relationships are documented.

3. Task != Job is either justified or deliberately collapsed.

4. Job != Execution is either justified or deliberately collapsed.

5. Execution != Process is explicit and enforced architecturally.

6. Retry/Attempt semantics are coherent.

7. cancellation and timeout have defined conceptual places.

10. "exitted" has been normalized to "exited".

12. zombie does not conflict ambiguously with Linux process semantics.

13. persistence boundaries have been considered.

14. crash/restart implications have been considered.

15. Linux-native mechanisms have been mapped where relevant.

17. no directory/class/manager proliferation occurred merely to mirror
    vocabulary.

# Core Principle

Rebuntu must distinguish:

    WHAT CAN BE DONE
        Unit / capability

    WHAT WORK IS REQUESTED
        Task

    WHAT CONCRETE WORK IS BEING MANAGED
        Job

    WHAT ACTUALLY HAPPENS AT RUNTIME
        Execution

    WHICH TRY PERFORMED IT
        Attempt

    WHAT THE OPERATING SYSTEM RUNS
        Process / thread / systemd unit / native mechanism

These are different dimensions unless implementation evidence proves
that a distinction provides no value.


# Final Rule

DO NOT CREATE ABSTRACTIONS BECAUSE OTHER FRAMEWORKS HAVE THEM.

DO NOT TURN EVERY FUNCTION CALL INTO A TASK.

DO NOT TURN EVERY TASK INTO A PERSISTED JOB.

DO NOT TURN EVERY JOB INTO A PROCESS.

DO NOT TURN EVERY PROCESS INTO A DAEMON.

DO NOT TURN EVERY RETRY INTO A NEW JOB.

DO NOT BUILD A QUEUE BECAUSE JOBS EXIST.

DO NOT BUILD A SCHEDULER BECAUSE TASKS EXIST.

DO NOT BUILD ANOTHER SYSTEMD.

SEARCH BEFORE IMPLEMENTING.

USE NATIVE LINUX MECHANISMS WHERE THEY ALREADY SOLVE THE PROBLEM.

PRESERVE SEMANTIC IDENTITY WITHOUT FORCING PROCESS IDENTITY.

PRESERVE ATTEMPT HISTORY WHEN IT MATTERS.

KEEP STATE AXES ORTHOGONAL.

KEEP BOUNDED WORK BOUNDED.

MAKE EXECUTION OBSERVABLE.

MAKE RESULTS EXPLICIT.

MAKE FAILURE HONEST.

MAKE RETRIES TRACEABLE.

MAKE THE SIMPLE SYNCHRONOUS CASE SIMPLE.
