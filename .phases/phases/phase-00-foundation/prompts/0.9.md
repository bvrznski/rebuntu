# Rebuntu — Phase 0.9 — Scheduling & Temporal Grammar
## Time, Activation, Deadlines, Waiting, Recurrence and Native Linux Temporal Semantics

## Objective

Establish Rebuntu's canonical architecture and vocabulary for TIME.

Phase 0.8 defines bounded work and its runtime realization:

    Unit
    Task
    Job
    Execution
    Attempt

Phase 0.9 must determine how time relates to those entities without
making time an accidental property of Tasks, Jobs, Services, Daemons,
Automatons or shell scripts.

The central principle is:

    WORK != TIME

A Task describes work.

A Schedule describes when work should become eligible for activation.

A Timeout constrains how long something may take.

A Deadline defines a temporal boundary.

A Delay postpones something.

An Interval measures separation between events.

A Duration measures elapsed time.

A Retry policy may use temporal backoff.

A Timer is a mechanism.

These concepts must not collapse into one generic "time" field.

Starting conceptual model:

    Temporal Specification
            |
            v
        Activation
            |
            v
           Work

For scheduled work:

    Schedule
       |
       v
    Activation
       |
       v
      Task
       |
       v
       Job
       |
       v
    Execution

This is a hypothesis to investigate, not an architecture to impose.

This phase is primarily architecture, archaeology, vocabulary,
contracts, native-Linux mapping, skeleton work and tests.

DO NOT build a giant scheduler.

# 4. Time != Schedule

Time is a dimension.

Schedule is a specification describing temporal activation.

Do not use "schedule" as a generic container for all temporal
information.

For example:

    created_at
    deadline
    timeout
    schedule

represent different concepts.


# 5. Schedule != Scheduler

This distinction is mandatory.

    Schedule
        specification of WHEN something should activate

    Scheduler
        mechanism responsible for realizing schedules

A Schedule can exist without Rebuntu implementing its own Scheduler.

For example:

    Rebuntu Schedule
           |
           v
    systemd timer
           |
           v
      activation

Therefore:

    HAVING SCHEDULES != NEEDING A SCHEDULER


# 6. Schedule != Task

A Task describes bounded work.

A Schedule describes temporal activation.

Prefer composition:

    Task + Schedule

rather than:

    ScheduledTask extends Task

unless implementation evidence strongly justifies specialization.

A Task may be:

    executed immediately
    manually activated
    event activated
    condition activated
    dependency activated
    scheduled

Scheduling is one activation mechanism.


# 7. Schedule != Job

A Job is a concrete managed realization of work.

A Schedule may CREATE or ACTIVATE Jobs.

Example:

    Schedule:
        every day at 03:00

    Task:
        verify backup integrity

At 03:00:

    Schedule
        ↓
    Activation
        ↓
    Job #184
        ↓
    Execution

Tomorrow:

    same Schedule
        ↓
    Job #185

Do not treat the Schedule itself as the running Job.


# 8. Schedule != Automation

Scheduling answers primarily:

    WHEN?

Automation answers:

    WHEN / WHY / UNDER WHAT CONDITIONS SHOULD SOMETHING HAPPEN?

A Schedule may be one trigger source for Automation.

For example:

    Schedule
        every hour

is different from:

    Automation
        every hour,
        IF storage utilization > threshold,
        THEN perform operation X

Do not embed a full policy engine inside scheduling.


# 9. Schedule != Workflow

A Workflow describes how composed work progresses.

A Schedule describes when activation occurs.

A Workflow may be scheduled.

A Workflow may contain temporal waits.

Neither makes Workflow and Schedule equivalent.


# 10. Schedule != Daemon

Never create a persistent process merely because something must happen
periodically.

Before implementing any periodic daemon ask:

    Can systemd timer do this?

    Can kernel/native event activation remove the need for polling?

    Can a path/device/socket/D-Bus event activate the work?

Persistent:

    while true:
        do_work()
        sleep(60)

must be treated as suspicious architecture.


# 11. Clock Semantics

Explicitly investigate Linux clock domains.

At minimum understand:

    CLOCK_REALTIME
    CLOCK_MONOTONIC
    CLOCK_BOOTTIME

and other clocks where genuinely relevant.

Do not treat all timestamps and elapsed-time measurements as equivalent.


# 12. Wall Clock vs Monotonic Time

This distinction must be explicit.

Wall-clock time answers questions such as:

    What time is it?
    Run this at 03:00.
    What date did this occur?

Monotonic time answers:

    How long has this been running?
    Has the timeout elapsed?
    Has the retry delay elapsed?

Wall-clock adjustments must not unexpectedly break elapsed-time logic.

Therefore, durations and timeouts should normally be based on an
appropriate monotonic clock.


# 13. Boot-Aware Time

Investigate CLOCK_BOOTTIME and related semantics.

Some timers should include system suspend time.

Others should not.

Example distinction:

    "retry after 10 seconds of active runtime"

versus:

    "perform maintenance after machine has existed for 8 hours,
     including suspend"

Do not select clock semantics accidentally.


# 14. Timestamp

Define what a Timestamp represents.

Potential forms:

    created_at
    requested_at
    scheduled_for
    activated_at
    started_at
    last_progress_at
    completed_at
    verified_at
    failed_at
    cancelled_at

Do not populate every entity with every timestamp.

Only record timestamps that have semantic or diagnostic value.


# 15. Duration

Duration is an amount of elapsed time.

Examples:

    timeout = 30 seconds
    execution_duration = 4.2 seconds
    retry_delay = 5 seconds

Duration is not a Timestamp.

Avoid ambiguous fields such as:

    time = 30


# 16. Delay

A Delay postpones an action or transition.

Examples:

    start after 10 seconds
    retry after 5 seconds

Delay should not automatically imply:

    sleep()

The implementation may use:

    event-loop timers
    systemd timers
    kernel timers
    native blocking/waiting mechanisms

depending on ownership and lifecycle.


# 17. Interval

An Interval describes temporal separation.

For example:

    sample every 5 seconds

Do not confuse:

    interval
    duration
    timeout
    period
    frequency


# 18. Period and Frequency

Investigate whether both terms are useful.

Potential mathematical relationship:

    frequency = occurrences / time
    period    = time / occurrence

But user-facing system configuration often uses them less formally.

Determine canonical Rebuntu usage.

Avoid two names for the same concept unless the distinction provides
real value.


# 19. Recurrence

A recurring Schedule should represent recurrence declaratively.

Examples:

    every hour
    every Monday
    daily at 03:00
    every 15 minutes while machine is active
    after boot and then every 6 hours

Do not represent recurrence as an imperative loop when a native
scheduler can own it.


# 20. Calendar Scheduling

Investigate calendar-based scheduling.

Examples:

    daily at 03:00
    Monday at 09:00
    first day of month
    specific date/time

systemd OnCalendar should be considered a primary native Linux
mechanism.

Do not implement a custom calendar parser unless Rebuntu genuinely needs
semantics beyond native facilities.

If Rebuntu provides friendlier syntax, translate it into a stable
internal representation and then into the appropriate provider.


# 21. Monotonic Scheduling

Not all schedules are calendar schedules.

Examples:

    10 minutes after boot
    30 seconds after activation
    1 hour after previous successful completion
    every 5 minutes while active

Investigate native systemd monotonic timer facilities such as:

    OnBootSec
    OnStartupSec
    OnActiveSec
    OnUnitActiveSec
    OnUnitInactiveSec

Do not force all schedules through wall-clock timestamps.


# 22. Persistent Scheduling

Ask what should happen when the machine was powered off during a
scheduled activation.

Possible policies:

    SKIP
    RUN_ON_NEXT_START
    RUN_IF_STILL_RELEVANT
    RECONCILE
    EXPIRE

Do not silently choose catch-up behavior.

Where appropriate, investigate systemd timer persistence rather than
implementing custom missed-run tracking.


# 23. Deadline

A Deadline specifies a temporal boundary associated with an objective.

Examples:

    complete before 18:00
    verification must finish before shutdown
    package update must complete before maintenance window closes

Deadline != Timeout.

A deadline may be absolute.

A timeout is usually relative to some activation/start point.


# 24. Timeout

Define timeout as a temporal control condition.

Potential categories:

    startup_timeout
    execution_timeout
    inactivity_timeout
    request_timeout
    IPC_timeout
    dependency_timeout
    shutdown_timeout
    verification_timeout

Do not create one universal timeout whose semantics depend on context.

Timeout expiration does not automatically mean:

    kill -9

Possible flow:

    timeout detected
        ↓
    cancellation requested
        ↓
    graceful termination window
        ↓
    escalation if policy permits
        ↓
    verification
        ↓
    outcome


# 25. Inactivity Timeout

This deserves explicit investigation.

Execution may legitimately run for one hour while making progress.

Another execution may be jammed after 30 seconds without progress.

Therefore:

    execution timeout

and:

    inactivity timeout

are different.

This connects directly with Phase 0.8's concept of:

    JAMMED

Potential relation:

    last_progress_at
          +
    inactivity threshold
          ↓
    possible JAMMED condition

Do not equate absence of visible output with absence of progress.


# 26. Temporal Window

A Window represents a bounded temporal region.

Examples:

    maintenance window
    allowed execution window
    observation window
    correlation window
    retry window
    scheduling window

Example:

    service failed 3 times within 5 minutes

Here:

    5 minutes

is not a Schedule.

It is an observation/correlation window.

This distinction will become important for later Events, Assertions and
Internal Alerts.


# 27. Expiration

Some information or requests may become invalid after time.

Examples:

    cached observation
    authorization
    temporary capability
    request
    diagnostic evidence
    pending operation

Distinguish:

    expires_at

from:

    timeout

Expiration concerns validity.

Timeout concerns waiting/execution constraints.


# 28. Wait

"wait" is an important historical and shell/runtime concept.

Investigate its semantic roles.

Possible meanings:

    wait for process
    wait for Job
    wait for Event
    wait for Condition
    wait until time
    wait for dependency
    wait for resource
    wait for user input

Do not implement all of these as polling.

Use native blocking/event mechanisms where possible.


# 29. Waiting State

Phase 0.8 establishes WAITING as a possible activity state.

Phase 0.9 should allow structured temporal waiting.

For example:

    activity = WAITING
    waiting_for = TIME
    until = ...

or:

    activity = WAITING
    waiting_for = JOB
    target = ...

Do not create separate lifecycle states for every reason for waiting.


# 30. Sleep

Distinguish:

    sleep as an implementation mechanism

from:

    waiting as a semantic state

and from:

    delayed/scheduled activation

A shell or Python sleep is appropriate in some local bounded situations.

It is not a scheduling architecture.


# 31. Retry

Retry belongs partly to work execution and partly to temporal policy.

Phase 0.8 establishes Attempts.

Phase 0.9 must define the temporal side of retries.

Potential concepts:

    retry immediately
    fixed delay
    linear backoff
    exponential backoff
    bounded exponential backoff
    jitter
    retry window
    cooldown
    maximum attempts

Do not automatically retry all failures.


# 32. Backoff

Backoff is not merely sleep between retries.

It is a policy determining temporal spacing between Attempts.

Possible input:

    attempt number
    failure class
    resource condition
    provider response
    policy

Possible output:

    next eligible attempt time

Keep calculation separate from execution mechanism.


# 33. Jitter

Investigate jitter where repeated or network-facing work could otherwise
synchronize undesirably.

Do not introduce jitter everywhere.

For local single-host deterministic operations it may add needless
unpredictability.

Use it where synchronized retries or recurring actions are actually a
problem.


# 34. Cooldown

Cooldown represents a period during which an action should not be
repeated after a relevant occurrence.

Example:

    GPU recovery attempted
        ↓
    cooldown 60s
        ↓
    another automatic recovery becomes eligible

Cooldown != Backoff.

Cooldown != Debounce.

Cooldown != Rate Limit.


# 35. Debounce

Debounce is particularly important for event-driven Rebuntu.

Example:

    filesystem event
    filesystem event
    filesystem event
    filesystem event
        within 200 ms
           ↓
    one meaningful activation

This prevents event storms from producing redundant work.

Later kernel/event-driven chains will need this.


# 36. Coalescing

Investigate event/work coalescing.

Multiple equivalent activations may sometimes be combined.

Example:

    CONFIG_CHANGED
    CONFIG_CHANGED
    CONFIG_CHANGED

may become:

    one reconciliation Job

But never coalesce events when individual occurrences carry meaningful
semantics or evidence.


# 37. Throttle

Throttle limits execution frequency or throughput.

Example:

    no more than one expensive diagnostic per minute

Throttle != Debounce.

Throttle != Cooldown.

Throttle != Rate Limit, unless Rebuntu deliberately chooses one
canonical concept.


# 38. Rate Limiting

Investigate rate limiting separately from scheduling.

Examples:

    maximum N activations per interval
    maximum N requests per second
    maximum N recovery attempts per hour

Rate limiting protects resources or systems.

It does not specify ordinary recurrence.


# 39. Temporal Conditions

Time may participate in Conditions.

Examples:

    IF service failed 3 times within 5 minutes

    IF filesystem remained unavailable for 30 seconds

    IF no progress for 60 seconds

    IF temperature > threshold for 10 seconds

These are not ordinary Schedules.

Prepare vocabulary for later Event/Assertion phases without implementing
the full condition engine now.


# 40. Temporal Sequences

Prepare for future expressions such as:

    A
    THEN B within 10 seconds
    THEN C OR D within 30 seconds
    WHILE NOT E

This belongs primarily to future event/assertion/correlation machinery.

Phase 0.9 should ensure the temporal grammar can represent the required
concepts without building that engine now.


# 41. Absence as Temporal Information

An important future capability is detecting that something DID NOT
happen.

Examples:

    request sent
    but no response within 10 seconds

    service started
    but READY was never observed

    mount requested
    but mount did not appear

This requires:

    expectation
    temporal boundary
    absence detection

Do not reduce all absence detection to polling.


# 42. Activation

Define Activation carefully.

An Activation is the occurrence that makes work eligible to begin or
causes work to be instantiated.

Potential sources:

    manual request
    shell command
    API request
    schedule
    event
    signal
    condition
    dependency completion
    system startup
    device appearance
    socket request
    path change

Time is only one activation source.


# 43. Trigger

Determine the relationship:

    Trigger
    Activation

Possible distinction:

    Trigger
        condition/source capable of causing activation

    Activation
        concrete occurrence of activation

Example:

    Trigger:
        daily at 03:00

    Activation:
        2026-09-15 03:00 occurrence

Avoid retaining both if the distinction has no consumer.


# 44. Event Time vs Processing Time

Prepare Rebuntu to distinguish:

    when something happened

from:

    when Rebuntu observed or processed it

Possible timestamps:

    occurred_at
    observed_at
    processed_at

This becomes important for journald, kernel events and delayed
processing.

Do not overpopulate every event now, but define the distinction.


# 45. Created Time vs Activated Time vs Started Time

For work:

    created_at
    activated_at
    started_at

may all differ.

Example:

    Job created:      02:50
    scheduled for:    03:00
    activated:        03:00
    started:          03:02

because a required resource was unavailable.

Do not use one ambiguous:

    timestamp


# 46. Completion Time vs Verification Time

Likewise:

    execution finished at 03:10
    verification finished at 03:12

These are different facts.

This reinforces:

    EXECUTION SUCCESS != VERIFIED SUCCESS


# 47. Time Zones

Calendar scheduling requires explicit timezone semantics.

Investigate:

    local timezone
    UTC
    explicit named timezone
    system timezone changes

Do not store ambiguous local timestamps as durable cross-context
identifiers.

Use timezone-aware representations where calendar semantics require
them.


# 48. DST

Daylight Saving Time must be considered for calendar schedules.

Questions include:

    What happens when a local clock time occurs twice?

    What happens when a local clock time does not occur?

Do not build a custom DST engine.

Prefer mature native/system libraries and systemd semantics.


# 49. Clock Changes

Wall clock can change due to:

    NTP
    manual adjustment
    timezone change
    RTC correction
    suspend/resume

Elapsed-time behavior should not depend accidentally on CLOCK_REALTIME.

Tests should cover relevant clock-domain assumptions without modifying
the host clock.


# 50. Precision

Do not give every temporal concept nanosecond precision because Linux can.

Choose precision according to semantics.

Examples:

    shell schedule:
        seconds/minutes may suffice

    performance tracing:
        high-resolution monotonic timestamps may matter

    filesystem maintenance:
        minute/hour resolution may suffice

Precision is part of the contract.


# 51. Human Duration Parsing

Eventually Rebuntu may accept convenient forms such as:

    5s
    10m
    2h
    3d

or shell language such as:

    schedule backup every 6h

If parsing is introduced, it must be:

    deterministic
    validated
    unambiguous
    canonicalized internally

Do not make BitNet responsible for parsing deterministic duration syntax.


# 52. Semantic Time Parsing

Natural expressions such as:

    tomorrow evening
    next Monday
    after work
    when idle for a while

are a different class.

Do not pretend they are deterministic syntax.

Future semantic interpretation may translate them into structured
temporal specifications, but execution must operate on validated
canonical data.


# 53. Native Linux Scheduling

Investigate Linux-native facilities before building Rebuntu mechanisms.

At minimum:

    systemd timers
    systemd calendar expressions
    systemd monotonic timers
    timer persistence
    timer accuracy/randomized delay
    service activation
    user timers
    system timers

Also understand where relevant:

    timerfd
    POSIX timers
    kernel clocks
    event-loop timers

The correct layer depends on lifetime and ownership.


# 54. systemd Timer as Default Persistent Scheduler

For persistent machine-level or user-level scheduled work, systemd
timers should be the default candidate.

Rebuntu may provide:

    semantic schedule definition
        ↓
    validation
        ↓
    provider mapping
        ↓
    systemd timer
        ↓
    activation
        ↓
    Rebuntu work

Do not build another cron daemon.


# 55. Cron

Cron may exist on the host and may be supported as an external/native
provider where appropriate.

But do not architect Rebuntu around cron merely because historical shell
automation often used it.

Compare capabilities and choose intentionally.


# 56. timerfd / Event Loop Timers

For temporal behavior inside an already-running process, spawning
systemd timers may be inappropriate.

Investigate:

    timerfd
    asyncio timers
    native event-loop scheduling

Use process-local timers for process-local lifetime.

Use persistent system scheduling for persistent system intent.

Do not mix the two accidentally.


# 57. Kernel/Event Activation Before Polling

For requirements phrased as:

    "check every N seconds whether X changed"

first ask:

    Can Linux notify us when X changes?

Potential mechanisms:

    inotify
    fanotify
    netlink
    udev
    D-Bus signals
    systemd path units
    systemd device units
    socket activation
    journald following
    pidfd
    eBPF/tracepoints where justified

Prefer:

    EVENT → ACTIVATION

over:

    LOOP → SLEEP → CHECK → LOOP

when native event delivery provides the needed semantics.


# 58. Polling Is Not Forbidden

Polling remains appropriate when:

    no reliable event source exists
    reconciliation is required
    external state can only be queried
    eventual consistency is sufficient
    polling cost is negligible

But polling must be intentional.

Document:

    interval
    cost
    expected latency
    failure behavior
    backoff
    jitter if relevant


# 59. Scheduling and Services

A Service may be:

    always available
    manually activated
    socket activated
    event activated
    scheduled

Do not require a persistent Daemon merely because the functionality is
a Service.

Example:

    scheduled maintenance service
        ↓
    systemd timer
        ↓
    oneshot service
        ↓
    bounded Job


# 60. Scheduling and Automatons

Future Automatons may consume temporal triggers.

Example:

    Schedule
       +
    Condition
       ↓
    Automation
       ↓
    Operation

But do not implement the Automation engine in Phase 0.9.

Phase 0.9 supplies temporal semantics.


# 61. Scheduling and Init Chains

Prepare for Phase 4.x kernel/native-triggered init chains.

An init chain may be activated by:

    boot phase
    device appearance
    mount availability
    service readiness
    network availability
    session start
    kernel event
    explicit request
    temporal schedule

Do not make "init" synonymous with "boot".


# 62. Boot Scheduling

Investigate semantics such as:

    at boot
    after boot
    after user session starts
    after dependency becomes ready
    once per boot

Distinguish:

    boot identity

from:

    elapsed time since boot

where useful.

Prefer native systemd dependencies and activation rather than sleeps
such as:

    sleep 30 && start_something


# 63. Once Semantics

A schedule may mean:

    once ever
    once per installation
    once per boot
    once per session
    once after event
    once at timestamp

These are not equivalent.

Do not implement "once" using arbitrary marker files without considering
the proper scope and persistence semantics.


# 64. Catch-Up Semantics

For recurring work, define what happens after downtime.

Example:

    backup scheduled every hour
    machine off for 8 hours

Possible behavior:

    run once after boot
    run eight times
    skip missed runs
    reconcile desired outcome

Usually replaying every missed occurrence is not desirable.

Make policy explicit.


# 65. Overlapping Activations

What happens when the next scheduled activation occurs while previous
work is still running?

Possible policies:

    ALLOW
    SKIP
    QUEUE
    COALESCE
    REPLACE
    CANCEL_PREVIOUS
    REJECT

Do not choose globally.

The underlying work contract and safety requirements determine policy.


# 66. Reentrancy

Recurring scheduling interacts with operation reentrancy.

Do not assume:

    recurring == safe to overlap

Use locks, service semantics, systemd behavior, or work contracts where
appropriate.


# 67. Missed Deadline

A missed deadline is not automatically execution failure.

Possible outcomes:

    continue
    cancel
    degrade priority
    report violation
    compensate
    reschedule
    require decision

Separate:

    temporal policy violation

from:

    technical execution failure.


# 68. Temporal Policy

Some temporal semantics may belong to Policy rather than Schedule.

Examples:

    backups may only run at night
    expensive diagnostics must not run more than once per hour
    updates must finish before shutdown window
    recovery may retry at most three times in ten minutes

Do not stuff all policy into scheduling configuration.


# 69. Temporal Evidence

Temporal claims should be evidential.

Examples:

    activated_at
    started_at
    last_progress_at
    finished_at
    deadline
    timeout_at
    attempt delay
    missed activation

Evidence should make it possible to reconstruct:

    what was supposed to happen
    when it was supposed to happen
    when it actually happened
    what delayed it
    what the outcome was


# 70. Journald Integration

Use journald for system-managed temporal execution evidence where
appropriate.

Structured metadata may correlate:

    schedule
    activation
    job
    execution
    attempt

Do not create an independent chronological logging system merely to
track schedules.


# 71. Temporal Persistence

Determine which temporal specifications must survive process restart or
machine reboot.

Examples:

    persistent Schedule
        yes

    local timeout for one in-process call
        no

    retry-after timestamp for recoverable Job
        maybe

    maintenance window
        yes if configured

Persistence must follow semantic lifetime.


# 72. Serialization

If temporal specifications are persisted or transferred:

    use explicit canonical formats
    preserve timezone semantics
    preserve clock-domain assumptions where relevant
    validate ranges
    reject ambiguous values

Do not serialize Python datetime objects through unsafe mechanisms.


# 73. Configuration

Determine how temporal configuration should be represented.

Possible examples:

    interval: 5m

    timeout: 30s

    schedule:
        calendar: "*-*-* 03:00:00"

or higher-level Rebuntu structures.

Do not blindly expose systemd syntax as Rebuntu's entire temporal
ontology.

But do not invent a pointless translation layer if native syntax already
matches the need.


# 74. Provider Boundary

A future Schedule may map to different mechanisms:

    systemd timer
    process-local event loop
    external scheduler
    immediate activation
    testing fake clock

Therefore distinguish:

    temporal semantics

from:

    scheduling provider

without building a generic plugin framework unless required.


# 75. Testability and Clocks

Temporal code must be testable without waiting real minutes or hours.

Where Rebuntu owns temporal logic, consider injectable/fake clock
boundaries.

Do not overabstract code that merely delegates to systemd.

Use the smallest test seam appropriate to ownership.


# 76. Testing

Test any concrete temporal primitives introduced.

Relevant cases may include:

    duration parsing
    invalid duration rejection
    monotonic timeout calculation
    wall-clock scheduling representation
    timezone-aware timestamps
    recurrence representation
    retry backoff calculation
    deadline comparison

Can the architecture choose appropriate clock semantics?

The resulting architecture should be able to express:

    WHAT?
        Task / Operation / Workflow

        Schedule / Activation

        Delay / eligibility time

    NO LATER THAN?
        Deadline

        Timeout

    DURING WHAT PERIOD?
        Window

    WHEN DOES IT STOP BEING VALID?
        Expiration

        Wait condition

without collapsing these questions into one generic temporal mechanism.


# Final Rule

TIME IS A DIMENSION, NOT A SUBSYSTEM BY DEFAULT.

A TASK IS WORK.

A SCHEDULE IS WHEN WORK BECOMES ELIGIBLE.

A JOB IS A CONCRETE MANAGED REALIZATION OF WORK.

AN EXECUTION IS WHAT ACTUALLY RUNS.

A TIMER IS A MECHANISM.

A TIMEOUT IS A CONSTRAINT.

A DEADLINE IS A BOUNDARY.

A WINDOW IS A REGION OF TIME.

A RETRY IS A DECISION TO TRY AGAIN.

BACKOFF DETERMINES WHEN THAT NEXT ATTEMPT BECOMES ELIGIBLE.

WAITING IS A RUNTIME CONDITION, NOT A SCHEDULER.

DO NOT USE WALL CLOCK FOR ELAPSED-TIME LOGIC WITHOUT JUSTIFICATION.

DO NOT IMPLEMENT PERIODIC WORK AS A DAEMON MERELY BECAUSE IT REPEATS.

DO NOT POLL WHEN LINUX CAN DELIVER THE EVENT.

DO NOT BUILD ANOTHER CRON.

DO NOT BUILD ANOTHER SYSTEMD TIMER ENGINE.

USE SYSTEMD FOR PERSISTENT NATIVE SCHEDULING WHERE IT FITS.

USE PROCESS-LOCAL TIMERS FOR PROCESS-LOCAL LIFETIMES.

USE KERNEL/NATIVE EVENTS WHEN THE REQUIREMENT IS ACTUALLY EVENT-DRIVEN.

MAKE TEMPORAL POLICY EXPLICIT.

MAKE MISSED ACTIVATIONS EXPLICIT.

MAKE OVERLAP POLICY EXPLICIT.

MAKE CLOCK SEMANTICS EXPLICIT.

SEARCH BEFORE IMPLEMENTING.

KEEP TIME ORTHOGONAL TO WORK.
