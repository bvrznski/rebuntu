### Safe host-modification policy

Installation/setup code is unusually dangerous because it operates on the
developer's actual machine.

Default test behavior must NOT:

- remove unrelated files;
- rewrite `/etc` indiscriminately;
- recursively chown/chmod broad trees;
- alter firewall/network configuration;
- alter boot configuration;
- modify storage layouts;
- format filesystems;
- disable unrelated services;
- delete user data;
- overwrite user-authored configuration;
- expose secrets;
- install packages without an explicit test/integration mode;
- run arbitrary commands as root.

Use isolated temporary roots, fixtures, mocks/fakes, containers only where
appropriate, or explicit opt-in host integration tests.

For consequential mutation prefer:

    DISCOVER
      -> RESOLVE TARGET
      -> VALIDATE
      -> PLAN
      -> AUTHORIZE
      -> CHECKPOINT/BACKUP IF WARRANTED
      -> EXECUTE
      -> OBSERVE
      -> VERIFY
      -> EVIDENCE
      -> RESULT

### Python/Bash boundary

Python normally owns:

- installer state;
- discovery results;
- schemas;
- validation;
- planning;
- configuration merge;
- structured user input;
- migration;
- verification;
- reporting;
- typed results;
- tests.

Bash normally owns:

- minimal bootstrap;
- interactive shell convenience;
- direct native glue where Python adds no semantic value.

Avoid `shell=True` and `bash -c` as generic execution mechanisms.
Prefer argv arrays, explicit cwd, explicit environment and explicit timeout.

### Idempotency

A successful installer/setup/reconfiguration command should be safe to run
again unless its contract explicitly says otherwise.

Idempotency does not mean "ignore all errors".

Repeated execution should converge on the same managed state without
duplicating entries, units, users, directories, PATH fragments or config blocks.

### Ownership

Every artifact created by Rebuntu must have an answer to:

- who owns it?
- who may modify it?
- who may read it?
- what phase/component manages it?
- is it configuration, state, cache, runtime data, code or evidence?
- how is it upgraded?
- how is it repaired?
- how is it uninstalled?
- what happens if the user edits it?

### Verification

Installer command exit status is evidence, not proof.

Examples:

    mkdir returned 0
        !=
    directory has correct owner/mode

    package manager returned 0
        !=
    required dependency is usable

    systemctl enable returned 0
        !=
    service is functionally ready

    config write succeeded
        !=
    effective configuration is correct

## Mission

Define the boundary between installation, setup and ongoing configuration, then
implement the minimal setup/configuration machinery needed by Rebuntu.

## Canonical distinction to validate

    Installation = place/establish Rebuntu artifacts and prerequisites.
    Setup = establish an initial usable Rebuntu environment for a user/host.
    Configuration = durable parameters governing behavior.

Setup is not necessarily a persistent object.

## Setup pipeline

Candidate:

    discover
      -> collect validated input
      -> derive desired initial configuration
      -> plan
      -> apply
      -> verify
      -> report

## Managed vs user-authored config

For every config file decide:

- Rebuntu-owned generated file;
- user-owned editable file;
- shared/merged file;
- external system config.

Do not overwrite arbitrary user files.

## Merge strategy

Avoid regex/string surgery in complex config when structured formats exist.

For shell rc integration prefer clearly delimited managed blocks or sourced
dedicated files where appropriate.

Repeated setup must not duplicate blocks.

## Configuration sources

Implement only the precedence established in Phase 0.18.

Expose effective config/provenance for diagnostics.

## Reconfiguration

Architecture should permit Phase 1.11 reconfiguration without reinstalling.

## Verification

Configuration write success is not enough.

Verify effective configuration and, when applied to system behavior, the
relevant observed postcondition.

## Cross-Cutting Review Questions

For this phase, answer every applicable question before coding:

### Existing implementation
- Is this already implemented under another name?
- Is there a historical implementation worth extracting?
- Is there a utility project with a stronger implementation?
- Are tests already expressing the intended contract?
- Is the proposed new abstraction merely wrapping an existing one?

### Linux ownership
- Which part is authoritative Linux state?
- Which part is Rebuntu desired state?
- Which part is cached/derived?
- Which native mechanism should Rebuntu call rather than emulate?
- What happens when the native mechanism is unavailable?

### Scope
- Is this system-wide, per-user, per-session, per-installation or per-invocation?
- Can two users use it concurrently?
- Can root invocation accidentally target the wrong user's environment?
- Does it remain correct after reboot/login/logout?

### Mutation
- What exact object changes?
- Who owns it before and after?
- Can the target be a symlink?
- What happens if it changes between plan and execution?
- Is mutation atomic?
- Is a checkpoint needed?
- Is rollback genuinely possible?
- What verifies the resulting state?

### Failure
- What is a validation failure?
- What is a precondition failure?
- What is an execution failure?
- What is a verification failure?
- What remains UNKNOWN?
- What state is left after interruption?
- Can rerunning safely converge?

### Security
- Is untrusted text interpreted as a path/command?
- Is privilege necessary?
- Is authorization checked separately?
- Can secrets enter logs/results?
- Can a malicious local user influence a privileged target?
- Are file modes/ownership correct?

### Maintainability
- Does the design create a new generic Manager/Base class?
- Is a registry actually consumed?
- Is a new process actually required?
- Is a new config format required?
- Can the design be expressed with ordinary Python and native Linux more
  clearly?
