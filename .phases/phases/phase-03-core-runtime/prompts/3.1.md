## Phase Mission

Bootstrap the native CPU-only BitNet runtime required for Rebuntu's semantic provider. Target Microsoft bitnet.cpp and the BitNet b1.58 2B4T family as the initial concrete path, while keeping Rebuntu's semantic interface independent from one executable layout. Establish discovery, installation/build, model artifact handling, integrity, CPU-only enforcement, startup verification, and reproducibility.

## Semantic Infrastructure Hard Boundary

Rebuntu's native semantic model is a **systems semantic utility**.

It may help with bounded tasks such as:
- interpreting logs/events;
- classifying structured evidence;
- mapping constrained language to typed intent candidates;
- summarizing diagnostics;
- selecting relevant evidence;
- suggesting candidate operations that deterministic code must validate.

It is not:
- a privileged executor;
- an authorization oracle;
- a source of observed system truth;
- a replacement for deterministic parsers where deterministic parsing exists;
- a hidden workflow engine;
- a general autonomous agent architecture.

### Initial model/runtime direction

The initial target is the BitNet b1.58 2B4T family with Microsoft `bitnet.cpp`,
deployed as a CPU-only semantic provider.

Treat model name/runtime path as configuration/provider detail rather than leaking it
through all consumers.

The CPU-only contract is deliberate: GPUs are reserved resources. Verify it rather than
merely documenting it.

### Structured output

Model output must cross a validation boundary.

Prefer constrained schemas such as:
- classification;
- candidate intent;
- evidence relevance;
- diagnostic summary;
- suggested next observation;
- candidate operation identifier + typed arguments.

Reject malformed, out-of-schema, oversized, timed-out or policy-incompatible output.

Never make successful JSON parsing equivalent to semantic correctness.

## Provider Architecture Rules

A provider is an implementation mechanism behind a stable Rebuntu capability/contract.

Provider selection must be explainable from:
- requested capability;
- target/scope;
- native availability;
- policy;
- security;
- resource constraints;
- explicit preference;
- compatibility;
- health/readiness where relevant.

Do not build a universal provider superclass merely because BitNet, Docker and Ansible
are all called providers.

Provider discovery != provider readiness.
Provider process exit 0 != verified operation success.
Provider installed != provider usable.
Provider available != provider authorized.

Every provider adapter should expose only the semantics its consumers need.
Preserve underlying diagnostics as evidence.
