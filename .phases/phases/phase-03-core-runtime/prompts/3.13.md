## Canonical Semantic Contract

### Provider Selection Architecture

```
ProviderSelectionContext (capability, scope, policy, preference)
    -> ProviderSelector.select(context)
        -> discover_providers() → List[ProviderInfo]
            → Filter by capability
            → Apply policy constraints
            → Apply preference
            → Select winner
    -> ProviderSelectionResult (outcome, selected, candidates, rejected, evidence)

ProviderAdapter(selected_provider)
    -> execute(request) → Result with outcome + verification
```

### Selection Principles

1. **Capability-driven**: Start from requested capability
2. **Native-first**: Linux/systemd preferred when they directly solve the task
3. **Policy-enforced**: Security/resource constraints checked before execution
4. **Preference-honored**: User preferences guide selection within constraints
5. **Verification-required**: Outcome verified separately from execution success

### Selection Policy Types

| Policy | Behavior |
|--------|----------|
| NATIVE_FIRST | If any native providers available, only consider those |
| ALLOW_EXTERNAL | All available providers considered |
| EXTERNAL_ONLY | Only non-native (fallback case) |

## Security & Resource Boundary

### Security Controls Implemented

1. **Policy enforcement**
   - Native-first when available
   - User preferences cannot bypass security policies
   - Selection happens before execution

2. **No privilege escalation**
   - Provider selection is read-only metadata
   - No execution of untrusted code in selector

3. **Evidence collection**
   - All selection decisions recorded with timestamps
   - Reject reasons documented for auditability

### Resource Constraints

| Constraint | Value | Rationale |
|------------|-------|-----------|
| Default timeout | 30s | Standard timeout for provider operations |
| Cache TTL | 60s | Fresh provider state within session |
| Max candidates | Unlimited | Filtered by capability, not count |

### Key Design Decisions

1. **Dataclass for Context**
   - Immutable ProviderSelectionContext ensures consistent input
   - Frozen=True prevents modification mid-selection

2. **Separate Discovery and Selection**
   - `discover_providers()` populates cache
   - `select_provider()` uses cached data
   - Cache TTL (60s) balances freshness with performance

3. **Native First Priority**
   - Native providers get priority=1-99 (lower = higher priority)
   - External providers default to priority=100
   - NATIVE_FIRST policy enforces selection from lower-priority set

4. **Explainable Results**
   - `explanation` property generates human-readable reason
   - Rejected providers documented with reasons
   - Evidence collected for traceability

5. **Adapter Pattern for Execution**
   - ProviderAdapter wraps selected provider
   - Separates selection from execution concerns
   - Future-proof for different execution mechanisms

2. **Preference specified but unavailable**: Falls back to other available providers
3. **NATIVE_FIRST when only external available**: Returns failure as expected
4. **Rapid selections**: Cache ensures performance (< 2s for discovery + selection)

## Rejected Alternatives

### Alternative 1: Giant ProviderManager Class
**Rejected because:**
- Violates single responsibility principle
- Would become a monolithic hub for all providers
- Makes testing difficult (too many concerns in one class)
- Goes against "Provider != Capability != Operation" contract

### Alternative 2: Static Configuration File for Providers
**Rejected because:**
- Runtime availability detection needed
- Cannot handle dynamic provider state changes
- Would require file I/O on every selection

### Alternative 3: Direct Provider Instantiation in Consumers
**Rejected because:**
- Duplicates discovery logic everywhere
- No explainable selection model
- Hard to test (no central place for stubbing)

### Alternative 4: Priority-Based Only Selection
**Rejected because:**
- Policy-based filtering more expressive
- Native-first is a common requirement not just priority

## Remaining Risks

### Evidence-Based Risks

1. **Discovery failures during import**
   - Risk: Import time discovery could fail if providers unavailable
   - Mitigation: Discovery happens lazily in select_provider()
   - Evidence: `discover_providers()` only called when needed

2. **Cache staleness**
   - Risk: Provider state may change between selection calls
   - Mitigation: 60s cache TTL forces periodic refresh
   - Evidence: Cache invalidation checks timestamp

3. **No fallback provider for critical capabilities**
   - Risk: If native unavailable and no external, service fails
   - Mitigation: Explicit NO_PROVIDER_FOUND outcome with evidence
   - Evidence: `is_selectable()` filters by status
