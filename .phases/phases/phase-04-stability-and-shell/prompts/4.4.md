## Canonical Runtime Flow

The default conceptual flow is:

    REQUEST
      -> VALIDATION
      -> TARGET / CAPABILITY RESOLUTION
      -> AUTHORIZATION / POLICY
      -> DISPATCH
      -> TASK / JOB REALIZATION where applicable
      -> EXECUTION
      -> ATTEMPT
      -> NATIVE / PROVIDER ACTION
      -> OBSERVED RESULTING STATE
      -> POSTCONDITIONS
      -> VERIFICATION
      -> EVIDENCE
      -> RESULT

This is a semantic grammar, not an instruction to create one class/directory for every
arrow.

For mutating Operations preserve:

    DISCOVER
      -> RESOLVE
      -> PRECHECK
      -> PLAN
      -> AUTHORIZE
      -> CHECKPOINT when justified
      -> EXECUTE
      -> OBSERVE
      -> VERIFY
      -> EVIDENCE
      -> RESULT

## Concurrency & Resource Discipline

Before introducing threads/async/processes:
- identify why concurrency is required;
- define ownership;
- define cancellation;
- define backpressure;
- define shutdown behavior;
- define failure propagation;
- define evidence;
- define resource bounds.

Prefer native/event-driven mechanisms. Avoid polling loops where events exist.

No unbounded:
- queues;
- thread creation;
- subprocess creation;
- retry loops;
- output buffering;
- event fanout;
- workflow expansion.

Locks should use native kernel-mediated semantics where possible.
Do not treat stale `.lock` files as truth.

## Subprocess Discipline

For external processes:
- argv arrays, never interpolated shell strings;
- explicit cwd;
- controlled environment;
- explicit stdin/stdout/stderr strategy;
- timeout/deadline;
- cancellation escalation;
- output size limits where relevant;
- preserve exit code/signal;
- capture evidence;
- independently verify semantic postconditions.

Avoid `shell=True`, `bash -c`, `nohup`, `disown`, background `&`, self-daemonization and
PID-file supervision unless a narrowly documented native requirement exists.

## Security Boundary

Privilege and authorization are separate.

A privileged runtime/provider may execute only an already-authorized, canonical, typed
request. It must not accept arbitrary command strings.

Semantic model output from Phase 3 remains untrusted:
    semantic candidate -> schema validation -> deterministic resolution/policy -> runtime.

Never:
    LLM -> Executor -> sudo shell

## Runtime Persistence Rule

Persist only information that must survive the lifetime boundary.

Definition/configuration belongs in configuration/catalog sources.
Ephemeral live execution state belongs in runtime memory/native runtime facilities.
Durable execution history/checkpoints/evidence belongs in appropriate Phase 2 state/data
locations.

After crash/reboot, never pretend persisted `RUNNING=true` means the execution is still
running. Reconcile persisted identity against native evidence and classify it.
