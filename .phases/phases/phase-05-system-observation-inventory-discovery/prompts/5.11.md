# Rebuntu — Phase 5.11 — Hang / Stall / Jam Detection

## Agent Task

## Phase Mission

Implement evidence-based detection of hangs, stalls and jams across processes/services/
runtime work and selected system resources. Define progress evidence and observation
windows rather than equating high CPU, sleeping, waiting or long runtime with a hang.
Support multi-signal suspicion and escalation without automatically killing anything.

### Phase 3 semantic-service boundary

The local semantic service may:
- classify bounded evidence;
- summarize;
- rank likely interpretations;
- suggest additional evidence to request;
- map constrained text to typed candidates.

It may not:
- invent observations;
- silently overwrite deterministic classifications;
- execute repair;
- invoke arbitrary shell;
- authorize actions;
- turn a hypothesis into a verified fact.

Required trust chain:

    native evidence
      -> deterministic acquisition
      -> normalization
      -> deterministic facts/rules where possible
      -> bounded semantic interpretation where useful
      -> schema validation
      -> evidence-linked assessment
      -> report

Never:

    logs -> LLM -> sudo bash

### Host safety

Monitoring should normally be read-only.

Phase 5 must not casually:
- restart services;
- kill processes;
- remount filesystems;
- reset GPUs;
- modify driver settings;
- alter power limits;
- run filesystem repair;
- delete logs;
- change sysctl;
- clear kernel state;
- modify package state;
- rewrite system configuration.

Those belong to explicit later Operations/recovery phases.

Diagnostic commands must be bounded, timed out, and treated as evidence acquisition.

### Privacy

Do not collect user documents, browser content, clipboard, keystrokes, message contents,
or unrelated process arguments/environment merely because they are accessible.

Diagnostic evidence should be the minimum required for the technical question.

Secrets must be redacted at presentation/storage boundaries without corrupting raw
technical meaning unnecessarily.

## 5. Observation Grammar

Every observation should answer as applicable:

    WHAT was observed?
    WHERE / WHICH subject?
    WHEN did it occur?
    WHICH boot/session/runtime?
    FROM WHICH source?
    HOW was it acquired?
    HOW fresh is it?
    IS it complete?
    WAS it truncated?
    WHAT raw evidence references it?
    WHAT normalization was applied?

Prefer a small shared observation envelope over per-monitor incompatible dicts.

Do not force every domain payload into one giant universal schema.

### Time

Preserve relevant time dimensions:
- source realtime timestamp;
- monotonic timestamp where available;
- acquisition time;
- processing time;
- boot ID;
- temporal window.

Clock jumps must not break duration/stall logic. Use monotonic clocks for elapsed-time
decisions.

### Provenance

Normalized evidence must retain enough provenance to recover or identify the raw source.

Do not rewrite raw messages in-place.

## 6. Event / Fact / Assertion / Condition / Alert Pipeline

Target conceptual pipeline:

    native source
      -> raw observation
      -> normalized observation/event
      -> fact
      -> assertion / condition evaluation
      -> internal alert if warranted
      -> correlation
      -> diagnostic evidence request
      -> assessment
      -> report / notification

Not every observation becomes every stage.

Examples:

    journal says systemd unit entered failed state
        = observation/fact

    service has failed 5 times in 2 minutes
        = temporal condition

    crash-loop condition satisfied
        = internal alert candidate

    crash loop began immediately after filesystem I/O errors
        = correlation

    filesystem caused service crash
        = causal hypothesis until evidence supports it

## 9. Backpressure and Event Storms

Monitoring systems fail by drowning in their own observations.

Every continuous acquisition path must consider:
- source rate;
- queue capacity;
- coalescing;
- deduplication;
- sampling;
- suppression;
- priority;
- drop policy;
- loss accounting;
- recovery after overload.

Never silently drop evidence.

If dropping/coalescing occurs, emit explicit metadata such as:
- count dropped;
- window affected;
- source;
- reason.

## 16. Deterministic-First Analysis

Before semantic inference, exploit structured evidence.

Examples:
- systemd unit fields;
- journal priority/facility/transport;
- kernel subsystem identifiers;
- boot IDs;
- process exit status/signal;
- cgroup/unit identity;
- NVMe/SCSI error structure;
- OOM killer records;
- PSI counters;
- thermal zones;
- provider machine-readable output.

Semantic inference is valuable when:
- multiple records need human-level synthesis;
- message text is semantically rich but structurally weak;
- causal alternatives need ranking;
- a human report needs compression.

Semantic inference is not valuable when a deterministic field already answers the question.

## 17. Causal Reasoning Discipline

The analyzer/reporting path should distinguish:

OBSERVED:
    exact evidence.

DERIVED:
    deterministic computation from observations.

CORRELATED:
    events associated by subject/time/topology.

HYPOTHESIS:
    plausible causal explanation.

SUPPORTED HYPOTHESIS:
    hypothesis with multiple independent supporting signals.

VERIFIED:
    only when an explicit verification mechanism exists.

Never render a hypothesis as "the cause was X" without evidence strong enough for that
language.

For incident timelines preserve alternatives:
- A preceded B;
- A and B share subject;
- A may have caused B;
- C is an alternative;
- evidence D would discriminate.

## 18. Reboot / Previous-Boot Diagnostics

Phase 5 must be designed around a critical real-world case:

    machine becomes unstable or hangs
        -> user hard-reboots
        -> current process memory is gone
        -> previous boot journal/evidence remains
        -> Rebuntu identifies abnormal previous termination
        -> retrieves bounded previous-boot evidence
        -> reconstructs likely failure sequence
        -> correlates kernel/driver/storage/memory/systemd/process signals
        -> creates a human-readable report

Do not assume an orderly shutdown marker is always written.

Use native boot identity and journal boundaries.

Distinguish:
- clean shutdown;
- expected reboot;
- abrupt termination;
- evidence insufficient / unknown.

The report must not fabricate a reason merely because the previous boot ended abruptly.

## Phase-Specific Implementation Contract

## Phase-Specific Deep Requirements — Hang / Stall / Jam

Define progress evidence before defining a stall.

Possible evidence:
- heartbeat/progress counter;
- expected state transition;
- queue consumption;
- I/O completion;
- service watchdog;
- runtime execution milestones;
- request completion.

A process sleeping in a syscall may be healthy.

High CPU may mean productive work.

Zero CPU may mean healthy waiting.

Use multi-stage suspicion:
NORMAL -> SUSPECTED_STALL -> CORROBORATED_STALL/JAM where evidence supports it.

Require temporal windows using monotonic time.

Collect diagnostic evidence on suspicion before escalation when safe.

Do not kill or restart in Phase 5.

Distinguish application stall from whole-system stall, I/O stall and source-observation
failure.

Test false positives aggressively.

- different subjects;

- timeout;
- malformed schema;

- unsupported conclusion;

- evidence write success;
- disk full simulation;
- partial write;
- restart;
- retention;
- corrupted stored metadata;

- dependency absent;
- degraded startup;
- graceful shutdown;
- shutdown during burst;

### Security/privacy

- raw evidence access permissions;
- untrusted log text cannot execute anything;

- no arbitrary path read;
- no privileged mutation.

### Long-running behavior

- bounded queue;
- bounded retained correlation state;
- no duplicate timer/task accumulation;
- no subprocess zombies;
