### Fundamental shell-language rule

The Rebuntu shell language is a **frontend to Rebuntu**, not a second operating runtime.

Target direction:

    shell tokens / stdin / explicit context
        -> lexical + grammatical parse
        -> canonical command candidate
        -> typed intent / command IR
        -> subject + scope resolution
        -> validation
        -> authorization / policy
        -> canonical Operation / Query / Workflow / capability
        -> Phase 4 runtime
        -> observation / verification / evidence
        -> structured result
        -> human or machine renderer

Never:

    shell verb -> giant Bash function implementing the system action

Never:

    free text -> LLM -> sudo bash

## 2. Historical UX Principle

Historical Rebuntu had an important strength: short, semantically dense shell functions
such as:

    install
    uninstall
    installed
    declared
    download
    extract
    catdir

The modern architecture should preserve the **semantic convenience**, not unsafe historical
implementation details.

Desired experience:

    install foo

conceptually becomes:

    tokens
      -> verb=install
      -> subject/package target=foo
      -> typed request
      -> canonical package.install Operation
      -> provider resolution
      -> preconditions/policy
      -> execution
      -> post-state observation
      -> verification
      -> evidence
      -> structured result
      -> human rendering

Possible human rendering:

    Installed foo ✓

But the renderer must be able to express:

    foo already installed ✓
    foo installation failed ✗
    installation executed, verification failed
    package state unknown
    ambiguous package target
    authorization denied

Do not reduce these to exit code alone.

## 3. Shell vs Python Boundary

Python owns:
- grammar;
- command specifications;
- typed IR;
- validation;
- subject resolution;
- Operation/query mapping;
- structured output;
- render models;
- context;
- completion metadata;
- semantic-service integration;
- tests.

Bash owns:
- interactive shell integration;
- tiny wrapper functions;
- completion hook;
- environment handoff;
- Unix pipeline glue where native shell semantics are useful.

A Bash function should ideally forward structured arguments to the Rebuntu CLI/runtime,
not reimplement provider logic.

Avoid:
- giant sourced Bash framework;
- associative-array object system;
- shell eval;
- dynamically constructed command strings;
- hidden sudo;
- parsing human output back into state;
- one shell function per provider.

## 4. Native Shell Compatibility

Rebuntu must coexist with Bash/POSIX/ordinary Linux tools.

Do not assume ownership of all English verbs.

Before introducing/exporting a command verb run equivalent discovery:

    command -v <verb>
    type -a <verb>

Classify:
- FREE;
- REBUNTU;
- SHELL_BUILTIN;
- SYSTEM_COMMAND;
- USER_DEFINED;
- AMBIGUOUS.

Do not silently shadow:
- shell builtins;
- common system commands;
- user aliases/functions;
- installed executable commands.

Collision policy must be explicit.

## 6. Command Ontology

A shell command specification should distinguish at least:

- verb or predicate;
- subject kind;
- target identity;
- arguments;
- qualifiers/modifiers;
- scope;
- options;
- output mode;
- execution policy hints that are actually user-controllable;
- source context/provenance.

Do not encode everything as arbitrary strings.

Do not force every command into `verb noun` if a predicate or established shell idiom is
better.

### Verb

A verb expresses an action/intention, ideally independent of provider.

Good:
    install package foo
    restart service nginx
    verify mount data

Bad:
    apt-install foo
    systemctl-restart nginx

unless the user explicitly requests a provider-specific operation.

### Predicate

A predicate asks whether a condition/state relation holds.

Examples:
    installed foo
    running nginx
    healthy service nginx
    reachable host x

Predicates must define TRUE/FALSE/UNKNOWN semantics.

### Subject

The subject identifies the type/domain being acted upon.

Examples:
    package
    service
    process
    file
    directory
    mount
    device
    gpu
    display
    network
    workflow
    operation

Subjects must align with established Rebuntu ontology and domain adapters.

### Target

Target is a concrete identity within the subject kind.

Do not confuse a target string with resolved identity.

## 7. Typed Intermediate Representation

Create/reuse a small typed command IR if justified by consumers.

Illustrative shape only:

    CommandIntent(
        command_id=...,
        verb=...,
        subject=...,
        target=...,
        arguments=...,
        qualifiers=...,
        scope=...,
        output=...,
        provenance=...
    )

Do not copy this blindly if Phase 0/4 already has a canonical Request/Intent type.

The IR must be:
- deterministic;
- serializable where useful;
- inspectable;
- validation-friendly;
- independent of human rendering;
- independent of model prose.

It must not contain executable shell fragments.

## 8. Resolution Is Not Execution

Command resolution may:
- tokenize;
- parse;
- lookup vocabulary;
- resolve aliases;
- identify candidate subjects;
- consult registries;
- resolve context;
- detect ambiguity.

It must not:
- install;
- restart;
- delete;
- mount;
- elevate;
- run arbitrary provider commands.

Resolution errors should be precise:
- unknown verb;
- unknown predicate;
- unknown subject;
- ambiguous target;
- conflicting scope;
- invalid qualifier;
- collision;
- unavailable capability.

## 9. Scope and Privilege

Scope is semantic, not inferred from effective UID alone.

Examples:
- user;
- system;
- session;
- runtime;
- host;
- explicitly named target/domain scope.

A command that can apply at user or system scope must not silently choose the broader one
when ambiguity is consequential.

Privilege != authorization.

`sudo rebuntu ...` does not mean every target/action is authorized by architecture.

Do not add hidden sudo inside shell functions.

## 10. Output Contract

Every command should conceptually produce a structured result first.

Human rendering is a view.

Machine output must not depend on terminal colors or prose parsing.

stdout:
- requested data/result stream.

stderr:
- diagnostics that are not part of the requested data stream.

exit status:
- coarse shell-level outcome suitable for composition.

Do not try to encode the entire Rebuntu result ontology in 0-255 exit codes.

Document exit-status conventions.

## 11. UNIX Pipeline Discipline

Rebuntu should compose naturally with Linux tools.

Examples of desired behavior:

    rebuntu list service --output jsonl | jq ...
    rebuntu query ... | ...
    some_command | rebuntu parse ...
    rebuntu ... | clip

Do not print banners/progress chatter to stdout when stdout is data.

TTY detection may select human rendering, but explicit output mode must override it.

Structured streaming should avoid loading arbitrarily large input into memory.

Backpressure must be respected.

## 12. Safety

Destructive verbs require stronger target/scope validation.

Examples:
- delete;
- remove;
- uninstall;
- format;
- reset;
- rollback;
- restore;
- clean.

Do not inherit historical dangerous defaults such as `extract` deleting the source archive
after successful extraction.

Do not make `clean` mean unrestricted deletion.

Dry-run/plan must be semantically honest: it predicts/plans; it does not verify future
success.

## 13. Semantic Service Boundary

Deterministic grammar has priority.

Only when deterministic parsing cannot produce one safe unambiguous interpretation may
the semantic service be considered.

Semantic path:

    user text
      -> bounded semantic request
      -> candidate typed intent
      -> schema validation
      -> canonical vocabulary lookup
      -> subject/scope resolution
      -> ambiguity/risk checks
      -> policy/authorization
      -> normal runtime path

The semantic service may never return arbitrary shell to execute.

If semantic interpretation is ambiguous, ask/show candidates rather than guessing a
consequential action.

## 14. Discoverability

A language that is powerful but impossible to discover is a failure.

Design machine-readable vocabulary metadata that can drive:
- help;
- completion;
- command listing;
- examples;
- schema introspection;
- semantic-service constrained vocabulary.

Do not maintain separate manually divergent command lists for parser, completion and docs.

## 15. Performance

Interactive shell latency matters.

Avoid:
- model invocation for ordinary commands;
- starting expensive services for `--help`;
- scanning the whole filesystem for completion;
- loading every provider on every shell command;
- subprocess chains for vocabulary lookup.

Measure cold and warm path where useful.

## 20. Side-Effect Classes

Preserve established distinctions such as:
- PURE;
- READ_ONLY;
- MUTATING;
- PRIVILEGED;
- DESTRUCTIVE.

These are not necessarily one mutually exclusive enum; privilege and destructiveness can
be orthogonal dimensions if prior architecture says so.

Shell rendering/help should make consequential behavior understandable without turning
every command into warning spam.

## 21. Predicate Logic

Predicates are especially important for shell composition.

Do not make:
    predicate false
indistinguishable from:
    query failed
or:
    state unknown.

Design both:
- structured predicate result;
- shell exit convention.

For example, a conventional shell mapping might reserve distinct statuses for TRUE,
FALSE and ERROR/UNKNOWN, but validate compatibility with project policy rather than
blindly adopting numbers.

Predicates should be side-effect free except unavoidable bounded observation.

Examples to pressure-test:

    installed foo
    declared some_name
    running service nginx
    enabled service nginx
    healthy service nginx
    ready service nginx
    reachable host example
    writable path /x
    mounted /mnt/data

`running`, `enabled`, `healthy`, `ready` are not synonyms.

## 22. Collision Governance

Collision detection occurs at several times:

DEVELOPMENT:
    new vocabulary proposal -> host/common command audit.

INSTALLATION:
    exported command/function -> target environment audit.

SHELL LOAD:
    detect user alias/function changes.

RUNTIME:
    command resolution knows whether a token belongs to Rebuntu or native shell context.

Do not silently remove user definitions.

If collision prevents safe short-form export, preserve explicit namespaced CLI form.

Maintain a generated collision report/test fixture.

## 23. Context Model

Context can improve ergonomics but is dangerous if invisible.

Candidate context:
- current Rebuntu subject/domain;
- current target set;
- current user/system scope;
- selected host;
- output preference.

Context must be:
- inspectable;
- explicit enough to understand;
- resettable;
- scoped to session unless intentionally persisted;
- incapable of granting authorization;
- incapable of silently escalating from user to system.

Do not import arbitrary shell cwd/environment as semantic context without explicit rules.

## 24. Semi-Natural Grammar Philosophy

Good semi-natural grammar is controlled sugar over canonical IR.

Potential examples to evaluate:

    install package foo
    install foo
    status service nginx
    show status of service nginx
    restart nginx service
    list failed services

Do not support every word order merely because an LLM can understand it.

Define deterministic transformations and ambiguity rules.

Keep the canonical concise form obvious.

## 25. Explainability

    subject
    target
    scope
    qualifiers
    resolved capability/Operation
    provider candidates if relevant
    semantic fallback used? yes/no
    ambiguity
    side-effect/risk class

Do not expose secrets.

## 26. Help System

Help should derive from command specifications where possible.

Support levels such as:
- command summary;
- arguments/options;
- examples;
- subject-specific variants;
- output schema;
- safety notes.

Do not generate authoritative help text live with an LLM.

Semantic service may assist search over help, but source data remains deterministic.

## 27. Error UX

Errors should be precise and actionable.

Bad:
    Invalid command.

Better:
    `restart` is valid, but target `foo` resolves to both a system service and a
    user service. Specify `--scope system` or `--scope user`.

Structured errors should preserve:
- category;
- field/token;
- candidate values;
- evidence/resolution detail;
- safe suggested correction.

Do not auto-correct a destructive command into a different valid command.

## 28. Completion Safety

Completion must not:
- trigger mutations;
- elevate privilege;
- call semantic model for every keystroke;
- scan huge trees;
- expose secrets;
- enumerate sensitive process arguments;
- hang the shell.

Cache only safe metadata with invalidation/TTL as appropriate.

Use registries/catalogs and bounded native queries.

## 29. Compatibility with Scripts

Human convenience must not make automation fragile.

Scripts should be able to:
- request explicit output format;
- disable color;
- avoid prompts;
- distinguish unknown/error;
- set explicit scope;
- use stable canonical names;
- inspect schema/version if needed.

Interactive ambiguity prompting must have a noninteractive deterministic failure mode.

## 30. No Duplicate CLI Ontology

Search for existing:
- argparse/click/typer parsers;
- shell functions;
- command tables;
- aliases;
- completion definitions;
- Operation names;
- query names;
- help text;
- semantic intent schemas.

Consolidate sources of truth.

Do not leave one vocabulary in Bash and another in Python.
