# Rebuntu — Phase 7.15 — Security-State Observation

## Agent Task

## Phase Mission

Observe security-relevant host state—identity, permissions, capabilities, firewall/service exposure and protection status—without turning observation into a security scanner or remediation engine.

## 1. Global Agent Contract

You are implementing **Rebuntu**.

The project identity is exactly `Rebuntu`. Never introduce versioned project identities
such as `Rebuntu 2`, `Rebuntu Next`, `new Rebuntu`, `rebuntu2`, `v2`, or `next`.

Historical implementations are historical Rebuntu artifacts. They are archaeology and
requirements evidence, not architectural authority.

Mandatory engineering method:

SEARCH BEFORE IMPLEMENTING.
COMPOSE BEFORE GENERATING.
UNDERSTAND BEFORE MODIFYING.
USE LINUX BEFORE EMULATING LINUX.
OBSERVE BEFORE INFERRING.
PRESERVE SOURCE BEFORE NORMALIZING.
PRESERVE UNKNOWN BEFORE GUESSING.
TIMESTAMP BEFORE CLAIMING CURRENTNESS.
DISTINGUISH EVENT TIME FROM ACQUISITION TIME.
DISTINGUISH STATE FROM STATUS.
DISTINGUISH LIFECYCLE FROM ACTIVITY, HEALTH, READINESS AND OUTCOME.
DISTINGUISH OBSERVATION FROM DIAGNOSIS.
DISTINGUISH OBSERVATION FROM CONTROL.
DISTINGUISH OBSERVED STATE FROM DESIRED STATE.
DISTINGUISH CURRENT STATE FROM HISTORICAL STATE.
VERIFY CLAIMS WITH EVIDENCE.
MAXIMALIST EXPLORATION; CONSERVATIVE IMPLEMENTATION.

Phase 7 is where Rebuntu obtains a coherent observational model of the host.

The target conceptual chain is:

    native Linux source
        -> acquisition
        -> raw observation
        -> source-specific parsing
        -> typed normalization
        -> Fact
        -> provenance + time + quality
        -> current-state projection
        -> optional historical change record
        -> query / shell / service consumer

Do not turn this into:

    poll everything -> dump into global dict -> call it system state

or:

    LLM reads command output -> guesses system state

### Earlier architecture to reuse

Phase 0 established the grammar for state/status/lifecycle/health/readiness, events,
interfaces/providers, results/evidence, naming/registries and execution.

Phase 2 established identity, scope, authorization and filesystem/runtime boundaries.

Phase 3 established infrastructure and the bounded semantic service.

Phase 4 established runtime/resolution/activation/execution.

Phase 5 established event/journal/stability/evidence/diagnostic collection services.

Phase 6 established the shell language and predicates/query mapping.

Phase 7 must integrate those mechanisms. Do not create parallel observation APIs merely
because a domain has a convenient command-line utility.

### Native Linux first

Prefer the lowest appropriate stable native interface:
- `/proc`;
- `/sys`;
- sysfs;
- procfs;
- systemd D-Bus / sd-bus-compatible interfaces;
- journald APIs/structured journal access;
- udev;
- netlink;
- rtnetlink;
- cgroups;
- PSI;
- mountinfo;
- kernel-exposed counters;
- appropriate driver/vendor APIs where no generic kernel interface suffices.

CLI tools such as `ps`, `ip`, `lsblk`, `systemctl`, `nvidia-smi`, `sensors`, `df`,
`findmnt`, `loginctl` may be useful as discovery/reference/fallback providers, but do not
blindly parse unstable human output when a structured/native interface exists.

Do not reimplement Linux.

### Python-first

Python owns:
- typed observations/facts;
- acquisition coordination;
- normalization;
- provenance;
- freshness;
- domain adapters;
- state composition;
- bounded history;
- queries/tests.

Bash remains thin interactive/native-command glue.

C/C++ is justified only when a native/performance interface actually requires it.

### No hidden mutation

Observation paths are read-only unless an unavoidable kernel/API interaction has explicitly
documented benign side effects.

Do not:
- restart a service to learn its state;
- mount a filesystem to inspect whether it is mounted;
- wake a GPU just to populate optional metrics without policy;
- change a governor to inspect CPU frequency;
- alter permissions to test writability;
- probe network targets aggressively;
- repair filesystems while observing them.

Observation must not silently become control.

### UNKNOWN is valid

The system must distinguish at least:
- known value;
- known absence;
- unknown;
- unsupported;
- unavailable;
- stale;
- acquisition failure;
- permission denied;
- partial/truncated.

Never turn:
permission denied -> false
provider missing -> false
stale cache -> current
parse error -> absent
unsupported metric -> zero.

### Observation versus Fact

An Observation is source-bound evidence obtained at a time.

A Fact is a typed claim derived from one or more observations under explicit rules.

Do not prematurely force one class model if existing architecture has equivalent names,
but preserve this semantic distinction.

Example:

    Observation:
        source=/proc/123/status
        acquired_at=...
        raw/parsed state="S"

    Fact:
        process 123 lifecycle/activity indicates sleeping
        provenance=[observation-id]
        observed_at=...
        freshness=...

Facts must be traceable back to evidence.

### Identity

State is meaningless without stable-enough subject identity.

Do not identify:
- process solely by PID across time;
- GPU solely by `nvidia-smi` index;
- block device solely by `/dev/sdX`;
- network interface solely by a transient name if stronger identity is available;
- mount solely by textual path when mount identity matters.

Use domain-appropriate identities and record aliases.

### Time

Every time-sensitive observation must reason about:
- event time if known;
- acquisition time;
- monotonic sample interval where appropriate;
- wall-clock timestamp for reporting;
- freshness TTL/policy;
- source update cadence;
- age;
- staleness.

Counters requiring deltas must not be presented as instantaneous rates without a sampling
interval.

### Evidence

Evidence/provenance is first-class.

For significant facts retain enough to answer:
- where did this come from?
- when was it observed?
- which provider/interface?
- was it direct or derived?
- what raw/native evidence supports it?
- was anything truncated?
- how fresh is it?
- what failed to be observed?

Do not log secrets or huge raw dumps by default.

### Semantic service

The semantic service is not the state authority.

It may later summarize or classify evidence, but Phase 7 state truth must come from
deterministic/native observations.

Never use an LLM to decide whether a process exists, a filesystem is mounted, a service is
running, or a GPU has a temperature when deterministic sources exist.

## 2. Canonical Observation Model

Inspect existing Phase 0 state/result/evidence types before creating anything.

A useful observation representation may need:

- observation_id;
- subject identity;
- domain;
- field/metric;
- value;
- unit;
- source/provider;
- source locator;
- acquired_at;
- event_time if available;
- monotonic sample marker if useful;
- quality;
- freshness;
- raw evidence reference;
- error/unknown reason;
- derivation metadata.

Do not implement this exact shape blindly.

### Fact model

A fact may need:
- fact identity/type;
- subject;
- canonical value/state;
- supporting observation IDs;
- derived/direct flag;
- valid/fresh interval;
- confidence/quality only when meaningful;
- contradiction metadata.

Do not use fake numeric confidence percentages for deterministic facts.

### State dimensions

Reuse established orthogonal dimensions where applicable:

Lifecycle:
    initialized / running / completed / failed / ...

Activity:
    busy / waiting / idling / sleeping / resting / ...

Control:
    enabled / disabled / paused / locked / frozen / ...

Availability:
    available / unavailable / unknown / ...

Readiness:
    ready / not_ready / unknown / ...

Health:
    healthy / degraded / unhealthy / unknown / ...

Outcome:
    completed / failed / cancelled / timed_out / ...

Do not force every domain into every dimension.

### State snapshot

A snapshot is a coherent projection of observations/facts for a bounded subject/domain/time.

It is not necessarily an atomic view of the whole machine.

Record snapshot timing/partiality.

### Contradiction

Two providers can disagree.

Do not silently pick one.

Define:
- source priority only where justified;
- contradiction representation;
- freshness comparison;
- direct versus derived precedence;
- diagnostic evidence.

### Freshness

Freshness policy can be field/domain-specific.

Examples:
- static CPU topology can remain fresh much longer than CPU utilization;
- package inventory changes rarely;
- process existence changes quickly;
- thermal readings age quickly;
- device serial number is effectively static during device lifetime.

Avoid one global TTL.

### Pull versus push

Observation can be:
PULL:
    query/acquire on demand.

PUSH:
    event/native notification updates known state.

HYBRID:
    event-driven updates plus periodic reconciliation.

Prefer event-driven mechanisms where reliable, but retain reconciliation where events can
be missed.

Do not create a polling daemon for every metric.

### Sampling

For metrics such as utilization/rates:
- define sample window;
- use monotonic time;
- handle counter wrap/reset;
- handle subject disappearance;
- distinguish cumulative counter from rate;
- avoid synchronized high-frequency polling across all domains.

### Caching

Cache only when useful.

Cache entries require:
- subject identity;
- value/fact;
- acquisition time;
- freshness policy;
- invalidation trigger if known.

Cache is not truth.

Stale data must be marked stale.

### Partial observation

A system view can be useful even if one provider fails.

Return partial results with explicit missing/failed components rather than failing the whole
host snapshot by default.

### Cost classes

Classify acquisitions where useful:
- cheap/local;
- moderate;
- expensive;
- potentially waking hardware;
- privileged;
- externally networked.

Default current-state queries should avoid expensive or intrusive probes unless requested.

### Security/privacy

Process command lines, environment, network sockets, usernames, mount paths and device
metadata can be sensitive.

Collect only what the consumer needs.

Do not expose secrets in logs/evidence.

Respect user/system scope and permissions.

## 3. Domain Observation Requirements

### Processes

Study `/proc`, procfs semantics, process start time, PID reuse, task/thread distinction,
process state, parentage, credentials, namespaces/cgroups where useful, CPU/memory counters,
I/O counters and permission limitations.

Stable process identity should combine PID with start-time/boot identity or an equivalent
established mechanism.

Do not call every sleeping process unhealthy.

Linux zombie state has precise semantics.

### Services

Prefer systemd structured interfaces.

Observe independently:
- existence/load state;
- active state;
- substate;
- enablement;
- failed state;
- main PID where meaningful;
- readiness only when there is an actual readiness contract;
- health only when a health contract exists;
- user/system manager scope.

Do not equate `active` with healthy or ready.

### Filesystems/storage

Observe:
- mount table/mountinfo;
- filesystem type/options;
- source device;
- capacity/free/available/inodes;
- read-only state;
- block topology;
- stable UUID/WWN/serial where available;
- device-mapper/LUKS/MD/LVM relationships where safely discoverable;
- kernel/journal error evidence references where integrated.

Do not run fsck as observation.

Do not open raw block devices unnecessarily.

### Devices

Use sysfs/udev identity and lifecycle.

Observe:
- subsystem;
- sysfs path;
- stable properties;
- driver;
- parent/child relation;
- presence;
- add/remove/change events where Phase 8 integration will use them.

Do not encode every device type into one giant Device class.

### Network

Use netlink/rtnetlink or justified structured providers.

Observe separately:
- interface existence;
- administrative state;
- carrier/operational state;
- addresses;
- routes;
- neighbors where useful;
- sockets/listeners where permitted;
- DNS configuration if within scope;
- reachability only via explicit bounded probe.

`interface UP` != Internet reachable.

### CPU

Observe:
- topology;
- online/offline;
- frequency/cpufreq where available;
- load;
- cumulative CPU counters;
- utilization derived from intervals;
- pressure;
- thermal relation only where topology supports it.

Do not infer instantaneous utilization from a single cumulative counter.

### Memory

Observe:
- total/available/free;
- swap;
- page/cache fields as appropriate;
- PSI;
- cgroup limits/usage when relevant;
- OOM evidence through journal/event integration.

Avoid simplistic `free == available`.

### GPU

Support the actual host while keeping architecture provider-aware.

Potential sources:
- sysfs/DRM;
- NVIDIA NVML;
- vendor APIs;
- `nvidia-smi` only as justified fallback/reference.

Observe stable PCI identity/UUID, not only ordinal index.

Possible fields:
- model;
- PCI address;
- driver;
- memory total/used;
- utilization;
- power;
- temperature;
- clocks;
- performance state;
- display attachment where discoverable;
- errors/fault evidence.

A missing metric must be unsupported/unknown, not zero.

### Power/thermal

Observe hwmon, thermal zones, power supply class and vendor interfaces as justified.

Map sensors to hardware cautiously.

Do not claim a temperature belongs to a CPU/GPU/device without evidence.

### Desktop/session

Observe:
- logind sessions/seats;
- session type;
- display server;
- desktop environment;
- active session;
- display topology through appropriate session APIs/providers;
- Wayland/X11 boundaries.

Do not require graphical session for host observation.

### Packages/software

Distinguish:
- package installed;
- executable available in PATH;
- Flatpak installed;
- Snap installed;
- Python package/import available;
- service available;
- application operational.

Use provider-specific evidence behind canonical facts.

### Security state

Observation may include:
- effective identity;
- groups;
- file ownership/mode/ACL where requested;
- Linux capabilities;
- service/socket exposure;
- firewall state through appropriate provider;
- AppArmor/SELinux status if applicable;
- relevant system hardening facts.

Do not attempt vulnerability remediation in Phase 7.

## Phase-Specific Contract

Implement bounded security-state facts using existing Phase 2/13-facing concepts and native sources. Observe capabilities, identity, relevant firewall/protection/service exposure where reliable. Do not market this as vulnerability detection or remediation.

## 4. Mandatory Cross-Domain Test Matrix

Test every implemented domain for:

- source available;
- source unavailable;
- permission denied;
- malformed/unexpected source data;
- subject disappears mid-read;
- provider timeout;
- partial data;
- unsupported metric;
- stale cached observation;
- refresh;
- contradiction between sources;
- Unicode/path spaces;
- large subject count;
- cancellation;
- concurrent readers;
- reboot/boot identity where relevant;
- no mutation;
- provenance retained;
- structured serialization;
- shell/query consumption.

### Time/freshness tests

- current fresh;
- just expired;
- stale accepted only when caller explicitly permits;
- wall clock changes;
- monotonic sampling;
- event timestamp older/newer than acquisition;
- counter reset;
- provider returns no timestamp;
- cached static metadata;
- rapidly changing metric.

### Identity tests

- PID reuse simulation;
- GPU index reorder;
- block device path rename;
- network interface rename;
- device hotplug;
- mount source/path change;
- service user/system same name.

### State semantics

- running != ready;
- ready != healthy;
- enabled != running;
- available != active;
- known absent != unknown;
- stale != unavailable;
- failed acquisition != false.

### Performance

Test bounded observation cost for:
- one subject;
- one domain;
- full current-state view;
- large process list;
- completion/query hot path.

No high-frequency polling loops merely to make tests pass.

### Safety

Verify:
- no sudo inside observation adapters;
- no service restart;
- no mount/unmount;
- no package mutation;
- no GPU clock/power mutation;
- no network configuration mutation;
- no filesystem repair;
- no arbitrary shell=True;
- no semantic model determining deterministic facts.

### Adversarial review

Search specifically for:
- `subprocess` calls parsing human CLI output;
- `shell=True`;
- `sudo`;
- hidden writes to `/proc` or `/sys`;
- service restart/start calls;
- mount/package/network mutations;
- GPU setters;
- state booleans defaulting false after exception;
- `except: pass`;
- timestamps created at render time rather than observation time;
- PID-only historical identity;
- GPU-index-only identity;
- `/dev/sdX` as persistent identity;
- one global freshness TTL;
- raw command output treated as canonical state;
- state caches without age;
- global dictionaries mutated from multiple collectors;
- high-frequency polling loops;
- LLM calls inside deterministic state acquisition.

Every finding must be fixed, explicitly justified, or documented as deferred with exact owner phase.
