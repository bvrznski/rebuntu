### Native event sources first

Prefer appropriate native mechanisms:
- journald structured entries;
- systemd D-Bus signals;
- udev;
- netlink/rtnetlink;
- inotify/fanotify where appropriate;
- kernel tracepoints/eBPF/perf only when justified;
- signalfd/eventfd/timerfd where relevant to runtime;
- Unix sockets/D-Bus for Rebuntu internal event producers.

Do not implement a polling event bus when Linux already emits the transition.

Periodic reconciliation remains valid where native events can be missed.

### Python first

Python owns typed events, normalization, assertion evaluation, correlation, bounded
retention, evidence requests, alerts and tests.

Bash is thin glue only.

Do not pipe logs through grep loops as the event architecture.

### Event is not Fact

An Event says that a source reported/observed an occurrence or transition.

A Fact is a typed claim about the system supported by evidence.

A journal message saying "GPU Xid" is an Event/evidence item. It is not automatically a
Fact that the GPU is physically defective.

### Event is not Request

Event:
    something occurred / was observed.

Request:
    someone/something asks Rebuntu to do work.

Signal:
    low-level notification/coordination mechanism.

Message:
    transported information envelope.

Trigger:
    a condition/binding that makes work eligible.

Alert:
    an internal/user-facing indication requiring attention.

Do not collapse these into one generic message class.

### Event identity

Every event must have sufficient identity to support deduplication and provenance without
assuming globally distributed UUID semantics are always necessary.

Consider:
- source instance;
- source sequence/cursor if available;
- boot ID;
- subject identity;
- event type;
- event time;
- acquisition time;
- provider-native identifier.

Synthetic Rebuntu event IDs may wrap source identity but must not erase it.

### Time

Distinguish:
- source/event time;
- acquisition/processing time;
- monotonic time;
- wall clock;
- boot/session identity;
- temporal window;
- lateness;
- ordering certainty.

Never compare unrelated monotonic clocks across boots.

A reboot is an explicit temporal boundary.

### Delivery semantics

Do not promise exactly-once delivery unless the actual mechanism proves it.

Model practical semantics:
- at-most-once;
- at-least-once;
- replayable;
- cursor-based;
- lossy;
- best effort.

Consumers must tolerate duplicates where sources can replay.

### Loss

Loss is a state/evidence condition.

If queue overflow, journal cursor gap, source disconnect or event storm causes loss, record
it explicitly.

Never silently drop events and continue claiming complete causal history.

### Backpressure

All event pipelines must be bounded.

Define:
- queue limits;
- overflow behavior;
- producer behavior;
- consumer lag metrics;
- coalescing;
- drop policy if unavoidable;
- loss evidence;
- recovery/reconciliation strategy.

No unbounded Python Queue/list of historical events.

### Persistence

Persist only where a consumer/recovery requirement justifies it.

Do not build Kafka.

Journald is already a persistent event/evidence substrate for many host events.

Prefer source cursors/boot IDs and compact derived records over copying the whole journal
into a second database.

### Safety

Phase 8 evaluation is deterministic and read-oriented.

Rules/conditions may emit typed requests or alerts, but they must not execute arbitrary
shell or privileged actions.

No:
    event -> Python eval()
    event -> shell=True
    alert -> sudo command
    model summary -> action

### Semantic model

The semantic service may later assist classification/summarization of ambiguous evidence,
but deterministic event/state semantics must remain authoritative.

If model assistance is used at all:
    evidence -> bounded model classification -> typed candidate -> validation -> marked
    derived/semantic result.

Never let model prose become an invariant, fact or executable rule implicitly.

## 2. Canonical Phase 8 Ontology

Validate these distinctions against the repository and Phase 0 documents.

### Event

A typed occurrence/transition notification with:
- event type;
- subject;
- source;
- event time if known;
- acquisition time;
- payload;
- provenance/evidence;
- source identity/cursor;
- scope;
- quality/loss metadata.

### Fact

A typed claim about a subject/state, direct or derived, backed by observations/events.

### Assertion

An evaluable proposition over facts/state.

Examples:
    service nginx is running
    filesystem /home has available_space > threshold
    GPU UUID X has temperature < threshold

Assertion result should support:
TRUE / FALSE / UNKNOWN / ERROR or the canonical equivalent.

### Condition

A reusable boolean/temporal composition over assertions/facts/events.

### Invariant

A condition expected to hold throughout an explicit applicability scope/window.

Example:
    while workload profile X is active, mount Y must remain present.

Do not define "everything healthy" as a giant invariant.

### Constraint

A restriction on admissible state/action/configuration.

Example:
    GPU temperature must not exceed policy ceiling for a proposed performance operation.

Constraint is not necessarily a claim that the current state is already compliant.

### Rule

A deterministic mapping:
    WHEN typed condition
    THEN typed conclusion/request/alert classification

A Rule is not arbitrary Python code.

### Violation

A concrete instance where an applicable invariant/constraint/rule expectation is broken.

It has evidence, first_seen, last_seen, current/resolved state and subject/scope.

### Correlation

A relationship among events/facts/violations based on explicit correlators.

Correlation may be strong without being causal.

### Causal chain

A candidate explanation linking evidence with explicit relationship types and uncertainty.

### Internal Alert

A machine-oriented attention object indicating a condition/violation worth routing,
tracking, correlating or presenting.

It is not necessarily a desktop notification.

### Evidence Request

A bounded request to acquire additional observations/evidence to resolve UNKNOWN,
contradiction or competing hypotheses.

### Escalation

A state transition in attention/handling based on persistence, worsening, repeated failure,
broader impact or policy—not merely a larger number.

## 3. Assertion Direction

Preserve the conceptual direction:

    Observation
      -> Fact
      -> Assertion
      -> Condition
      -> Invariant / Constraint / Rule
      -> Violation
      -> Internal Alert
      -> Correlation
      -> Evidence Request / Escalation

Not every Fact needs an Assertion.
Not every false Assertion is a Violation.
Not every Event becomes an Alert.
Not every Alert requires automation.
Not every correlation becomes causation.

## 4. Temporal Grammar

Reuse Phase 0.9 rather than inventing a second time language.

Support only justified temporal constructs such as:

    A THEN B
    A THEN B WITHIN 10s
    A AND B WITHIN 30s
    A WHILE B
    A PERSISTS FOR 20s
    A UNTIL B
    NOT A FOR 5m

Pressure-test the richer historical idea:

    A THEN B within 10s
      THEN {C OR D} within 30s
      WHILE NOT E

Implement only the smallest grammar justified by real Phase 8 consumers.

Temporal operators must define:
- event-time vs processing-time basis;
- inclusive/exclusive bounds;
- late event handling;
- reboot/session boundaries;
- UNKNOWN;
- cancellation/expiration;
- retained evidence.

Do not implement a general CEP language unless actual use proves necessary.

## 5. Correlation and Causality Discipline

Correlation dimensions may include:
- same stable subject;
- parent/child/topology relation;
- same device PCI path;
- same filesystem/block-device chain;
- same process/service/cgroup;
- same boot;
- same session;
- same execution/job/workflow ID;
- same evidence/request correlation ID;
- temporal proximity;
- known dependency;
- known producer/consumer relation;
- kernel error sequence.

Each relationship must be explicit.

### Causality levels

Use a vocabulary such as:
1. ORDERED_WITH — observed temporal ordering only.
2. CORRELATED_WITH — explicit correlation criteria satisfied.
3. DEPENDS_ON — known architectural/system dependency.
4. CONTRIBUTED_TO — evidence supports contribution.
5. CANDIDATE_CAUSE — plausible hypothesis requiring evidence.
6. CAUSE_SUPPORTED — strong evidence under defined diagnostic rule.

Do not use these exact names if repository vocabulary already exists, but preserve the
distinction.

### Alternative hypotheses

For diagnostics, retain competing explanations.

Example after a hang/reboot:

    hypothesis A:
        NVIDIA driver fault -> GPU reset/stall -> workload freeze

    hypothesis B:
        NVMe I/O stall -> blocked tasks -> desktop/system hang

    hypothesis C:
        memory pressure -> reclaim/OOM-related degradation -> apparent hang

Evidence may strengthen/weaken each.

Do not collapse to one root cause because one scary log line exists.

### Negative evidence

Absence can be informative only when source coverage is known.

"No Xid in captured journal" is not equivalent to "no GPU fault" if journal capture has a
gap.

Track coverage/loss before using negative evidence.

## 6. Event Storm and Loop Safety

Sources can generate storms:
- filesystem change cascades;
- network flaps;
- device hotplug;
- service restart loops;
- kernel repeated errors;
- automation-caused events.

Provide:
- event fingerprinting;
- dedup windows;
- coalescing;
- debounce;
- rate limits;
- bounded queues;
- per-source quotas where justified;
- recursion/loop correlation IDs;
- source loss accounting;
- storm summaries.

Do not hide a storm by deleting all repeated evidence.

Keep representative samples + counts + first/last times.

### Feedback loop preparation

Phase 9 automation may produce system changes that emit Phase 8 events.

Prepare correlation/provenance fields so later logic can recognize:
    automation request -> operation -> resulting event

without suppressing legitimate external events.

Do not implement Phase 9 automation now.

## 7. Evidence Requests

When evaluation cannot decide safely:

    assertion -> UNKNOWN
        -> identify missing evidence
        -> bounded EvidenceRequest
        -> acquisition through Phase 7
        -> new observations/facts
        -> reevaluate

EvidenceRequest must specify:
- subject;
- requested fact/field;
- reason;
- requester/correlation;
- cost class;
- deadline/timeout;
- scope;
- privilege requirement;
- maximum expansion;
- whether waking/external probing is allowed.

Evidence requests must not become arbitrary commands.

Examples:
- refresh service state;
- acquire GPU metrics;
- read previous-boot journal range;
- refresh mount topology.

Riskier probes should remain disallowed or require explicit policy.

### Evidence budget

Prevent recursive evidence loops.

Bound:
- depth;
- number of requests;
- time;
- acquisition cost;
- subject expansion.

Record when evaluation remains UNKNOWN because budget was exhausted.

## 8. Internal Alerts

Internal alerts should contain:
- alert type;
- subject/scope;
- source violation/condition;
- first/last seen;
- current lifecycle;
- severity dimensions;
- evidence;
- dedup key;
- correlation group;
- confidence/uncertainty where derived;
- recommended next evidence if applicable.

Do not force one fake scalar severity if dimensions are useful.

Possible dimensions:
- impact;
- urgency;
- persistence;
- scope;
- confidence;
- recoverability.

### Alert lifecycle

Candidate:
NEW -> ACTIVE -> ACKNOWLEDGED? -> RESOLVED -> CLOSED

But acknowledgment is user/workflow semantics and may be deferred.

At minimum distinguish active versus resolved/repeated.

A repeated event should not necessarily create a new alert.

### User notification boundary

Internal Alert != desktop/email/user notification.

Phase 5 reporting may render selected alerts.
Future automation may consume them.

Do not hardwire notification channels into assertion evaluation.

## Phase-Specific Contract

Build an event-source catalog with source type, native mechanism, reliability, replay/cursor support, clock, privilege, cost and loss semantics. Integrate only sources with real consumers. Include journald/systemd/udev/netlink/runtime sources where already justified. Avoid polling-as-events when a native event exists.

- condition/rule;
- one evolving violation/alert rather than hundreds;
- restart-loop correlation;

Input may include:
- NVIDIA Xid/driver messages;

### Scenario F — low disk space

### Scenario G — incomplete evidence

Input:

### Scenario H — event storm
