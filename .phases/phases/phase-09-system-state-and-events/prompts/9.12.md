# Rebuntu --- Phase 9.12 --- Automation Policy

## Agent Task

Execute this phase as a full repository-aware implementation/audit task.
Do not treat this file as an outline. Inspect, reason, implement the
smallest coherent architecture, integrate, test, document, and audit.

## Phase Mission

Implement explicit policy governing whether an otherwise matched
Automaton may activate or execute, including scope, authorization, risk,
context, resource and suppression constraints.

## Core architectural contract

Rebuntu is the only project identity. Historical Rebuntu artifacts are
archaeology, not a compatibility target. SEARCH BEFORE IMPLEMENTING.
COMPOSE BEFORE GENERATING. UNDERSTAND BEFORE MODIFYING. USE LINUX BEFORE
EMULATING LINUX. Automation answers **when/why bounded work becomes
eligible**. Operations answer **what one bounded action means**.
Workflows answer **how multiple meaningful actions are coordinated**.
Schedules answer **when temporal eligibility occurs**. Events describe
occurrences. Conditions evaluate state. Services provide managed
functionality. Daemons are long-lived processes. Do not collapse these
concepts.

Canonical direction: Phase 7 observation/state + Phase 8
events/assertions/conditions + Phase 0.9 time → TriggerBinding →
Automaton eligibility → automation policy → Activation → Phase 4 runtime
→ Operation / Workflow / Task → Execution / Attempt → verification →
evidence/result → Automaton state/history.

Never implement `event -> shell command`, `condition -> sudo bash`,
`LLM -> automation action`, or a generic callback registry that bypasses
Operations/Workflows.

## Native Linux first

Prefer systemd timers, path/socket/device activation, udev, D-Bus,
kernel event sources and established Phase 8 event streams. Rebuntu
should add semantic policy, typed bindings, evidence and
composition---not replace Linux supervision/scheduling. Persistent
recurring wall-clock work should normally use systemd timers when their
semantics fit. In-process timers are appropriate only for bounded
runtime-local behavior. Do not build cron, systemd or udev again in
Python. Long-running work must not execute inside udev handlers. Socket
activation must delegate lifecycle to the appropriate service/runtime
boundary. Path activation must account for coalescing and missed
transitions.

## Automaton ontology

An Automaton is a reusable automation definition/specification. An
AutomationOccurrence/Activation is a concrete runtime occurrence. A
TriggerBinding connects a typed trigger source to an Automaton.
Eligibility means trigger/condition/time criteria matched; it does not
mean authorization or execution succeeded. Keep separate: definition
identity, activation identity, Job/Execution/Attempt identity, result,
verification, and evidence. Candidate definition fields: stable ID,
purpose, trigger bindings, condition gates, target capability reference,
arguments/template, scope, policy, overlap policy, debounce/coalesce
policy, throttle/cooldown, retry policy, state persistence requirements,
evidence policy, enablement, version/provenance. Reuse existing
canonical types instead of copying this shape blindly.

## Activation semantics

Activation must be typed and inspectable. Record trigger identity,
source event/fact/schedule, subject, scope, event time, processing time,
correlation/provenance IDs, dedup identity and why the binding matched.
A trigger may make an Automaton eligible. Policy may still suppress it.
Resource/runtime constraints may delay it. Overlap policy may
reject/coalesce/queue it. Execution may fail. Verification may fail.
These states must not be collapsed into one boolean. Raw event payloads
are inert data. Never interpolate raw udev/journal/path/socket fields
into shell command strings.

## Overlap, concurrency and idempotency

Define overlap policy explicitly: ALLOW, FORBID/SKIP, COALESCE,
QUEUE_BOUNDED, REPLACE/CANCEL_PREVIOUS only where semantically
justified. Never allow unbounded pending activations. Do not assume an
idempotent Operation makes repeated automation harmless: repeated
notifications, resource cost and external effects may still matter. Use
native/runtime locks only where ownership semantics require them. Do not
revive stale marker-file `.lock` truth as a concurrency system.

## Time and scheduling

Reuse Phase 0.9 clocks and temporal grammar. Distinguish schedule,
delay, timeout, deadline, interval, recurrence, retry backoff, cooldown,
debounce and rate limit. Persistent schedules must define
missed-run/catch-up behavior, timezone/DST semantics, boot boundaries,
persistence and overlap. Monotonic clocks are for elapsed intervals;
wall clock is for calendar scheduling/reporting. Never compare monotonic
values across boots.

## Failure model

Separate: source failure, trigger-evaluation failure, binding failure,
policy denial/suppression, activation submission failure, execution
failure, timeout, cancellation, verification failure, evidence failure
and state-persistence failure. Retry belongs to a specific failed unit
of work and must reuse Attempt semantics. An event replay is not a
retry. A new trigger is not necessarily a retry. Cooldown is not
backoff. Retry policy must be bounded by attempts/time/deadline and must
preserve all attempt history.

## Verification and evidence

Execution success is not verified success. The invoked
Operation/Workflow remains authoritative for its
postconditions/evidence. Automation may add a higher-level condition
such as 'desired event consequence observed within window', but must not
duplicate domain verification. Trace: source evidence → trigger match →
policy decision → activation → target capability →
Job/Execution/Attempts → result → verification → automation outcome.
Preserve suppression/no-op decisions as evidence where operationally
useful.

## Feedback-loop prevention

Automation causes changes; changes produce events; events can reactivate
automation. Preserve correlation/provenance so self-induced events can
be recognized without blindly suppressing them. Implement loop
safeguards using bounded recurrence detection, causality/correlation
IDs, cooldown, dedup, policy and explicit self-trigger rules. Do not
globally ignore all Rebuntu-caused events: legitimate follow-up
automation may depend on them. Test A→Operation→event A loops, A→B→A
cycles and multiple Automatons sharing a subject.

## Security and authorization

Enablement is not authorization. Root execution is not authorization. A
valid trigger is not authorization. Policy must be checked at the
appropriate activation/execution boundary using Phase 2 semantics.
Automaton definitions cannot contain arbitrary privileged shell
fragments. Arguments must validate against target Operation/Workflow
schemas. Secrets use established secret/config boundaries and never
appear in evidence/logs. Destructive/privileged work requires the same
or stronger controls as interactive execution. Automation must not
weaken safeguards merely because no human is present.

## State and persistence

Persist only state needed for correctness/recovery: enablement if
user-configurable, last processed cursor/activation where required,
cooldown/retry state, bounded history, provider identity and recovery
metadata. Do not store volatile truth in marker files. Do not create one
mutable JSON blob for all Automatons. Use established runtime/state
directories, ownership, atomic updates/transactions and schema/version
rules. After crash/reboot classify pending/running activations using
evidence: completed, interrupted, still represented by native provider,
unknown, requires verification, retryable, abandoned. Never blindly
rerun unknown destructive work.

## Semantic-model boundary

BitNet/semantic interpretation is not an automation authority. Model
output may help a human formulate a typed Automaton definition in later
UX, but definitions must validate against canonical triggers, subjects,
Operations, scopes and policy. No model-generated Python, shell, systemd
directive or udev rule may become executable merely because it parsed
successfully.

## Performance and boundedness

All trigger queues, histories, pending activations, retry sets,
coalescing windows and caches are bounded. Event storms must not create
unbounded Jobs. Measure trigger-to-activation latency for representative
native sources and scheduled work. Avoid model calls and expensive
full-state scans on every event. Reuse Phase 8 correlation/coalescing
and Phase 7 targeted evidence acquisition.

automaton/automation classes, `automatons`, pipes/FIFOs,
`.lock/.stop/.hold/.on/.en`, while/sleep loops, cron entries, systemd

## Required pressure scenarios

### Service crash loop

systemd failed/restart events trigger one bounded diagnostic/reporting
Automaton; repeated events coalesce; no infinite restart feedback.

### GPU fault after workload

GPU Xid/driver event can trigger bounded evidence collection; stable GPU
UUID/PCI identity preserved; no GPU reset or clock change unless a
separately authorized future Operation is explicitly bound.

### NVMe I/O fault

kernel/storage event triggers evidence snapshot; no fsck, mount mutation
or destructive recovery; stormed I/O errors remain bounded.

### Low disk

condition crosses threshold, fires on transition/persistence according
to definition, resolves when state recovers, and does not repeatedly
fire every poll.

### File organizer

historical auto-organization intent is represented as path/event trigger
→ typed Workflow/Operation with plan/verification, never watcher shell
loop + destructive mv.

### Hotplug

udev add/remove duplicates are tolerated; substantial work leaves udev
context; device stable identity is used.

### Scheduled maintenance

systemd timer provider survives reboot and records missed-run/overlap
semantics; runtime does not maintain a duplicate sleeping process.

### Feedback cycle

Automaton A changes service → service event matches B → B changes state
that matches A; correlation/cooldown/policy prevents uncontrolled
oscillation while preserving evidence.

### Crash/reboot

Rebuntu restarts with an activation whose target outcome is unknown;
system verifies/reconstructs before deciding retry; destructive work is
never blindly repeated.

### Hostile payload

event/path/device metadata contains command substitution, quotes or
prompt-injection text; it remains inert typed data.
