### Binding earlier phases

Reuse rather than duplicate: - Phase 0.8 Task/Job/Execution/Attempt
semantics; - Phase 0.10 Operations; - Phase 0.11 Workflow grammar; -
Phase 0.13 execution runtime roles; - Phase 0.17

Automatons/triggers/policy.

The Workflow runtime must submit real work through Phase 4. Do not build
another executor, process manager, scheduler, event bus or automation
engine inside `workflow`.

### Workflow is not Automation

Automation decides when/why a Workflow becomes eligible. Workflow
defines how coordinated work proceeds.

A Workflow may be invoked manually, from CLI/API, from an Automaton, or
from another explicit composition mechanism.

Do not put event watchers, timers, cron loops or udev subscriptions into
Workflow code.

### Workflow is not Operation

An Operation is one semantically bounded system capability. A Workflow
coordinates multiple independently meaningful capabilities.

If a "workflow" contains one Operation and no meaningful coordination
semantics, question whether it should exist.

If a "step" contains 200 lines of domain logic, question whether that
logic belongs in an Operation/provider instead.

### Definition versus execution

WorkflowDefinition != WorkflowExecution. StepDefinition !=
StepExecution. Plan != Execution. Checkpoint != Snapshot of Python
objects. Result != stdout. Workflow completed != Workflow verified.

Runtime identities must link to the definition/version and all
underlying execution identities without confusing them.

### No arbitrary code in definitions

Persisted/configured workflow definitions must not contain: - Python
eval/exec; - arbitrary lambdas/callables; - shell snippets; - `sudo`
strings; - unrestricted Jinja expressions that become code; -
model-generated executable source.

Definitions reference registered typed capabilities and allowed
expression/condition forms.

### Python first

Python owns: - workflow definitions/schema; - graph/control flow; -
typed data propagation; - planning; - orchestration; - checkpoint
metadata; - retry/resume coordination; - rollback/compensation
planning; - verification composition; - reporting/tests.

Bash remains thin shell/native glue.

### Native Linux first

A Workflow coordinates Linux-native Operations; it does not wrap every
native mechanism with an extra orchestration process.

Use systemd lifecycle/scheduling/activation where those are the actual
native owners. Use the Phase 4 runtime for execution. Use Phase 9 for
automation. Use Phase 8 for conditions/events. Use Phase 7 for state
acquisition.

### Semantic model boundary

BitNet/semantic services may help interpret a human request into a typed
candidate Workflow request, but they are never the workflow executor or
authority.

Required boundary:

    natural language
        -> typed candidate intent
        -> schema validation
        -> capability/workflow resolution
        -> authorization/policy
        -> deterministic Workflow runtime

Never: LLM -\> shell LLM -\> arbitrary Workflow graph -\> privileged
execution

## Workflow Graph and Structural Semantics

Start from the smallest useful graph model.

A Workflow may require: - nodes: Steps and only justified structural
nodes; - edges: explicit control/data dependencies; - entry
conditions; - terminal conditions; - branch edges; - join/barrier nodes
or semantics; - failure edges/policies; - rollback/compensation
metadata.

Do not assume every Workflow needs Phase -\> Stage -\> Step.

### Phase

A Phase is justified when it expresses a meaningful coarse semantic
boundary such as: - prepare; - mutate; - verify; - recover; - finalize.

It may have phase-level gates/checkpoints/reporting.

If it merely groups files/UI rows, do not make it runtime ontology.

### Stage

A Stage is justified only if it has distinct semantics, e.g.: - a
concurrency wave; - a barrier; - a resource boundary; - a verification
boundary; - a deployment cohort.

Do not create Phase and Stage merely because both words exist.

### Step

A Step references a registered executable capability.

Candidate StepDefinition: - step_id; - capability reference; - typed
input bindings; - dependency references; - condition/gate; -
timeout/deadline; - retry policy reference; - expected outputs; -
side-effect metadata inherited from target; - rollback/compensation
reference if valid; - evidence policy.

Reuse existing types.

### Graph validation

Before execution validate: - node identity uniqueness; - all references
resolve; - no unintended cycles; - reachable terminal state; - required
inputs available; - output references valid; - branch/join
compatibility; - rollback/compensation references valid; -
resource/concurrency policy valid; - authorization/policy can be
evaluated; - no secret is routed to an unauthorized consumer.

Cycles must be rejected unless a deliberately bounded loop construct is
later justified. Do not smuggle loops into graph edges.

### Planning

Workflow planning should produce an inspectable execution plan: -
resolved definition/version; - target subjects; -
providers/capabilities; - graph/dependency order; - possible branches; -
side effects; - privilege/risk; - resource needs; - checkpoints; -
rollback/compensation coverage; - verification plan.

Dry-run predicts; it does not verify future success.

## Typed Data Flow

Avoid a giant mutable `context: dict[str, Any]`.

Workflow inputs and outputs must be typed enough to validate references
before execution.

Distinguish: - workflow input; - step input; - step output; - Result; -
Evidence; - state/fact reference; - secret reference; - runtime
metadata.

A step should consume explicit bindings, for example conceptually:

    workflow.input.device
        -> step.resolve_device.input

    step.resolve_device.output.identity
        -> step.inspect_device.input.subject

Do not expose all prior outputs implicitly to every later step.

### Transformations

Prefer canonical typed transformations/resolvers already in Rebuntu.

If workflow-level transforms are needed, keep them deterministic,
bounded and declarative.

Do not implement arbitrary Python expressions in YAML/JSON.

### Secrets

Secret values: - are passed only to authorized consumers; - are not
copied into reports/checkpoints; - are redacted from evidence; - use
Phase 2/3/11 secret/config mechanisms as applicable.

### Large outputs

Do not copy huge logs/blobs through every step.

Use evidence/artifact references where appropriate.

Bound retained output sizes.

### Data provenance

Every derived workflow value should be explainable: - workflow input; -
step output; - current-state fact; - config; - resolver; - secret
reference.

This matters for reproducibility and debugging.

## Control Flow

### Sequential composition

Sequence means an explicit dependency, not merely lexical order in a
file.

If B requires A's result, encode it.

If B is independent, do not serialize it accidentally.

### Parallel composition

Parallel work must be bounded.

Define: - maximum concurrency; - resource constraints; - independence
requirements; - cancellation behavior; - failure policy; - output
aggregation; - join semantics.

Parallelism must not violate target Operation locks/resources.

Do not create one Python thread/process per Step without using
established runtime facilities.

### Branching

Branch decisions use typed conditions/results/facts.

Explicitly define UNKNOWN: - fail closed; - request evidence; - choose
safe default only when policy explicitly permits; - stop/defer.

Never treat UNKNOWN as false silently.

### Join

A join must specify what it waits for: - ALL; - ANY_SUCCESS; -
FIRST_COMPLETED; - bounded quorum only if a real consumer requires it.

Define: - failed branch; - cancelled branch; - skipped branch; - branch
that never started; - timeout; - partial output.

Do not add every possible join mode speculatively.

### Gates

Keep distinct: - input/schema validation; - precondition; -
assertion/condition gate; - authorization; - policy; - resource
availability; - readiness; - operator approval if ever applicable.

A Gate should not become a generic "run arbitrary predicate" hook.

## Failure, Retry, Resume, Checkpoint, Rollback and Compensation

These concepts must remain separate.

### Retry

Retry repeats a failed bounded attempt under a declared policy.

Reuse Phase 0.8 Attempt semantics.

A retry does not erase previous attempts.

### Resume

Resume continues an interrupted Workflow from verified/checkpointed
semantic progress.

Do not "resume" merely by starting from the last integer step index.

Before skipping completed mutating steps, verify their effects still
satisfy required postconditions where necessary.

### Checkpoint

A checkpoint records enough semantic state to recover safely: -
WorkflowExecution identity; - definition/version; - completed/verified
steps; - outputs/evidence references required later; - pending
branches; - rollback/compensation ledger; - relevant policy/config
version; - boot/session/provider state where correctness depends on it.

Do not pickle arbitrary Python runtime state.

Checkpoint writes must be atomic/durable enough for the promised
recovery semantics.

### Rollback

Rollback attempts to restore prior state for reversible effects.

Properties: - explicit support; - known target; - prior/checkpoint
state; - ordering/dependencies; - independent result/evidence; -
verification.

Rollback can fail.

`ROLLBACK_EXECUTED != ROLLBACK_VERIFIED`.

Never claim universal rollback.

### Compensation

Compensation performs a new action to offset an
irreversible/non-reversible effect.

Examples may include: - create compensating configuration; - release an
allocated external resource; - restore service availability through a
different valid action.

Compensation is not semantic time travel.

It has its own failure/verification evidence.

### Recovery decision

On failure, policy may choose among: - stop; - retry step; - retry from
checkpoint; - rollback reversible subset; - compensate; - leave degraded
with report; - require operator decision.

Do not implement an opaque "recover()" method that guesses.

### Crash recovery

After process/host crash: - load durable WorkflowExecution/checkpoint
metadata; - reconcile with underlying Jobs/Executions/native provider
state; - classify each in-flight effect; - verify uncertain completed
effects; - resume only when safe.

Unknown destructive outcomes require verification/operator policy, never
blind repetition.

## Cancellation and Shutdown

Cancellation is a structured request/state transition, not `kill -9`.

Propagate: Workflow -\> active branches -\> Steps -\> Phase 4 runtime
-\> Job/Execution/provider.

Define: - cancellation requested; - cooperative cancellation; - grace
period; - provider-specific termination; - forced termination only where
justified; - cleanup/finalization; - checkpoint behavior; -
rollback/compensation policy after cancellation.

A cancelled Step may already have side effects.

Therefore: `CANCELLED != NO_EFFECT`.

Cancellation evidence must state what completed before cancellation and
what remains unknown.

Shutdown of Rebuntu runtime must not orphan unmanaged workflow child
processes.

## Workflow Verification

Workflow verification answers whether the declared overall
purpose/postconditions hold.

It is not: - all subprocesses returned 0; - every Step reached
COMPLETED; - no exception was raised.

Compose: - Step/Operation verification; - workflow postconditions; -
current-state observations from Phase 7; - assertions/conditions from
Phase 8; - expected outputs; - rollback/compensation outcomes where
relevant.

Possible workflow outcomes must preserve distinctions such as: -
verified success; - execution completed but verification failed; -
partial success; - compensated; - rollback verified; - rollback
failed; - cancelled with effects; - timed out; - unknown/requires
verification.

Use canonical Phase 0.17 result vocabulary where already defined.

### Evidence report

The operator/agent should be able to answer: - what was requested? -
what plan was resolved? - which branch ran and why? - which Operations
actually executed? - what changed? - what failed? - what was retried? -
what was skipped? - what was rolled back/compensated? - what evidence
verifies the final state? - what remains unknown?

Reports are renderings over structured evidence, not the evidence store
itself.

## Security and Safety

Workflow composition must never weaken Operation-level safety.

Enforce: - typed capability references; - typed target subjects; -
canonical path resolution; - authorization at consequential
boundaries; - policy evaluation; - privilege minimization; - secret
isolation; - destructive-action controls; - resource/lock contracts; -
evidence.

A Workflow cannot gain authority by chaining individually
harmless-looking Steps.

Perform composition-level risk review: - combined side effects; -
privilege transitions; - TOCTOU across Steps; - path/device identity
changes; - stale facts; - symlink replacement; - subject
disappearance/reuse; - environment injection; - provider substitution.

### Untrusted definitions

Treat user/model/imported workflow definitions as untrusted input.

Validation must reject: - unknown capability IDs; - arbitrary
commands; - shell snippets; - invalid data references; - unbounded
loops/fanout; - unsupported privilege requests; - unsafe secret
routing; - malformed graph; - unauthorized targets.

### Historical code

Never execute historical workflow/scripts during archaeology.

Historical destructive helpers are evidence of intent, not reusable
defaults.

## Real-world pressure scenarios

### Package/config/service transaction

Resolve current state → plan package/config change → apply canonical
Operations → reload/restart only if required → verify
package/config/service state; exercise rollback where truly reversible.

### Storage maintenance workflow

Observe target storage → preconditions → checkpoint relevant metadata →
bounded maintenance Operations → verify; never let workflow invent
destructive filesystem commands.

### GPU workload preparation

Resolve stable GPU identity → inspect health/resources → apply
explicitly authorized profile Operations → launch workload → verify →
restore/compensate profile if required; ordinal index cannot be sole
identity.

### System diagnostic workflow

Collect Phase 7/5 evidence in parallel → join → deterministic
correlation/diagnostic steps → report. Read-only path demonstrates
parallelism without mutation.

### File organization

Plan source/target mappings → validate paths/collisions →
checkpoint/manifest → execute typed move Operations → verify → rollback
moved subset on failure where safe.

### Service deployment/update

Precheck → stop/reload only as required → mutate → verify →
rollback/compensate on failure; systemd remains lifecycle authority.

### Parallel host checks

Run independent bounded checks concurrently, aggregate partial results,
preserve failed/unknown checks and produce one verified report.

### Conditional branch

If canonical state already satisfies target, take no-op/verification
branch; otherwise mutate. UNKNOWN must not silently select the mutating
branch.

### Crash after mutation

Simulate side effect completed but checkpoint/result write lost;
recovery must verify actual state before retrying.

### Cancellation during parallel mutation

Cancel Workflow while branches are in different states; report completed
effects, cancel active work and invoke only explicitly configured
rollback/compensation.

### Rollback failure

Primary Step fails, rollback begins, one rollback Step fails; final
result must not claim restored state.

### Hostile definition

Definition contains shell text, eval-like expression, secret
exfiltration reference, unbounded fanout or unknown capability;
validation rejects it inertly.
