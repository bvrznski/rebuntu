# Rebuntu --- Phase 11.15 --- Configuration Verification

## Agent Task

Execute this as a full standalone repository-aware engineering task:
archaeology, semantic analysis, architecture, implementation,
integration, adversarial testing, documentation and closure audit. Do
not reduce it to an outline.

## Phase Mission

Verify configuration application against authoritative files/APIs and
resulting system state, preserving execution-success versus
verified-success distinctions.

## Global Agent Contract

You are implementing **Rebuntu**. The project identity is exactly
`Rebuntu`.

Historical Rebuntu is archaeology and requirements evidence, not a
compatibility authority.

Mandatory method:

SEARCH BEFORE IMPLEMENTING. COMPOSE BEFORE GENERATING. UNDERSTAND BEFORE
MODIFYING. USE LINUX BEFORE EMULATING LINUX. CONFIGURATION IS NOT STATE.
CONFIGURATION IS NOT POLICY. CONFIGURATION IS NOT A PREFERENCE.
CONFIGURATION IS NOT A SECRET STORE. CONFIGURATION IS NOT AN EXECUTABLE
SCRIPT. OBSERVED STATE IS NOT CONFIGURATION. DESIRED STATE MAY BE
DERIVED FROM CONFIGURATION, BUT IS NOT IDENTICAL TO IT. PRESERVE

SILENTLY OVERWRITE USER-OWNED CONFIGURATION. MAXIMALIST EXPLORATION;
CONSERVATIVE IMPLEMENTATION.

### Python first

### Native Linux first

Respect native configuration authorities: - systemd unit/drop-in
configuration; - sysctl configuration; - package-manager
configuration; - NetworkManager/systemd-networkd as actually present; -
udev rules; - XDG configuration; - desktop/session APIs; -
application-native config formats.

Rebuntu should use domain adapters/Operations rather than inventing one
universal `/etc/rebuntu.conf` that shadows every subsystem.

### No arbitrary executable config

Configuration must not contain arbitrary: - shell commands; - Python
code; - eval expressions; - unrestricted templates; - sudo strings; -
model-generated executable payloads.

References to Operations/Profiles/providers use canonical typed IDs and
schemas.

### Semantic service boundary

A model may help interpret human intent into candidate typed
configuration/profile changes. It is never configuration authority.

Required: human text -\> candidate typed patch -\> schema validation -\>
diff/plan -\> policy/auth -\> deterministic application -\>
verification.

Never LLM -\> config file overwrite / shell / sudo.

## Configuration Ontology

Validate against existing Phase 0/1 vocabulary.

### Configuration

Explicit declarative input controlling Rebuntu/system behavior.

### Setting

A named configurable value only if Phase 1 retained this concept as a
useful first-class term. Do not resurrect rejected ontology.

### Option

A set/range of allowed choices or schema metadata, not necessarily
runtime configuration.

### Preference

A soft user choice. It may influence selection but can be unsatisfied
due to capability, policy, safety or availability.

### Property / Attribute

Use only if existing ontology assigns a precise role. Do not use them as
synonyms for every key/value.

### Observed State

What the system currently is, obtained from Phase 7.

### Desired State

A target condition that may be derived from effective
configuration/profile. Phase 19 owns continuous reconciliation.

### Policy

Rules/constraints governing what is allowed. Configuration may select
policy references, but cannot override authorization simply by declaring
itself.

### Profile

A named reusable composition of typed configuration/desired-environment
choices.

Profile != shell script. Profile != Workflow. Profile != current state
snapshot. Profile != hardware inventory. Profile != user identity.

### Effective configuration

The resolved typed result after source
precedence/layering/defaults/profile composition.

It must retain provenance sufficiently to answer: - where did this value
come from? - what did it override? - what default applied? - which
profile contributed it? - what source would need editing to change it
persistently?

## Configuration Sources and Scope

Potential sources must be justified, not all automatically implemented:

-   built-in schema defaults;
-   packaged Rebuntu defaults;
-   system administrator configuration;
-   host-specific configuration;
-   user configuration;
-   profile definitions;
-   environment/session-specific configuration;
-   invocation/CLI override;
-   test fixture override.

Environment variables are not automatically trusted configuration.
Define an explicit allowlist/schema if supported.

### Scope

Every source/value should have a meaningful scope: - global/system; -
host; - user; - session; - workload; - environment; - invocation.

Prevent a user-scoped source from silently overriding protected system
policy/config.

### Provenance

For each effective value retain: - source ID/type; - file/native
authority if applicable; - location/field; - layer; - original value if
safe; - normalized value; - override chain; - profile contribution; -
default/deprecated/migrated status.

Secrets require redacted provenance.

### Missing/invalid sources

Distinguish: - source absent; - optional source absent; - unreadable; -
permission denied; - malformed; - schema incompatible; - version
unsupported; - partial/deprecated.

Do not silently treat malformed higher-precedence config as if it did
not exist when that could unexpectedly expose a lower-precedence value.

## Layering, Merge and Override Semantics

Do not implement `dict.update()` as configuration architecture.

Define merge semantics per schema type.

Possible strategies: - replace scalar; - replace collection; - append; -
set union; - keyed merge; - deep object merge; - explicit delete/unset
tombstone.

Avoid magical deep merge everywhere.

Each field/schema may declare its supported merge behavior.

### Precedence

Precedence must be documented and tested.

Example hypothesis only: built-in defaults \< packaged defaults \<
system config \< host config \< user config where allowed \< selected
profile composition \< invocation override.

Do not adopt this exact order blindly. Validate against Phase 1 and
security boundaries.

### Explicit unset

Differentiate: - absent; - null if valid domain value; - reset to
default; - remove inherited value; - empty list/string.

### Conflict

Profile composition can create semantic conflicts even when a mechanical
merge is possible.

Detect: - incompatible resource choices; - two providers required
exclusively; - contradictory desired values; - cross-scope ownership
conflicts; - secret/reference conflicts.

Do not silently select by alphabetical order.

### Provenance-aware diff

A diff should show both value and source change when useful.

`value unchanged, provenance changed` can matter operationally.

## Schema, Validation and Migration

Schemas must support: - types; - enums/ranges; - units; -
required/optional; - defaults; - nested structures only where
justified; - references to canonical IDs; - scope restrictions; - secret
markers; - deprecation; - versioning/migration; - documentation
metadata.

### Validation levels

Keep distinct:

1.  Parse validation --- syntax.
2.  Structural/schema validation --- shape/type.
3.  Semantic validation --- value meaning.
4.  Reference validation --- IDs/providers/profiles exist.
5.  Scope validation --- source may set field.
6.  Capability validation --- host/provider supports request.
7.  Policy/authorization --- allowed to apply.
8.  Preconditions --- current state permits operation.
9.  Verification --- application actually achieved effect.

Do not call all of these `validate()` without structured results.

### Offline versus live validation

Schema/reference validation can often run offline.
Capability/current-state validation may require Phase 7.

Represent deferred/UNKNOWN checks honestly.

### Migration

Configuration migration must: - identify source version; - preserve
original; - produce deterministic transformed candidate; - show diff; -
validate target schema; - write atomically only with explicit
application; - retain backup/checkpoint where appropriate.

Do not auto-rewrite user config merely because Rebuntu starts.

## Profiles

Profiles should be thin compositions over canonical configuration.

Potential categories: - host profile; - user profile; - workload
profile; - environment profile.

Do not force separate runtime classes if one typed Profile model with
scope/type metadata is cleaner.

### Host profile

Host profile may express desired choices for a specific host
identity/capability set.

Observed hardware facts remain Phase 7 facts.

Do not copy the entire hardware inventory into configuration.

### User profile

Respect user identity, XDG locations and permissions.

Never leak one user's preferences/secrets into another user's profile.

### Workload profile

A workload profile may select: - resource preferences; - GPU selection
policy; - CPU affinity policy references; - environment variables from
an allowlisted typed schema; - service/environment prerequisites; -
performance/power choices.

Actual resource control belongs to Phase 14 Operations and
execution/runtime.

### Environment profile

May compose coherent desktop/development/runtime configuration.

Do not make profile activation equivalent to sourcing arbitrary shell
scripts.

### Composition

Prefer shallow explicit composition.

If inheritance exists: - detect cycles; - bound depth; - retain
provenance; - make override order explicit.

Avoid OOP-style profile inheritance forests.

### Activation

Profile resolution/selection is read-only.

Profile activation is consequential: resolve -\> diff -\> plan -\>
validate -\> auth/policy -\> Operations/Workflow -\> observe -\> verify
-\> evidence.

Activation may be partial/unsupported and must report this explicitly.

## Application and Verification

Configuration application must route through canonical domain
Operations/Workflows.

Examples: - write managed Rebuntu config atomically; - apply a systemd
drop-in through a service/config Operation; - set a display/resource
profile through Phase 15/14 Operations; - update a user environment file
through a safe file Operation.

Do not create a universal privileged config writer.

### Managed versus user-owned files

Classify: - Rebuntu-owned; - Rebuntu-managed section; - user-owned; -
external subsystem-owned.

Never overwrite an entire user-owned file when only a managed
fragment/drop-in is needed.

Use native drop-in/include mechanisms where available.

### Atomicity

For file-backed managed configuration: - canonical target; -
same-filesystem temp where needed; - correct ownership/mode; -
fsync/durability proportional to requirement; - atomic rename; -
backup/checkpoint when rollback requires it; - symlink/TOCTOU defenses.

### Verification

After application: - re-read authoritative config/API; - observe
resulting Phase 7 state if runtime effect expected; - evaluate declared
postconditions; - preserve evidence.

`FILE_WRITTEN != CONFIG_APPLIED != SYSTEM_EFFECT_VERIFIED`.

Reload/restart only when the domain Operation says it is required.

Do not restart services gratuitously.

## Configuration Diff

Support semantic diff useful to humans and automation.

Distinguish: - source A vs source B; - profile A vs profile B; -
effective config before vs after candidate patch; - effective desired
config vs managed authoritative config; - optionally desired values vs
observed state, clearly labeled as cross-domain comparison.

Diff entries may include: - field/path; - old/new value; - old/new
provenance; - merge reason; - applicability; - sensitive/redacted
marker; - expected side effect; - restart/reload implication from domain
capability.

Do not diff secrets in plaintext.

Ordering must be deterministic.

Large diffs must remain bounded/renderable.

## Security and Adversarial Configuration

Treat every external config/profile as untrusted input.

Test: - path traversal; - symlink target replacement; - malicious
environment variable; - YAML tags/object constructors if YAML is used; -
duplicate keys; - Unicode confusables; - huge nested config; -
alias/reference bombs; - unknown fields; - privilege escalation by scope
override; - secret exfiltration through reports; - shell
metacharacters; - arbitrary executable template; - provider name
injection; - profile cycle; - cross-user path/reference.

Use safe parsers.

Unknown fields should follow explicit compatibility policy, not be
silently ignored by default.

Configuration must not grant authority beyond the
authenticated/authorized actor.

effects. Distinguish applied, reload-required, effect-verified,
verification-failed and unknown.

## Real-world pressure scenarios

### User preference override

System default exists; user preference requests another allowed value;
effective config records both provenance and selected value.

### Forbidden user override

User source attempts to change a protected system-only setting;
validation rejects it rather than silently escalating scope.

### GPU workload profile

Profile requests a preferred stable GPU/resource policy; unavailable GPU
produces explicit fallback/unsupported result, never silent ordinal
substitution.

### Desktop environment profile

User profile composes display/session preferences while headless
execution remains valid and no GUI state is fabricated.

### Service configuration

Candidate config uses native systemd drop-in/Operation, plans
reload/restart only when required, then re-reads and verifies.

### Malformed high-precedence config

Higher-priority source exists but is malformed; system reports error and
does not silently expose lower layer as effective truth.

### Profile conflict

Two composed profiles request incompatible values; conflict is explicit
with provenance rather than arbitrary winner.

### Migration

Old schema version is read, migrated to candidate, diffed and validated;
original remains untouched until explicit apply.

### Crash during file application

Atomic managed-file write/checkpoint path is fault-injected; target is
old or new valid state, not torn content.

### Host mismatch

Host profile references capability absent on fixture host;
validation/applicability returns unsupported/partial rather than
mutating.

### Secret handling

Secret reference participates in application but plaintext never appears
in diff, logs, checkpoint or report.

### Hostile config

Config contains traversal, shell payload, YAML object constructor or
profile cycle; it remains inert and is rejected.
