### Recovery is not reconciliation

Recovery responds to a failure/degradation/interruption and aims to
return the system to a safe acceptable condition.

Phase 19 reconciliation continuously converges observed state toward
desired state.

A recovery action may restore a desired condition, but Phase 12 must not
become a general always-on desired-state controller.

### Recovery is not diagnosis

Diagnosis/correlation identifies what is likely wrong. Recovery changes
something.

The system must be able to diagnose and stop without mutation.

### Recovery is not "restart everything"

Restart is one recovery primitive and often masks root causes.

Prefer: evidence -\> cause/condition -\> least invasive action -\>
verify.

### Python first, native Linux underneath

Python owns structured evidence, classification, planning, policy
integration, recovery composition, verification and reports.

Native Linux owns mechanisms: systemd lifecycle, journald, kernel/device
interfaces, filesystems, package managers, mount APIs, cgroups, udev,
SMART/NVMe tools through typed providers, etc.

Bash remains thin glue.

### Semantic model boundary

A local semantic model may summarize evidence or rank diagnostic
hypotheses. It must not autonomously produce executable recovery
commands.

Allowed direction: bounded evidence -\> structured semantic assessment
-\> schema validation -\> deterministic policy/planner -\> canonical
Operation/Workflow.

Never: LLM -\> sudo LLM -\> fsck command LLM -\> rm/mv LLM -\> systemctl
restart arbitrary target.

## Stability State and Outcome Grammar

Do not collapse orthogonal dimensions.

Potential dimensions: - observed health; - readiness; - availability; -
progress; - degradation; - failure; - recovery state; - verification
state.

Examples: healthy but unavailable due intentional disablement; running
but jammed; available but degraded; recovery action completed but
verification failed; symptom disappeared but root cause remains unknown.

Candidate recovery lifecycle: DETECTED -\> EVIDENCE_GATHERING -\>
CLASSIFIED -\> PLANNED -\> AUTHORIZED -\> RECOVERING -\> VERIFYING -\>
RECOVERED / DEGRADED / FAILED / UNKNOWN / ESCALATED.

Validate against existing Phase 0.14 vocabulary rather than creating
duplicate enums.

### UNKNOWN

UNKNOWN is first-class.

Unknown cause does not imply no failure. Unknown outcome does not imply
retry. Unknown health does not imply unhealthy. Unknown baseline does
not justify restoring arbitrary historical state.

## Healthy Baseline / Known-Good State

A baseline is contextual evidence about previously healthy/acceptable
behavior.

It is not: - a byte-for-byte snapshot of the machine; - all current
state copied forever; - a static "golden config"; - desired state; - a
backup; - a proof that every historical value was correct.

Candidate baseline dimensions: - boot/service success patterns; - device
presence/identity; - storage mount/health state; - resource ranges; -
expected driver/service topology; - recurring benign warnings; -
user/session context; - workload context.

Record: - provenance; - observation time; - boot/session identity; -
applicability context; - freshness/expiry; - confidence/quality; -
intentional changes.

Do not learn a failing state as healthy merely because it persisted.

Baseline promotion should require explicit evidence/rules and, for
consequential use, possibly user/operator confirmation.

Use compact features/facts, not unlimited journal archives.

## Deviation, Degradation and Stall Detection

### Deviation

Deviation = observed value/behavior differs from relevant
expected/baseline value.

Deviation is not automatically failure.

Classify: expected/intentional; benign; unknown; suspicious; degrading;
failed.

### Degradation

Degradation means reduced quality/capability while some function
remains.

Examples: - repeated GPU resets but recovery still succeeds; - rising
I/O latency/errors; - service restart frequency increasing; - thermal
throttling; - memory pressure; - link flapping.

Use hysteresis/debounce/persistence windows where appropriate.

### Stall / jam

A jam is alive but lacks expected forward progress.

Evidence can include: - unchanged progress counter; - blocked I/O with
corroborating kernel events; - workflow Step no progress while process
remains alive; - service requests timing out while unit is active.

Elapsed time alone is insufficient unless the contract defines a
deadline.

Distinguish: slow; waiting legitimately; blocked; starved; deadlocked;
jammed; hung; failed; zombie.

Do not infer kernel deadlock from a single slow user-space operation.

## Failure Classification and Root-Cause Evidence Correlation

Classification dimensions may include: - domain:
process/service/kernel/driver/storage/fs/network/device/resource/config/security; -
scope: one Operation/process/service/user/session/device/host; - onset:
transient/intermittent/persistent/progressive; - severity; -
recoverability; - evidence quality; - suspected layer; - recurrence.

Classification != cause.

### Correlation

Build evidence chains using: - event time and processing time; - boot
ID; - monotonic relationships within a boot; - subject identity; -
process/service ancestry; - device identity; - dependency graph; -
correlation/causation IDs from Rebuntu actions; - kernel/systemd/journal
sequence; - previous known-good observations.

Represent causal hypotheses with: - candidate cause; - supporting
evidence; - contradicting evidence; - missing evidence; -
confidence/strength category; - alternative hypotheses.

Never say "X caused Y" merely because X preceded Y.

### Previous-boot analysis

For abnormal reboot/hang: - identify boot boundaries; - inspect previous
boot journal; - capture final kernel/systemd/service/storage/GPU/memory
evidence; - distinguish clean shutdown, watchdog, panic, power loss,
hard reset, unknown; - avoid inventing events after logging stopped.

The absence of a log entry after a hard lock is not proof that nothing
happened.

## Recovery Planning

Recovery planning consumes: - classified failure; - causal hypotheses; -
current observed state; - baseline/desired constraints; - available
canonical Operations; - risk/side effects; - authorization/policy; -
checkpoints/backups; - resource constraints.

Prefer escalation ladder: 1. no mutation / gather more evidence; 2.
retry bounded transient operation; 3. refresh/reload/reconnect; 4.
restart narrowly scoped component; 5. repair targeted defect; 6. restore
trusted prior artifact; 7. rollback recent reversible change; 8.
compensation/degraded mode; 9. operator intervention.

This is not a universal order; domain policy may differ.

Every plan must state: - target; - rationale; - evidence; -
preconditions; - expected effects; - risks; - reversibility; -
verification; - fallback/escalation.

Do not choose more destructive action merely because less destructive
action failed once.

## Recovery Primitive Semantics

### Retry

Repeat a bounded failed attempt when failure is plausibly transient and
operation semantics permit it. Reuse Attempt history and Phase 0.9
backoff.

### Restart

Stop/start or native restart of a managed service/component when
lifecycle restart is a valid recovery mechanism. systemd remains
authority for systemd services.

### Repair

Modify the current broken state to correct a diagnosed defect.

### Restore

Replace/reconstruct state from a known trusted artifact/source.

### Rollback

Reverse a recent Rebuntu-managed reversible change using explicit
rollback contract.

### Compensation

Perform a new action to offset an irreversible/non-reversible effect.

### Degraded mode

Deliberately operate with reduced capability/safety envelope when full
restoration is unavailable or too risky.

Do not use these terms as synonyms.

Every mutating primitive routes through canonical Operations/Workflows
and produces Result/Evidence/Verification.

## Filesystem and Storage Safety

This area is safety-critical.

Default sequence: IDENTIFY -\> READ-ONLY OBSERVE -\> CORRELATE -\>
ASSESS -\> PLAN -\> AUTHORIZE -\> CHECKPOINT/BACKUP IF POSSIBLE -\>
MUTATE -\> VERIFY.

Use stable identity: - filesystem UUID; - PARTUUID; - WWN/serial where
appropriate; - sysfs topology; - mount identity.

Do not rely solely on `/dev/sdX`, `/dev/nvme0n1` ordinal names.

Never automatically: - format; - recreate filesystem; - wipe
signatures; - run destructive fsck repair; - remove unknown data; -
overwrite LUKS headers; - reinitialize RAID; - force mount a suspect
filesystem read-write.

Diagnostic commands/providers must prefer read-only modes.

If filesystem repair requires offline/unmounted state, represent that as
a precondition and stop safely if not satisfied.

Encrypted storage: - never guess keys in live recovery; - preserve
headers; - do not reformat/reinitialize; - clearly distinguish
container, block device and filesystem layers.

A storage recovery plan must name the exact device/filesystem identity
and evidence.

## Crash and Boot Recovery

### Rebuntu runtime crash

Persist only semantic recovery information required for correctness: -
active Workflow/Operation identities; - checkpoints; -
completed/verified effects; - unknown in-flight effects; - evidence
references.

On restart: DISCOVER -\> LOAD DURABLE RECORDS -\> REACQUIRE LIVE STATE
-\> RECONCILE IN-FLIGHT WORK -\> VERIFY UNCERTAIN EFFECTS -\> DECIDE
RESUME/ABANDON/ESCALATE.

Do not blindly rerun a mutating Operation whose previous outcome is
unknown.

### Host crash / abnormal reboot

At next healthy startup, detect whether previous boot ended normally.

If abnormal: - create a diagnostic incident; - identify previous boot
ID; - collect bounded previous-boot evidence; - correlate last
meaningful events; - generate likely causal sequence/hypotheses; -
report uncertainty.

This is a primary Phase 12 pressure path.

### Boot failure

Rebuntu must not attempt to replace initramfs/bootloader/systemd.

Provide tooling/plans that can operate from a valid rescue/recovery
environment where possible.

Any boot repair is explicit, narrowly scoped and separately authorized.

## Recovery Policy and Autonomy Boundary

Failure pressure must never silently expand authority.

Policy evaluates: - actor/automation identity; - target/scope; - failure
class; - evidence sufficiency; - recovery primitive; - side effects; -
destructiveness; - reversibility; - current user/session/workload; -
maintenance constraints; - resource impact; - prior failed recoveries; -
loop/escalation count.

Candidate decisions: ALLOW_AUTOMATIC; ALLOW_WITHIN_BOUND; DEFER;
REQUIRE_CONFIRMATION; DENY; ESCALATE; EVIDENCE_REQUIRED.

Do not hardcode these exact names if Phase 2/9 already defines policy
outcomes.

### Recovery-loop protection

Detect: failure -\> recovery -\> same failure -\> recovery cycles.

Bound: - attempts; - time; - restarts; - repeated plans; - oscillating
state.

Escalate rather than thrash.

A "self-healing" system that restart-loops a failing device/service is
not resilient.

## Required pressure scenarios

### GPU/Xid → hang → hard reboot

After reboot inspect previous boot, correlate
Xid/NVRM/PCIe/systemd/process/resource evidence, rank hypotheses and
produce report without claiming the GPU event definitely caused the
hang.

### NVMe I/O stall

Detect latency/error degradation, correlate block/kernel/filesystem
evidence, identify stable device, gather read-only diagnostics and
refuse destructive repair without explicit evidence/policy.

### Service crash loop

Detect repeated failures/restarts, suppress recovery thrash, collect
unit/journal/dependency evidence, attempt bounded narrow recovery only
if policy allows, then verify service function.

### Memory pressure/OOM

Correlate PSI/OOM/kernel/process/cgroup evidence, distinguish workload
pressure from leak hypothesis, avoid killing arbitrary processes as
automatic default.

### Filesystem read-only remount

Detect mount state change, collect kernel/fs/device evidence, preserve
data, avoid blind remount-rw/fsck and produce safe offline-repair plan
if required.

### Thermal degradation

Detect throttling/temperature degradation with hysteresis, identify
workload/context, enter bounded degraded mode if policy allows, verify
temperatures/performance state.

### Network flapping

Correlate link/carrier/route/service events, debounce transient changes,
avoid restarting entire networking stack without evidence.

### Rebuntu crash after side effect

On restart classify prior Operation outcome as unknown, reacquire
authoritative state, verify before retry/resume.

### Failed rollback

Primary recovery mutates, verification fails, rollback starts and itself
partially fails; final report preserves degraded/unknown state rather
than claiming recovery.

### Evidence gap

Logging stops before hard lock; report last known evidence and missing
interval explicitly rather than fabricating causal certainty.

### Recovery loop

Restart temporarily clears symptom but failure returns repeatedly;
bounded policy stops restart thrash and escalates with accumulated
evidence.

### Corrupt baseline

Baseline conflicts with current known valid intentional configuration;
baseline is not blindly restored and is marked stale/inapplicable.
