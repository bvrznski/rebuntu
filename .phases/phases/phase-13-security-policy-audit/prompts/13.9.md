# Rebuntu --- Phase 13.9 --- Process / Service Protection

## Agent Task

Execute this as a full standalone repository-aware security engineering
task: archaeology, threat analysis, architecture validation,
implementation, adversarial testing, privilege review, documentation and
closure. Do not reduce it to an outline.

## Phase Mission

Protect process/service Operations against PID reuse, target confusion,
privilege mistakes, restart/kill abuse and interference with critical or
unrelated workloads.

## Global Agent Contract

Implement **Rebuntu** only.

Mandatory principles:

SEARCH BEFORE IMPLEMENTING. LINUX AUTHENTICATION != REBUNTU
AUTHORIZATION. ROOT != AUTHORIZED. PRIVILEGE != POLICY. LINUX CAPABILITY
!= REBUNTU CAPABILITY. IDENTITY != PID. PATH STRING != FILE OBJECT
IDENTITY. SECRET != CONFIGURATION. AUDIT LOG != PROOF OF NON-TAMPERING.
ANOMALY != COMPROMISE. QUARANTINE != DELETE. SECURITY RECOVERY !=
EVIDENCE DESTRUCTION. DENY SAFELY WHEN TARGET/SCOPE/AUTHORITY IS
AMBIGUOUS. LEAST PRIVILEGE WHERE PRACTICAL. NATIVE LINUX SECURITY FIRST.
MAXIMALIST EXPLORATION; CONSERVATIVE IMPLEMENTATION.

Reuse Phase 2 identity/permissions/capabilities/scopes, Phase 0.10
Operation contracts, Phase 4 runtime, Phase 7 observation, Phase 8
assertions/evidence, Phase 9 automation, Phase 10 workflows, Phase 11
configuration and Phase 12 recovery.

Do not build a second user database, authentication system, sudo
replacement, firewall, secret vault, audit subsystem or process
supervisor unless repository evidence proves a missing Rebuntu-specific
semantic layer.

Canonical consequential path:

    Actor / Automation / Service
        -> authenticated native identity + provenance
        -> typed Request
        -> target + scope resolution
        -> current authoritative observation
        -> Operation safety metadata
        -> authorization
        -> policy
        -> privilege/capability resolution
        -> plan / checkpoint
        -> deterministic Operation
        -> native Linux authority
        -> fresh observation
        -> verification
        -> audit/evidence/result

### Native mechanisms first

Evaluate and integrate existing authorities where appropriate: -
UID/GID/NSS/PAM boundaries; - sudo/polkit/systemd service privilege; -
Linux capabilities; - filesystem permissions/ACLs; - systemd
sandboxing/hardening; - AppArmor/SELinux where actually active; -
nftables/firewall provider; - systemd credentials/kernel keyring or
other justified secret providers; - auditd/journald where applicable; -
namespaces/cgroups/seccomp where justified.

Rebuntu describes, resolves, authorizes, composes and verifies. It does
not casually replace these mechanisms.

### Python first

Python owns typed requests, policy decisions, authorization context,
safety planning, redaction, evidence and verification.

External commands use argv arrays, explicit environment, timeout and
bounded output. No `shell=True`, eval, exec or interpolated privileged
command strings.

### Semantic model boundary

Model output is untrusted input.

Allowed: evidence -\> semantic summary/classification -\> typed
candidate -\> schema validation -\> deterministic security
policy/Operation.

Never: LLM -\> sudo LLM -\> firewall command LLM -\> chmod/chown/rm LLM
-\> quarantine target LLM -\> secret value LLM -\> authorization
decision.

## Identity, Authentication and Provenance

Distinguish: - OS user identity; - effective/real UID/GID; - session
identity; - invoking user when elevated; - service identity; -
automation identity; - Rebuntu Request actor; - Job/Execution
identity; - target subject identity.

Do not infer original user only from `$SUDO_USER` without validating
invocation context.

Authentication is normally delegated to native OS/session mechanisms.

Rebuntu authorization answers: "may this authenticated actor cause this
typed effect on this exact target in this scope now?"

Every consequential Request carries provenance sufficient to explain:
who/what requested it, through which interface/automation, under what
scope and policy.

## Authorization, Privilege and Scope

Authorization decision inputs can include: - actor; - request origin; -
Operation ID; - target identity; - scope; - side-effect/risk class; -
current state; - policy; - session/workload context; - required native
authority.

Do not scatter `if uid == 0` as authorization.

Privilege is a mechanism required to perform an already-authorized
action.

Preferred shape: authorize semantic action first -\> resolve minimum
execution authority second.

Scope examples: user; session; system; device; filesystem subtree;
service; network namespace/interface; workload/cgroup.

Cross-scope effects require explicit authorization.

A system-scope daemon must not become a confused deputy for an
unprivileged caller.

## Capability-Based Access

Keep two namespaces conceptually distinct:

Linux capability: `CAP_NET_ADMIN`, `CAP_SYS_ADMIN`, etc.

Rebuntu capability: semantic system capability such as
`service.restart`, `mount.unmount`, `package.install`,
`network.firewall.apply`.

A Rebuntu capability may require: no privilege; filesystem ownership;
polkit authorization; one Linux capability; a privileged systemd
helper/service; root in rare cases.

Never map semantic capabilities 1:1 to Linux capabilities blindly.

Prefer narrow systemd service privileges/capability bounding and
explicit IPC contracts over making the whole Rebuntu runtime root.

## Security Policy

Policy is deterministic and inspectable.

Potential decisions: ALLOW; DENY; REQUIRE_CONFIRMATION;
REQUIRE_STRONGER_AUTHORIZATION; REQUIRE_EVIDENCE; REQUIRE_CHECKPOINT;
DEFER/ESCALATE.

Reuse existing Phase 2/9/12 policy vocabulary if already implemented.

Policy should be able to express: - allowed actors; - allowed
targets/scopes; - time/session/workload constraints; -
destructive-action requirements; - automatic vs interactive authority; -
maximum retry/recovery behavior; - secret access; - network exposure; -
quarantine; - security recovery.

Policy failure must fail closed for consequential mutation when the
decision cannot be reliably established.

Do not fail closed for harmless read-only observation in ways that make
diagnosis impossible, unless the observation itself is sensitive.

## Secrets

A secret should usually be referenced, not copied.

SecretReference -\> authorized provider resolution -\> short-lived use
-\> zero/minimize retention -\> redacted evidence.

Potential native providers should be evaluated, not assumed.

Never put secret values in: - command line arguments when avoidable; -
journald messages; - Result repr; - exception trace context; -
environment inherited broadly; - profile/config dumps; - audit
records; - semantic-model prompts.

Test redaction with adversarial secret-like strings and nested
structured data.

Do not write a homegrown encryption scheme.

A missing secret and an unauthorized secret are distinct outcomes.

## Filesystem Protection

Every consequential path Operation must consider: - canonical target
resolution; - symlink races; - parent ownership; - mount boundaries; -
hardlinks where relevant; - TOCTOU; - file type; - permissions/ACL; -
expected inode/device identity when justified; - user/system scope.

Prefer dirfd/openat-style safe operations or equivalent robust
primitives where warranted.

Never recursively chmod/chown broad trees as generic repair.

Deletion: prefer quarantine/trash/snapshot/checkpoint where semantics
allow.

Destructive deletion requires exact scope, explicit policy and
independent verification.

Never follow a symlink outside an authorized subtree merely because the
lexical path began inside it.

## Process and Service Protection

PID alone is not identity.

Use pidfd/start time or canonical Job/Execution/service identity.

Before signal/priority/kill/restart: - resolve target; - verify
identity; - verify scope/ownership; - classify criticality; - authorize
exact effect; - revalidate immediately before action.

Do not kill arbitrary blockers as a generic fix.

systemd-managed services should be controlled through systemd.

Protect Rebuntu from accidentally stopping: init/systemd; session
infrastructure; storage/network dependencies; its own critical control
components, unless a specific recovery workflow explicitly permits it.

## Network Protection

Use native firewall/network authorities; do not implement packet
filtering.

Security Operations may manage typed policy/rules through a provider.

Requirements: - current ruleset observation; - exact
interface/address/family/protocol/port semantics; - plan/diff; -
authorization; - checkpoint/rollback where provider supports; - apply; -
fresh verification; - preserve controlling remote session when policy
requires.

Never flush an existing firewall ruleset as a convenience.

Do not expose a service on `0.0.0.0`/`::` by default.

Network protection must distinguish local-only, LAN, specific
interface/address and global exposure.

## Destructive-Action Controls

Destructive is not merely "requires sudo".

Examples: format/wipe; recursive permanent deletion; filesystem repair
with data-loss potential; LUKS/header overwrite; RAID reinitialization;
firewall replacement that can cut access; package/config removal with
broad effect; forced unmount; device reset with data-loss risk.

Required gates should include as appropriate: - exact typed target; -
fresh target identity; - explicit destructive classification; - actor
authorization; - policy; - evidence; - safer alternative evaluation; -
checkpoint/backup; - confirmation token/interaction for human-triggered
operations; - automation prohibition or stricter policy; - post-action
verification.

Do not create "yes_to_all=True" as an easy bypass.

Dry-run is not authorization.

## Audit Trail

Audit records should answer: WHO/WHAT requested WHAT effect on WHICH
target, WHEN, from WHERE/WHICH interface, WHAT authorization/policy
decision occurred, WHICH execution performed it, and WHAT was verified.

Record semantic identifiers, not only shell commands.

Audit is bounded and redacted.

Journald/auditd may provide native evidence. Rebuntu may add structured
semantic records.

Do not claim append-only/tamper-proof guarantees unless actually backed
by such a mechanism.

Correlate: Request -\> policy decision -\> Operation -\>
Job/Execution/Attempt -\> native effect -\> verification -\> Result.

Read-only high-volume observations should not flood security audit
unnecessarily.

## Security Assertions

Use Phase 8 deterministic assertion machinery.

Examples: - SSH is not globally exposed according to policy; - sensitive
directory ownership/mode matches invariant; - privileged Rebuntu service
has expected sandbox/capability set; - no unauthorized listener exists
in a protected scope; - secret file is not group/world-readable; -
destructive automation is disabled unless explicit policy allows it.

Assertions return TRUE/FALSE/UNKNOWN/ERROR as existing vocabulary
permits.

No magic `security_score = 87`.

A failed assertion is evidence of policy/invariant violation, not
automatically evidence of malicious compromise.

## Anomaly Response and Quarantine

Anomaly can mean unexpected deviation, suspicious behavior or policy
violation.

Do not label an incident "compromise" without evidence.

Response ladder can include: observe more; capture evidence; restrict
one capability; pause one automation; isolate one workload; quarantine
one file/artifact; block one network exposure; require operator
confirmation; escalate.

Quarantine is reversible containment.

File quarantine should preserve: identity/hash/metadata/original
path/evidence, use safe permissions/location and avoid executing
content.

Process/service quarantine may mean stop/freeze/isolate
network/capabilities, but must be explicit and policy-driven.

Do not delete suspicious artifacts as containment.

## Security Recovery

Reuse Phase 12 recovery grammar.

Security recovery adds constraints: - preserve incident evidence; - do
not restore known-vulnerable configuration blindly; - do not weaken
firewall/permissions to make a service "work"; - do not erase logs
before incident closure; - verify security invariants after functional
recovery; - preserve UNKNOWN when compromise extent is unknown.

Functional recovery and security recovery can disagree.

Example: service works after permissions changed to 0777 -\> functional
symptom may disappear, but security verification fails; recovery is not
successful.

## Phase-Specific Contract

Implement safe process/service targeting, pidfd/start identity where
applicable, critical-target policy and systemd-native service controls.

## Required pressure scenarios

### Unprivileged restart request

User requests restart of a protected system service; semantic
authorization occurs before privilege, denied path cannot trick
privileged helper.

### Confused-deputy IPC

Unprivileged client sends a crafted target/scope to a privileged Rebuntu
service; server independently resolves and authorizes exact target.

### Symlink swap

Authorized file inside managed subtree is replaced with symlink to
sensitive system file between plan and mutation; revalidation/safe
filesystem primitive prevents escape.

### PID reuse

Authorized target process exits and PID is reused by another
user/service; operation refuses to signal the replacement.

### Secret leakage

Provider raises exception containing secret-like nested data;
Result/audit/journal/semantic prompt remain redacted.

### Firewall lockout

Rule change could sever controlling SSH/session; plan identifies risk,
checkpoint/rollback is prepared and policy blocks unsafe automatic
apply.

### Destructive disk request

Automation requests wipe/format of a device due malformed event;
destructive policy rejects it and exact stable identity/evidence gates
prevent action.

### Suspicious file

Unexpected executable appears; system captures evidence and quarantines
reversibly rather than deleting or declaring compromise.

### Service recovery temptation

Service starts only after chmod 0777; functional verification passes but
security assertion fails, so recovery is rejected.

### Privilege escalation pressure

Repeated recovery failures do not cause Rebuntu to broaden capabilities
or run the whole runtime as root.

### Multi-user scope

One user cannot cause clipboard/session/process/file operations in
another user's scope through a system service.

### Audit reconstruction

Incident timeline reconstructs
actor→policy→Operation→execution→verification without logging secrets or
pretending missing records do not exist.
