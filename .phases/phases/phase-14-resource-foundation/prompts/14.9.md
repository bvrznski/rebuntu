# Rebuntu --- Phase 14.9 --- GPU Selection / Assignment

## Agent Task

Execute this as a full standalone repository-aware engineering task:
archaeology, architecture validation, implementation, integration,
host-safety analysis, adversarial tests, benchmarking where applicable,
documentation and closure. Do not reduce it to an outline.

## Phase Mission

Implement deterministic workload-to-GPU selection and assignment
policies with stable identities, visibility constraints,
provider-specific mechanisms and post-launch verification.

## Global Agent Contract

Implement **Rebuntu** only. Historical implementations are archaeology,
not compatibility targets.

Mandatory method:

SEARCH BEFORE IMPLEMENTING. OBSERVE BEFORE CONTROLLING. DISCOVER
CAPABILITY BEFORE SETTING A VALUE. USE THE KERNEL / SYSTEMD / DRIVER
BEFORE EMULATING THEM. RESOURCE IDENTITY MUST BE STABLE. RESOURCE POLICY
!= RESOURCE OBSERVATION. RESOURCE REQUEST != RESOURCE ALLOCATION.
RESOURCE LIMIT != RESOURCE USAGE. PERFORMANCE != UTILIZATION.
TEMPERATURE != THROTTLING. GPU INDEX != GPU IDENTITY. PROCESS PID !=
WORKLOAD IDENTITY. PROFILE != EXECUTION SCRIPT. BENCHMARK !=
VERIFICATION OF REAL WORKLOAD BENEFIT. PLAN BEFORE MUTATING. VERIFY
EVERY CONSEQUENTIAL CONTROL. RESTORE OR ROLLBACK WHEN A TEMPORARY
CONTROL ENDS. MAXIMALIST EXPLORATION; CONSERVATIVE IMPLEMENTATION.

Phase 14 builds on: - Phase 0 Operations/Results/State/Configuration; -
Phase 2 identity, permissions, Linux capabilities and scopes; - Phase 4
runtime; - Phase 5 monitoring; - Phase 7 observation; - Phase 8
assertions/events; - Phase 9 automation; - Phase 10 workflows; - Phase
11 profiles; - Phase 12 stability/recovery; - Phase 13
security/authorization.

Do not duplicate their mechanisms.

Canonical control path:

    workload / user / profile / policy request
        -> stable subject + resource identity
        -> current authoritative observation
        -> capability discovery
        -> constraints / authorization / policy
        -> resource plan
        -> typed native Operation
        -> Linux / systemd / cgroup / driver provider
        -> fresh observation
        -> verification
        -> performance/stability evidence
        -> Result

### Native Linux first

Prefer, where applicable: - `/proc`, `/sys`, sysfs topology; - sched
affinity APIs; - cgroup v2; - systemd resource-control
properties/scopes/slices; - PSI; - cpufreq / powercap / hwmon / thermal
sysfs; - block scheduler/native I/O priority APIs; - udev stable device
identity; - vendor GPU APIs/tools behind typed providers.

Do not build a custom scheduler, memory manager, GPU runtime or thermal
subsystem.

### Python first

Python owns topology models, resource requests, policy, provider
resolution, plans, verification, profiles, arbitration and evidence.

Use direct APIs/libraries when robustly available. External commands
must use typed argv, explicit timeout/environment, bounded output and
structured parsing.

No `shell=True`.

### Safety

Ordinary tests must not: - stress real storage destructively; -
overclock hardware; - disable thermal protections; - set unsafe
voltage; - exhaust host memory; - starve the desktop/session; - freeze
critical system services; - manipulate all GPUs simultaneously without
explicit fixture/operator authorization.

Tests use fakes, cgroup sandboxes, bounded child workloads and
explicitly marked host-integration tests.

### Semantic model boundary

A semantic model may interpret: "give this compile job more CPU but keep
desktop responsive" into a candidate typed resource intent.

It never emits or executes `taskset`, `chrt`, `nvidia-smi`, sysfs
writes, sudo or cgroup commands directly.

Text -\> typed intent -\> validation -\> policy -\> deterministic
resource Operations.

## Resource Ontology

Keep these distinct:

Resource --- finite/controllable system capacity or device capability.

ResourceObservation --- measured current fact with timestamp/provenance.

ResourceCapability --- what a resource/provider can support.

ResourceRequest --- workload/user desired
allocation/constraint/preference.

ResourceAllocation --- concrete granted assignment.

ResourceLimit --- enforced upper/lower bound.

ResourceReservation --- capacity intentionally held for a subject.

ResourceProfile --- reusable composition of typed resource
preferences/constraints.

ResourcePolicy --- rules governing allocation/control.

ResourcePressure --- evidence that demand approaches/exceeds practical
capacity.

ResourceContention --- multiple subjects competing for a resource.

ResourceArbitration --- deterministic decision process resolving
contention.

PerformanceObservation --- measured behavior/result, not merely
configured settings.

Do not create all as classes unless consumers justify them.

## Stable Resource Identity

CPU: - logical CPU ID is kernel-visible but topology context matters; -
package/die/core/thread relationships; - online/offline state; - NUMA
node.

Storage: - WWN/serial/UUID/sysfs topology as appropriate; - never only
`/dev/sdX`.

GPU: - PCI BDF; - vendor UUID where available; - DRM/render node
relation; - vendor/device IDs; - driver/provider identity.

Never persist "GPU 1" as canonical identity.

GPU ordinal is a transient provider/UI mapping and may change after
reboot, driver reload or visibility filtering.

Process: PID must be paired with start-time/pidfd or canonical
Execution/Job identity to avoid PID reuse races.

Workload: prefer Rebuntu Job/Execution/Workflow identity plus native
cgroup/systemd scope.

## CPU, Scheduling and Memory

Discover: - architecture; - packages/dies/cores/threads; - SMT; -
NUMA; - online CPUs; - frequency/governor capabilities where relevant; -
isolation/cpuset constraints.

Affinity must respect: - current allowed cpuset; - topology; -
process/thread semantics; - systemd/cgroup ownership; - user scope.

Scheduling policies/priorities are privileged where Linux requires it.
Never silently elevate.

Memory semantics distinguish: - virtual/resident memory; -
anonymous/file cache; - swap; - cgroup usage/limits; - pressure/PSI; -
reclaim; - OOM events; - NUMA locality where justified.

Do not implement "free RAM low =\> clear caches" automation.

Linux cache is not wasted memory.

Memory controls must be workload-scoped and cgroup-native where
possible.

## cgroup v2 and systemd Resource Control

Detect actual hierarchy and controllers.

Prefer systemd-managed scopes/services/slices when systemd owns the
workload.

Potential controllers: cpu, cpuset, memory, io, pids.

Do not assume every controller is delegated or writable.

Distinguish: - controller available; - enabled in subtree; - delegated
to current user; - configured; - effective.

Do not manually fight systemd by moving its managed processes between
arbitrary cgroups.

Resource Operations should expose semantic controls and let the provider
select systemd properties or direct cgroup v2 only where
ownership/delegation permits it.

Verification reads effective native state.

## Multi-GPU Architecture

Multi-GPU is a first-class pressure case.

Discovery should correlate: PCI device \<-\> DRM node \<-\> vendor
management identity \<-\> CUDA/compute UUID where available \<-\>
display attachment \<-\> driver \<-\> current processes/workloads.

Selection policy may consider: - stable requested identity; - free/used
VRAM; - compute utilization; - display role; - power/thermal state; -
capability; - workload compatibility; - reservation; - profile
preference; - policy.

Do not blindly select "least utilized GPU" if that violates
display/reservation/profile constraints.

### Assignment

Mechanism depends on workload/provider: - environment visibility
variables; - explicit device arguments; - container device mapping; -
application-native selection; - DRM/Vulkan selection where applicable.

Assignment must be verified after launch when possible by observing the
actual process/device relationship.

`CUDA_VISIBLE_DEVICES` or equivalent being set is not proof the
application used that GPU.

### Power and clocks

Discover supported ranges/capabilities first.

Distinguish: - power limit; - application clocks; - locked clocks; -
persistence mode; - performance state; - observed clock; - throttle
reason.

Never treat one vendor's terminology as universal.

Temporary tuning must record prior state when restoration is supported.

No voltage/unsafe overclock controls.

## Thermal and Power

Temperature observations require: - sensor identity; - unit; -
provenance; - timestamp; - validity; - relation to device.

Thermal policy uses hysteresis and persistence to avoid oscillation.

Distinguish: warm -\> hot -\> throttling -\> critical/emergency
according to native/device semantics; do not invent one universal
Celsius threshold for all hardware.

Mitigation can include workload/resource-profile adjustment before
invasive actions.

Never disable firmware/kernel thermal protections.

Power policy must respect: - platform/kernel authority; - laptop/desktop
context; - AC/battery if applicable; - device power states; - user
workload intent; - thermal/stability constraints.

Avoid competing daemons that continuously overwrite each other's
settings.

## Workload Detection and Profiles

Workload classification is evidence-based.

Potential evidence: - canonical executable/package; - Rebuntu
Job/Workflow metadata; - cgroup/systemd scope; - GPU attachment; -
process tree; - sustained resource behavior; - explicit user/profile
declaration.

Heuristic classification must be labeled heuristic and must not grant
privilege.

Examples: interactive desktop; game; compile/build; AI inference; AI
training; batch; storage-heavy maintenance.

Do not hardcode application names into core ontology when a
registry/rule/profile can express them.

ResourceProfile may specify: - CPU affinity preference/constraint; - CPU
weight/quota; - memory high/max preference; - I/O weight/class; - GPU
preferred/forbidden/reserved identities; - power policy; - thermal
ceiling/response policy; - priority; - fallback behavior.

Profile != script and profile activation routes through Operations.

## Resource Arbitration

Arbitration is required only when requests conflict or capacity is
finite.

Inputs: - active workloads; - allocations/reservations; - resource
capabilities; - profiles; - policy; - priority/fairness; - user/session
importance; - stability/thermal constraints.

Decisions must be deterministic and explainable.

Never infer that a background workload may be killed merely because an
interactive workload starts.

Prefer bounded controls: weights, quotas, cpusets, GPU reservations, I/O
weights.

Avoid global "performance mode" that blindly maximizes every device.

Arbitration must resist oscillation: hysteresis, cooldown, minimum
residency and event coalescing where justified.

Resource decisions must be observable and reversible when temporary.

## Performance Observation, Benchmarking and Verification

Measure before and after when tuning claims performance benefit.

Potential metrics: - latency; - throughput; - frame time; - job
completion time; - CPU/GPU utilization; - memory pressure; - I/O
latency/throughput; - thermal throttling; - power; - errors/stability.

Utilization alone is not performance.

### Benchmarking

Benchmarks must be: - bounded; - reproducible; - versioned; -
non-destructive by default; - explicit about warmup/sample count; -
explicit about noise/context; - comparable.

Storage benchmarks default to safe files/fixtures, never raw-device
destructive writes.

### Verification

Control verification: did native state actually change?

Performance verification: did the target metric improve without
unacceptable regression?

Stability verification: did the change introduce errors, throttling or
recovery events?

A tuning Operation can be successfully applied yet fail performance
verification.

## Required pressure scenarios

### Four-GPU workstation

Four similar GPUs reorder across boots/provider ordinals; Rebuntu
retains stable identities, display/reservation roles and assigns
workload to intended physical GPU.

### Game on selected GPU

Interactive workload requests a preferred GPU; assignment mechanism is
applied and actual process/device usage is verified rather than trusting
environment variables.

### AI workload reservation

One or more GPUs are reserved for AI inference/training while
desktop/game workload starts; arbitration respects reservations and
explains fallback.

### CPU-heavy compile

Compile job receives CPU weight/affinity while desktop responsiveness
constraint remains; effective cgroup/affinity is verified.

### Memory pressure

Sandbox workload approaches cgroup memory pressure; policy responds
within bounded scope and never clears global caches or kills arbitrary
host processes.

### I/O-heavy task

Maintenance workload competes with interactive storage I/O; I/O
weight/priority is adjusted without raw-device destructive benchmarking.

### GPU thermal pressure

Selected GPU heats/throttles; hysteresis prevents oscillation and policy
reduces bounded workload/power setting before unsafe actions.

### Provider disappears

GPU/vendor tool or cgroup controller becomes unavailable between plan
and execute; Operation fails safely and does not select a more
privileged fallback.

### Process PID reuse

Target process exits and PID is reused before priority change; stable
identity check prevents changing the wrong process.

### Profile conflict

Interactive profile requests GPU A while reservation policy forbids it;
arbitration returns explainable alternate/denial.

### Temporary tuning restore

Power/priority/affinity tuning is temporary; workload exits/crashes and
previous supported settings are restored and verified.

### Benchmark regression

Setting applies successfully and synthetic throughput rises but
latency/thermal/stability target regresses; result does not claim
unconditional improvement.
