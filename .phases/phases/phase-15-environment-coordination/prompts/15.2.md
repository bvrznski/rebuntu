# Rebuntu --- Phase 15.2 --- Device Lifecycle

## Agent Task

Execute this as a full standalone repository-aware engineering task:
archaeology, architecture validation, implementation, integration,
session/security analysis, adversarial testing, documentation and
closure. Do not reduce it to an outline.

## Phase Mission

Implement typed device lifecycle observations and event handling for
appearance, removal, readiness, failure and reconfiguration without
confusing kernel presence with usability.

## Global Agent Contract

Implement **Rebuntu** only.

Mandatory principles:

SEARCH BEFORE IMPLEMENTING. DISCOVER THE ACTIVE NATIVE AUTHORITY BEFORE
CONTROLLING IT. DEVICE PRESENCE != DEVICE READY != DEVICE AVAILABLE.
SESSION EXISTS != SESSION READY. DISPLAY CONNECTED != DISPLAY ENABLED.
GPU IDENTITY != DISPLAY OUTPUT IDENTITY. STORAGE DEVICE != FILESYSTEM !=
MOUNT. NETWORK INTERFACE != CONNECTION PROFILE != ROUTE. AUDIO DEVICE !=
AUDIO NODE != DEFAULT ROUTE. HOTPLUG EVENT != PERMISSION TO RECONFIGURE.
ENVIRONMENT VARIABLE != TRUSTED SYSTEM FACT. PROFILE SELECTION !=
PROFILE APPLICATION. PLAN BEFORE MUTATING. VERIFY AFTER MUTATING. EVENTS
BEFORE POLLING. MAXIMALIST EXPLORATION; CONSERVATIVE IMPLEMENTATION.

Reuse Phases 2, 4, 5, 7, 8, 9, 10, 11, 12, 13 and 14. Do not create a
second device inventory, event bus, resource manager, profile engine or
recovery framework.

Canonical path:

    kernel / udev / logind / compositor / PipeWire / network provider / BlueZ / mount authority
        -> native event + observation
        -> stable subject identity
        -> capability/state normalization
        -> Phase 7 facts
        -> request/profile/hotplug policy
        -> authorization
        -> Operation/Workflow
        -> native provider
        -> fresh observation
        -> verification/evidence

### Provider boundaries

The actual host may use different stacks. Detect them.

Examples: - Wayland compositor-specific output APIs; - X11 RandR; -
PipeWire/WirePlumber; - NetworkManager or systemd-networkd; - BlueZ; -
udisks/systemd mount units/kernel mount interfaces; - logind/systemd
user manager; - udev/sysfs.

Do not assume GNOME is the ontology merely because one development host
uses GNOME.

### Python first

Python owns typed identities, provider resolution, planning, profile
composition, event handling, verification and structured results.

Bash provides thin UX such as `clip`, not the implementation
architecture.

No `shell=True`, eval or arbitrary command strings.

### Session security

Graphical/session operations execute in the correct user's session and
authorization scope.

Never steal another user's Wayland/X11/Pulse/PipeWire/DBus environment
merely because the process is root.

Resolve target session explicitly.

### Headless is valid

Every subsystem must distinguish: unsupported/not present/headless from
failure.

Rebuntu core must remain functional without a graphical session.

## Device and Environment Identity

Device identity should use the strongest native stable identifiers
appropriate to domain: udev properties, sysfs path/topology, serial/WWN,
PCI BDF, USB VID/PID+serial, DRM connector identity/EDID where
appropriate, BlueZ address/identity, network permanent MAC where safe.

Never create one fake universal "device UUID".

Separate: physical device; kernel device instance; logical endpoint;
session endpoint; provider object.

A monitor, GPU, DRM connector and compositor output are related objects,
not synonyms.

A sound card, PipeWire device/node/port and default sink are related
objects, not synonyms.

Identity correlation must preserve uncertainty when hardware lacks
stable serial identity.

## Discovery and Lifecycle

Prefer udev/sysfs events and native subsystem events over repeated full
scans.

Normalize: ADDED/PRESENT; INITIALIZING; READY; CHANGED; UNAVAILABLE;
REMOVING; REMOVED; FAILED/UNKNOWN where justified.

Validate against Phase 0.14 rather than inventing duplicate lifecycle
enums.

Hot unplug can race with an Operation. Revalidate identity/capability
immediately before mutation and handle ENODEV/provider disappearance
safely.

Event storms must be debounced/coalesced by subject and semantics, not
by blindly sleeping.

## Displays and Layout

Observe: - connector/output identity; - connected/enabled; - current
mode; - supported modes; - refresh rate; - position; - scale; -
transform/orientation; - primary/preferred role where provider supports
it; - brightness/color capabilities where genuinely available; - GPU/DRM
association; - session/provider.

Do not promise monitor hardware brightness/color control merely because
software gamma is available.

Differentiate: compositor output settings; DRM/kernel properties; DDC/CI
monitor controls; software gamma/color management.

Each needs its own capability/provider boundary.

### Layout

A layout plan validates: - referenced outputs still exist; - requested
modes supported; - geometry; - scale/transform; - at least one usable
output remains unless explicitly authorized headless transition; -
session authority.

Apply atomically where provider supports it; otherwise use staged safety
and rollback.

Verification reacquires compositor/native state.

Never persist transient connector naming as the only monitor identity if
stronger correlation is available.

## Audio

Detect active audio authority.

For PipeWire/WirePlumber, model semantic concepts without mirroring the
entire graph.

Observe/control as justified: - devices; - nodes/endpoints; -
profiles; - ports; - default sink/source; - volume; - mute; - routing.

Volume application must define scale/units and bounds.

Hotplugged USB/Bluetooth audio may change defaults; policy/profile
decides whether Rebuntu changes routing.

Do not automatically route microphone/audio based solely on device
appearance.

Verify effective route/default after mutation.

## Input Devices

Discover keyboards, mice, touchpads, gamepads and other relevant input
classes through udev and desktop/session providers.

Raw `/dev/input/event*` access is security-sensitive.

Do not broaden permissions or add users to `input` group for
convenience.

Configuration may include supported user-level properties such as
pointer/touchpad behavior through desktop/native providers.

Input observation should not capture keystroke content unless an
explicit future capability requires it and security architecture permits
it.

## Storage Devices and Mounts

Reuse Phase 12 storage identity/safety.

Separate: block device; partition; encrypted container; mapped device;
filesystem; mount; mount namespace.

Mount Operations validate: - stable source identity; - filesystem/type
where known; - target path ownership; - mount namespace/scope; -
existing mounts; - busy/in-use state; - options/policy; - authorization.

Unmount failure because busy is not a reason to kill arbitrary
processes.

Never auto-format unknown media.

Hotplug removal while mounted is an incident/evidence path, not a
cleanup opportunity.

## Network Interfaces

Separate: physical/logical interface; link state; connection/profile;
address; route; DNS; network manager/provider.

Use the active native network authority rather than writing
configuration behind its back.

Observe: - stable interface identity; - carrier/link; - addresses; -
routes; - manager state; - active connection.

Configuration changes must be planned so Rebuntu does not accidentally
sever the controlling SSH/session without explicit policy.

Do not implement a second DHCP client, routing daemon or NetworkManager.

## Bluetooth and Peripherals

Use BlueZ/native provider.

Separate: discovered; paired; trusted; connected; service/profile
available.

Discovery does not imply trust. Pairing is consequential. Trust changes
require explicit policy/authorization.

Never auto-pair arbitrary nearby devices.

Handle device disappearance and reconnect loops with Phase 12/9 bounded
retry semantics.

## Desktop Session, Wayland and X11

Discover: - login/session identity; - user UID; - seat; -
graphical/headless; - session type; - compositor/desktop where
discoverable; - DBus/user-manager environment; - readiness.

Do not infer target session solely from DISPLAY/WAYLAND_DISPLAY
environment inherited by a privileged process.

### Wayland

Wayland intentionally restricts global control. Use compositor/desktop
supported interfaces. Do not bypass security by scraping sockets or
injecting into another session.

### X11

Use RandR/X11 provider only when actual X11/XWayland semantics fit the
capability.

Do not pretend XWayland grants authority over Wayland compositor output
configuration.

Provider selection must be observable and explainable.

## Clipboard and Historical `clip`

Preserve the excellent historical Rebuntu UX:

    some_command | clip

The semantic capability is `clipboard.write` / `clipboard.read`
(validate canonical IDs).

`clip` is a thin shell verb/frontend.

Provider resolution may use the actual session stack: Wayland clipboard
tool/API; X11 clipboard provider; desktop-specific API if justified.

Requirements: - stdin/stdout discipline; - text/binary/MIME behavior
explicitly bounded; - correct target user/session; - no silent network
clipboard; - bounded payload; - no secret logging; - headless returns
structured unavailable/unsupported; - provider executable presence !=
session usability.

Do not hardcode `xclip` as Rebuntu architecture.

## User Environment

Distinguish: process environment; login environment; systemd
user-manager environment; desktop session environment; shell startup
configuration; XDG directories; application-specific environment.

Do not build one giant mutable global environment dictionary.

Environment changes need explicit persistence scope: current invocation;
child process; user session; future login; managed application/workload.

Never modify `.bashrc`, `.profile`, `/etc/environment` or similar whole
files casually.

Prefer managed fragments/drop-ins/native mechanisms where available.

Secrets must not be propagated into broad session environments by
default.

## Hotplug and Dynamic Reconfiguration

Canonical pattern:

native event -\> normalize -\> identify subject -\> acquire current
state -\> debounce/coalesce if needed -\> evaluate profile/policy -\>
produce bounded plan -\> authorize -\> Operation/Workflow -\> fresh
observation -\> verify.

Hotplug automations must be idempotent.

Examples: monitor connected; USB audio appeared; dock attached; storage
removed; network interface appeared; Bluetooth device connected.

A single physical dock can generate many events. Correlate/coalesce
rather than repeatedly reapplying the full environment.

Do not create `while true; scan devices`.

## Environment Profiles

Reuse Phase 11 Profile architecture.

Potential profile intent: - display arrangement; - preferred audio
endpoints; - device preferences; - network preference references; -
user/session environment; - resource profile references.

Profiles are capability-aware.

Application may be: FULLY_APPLIED; PARTIALLY_APPLIED; UNSUPPORTED;
BLOCKED; FAILED; UNKNOWN --- align with existing Result vocabulary.

Missing optional monitor/audio device should not necessarily fail the
entire profile.

Profile application is a Workflow of typed Operations, not a shell
script.

Hotplug may trigger reevaluation, but Phase 15 must avoid continuous
desired-state reconciliation that belongs to Phase 19.

## Required pressure scenarios

### Six-monitor workstation

Multiple 4K displays across several GPUs reconnect/reorder; Rebuntu
correlates identities, applies intended layout safely and verifies every
output without relying only on connector ordinal.

### Monitor hotplug storm

Dock/display attach emits many udev/compositor events; Rebuntu coalesces
them into one bounded reevaluation rather than repeatedly applying
layout.

### Bad display mode

Requested mode/scale becomes unsupported between plan and apply;
provider fails safely and preserves/restores a usable display
arrangement.

### GPU compute vs display

A GPU drives displays while Phase 14 wants compute assignment;
coordination preserves display role/reservation and explains selection.

### Wayland clipboard

`journalctl ... | clip` targets the correct graphical user session,
writes bounded text and reports unavailable cleanly when headless.

### Audio headset arrival

USB/Bluetooth headset appears; profile may prefer it, but mere presence
does not silently reroute unless policy/profile permits it.

### Busy removable mount

User requests unmount while processes hold files; Rebuntu reports
blockers/evidence and does not kill arbitrary processes.

### Storage surprise removal

Mounted device disappears; incident is recorded and Phase 12 safety path
is engaged rather than pretending unmount succeeded.

### Network change over SSH

Requested interface/profile change could sever the controlling session;
policy detects risk and requires explicit handling.

### Bluetooth stranger

Nearby unknown device is discovered; no pairing/trust occurs without
explicit authorization.

### Multi-user desktop

Two logged-in graphical users exist; Rebuntu resolves the requested
target session explicitly and never borrows another user's DBus/Wayland
context.

### Headless boot

No graphical session exists; device/network/storage core remains healthy
and display/audio/clipboard capabilities report unavailable rather than
failing Rebuntu.
