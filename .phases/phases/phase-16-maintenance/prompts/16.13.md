# Rebuntu --- Phase 16.13 --- Orphan Detection

## Agent Task

Execute this as a full standalone repository-aware engineering task:
archaeology, maintenance-domain analysis, architecture validation,
implementation, safety review, long-horizon/adversarial testing,
documentation and closure. Do not reduce it to an outline.

## Phase Mission

Detect genuinely orphaned Rebuntu-managed artifacts/resources through
ownership and reference evidence, distinguishing orphaned from merely
unused, inactive or old.

## Global Agent Contract

Implement **Rebuntu** only.

Mandatory principles:

SEARCH BEFORE IMPLEMENTING. MAINTENANCE != CLEANUP. OLD != ORPHANED.
UNUSED != SAFE TO DELETE. CACHE != GARBAGE. LOG != DISPOSABLE. LOW DISK
!= DELETE SOMETHING. UPDATE AVAILABLE != UPDATE AUTHORIZED. PACKAGE
INSTALLED != PACKAGE HEALTHY. CONFIGURATION DIFFERENT != CONFIGURATION
BROKEN. BACKUP EXISTS != BACKUP VERIFIED. INTEGRITY DIFFERENCE !=
COMPROMISE. RESTART != REPAIR. RETENTION != BLIND AGE-BASED DELETION.
QUARANTINE BEFORE PERMANENT DELETION WHEN OWNERSHIP/NEED IS UNCERTAIN.
NATIVE LINUX MAINTENANCE AUTHORITIES FIRST. PLAN BEFORE MUTATION. VERIFY
AFTER MUTATION. MAXIMALIST EXPLORATION; CONSERVATIVE IMPLEMENTATION.

Reuse: - Phase 0 Operations, Results, Configuration and ownership
semantics; - Phase 2 filesystem/scope/permission foundations; - Phase 5
monitoring/evidence; - Phase 7 observation; - Phase 8 assertions; -
Phase 9 automation; - Phase 10 workflows; - Phase 11
configuration/profiles; - Phase 12 recovery; - Phase 13 security; -
Phase 14 resource/performance; - Phase 15 devices/environment.

Do not create a second package manager, log daemon, backup engine,
filesystem repair system, scheduler, desired-state reconciler or
security scanner.

Canonical maintenance path:

    native observation / scheduled eligibility / operator request
        -> maintenance subject identity
        -> ownership + provenance
        -> current state + age/freshness
        -> policy / retention / criticality
        -> impact and dependency analysis
        -> maintenance plan
        -> authorization
        -> checkpoint/quarantine where needed
        -> canonical Operation / Workflow
        -> native provider
        -> fresh observation
        -> verification
        -> evidence / Result

Phase 16 performs bounded upkeep. Continuous desired-state convergence
belongs to Phase 19.

## Maintenance Ownership and Provenance

Before modifying or removing anything, determine who owns it
semantically.

Possible ownership: - Rebuntu-managed; -
operating-system/provider-managed; - application-managed; -
user-managed; - externally managed; - unknown.

Unknown ownership is not permission to clean.

Track provenance where practical: who/what created or registered the
artifact; which capability/profile/workflow references it; which
provider owns lifecycle; last verified use/change; retention policy;
whether it is reconstructable.

A file existing under a Rebuntu directory is useful evidence, not by
itself proof that permanent deletion is safe.

Avoid marker files as the only ownership truth.

## Package and Update Maintenance

Discover actual package providers and authority.

Separate: installed; available; upgradable; held/pinned;
broken/incomplete; obsolete according to provider; unused according to
provider; Rebuntu-required; user-explicitly-installed.

Do not infer "auto-removable" equals safe without considering
Rebuntu/user dependencies.

Updates require: - source/provider refresh semantics; - candidate
version; - policy; - dependency/impact plan; - disk-space
preconditions; - service/reboot implications; - checkpoint where
justified; - apply; - provider verification; - functional/security
verification where relevant.

Never parse human-oriented package-manager output if a structured/native
interface already exists and is practical.

Do not silently perform release upgrades.

## Configuration Drift

Drift requires a known managed intent or baseline.

Separate: desired managed value; observed effective value; source
representation; provider-generated representation; user override;
intentional local change; unknown change.

Normalize semantically where possible so formatting/order changes do not
become fake drift.

Drift classifications may include: expected; user-authorized;
provider-generated; unmanaged; actionable; security-relevant; unknown.

Phase 16 detects/reports and can perform bounded repair workflows where
already authorized. Do not implement Phase 19's continuous
reconciliation loop here.

Never overwrite an unknown user edit merely because it differs from a
template.

## Filesystem, Capacity and Temporary Data

Filesystem maintenance is conservative.

Potential observations: - free/used/reserved capacity; - inode
pressure; - mount/read-only/error state; - growth rate; - large managed
artifacts; - stale temporary objects; - provider caches/logs; -
filesystem-native maintenance status.

Low space response: OBSERVE -\> ATTRIBUTE -\> CLASSIFY -\> PLAN -\> SAFE
RECLAIM CANDIDATES -\> AUTHORIZE -\> RECLAIM -\> VERIFY.

Never: `find / -mtime +N -delete`; blindly truncate logs; clear
arbitrary caches; remove package databases; delete user downloads;
delete unknown temporary files merely by age.

Temporary data should align with systemd-tmpfiles/XDG runtime/native
lifecycle where appropriate.

Mount/filesystem repair remains Phase 12 territory.

## Log Maintenance

Prefer journald/logrotate/provider-native retention.

Preserve: - recent incident windows; - previous-boot evidence needed by
Phase 5/12; - security audit evidence required by Phase 13; -
correlation identifiers.

Retention policy can consider: age; size; importance; incident hold;
storage pressure; provider guarantees.

Do not delete logs to hide recurring failures or merely reduce disk
usage without recording what evidence was lost.

Maintenance evidence should record retention action, not reproduce
sensitive log content.

## Cache Maintenance

Classify cache: - owner/provider; - reconstructable or not; -
active/in-use; - rebuild cost; - size; - age; - performance role; - safe
native cleanup mechanism.

A cache can be large and still valuable.

Prefer provider-supported cleanup.

Do not treat: package cache; shader cache; model cache; browser cache;
compiler cache; application state as interchangeable.

Some "cache" directories contain state or downloaded assets
expensive/impossible to reconstruct. Verify semantics before removal.

Reclamation should be targeted and evidence-backed.

## Backup Maintenance

Rebuntu may coordinate providers; do not casually become a backup
implementation.

Observe: - configured backup jobs/providers; - last successful backup; -
last verified backup; - destination availability; - retention; - error
state; - scope coverage; - restore-test evidence.

Backup success != restore verified.

Verification should support bounded restore tests into safe temporary
fixtures where provider permits.

Do not delete source data because a backup command returned zero.

Retention must protect required generations and incident/recovery needs.

Secrets/encryption keys are handled through Phase 13 secret boundaries.

## Integrity Verification

Integrity means conformance to an expected trusted reference appropriate
to the artifact.

Potential references: - package manager metadata; - Rebuntu
manifest/hash; - configuration schema/invariant; - ownership/mode; -
provider state; - signed artifact metadata.

Hash mismatch is evidence of change, not proof of malicious
modification.

Preserve: expected reference provenance; observed value; timestamp;
verification method; uncertainty.

Do not hash enormous mutable trees continuously.

Use event-driven or scheduled bounded checks according to criticality.

## Service Maintenance

Use systemd as lifecycle authority for systemd-managed services.

Maintenance may involve: - configuration validation; - daemon-reload
when unit definitions changed; - reload if supported; - restart if
required; - health/readiness verification; - version/update
transition; - stale failure cleanup only when semantically justified.

Reload != restart. Restart != repair. Active != ready != healthy.

Avoid periodic restarts as generic maintenance.

Coordinate with Phase 12 so repeated failure becomes diagnosis/recovery
rather than a maintenance restart loop.

## Dependency Maintenance

Dependency categories: - Python/runtime dependency; - native package; -
external executable/provider; - systemd unit; - kernel feature; -
hardware capability; - configuration/schema version; - optional
integration.

Do not build a second SAT/package solver.

Use native provider dependency metadata and Rebuntu's semantic
capability graph.

Detect: missing; unavailable; incompatible; deprecated; superseded;
unused by known Rebuntu consumers; unknown.

An unused dependency is not automatically removable; ownership/user
intent still matters.

## Orphan Detection

Orphaned means the artifact/resource has a known ownership model but no
remaining valid owner or reference according to that model.

Examples may include: - abandoned Rebuntu runtime artifacts; - obsolete
generated config fragment; - stale registered capability version; -
detached temporary workspace; - old managed deployment artifact.

Not orphaned merely because: - old; - inactive; - not accessed
recently; - no current process has it open; - not referenced by one
registry; - user does not remember it.

Orphan confidence must be evidence-backed.

UNKNOWN -\> quarantine/report, not delete.

## Safe Cleanup and Quarantine

Cleanup is a planned maintenance Workflow, not a shell verb meaning "rm
stuff".

Candidate: -\> identify owner -\> prove scope -\> prove no active
references -\> estimate reclaim/benefit -\> classify reversibility -\>
policy/authorization -\> quarantine or provider-native cleanup -\>
verify functional state -\> retain recovery metadata -\> permanent
deletion only after explicit retention/policy.

Quarantine metadata should preserve original location, ownership,
reason, timestamp and restoration path without leaking secrets.

Never use `rm -rf` as a generic implementation primitive for uncertain
trees.

## Maintenance Automation

Use Phase 9.

Automation decides WHEN/WHY maintenance becomes eligible.

Examples: - package metadata refresh schedule; - disk pressure
condition; - log retention eligibility; - backup freshness violation; -
integrity-check schedule; - stale managed-temp eligibility.

Automated maintenance must have: - bounded scope; - idempotency; -
cooldown; - overlap policy; - resource budget; - authorization policy; -
evidence; - failure/retry bounds; - escalation.

Do not automate permanent destructive cleanup merely because a threshold
was crossed.

Maintenance automation must not create: low disk -\> delete -\> workload
regenerates -\> low disk -\> delete feedback storms.

Phase 16 can schedule bounded checks/actions; Phase 19 owns continuous
desired-state reconciliation.

## Phase-Specific Contract

Implement orphan detection with explicit ownership/reference proof and
confidence. Test old-but-valid and inactive-but-owned false positives.

## Required pressure scenarios

### Disk slowly fills

A filesystem trends toward low capacity; Rebuntu attributes growth,
identifies safe provider-owned candidates, preserves user data and
verifies reclaimed capacity.

### Post-crash evidence pressure

Disk is low after a hang/reboot, but previous-boot logs are under
incident hold; maintenance must not delete the evidence needed by Phase
5/12.

### Package updates pending

Updates include library and service changes; plan reports impact,
applies through native provider and verifies package plus affected
service health.

### User config edit

A managed config differs because the user intentionally changed an
override; drift is reported/classified and not blindly overwritten.

### Huge shader/model cache

Large cache is expensive to rebuild and actively useful; size alone does
not make it a cleanup target.

### Stale temp tree

Old temporary tree appears unreferenced but ownership is uncertain; it
is reported/quarantined rather than permanently deleted.

### Backup says success

Provider reports successful backup, but bounded restore verification
fails; backup health remains degraded.

### Orphan false positive

Artifact is old and inactive but referenced by a disabled profile;
orphan detector must preserve it.

### Service after update

Package update succeeds but service reload/restart causes health
regression; maintenance result is not successful until
verified/recovered.

### Cleanup feedback loop

Cache cleanup immediately causes workload regeneration and disk
pressure; automation cooldown/budget prevents oscillating deletion.

### Provider disappears

Package/backup/log provider becomes unavailable between plan and
execute; maintenance fails safely and records incomplete state.

### Long-running host

Simulated months of maintenance events do not leak state, grow queues
without bound, repeatedly restart services or progressively broaden
cleanup scope.
