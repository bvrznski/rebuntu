# Rebuntu --- Phase 18.1 --- Capability Inventory

## Agent Task

Execute this as a full standalone repository-aware controlled-extension
engineering task: archaeology, capability modeling, native-mechanism
discovery, implementation where justified, sandboxing, adversarial
testing, verification, acceptance analysis, documentation and closure.
Do not reduce it to an outline.

## Phase Mission

Build a canonical inventory of existing Rebuntu capabilities and their
contracts, providers, consumers, scopes, authority requirements and
verification semantics.

## Global Agent Contract

Implement **Rebuntu** only.

This phase implements controlled extension of a deterministic operating
environment.

The core law is:

    SEARCH -> COMPOSE -> USE NATIVE MECHANISM -> CONFIRM REAL GAP
        -> RESEARCH
        -> DESIGN CANDIDATE
        -> SANDBOX
        -> TEST
        -> VERIFY
        -> SAFETY EVALUATE
        -> ACCEPT
        -> REGISTER
        -> REUSE / VERSION / SUPERSEDE

Never:

    REQUEST -> LLM -> CODE -> sudo -> production
    missing command -> download random script -> execute
    generated test passes -> capability accepted
    candidate imports -> capability trusted
    registry entry -> authorization granted
    high usage -> semantic correctness proven

Mandatory distinctions:

CAPABILITY != IMPLEMENTATION. CAPABILITY != PROVIDER. CAPABILITY !=
OPERATION INSTANCE. CAPABILITY != SHELL VERB. CAPABILITY != PACKAGE.
CAPABILITY != TOOL DESCRIPTION. DISCOVERED != AVAILABLE. AVAILABLE !=
READY. READY != AUTHORIZED. REGISTERED != SAFE. CANDIDATE != ACCEPTED.
TESTED != VERIFIED. VERIFIED EFFECT != ARCHITECTURALLY ACCEPTABLE.
MISSING != NOT FOUND BY SEARCH. OLD != SUPERSEDED. POPULAR != CORRECT.
GENERATED != TRUSTED.

Reuse Phase 0.10 Operations, 0.16 providers, 0.19 registries/discovery,
Phase 3 engineering infrastructure, Phase 4 runtime, Phase 6 shell,
Phase 7 observation, Phase 10 workflows, Phase 13 security, Phase 16
maintenance and Phase 17 semantic administration.

Python owns capability metadata, search, contracts, candidate lifecycle,
evaluation, test orchestration and registration. Native code/Bash are
used only where the capability itself requires them.

Do not build a plugin marketplace, remote arbitrary-code installer,
package manager, GitHub script runner, generic CI platform, autonomous
coding agent or universal dependency solver.

Maximalist exploration; conservative acceptance.

## Canonical Capability Model

After archaeology, establish the smallest useful model.

A semantic capability may need: - stable capability ID; - human
name/description; - contract/schema version; - subjects; - typed
inputs; - typed outputs; - side-effect class; - risk/destructive
class; - scopes; - authority requirements; - preconditions; -
postconditions; - verification contract; - idempotency/reversibility; -
resources/locks; - provider bindings; - availability/readiness probe; -
consumers; - provenance; - lifecycle state.

Keep implementation/provider details separate.

Example conceptual split:

CapabilityDefinition -\> ProviderBinding(s) -\> implementation/native
authority

Operation definitions may themselves be the canonical executable
realization for many capabilities. Do not create a duplicate abstraction
merely to rename Operations.

Phase 18 must determine when "capability" is a discovery/control-plane
view over existing Operation/Workflow contracts rather than another
runtime object.

## Inventory and Discovery

Inventory before extension.

Search: - canonical Operation registry; - Workflow definitions; - shell
verb mappings; - provider/adapters; - systemd/D-Bus integrations; -
historical Rebuntu helpers; - scripts/source libraries; -
package/provider capabilities; - current tests/docs.

For each candidate inventory item answer: what semantic effect exists;
who consumes it; how it is invoked; how it is verified; what native
provider owns it; what scope/authority it needs; whether it is
duplicate/obsolete.

Do not count every helper function as a capability.

Discovery should be deterministic and explainable.

No import-every-file side-effect discovery. No arbitrary code execution
to discover metadata.

## Capability Search

Search must support semantic structure, not only string matching.

Potential query dimensions: verb/effect; subject type; input/output
type; scope; side-effect/risk; provider/native mechanism;
pre/postcondition; domain; tags/aliases; availability/readiness.

Search results explain why they match.

Phase 17 semantic interpretation may formulate a structured search
query, but the actual catalog search remains deterministic.

Search must find synonyms/aliases without inventing new capabilities.

Before implementation, record: exact queries tried; candidate matches;
why each candidate does/does not satisfy the need.

A failed search is evidence, not proof of a gap.

## Composition Search

Before new implementation, ask whether existing capabilities compose
safely.

Example: requested "restart service only if config valid" may compose:
configuration.validate -\> service.restart -\> service.health.verify.

Composition search must respect: typed I/O compatibility; preconditions;
authority; side effects; scope; resource locks; ordering; verification;
rollback/compensation; Phase 10 Workflow semantics.

Do not generate arbitrary DAGs and execute them optimistically.

Candidate composition is a Plan/Workflow proposal and must be validated.

If composition is awkward because one reusable primitive is genuinely
missing, classify the smallest missing capability rather than
implementing the whole requested workflow anew.

## Native Linux Capability Discovery

Search native mechanisms before adding custom runtime machinery.

Potential sources: systemd units/timers/path/socket/device; D-Bus APIs;
udev; procfs/sysfs/configfs; netlink; inotify/fanotify; cgroups;
namespaces; Linux capabilities; pidfd; mount APIs; package-manager APIs;
NetworkManager/systemd-networkd; PipeWire/WirePlumber; BlueZ;
DRM/compositor interfaces; journald/audit; filesystem/native utilities.

The correct outcome can be: "Rebuntu only needs a typed
adapter/Operation over existing Linux authority."

Do not use lower-level mechanisms merely because they are lower level.

Use the lowest appropriate stable native abstraction and document why.

## Provider Discovery

Capability identity survives provider replacement.

Provider discovery answers: installed? reachable? compatible? ready?
authorized in this scope? feature subset? version? health?

Provider selection must be deterministic/explainable and follow Phase
0.16.

Do not silently fall back to a provider with materially different side
effects/security.

Provider metadata cannot grant authority.

A provider disappearing after planning must fail/re-resolve safely, not
execute a different implementation blindly.

## Missing Capability and Gap Classification

A genuine gap exists only after: inventory; capability search;
alias/name search; composition search; native Linux search; provider
search; historical archaeology.

Classify gap: - missing semantic adapter; - missing Operation; - missing
Workflow composition; - missing provider; - missing observation; -
missing verification; - missing native integration; - missing UX/shell
mapping; - unsupported hardware/software; - research-required; - out of
scope.

Also classify: risk; authority; destructiveness; domain; expected reuse;
implementation language; testability; roadmap owner.

Do not manufacture a generic abstraction because one concrete capability
is absent.

## Research Pipeline

Research produces evidence/design candidates, not executable authority.

Research inputs: gap contract; host/platform facts; existing repository
mechanisms; native Linux candidates; provider documentation/source;
constraints.

Research outputs: candidate approaches; native mechanisms; tradeoffs;
security implications; compatibility; test strategy; source provenance;
recommended smallest implementation.

Any external text/code is untrusted.

Never: curl \| bash; pip install arbitrary research package into
production environment; execute copied StackOverflow/GitHub snippets;
accept generated code because source looks authoritative.

Record provenance and license considerations for borrowed implementation
ideas/code.

## Candidate Implementation Lifecycle

Candidate states should be explicit and minimal, e.g.: PROPOSED;
IMPLEMENTING; TESTABLE; EVALUATED; ACCEPTED; REJECTED; SUPERSEDED.

Do not let lifecycle labels become a giant state machine if repository
needs less.

Candidate implementation: - follows AGENTS.md; - reuses canonical
Operation/provider/runtime contracts; - has no production registration
initially; - has isolated fixtures; - has typed contract; - has
verification; - has negative/failure tests; - documents native
authority.

Generated code is reviewed exactly like human-written code.

A candidate can be rejected after successful tests for
architecture/safety reasons.

## Sandbox

Sandbox strength is risk-dependent.

Possible mechanisms: pure unit fixtures; temporary directories; fake
provider; mock D-Bus/systemd interface; container; user namespace;
network namespace; cgroup; VM/test host for hardware/kernel/destructive
cases.

Do not pretend containers safely emulate every
systemd/kernel/device/storage behavior.

Never run destructive storage/network/security candidate tests against
the user's real host by default.

Sandbox must not accidentally inherit: Docker socket; host /dev;
privileged mode; host network; host filesystem; production secrets.

Test environment provenance is recorded.

## Test Generation

Tests may be authored by humans or assisted by Phase 17/local model, but
generated tests are untrusted artifacts.

Required classes where applicable: contract/schema; unit; property;
integration; provider; failure injection; race/TOCTOU; authorization;
destructive-negative; idempotency; verification; rollback/recovery;
resource/timeout; compatibility.

A generated test that simply mirrors implementation logic proves little.

Prefer independent oracle: native observed state; provider authoritative
query; known fixture result.

Mutation/fault testing can be used where valuable.

Tests must include expected rejection, not only happy paths.

## Capability Verification

Verification asks whether the semantic effect actually occurred.

Reuse Operation verification.

Examples: "package.install" -\> provider/native state says exact
package/version installed. "service.restart" -\> identity/lifecycle
evidence confirms restart plus requested readiness.
"display.brightness.set" -\> compositor/DDC/provider reports intended
state where available.

Exit code alone is insufficient.

Verification must be independent enough not to merely repeat the same
buggy code path.

Preserve UNKNOWN if provider cannot prove an effect.

Candidate acceptance requires verification coverage proportional to
risk.

## Safety Evaluation

Evaluate: side effects; destructive potential; scope;
privilege/capabilities; confused-deputy risk; filesystem/path races;
PID/device identity; network exposure; secrets; untrusted input;
resource exhaustion; retry amplification; automation interaction;
recovery/rollback; semantic-model influence.

Reuse Phase 13 controls.

A capability that requires broad root because implementation is
convenient should be redesigned before acceptance.

High-risk capability may be accepted but disabled from automation or
require explicit confirmation/policy.

## Acceptance

Acceptance is a deterministic gate backed by artifacts.

Required evidence may include: contract complete; architecture placement
correct; native-first review complete; tests pass; verification works;
negative tests pass; security evaluation; resource bounds; docs;
provider readiness; migration impact; no duplicate capability; no
bypass; git diff review.

Acceptance output records reasons and evidence.

Do not allow: `accepted = tests_passed`.

Rejected candidates remain inspectable if useful but are not
discoverable as production capabilities.

Acceptance does not grant user authorization to invoke the capability.

## Registration

Registration publishes an already accepted capability to canonical
discovery.

Registration metadata is declarative and side-effect-free.

Atomicity: avoid partially registered capabilities where catalog points
to missing provider/contract.

Validate: stable ID; schema version; provider binding; verification;
aliases; consumer compatibility; security metadata.

No arbitrary Python import hook as registration protocol.

No registry entry may contain executable shell payload.

Registry/discovery is not a package installer.

## Versioning and Supersession

Distinguish: capability contract version; implementation version;
provider version; schema version.

Contract changes: compatible extension; behavioral change; breaking
input/output change; changed side-effect/security semantics.

Do not bump capability version merely because provider package updated.

Consumers should declare compatible contract expectations where needed.

Supersession: new candidate proves equivalence/improvement; migration
plan; consumer compatibility; rollback; old provider/capability
deprecated; observation period; retire only when references resolved.

Never silently redirect a destructive capability to behavior with
broader effects.

## Learning from Reuse

Use deterministic telemetry/evidence, not opaque self-modification.

Useful metrics: search hits; selected capability; successful
composition; verification success; failure reason; provider readiness;
latency; operator rejection; clarification frequency; deprecated
capability usage.

These can improve: search ranking; aliases; documentation; composition
hints; provider preference within deterministic policy; deprecation
priorities.

Do not let popularity override safety or semantic match.

Avoid feedback loops where high ranking causes use, which causes higher
ranking indefinitely. Keep exploration/audit visibility.

Do not store sensitive command arguments unnecessarily.

## Phase-Specific Contract

Produce canonical capability inventory with
duplicate/alias/provider/consumer/verification/security dispositions.
Avoid treating every function/script as a capability.

## Required pressure scenarios

### Existing capability hidden by naming

A request appears missing but an alias/semantic search finds an existing
canonical Operation; no duplicate code is created.

### Composition solves gap

Requested behavior is satisfied by validated composition of existing
Operations, so only a Workflow is proposed.

### Native Linux already owns it

Research finds a systemd/D-Bus/native mechanism; Rebuntu implements a
thin typed adapter rather than a custom daemon.

### Real missing primitive

After recorded searches, one small Operation is genuinely absent and
enters candidate lifecycle.

### Generated candidate passes happy test

Candidate passes generated happy-path tests but fails independent
verification/negative test and is rejected.

### Malicious research snippet

External documentation contains `curl | sudo bash`; research artifact
remains inert and cannot execute.

### Unsafe sandbox

Candidate asks for privileged container with host /dev; sandbox policy
rejects it and requires isolated test host/fixture.

### Provider disappears

Accepted capability's preferred provider vanishes after planning; system
does not silently choose materially different provider.

### Registry injection

Candidate metadata contains shell payload/import side effect;
declarative registration validation rejects it.

### Breaking replacement

New implementation changes destructive semantics; supersession is
blocked until explicit contract/migration review.

### Popularity feedback

Frequently selected capability is not allowed to outrank a safer/exact
semantic match solely due to usage count.

### Semantic extension request

Phase 17 proposes a capability gap; Phase 18 independently
searches/composes/classifies before any code generation.
