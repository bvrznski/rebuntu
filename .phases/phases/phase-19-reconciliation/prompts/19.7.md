Operations/Workflows and native providers, preserving idempotency,

## Global Agent Contract

Implement **Rebuntu** only.

Phase 19 is the first phase that may deliberately maintain selected
desired state over time. It must reuse the deterministic substrate
already built.

Canonical loop:

    DesiredState
        + authoritative ObservedState
        + Policy / Authorization
        + Resource / Capability context
        -> semantic comparison
        -> Drift
        -> Delta
        -> Reconciliation Plan
        -> canonical Operation / Workflow
        -> native provider
        -> fresh ObservedState
        -> Verification
        -> Evidence
        -> converged / remaining drift / blocked / degraded / unknown

Mandatory distinctions:

CONFIGURATION != DESIRED STATE. PREFERENCE != DESIRED STATE. POLICY !=
DESIRED STATE. OBSERVED STATE != CACHED ASSUMPTION. DIFFERENCE != DRIFT.
DRIFT != FAILURE. DRIFT != DELTA. DELTA != PLAN. PLAN != EXECUTION.
EXECUTED != CONVERGED. NO CHANGE != VERIFIED. DESIRED != AUTHORIZED.
DESIRED != POSSIBLE. CONVERGED != HEALTHY IN EVERY DIMENSION. RECOVERY
!= RECONCILIATION. RETRY != RECONCILIATION. EVENT != PERMISSION TO
MUTATE. CONTINUOUS != BUSY LOOP. IDEMPOTENT != "RUN IT AGAIN AND HOPE".
UNKNOWN MUST NOT BE COERCED TO FALSE/DRIFT.

Reuse: - Phase 7 Observation as authoritative current state; - Phase 8
Events/Assertions; - Phase 9 Automation/Scheduling; - Phase 10
Workflows; - Phase 11 Configuration/Profiles; - Phase 12 Recovery; -
Phase 13 Authorization/Policy; - Phase 14 Resources; - Phase 15
Environment coordination; - Phase 16 maintenance drift/ownership; -
Phase 18 capability discovery; - Phase 0.10 Operations and Phase 4
runtime.

Do not create a second observer, event bus, scheduler, resource manager,
recovery engine, configuration system, service supervisor or provider
stack.

Python owns desired-state models, comparison, deltas, planning,
control-loop state, verification and evidence.

Maximalist exploration; conservative enforcement.

## Desired State

Desired state is an explicit declaration that a managed subject should
satisfy a predicate or structured target condition.

Potential fields: - stable desired-state ID; - subject reference; -
scope; - target predicate/value; - owner/source; - provenance; -
priority only where semantics justify it; - applicability conditions; -
policy references; - enforcement mode; - verification contract; -
lifetime/activation; - conflict domain.

Sources may include: system configuration;
host/user/workload/environment profile; explicit operator request;
approved automation.

Do not infer desired state from whatever the machine currently happens
to look like.

Do not turn every preference into enforced state.

Examples: "service X should be enabled and healthy" may contain distinct
desired predicates. "prefer headset when present" is conditional
preference/profile intent and must be normalized carefully before
becoming enforceable desired state.

## Observed State

Observed state comes from Phase 7 and domain providers.

Every comparison must know: - provenance; - observation time; -
freshness; - subject identity; - completeness; - UNKNOWN/error state.

A stale observation cannot justify a consequential corrective action
without refresh.

Partial state can still reconcile independent known fields if policy
permits, but unknown fields must not be guessed.

Do not duplicate domain scans inside reconciliation.

Reconciliation may request fresh observation through existing typed
observation/evidence interfaces.

## Semantic State Comparison

Naive equality is insufficient.

Comparison may need: - canonical normalization; - set/order semantics; -
tolerance; - units; - provider representation; - default/effective
values; - absent vs unset vs null; - conditional applicability; -
current capability.

Examples: configuration file formatting difference may be semantically
equal; display refresh 59.94 vs nominal 60 may be equivalent under
domain semantics; service "active" does not imply desired
"ready/healthy"; unordered firewall/routing sets may need canonical
comparison.

Comparison returns structured relation, not only bool: SATISFIED;
DRIFTED; NOT_APPLICABLE; UNKNOWN; CONFLICTED/BLOCKED where appropriate
and aligned with existing vocabulary.

## Drift

Build on Phase 16 drift detection.

Drift is a meaningful unsatisfied relation between desired and observed
state.

Classify: actionable; intentional/temporarily accepted; blocked by
policy; blocked by resource/capability; unknown due stale/incomplete
observation; externally managed; conflicted; recovery-suppressed.

Do not "repair" user/external changes if Rebuntu does not own that
desired state.

Record when drift began only if evidence supports it.

Repeated identical drift should not produce unbounded events/evidence.

## Delta

Delta describes what semantically must change, not how to execute it.

Examples: service.enabled: false -\> true; mount.present: false -\>
true; display.scale: 1.0 -\> 1.25; package.version: A -\> B where
desired state legitimately owns version; file managed-value: X -\> Y.

Delta must preserve: subject; field/predicate; observed value; desired
value; comparison semantics; preconditions; risk hints; provenance.

Do not encode shell commands/provider calls in Delta.

Minimize deltas: already-satisfied fields produce no mutation.

## Reconciliation Planning

Planner maps Delta to registered canonical capabilities.

Use Phase 18 discovery if needed, but reconciliation cannot
generate/accept new capability inline.

Plan includes: Operations/Workflow; dependencies/order; preconditions;
authorization/policy; resource constraints; side effects; checkpoint;
expected effect; verification; rollback/compensation if applicable.

Plan only changes fields necessary for convergence.

Avoid restart/rewrite if native provider can apply narrower change.

Dry-run predicts the plan and unresolved constraints; it is not
convergence verification.

## Reconciliation Execution

All effects pass through Phase 0.10/10/4.

No direct: subprocess shell; file rewrite; systemctl; nft; mount; GPU
command from reconciliation logic.

Revalidate subject identity and current state before mutation.

If observed state changed after planning: recompare/replan rather than
blindly applying stale delta.

Each Operation returns evidence and is independently verified.

Partial plan failure leaves explicit remaining drift.

## Idempotent Convergence

A converged subject should require zero consequential mutations on the
next pass.

Test: R(S) -\> S' R(S') -\> no-op/satisfied

where R is reconciliation under unchanged desired state/context.

Avoid: rewriting identical files; restarting already-correct services;
reapplying display layout every event; toggling routes/default audio;
resetting GPU policy repeatedly.

Idempotency belongs to both comparison and Operations.

Detect oscillation: A -\> B -\> A -\> B.

Oscillation is a first-class non-convergence failure requiring
suppression/evidence/escalation, not faster retries.

## Conflict Detection

Conflicts can arise from: two profiles; system vs user desired state;
two automations; resource constraints; security policy; external manager
ownership; incompatible field targets.

Do not resolve by arbitrary load order or alphabetic winner.

Conflict resolution can use explicit ownership/priority/policy only when
defined.

Otherwise mark CONFLICTED/BLOCKED and explain competing declarations.

A lower-authority desired state cannot override protected system policy
merely because its numeric priority is higher.

## Policy and Resource Constraints

Desired state has no authority by itself.

Phase 13 decides whether the actor/source/enforcement mode may perform
the required effect.

Phase 14 determines resource feasibility.

Examples: desired GPU assignment cannot violate display reservation;
desired service cannot expose forbidden network listener; desired
memory/cgroup setting cannot exceed delegated limits; desired mount
cannot bypass storage safety; desired environment profile cannot control
another user's session.

Constraint failure may leave legitimate persistent drift.

Do not retry impossible/denied drift forever.

## Scheduling and Event-Driven Reconciliation

Use Phase 9/systemd timers for periodic checks where needed.

Prefer event-driven narrow reconciliation: service changed -\> reconcile
that service/predicate; display hotplug -\> relevant environment desired
state; mount lost -\> relevant mount desired state if not in recovery;
configuration changed -\> relevant managed object.

Event is a reason to re-evaluate, not proof of drift.

Debounce/coalesce by subject/desired-state set.

Periodic reconciliation is a safety net for missed events, not excuse
for high-frequency polling.

Use jitter/cooldown where fleets or expensive checks justify it, but do
not invent complexity without need.

## Recovery vs Reconciliation

Phase 12 Recovery responds to failure/degradation/incident.

Phase 19 Reconciliation moves managed state toward declared desired
state.

During active recovery, reconciliation may need to: pause; defer; limit
scope; accept temporary degraded desired state; coordinate through
explicit handoff.

Never: recovery restarts service -\> reconciliation immediately undoes
recovery workaround -\> recovery redoes it -\> loop.

Recovery can publish suppression/hold/context that reconciliation
respects.

After recovery completes, reconciliation reacquires fresh state and
reevaluates desired state.

Security incident quarantine from Phase 13 overrides ordinary
desired-state enforcement until explicitly released.

## Reconciliation Verification and Evidence

Verification asks: does fresh authoritative observed state satisfy the
desired predicate now?

Operation success is not enough.

Evidence chain: DesiredState source/version -\> ObservedState before -\>
comparison/drift -\> Delta -\> Plan -\> authorization/policy/resource
decisions -\> Operation/Workflow executions -\> ObservedState after -\>
predicate verification -\> remaining drift.

Bound repeated evidence by deduplicating unchanged drift while retaining
state transitions.

Explain no-op: already satisfied; not applicable; blocked; unknown;
conflicted; suppressed by recovery; policy denied.

Never claim convergence when verification is unavailable.

## Continuous Reconciliation

Long-running control-loop states may include: IDLE/SATISFIED; PENDING;
PLANNING; APPLYING; VERIFYING; BLOCKED; DEGRADED; PAUSED/SUPPRESSED;
NON_CONVERGENT; UNKNOWN, but reuse Phase 0.14 vocabulary rather than
inventing duplicates.

Required controls: bounded concurrency; per-subject serialization where
needed; cooldown; backoff; event coalescing; retry budgets; oscillation
detection; resource budget; recovery/security holds;
shutdown/cancellation; crash restart semantics.

Persist only semantic state necessary to avoid repeated unsafe actions
after restart.

Do not persist stale observed state as truth.

A restart must not cause all desired state to be blindly reapplied.

## Required pressure scenarios

### Already converged service

Desired enabled/running state is already satisfied; repeated passes
execute zero mutating Operations.

### Config formatting only

Managed config differs textually but normalized effective value matches;
no fake drift or rewrite occurs.

### User-vs-system conflict

Two declarations demand incompatible values; conflict is surfaced with
provenance rather than last-writer-wins.

### Display hotplug

Monitor reconnect triggers narrow environment reevaluation;
already-correct outputs are not repeatedly reconfigured.

### GPU resource conflict

Desired workload GPU conflicts with display/resource reservation;
reconciliation remains blocked instead of stealing resource.

### Recovery workaround

Phase 12 temporarily disables a failing service; reconciliation respects
recovery hold and does not immediately restart it.

### Security quarantine

Desired service running=true conflicts with Phase 13 quarantine;
quarantine wins and drift is explicitly blocked.

### Stale observation

Cached state says service stopped but fresh state says running before
execution; stale Delta is discarded/replanned.

### Oscillating provider

Provider normalizes A to B while desired comparator keeps demanding A;
oscillation detector halts repeated writes.

### Event storm

Thousands of equivalent change events coalesce into bounded subject
reconciliation.

### Provider unavailable

Desired state cannot be observed/applied because provider is
unavailable; state remains UNKNOWN/BLOCKED without infinite retries.

### Restart of Rebuntu

After controller restart, desired state is re-observed/recompared rather
than blindly reapplied from persisted stale state.
