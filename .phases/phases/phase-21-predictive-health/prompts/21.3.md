# Rebuntu — Phase 21.3 — CPU Load, Scheduler Pressure & Starvation

## Agent Task

Execute this as a full standalone implementation/audit/integration phase. Inspect the actual repository before designing. Search for existing mechanisms and migrate/extend them rather than duplicating them.

## Mission

Model scheduler pressure: run queue, load, runnable/blocked tasks, CPU PSI, steal/iowait where meaningful, affinity/cgroup starvation, IRQ/softirq pressure and sustained saturation trajectories.

# Rebuntu Phase 21 — Global Contract

This is a production-grade, repository-aware implementation task for **Rebuntu**.

Do not create a parallel monitoring platform. Reuse and extend the canonical mechanisms already
established by Phases 0-20.

Phase 5 owns foundational monitoring/evidence services.
Phase 7 owns authoritative observation/state.
Phase 8 owns events/assertions/correlation.
Phase 12 owns recovery.
Phase 13 owns authorization/security.
Phase 14 owns resource observation/control.
Phase 16 owns maintenance.
Phase 19 owns desired-state reconciliation.

Phase 21 owns **predictive health, precursor analysis, failure-risk estimation, crash/hang
prediction and policy-bounded preventive intervention**.

The fundamental pipeline is:

native signals
    -> timestamped observations
    -> normalized health features
    -> temporal windows / trends
    -> cross-signal correlation
    -> failure-mode hypotheses
    -> risk + horizon + confidence
    -> preventive plan
    -> authorization / policy
    -> canonical Operation / Workflow
    -> fresh observation
    -> verification
    -> evidence
    -> post-outcome validation / learning

Hard semantic distinctions:

Load != Pressure.
Pressure != Saturation.
Saturation != Degradation.
Degradation != Instability.
Instability != Failure Risk.
Failure Risk != Prediction.
Prediction != Diagnosis.
Prediction != Authorization.
Prediction != Recovery.
Prediction != Reconciliation.
Anomaly != Failure.
Warning != Crash Precursor.
High utilization != Unhealthy.
Correlation != Causation.
Temporal proximity != Causation.
Absence of evidence != Evidence of health.
UNKNOWN != HEALTHY.
Process alive != Making progress.
Operation executed != Preventive effect verified.
Reboot happened != Prediction proven correct.

Do not reduce host health to one arbitrary scalar score.

Represent risk by failure mode, horizon, confidence/evidence quality and supporting/contradicting
evidence.

Native Linux first:
- /proc
- /sys
- proc pressure stall information
- systemd and D-Bus
- journald
- cgroup v2
- kernel trace/event interfaces where justified
- udev/netlink
- hwmon/thermal/powercap
- block/NVMe interfaces and safe vendor tools/providers
- stable GPU/PCI identity and NVIDIA provider evidence where available

Do not build high-frequency polling everywhere.
Do not scrape shell commands when a stable native/API source exists.
Do not run expensive semantic/ML inference in the critical health loop by default.
Do not allow an LLM to decide privileged preventive action.
Do not silently kill workloads because a risk score increased.
Do not automatically reboot unless an explicit policy authorizes that class of action.
Do not disable kernel/thermal/storage safety mechanisms.
Do not perform destructive storage tests.
Do not induce real OOM, filesystem corruption, GPU reset or thermal emergency on the development
machine during ordinary tests.

Python is the primary implementation language. Bash remains thin glue/interactive UX.

The implementation must be useful on a single Linux workstation first and must not require Kafka,
RabbitMQ, Celery, Cassandra, ZooKeeper or any distributed infrastructure.

# Priority Host Reality

Design generically, but pressure-test against a demanding Linux workstation:
- many CPU cores / NUMA considerations,
- ~128 GiB memory class,
- multiple NVIDIA GPUs,
- sustained AI/GPU workloads,
- NVMe/storage history,
- desktop/session workload,
- occasional hard hangs requiring reboot.

Do not persist GPU ordinal as identity. Prefer PCI BDF + vendor UUID + provider/device evidence.
Do not persist /dev/sdX-like names as sole storage identity.
PID alone is not process identity; include start time or another stable runtime discriminator.

The system must distinguish a legitimately saturated compute workstation from a machine entering a
failure trajectory.

## Temporal Analysis Requirements

- [ ] Use monotonic time for interval/rate/persistence calculations; retain wall-clock/boot identity for human correlation.
- [ ] Support instantaneous value, rolling mean/median where justified, min/max, slope, acceleration, persistence, burst density and recovery rate.
- [ ] Do not use one window length for every signal.
- [ ] Represent missing samples and acquisition gaps explicitly.
- [ ] Detect stale collectors and observation lag.
- [ ] Use hysteresis to prevent threshold flapping.
- [ ] Support escalation and de-escalation independently.
- [ ] Distinguish a spike from a sustained precursor.
- [ ] Allow sequence features such as A THEN B WITHIN t THEN C.
- [ ] Preserve boot boundaries; do not compute nonsense trends across reboot.
- [ ] Record enough feature provenance to explain why risk changed.
- [ ] Bound retained high-frequency windows.
- [ ] Downsample/aggregate history deliberately rather than allowing unbounded growth.
- [ ] Prefer event-driven kernel/provider evidence where possible and adaptive sampling when risk rises.
- [ ] Sampling rate increases must themselves be resource-budgeted.
- [ ] Time jumps/DST must not corrupt monotonic risk windows.

## Risk Assessment Contract

A risk assessment must be structured approximately around these semantics (adapt names to canonical repository contracts rather than blindly creating this exact class):

```text
FailureRiskAssessment
  subject
  assessed_at
  boot_id
  health_context
  failure_modes[]
    mode
    risk_band
    calibrated_probability?      # only if genuinely calibrated
    confidence
    horizon
    supporting_evidence[]
    contradicting_evidence[]
    missing_evidence[]
    precursor_features[]
  coverage
  recommended_responses[]
  policy_constraints[]
  provenance
```

Do not emit fake decimal probabilities merely because a float looks scientific. If the model is not calibrated, use explicit ordinal risk bands plus confidence/evidence quality.

## Preventive Intervention Ladder

### 0 Observe
No mutation; normal collection.

### 1 Intensify observation
Increase bounded sampling, request targeted evidence, preserve precursor window.

### 2 Diagnose/notify
Explain likely pressure source/failure mode and safe operator options.

### 3 Admission/load control
Temporarily suppress new optional heavy Rebuntu jobs/workflows.

### 4 Reversible load shedding
Pause/throttle/cgroup-limit explicitly nonessential workloads under policy.

### 5 Targeted mitigation
Perform narrow verified action against identified source if authorized and safe.

### 6 Emergency preservation
Persist bounded evidence/state needed for post-reboot diagnosis and recovery.

### 7 Controlled shutdown/reboot
Only if explicit policy authorizes it and expected harm of continuing is greater; verify/preserve what is possible.
