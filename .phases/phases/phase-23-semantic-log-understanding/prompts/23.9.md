# Rebuntu — Phase 23.9 — GPU / NVIDIA / PCIe Semantic Understanding



## Agent Task

Execute this as a full standalone repository-aware implementation and integration phase. Inspect the actual repository first, reuse Phase 22/17/3 infrastructure, and do not create a second semantic framework.



## Mission

Interpret NVIDIA Xid/NVRM/PCIe evidence in context, distinguish application/GPU/driver/PCIe/system-level hypotheses and preserve stable device identity from deterministic providers.



## Global Phase 23 Contract

Implement **Rebuntu** only.

Phase 22 owns deterministic log acquisition, parsing, normalization, signatures, temporal windows,
correlation, evidence and incident reconstruction primitives.

Phase 23 adds **semantic understanding** on top of those primitives, initially coupled to a local
BitNet provider that we intend to run in Docker.

BitNet is a PROVIDER, not an architectural authority.

Canonical path:

Phase 22 typed evidence
  -> deterministic selection / redaction
  -> bounded EvidenceBundle
  -> SemanticLogRequest
  -> BitNet provider
  -> versioned structured candidate output
  -> schema validation
  -> evidence-reference validation
  -> epistemic classification
  -> deterministic consistency checks
  -> SemanticLogInterpretation
  -> optional additional EvidenceRequest
  -> bounded iteration
  -> diagnostic narrative / hypothesis set
  -> operator rendering

NEVER:

raw journal -> unbounded prompt
log text -> model -> shell
model -> sudo
model -> Docker socket
model -> arbitrary filesystem
model -> authorization
model -> direct recovery
model -> direct reconciliation
model -> direct load shedding
model output -> fact
model confidence -> evidence
JSON valid -> semantically trusted

Epistemic classes must remain explicit:

OBSERVED_FACT
DETERMINISTIC_DERIVATION
SEMANTIC_ANNOTATION
HYPOTHESIS
RECOMMENDATION
UNKNOWN

The model may explain, classify, correlate tentatively, summarize, generate competing hypotheses,
rank them with caveats, and request additional typed evidence.

The model may not fabricate evidence, execute commands, authorize action, mutate state, redefine
stable identity/timestamps, or override deterministic contradictions.

If BitNet is unavailable, Phase 22 still works.

If BitNet is wrong, the architecture must contain the damage to interpretation quality rather than
system authority.



## Docker / BitNet Boundary

The initial provider is expected to run in Docker.

Requirements:
- explicit image provenance/version;
- explicit BitNet runtime/model identity;
- CPU-only by default unless deliberately changed later;
- bounded CPU/memory/PID resources where practical;
- no `--privileged`;
- no host Docker socket;
- no broad host filesystem mounts;
- no host network unless justified;
- no secrets injected unnecessarily;
- read-only container filesystem where practical;
- writable temp/cache volumes narrowly scoped;
- health/readiness distinct from container liveness;
- request timeout and cancellation;
- maximum request/context/output sizes;
- concurrency limit/backpressure;
- restart behavior;
- structured logs/metrics;
- model checksum/version provenance where feasible.

Rebuntu must talk to a narrow semantic-service API, not to Docker internals throughout the codebase.

DockerProvider != SemanticProvider != BitNetModel.

Container running != inference ready.
Inference returned != schema valid.
Schema valid != evidence faithful.
Evidence faithful != hypothesis correct.



## EvidenceBundle Contract

A model input must be assembled from typed Phase 22 artifacts.

Candidate structure:

EvidenceBundle
  bundle_id
  incident_id
  boot_id
  anchor
  time_window
  question / semantic_task
  deterministic_summary
  records[]
    evidence_id
    timestamp
    source
    subject
    severity
    normalized_message
    selected_structured_fields
    raw_reference
  correlations[]
  signatures[]
  known_facts[]
  deterministic_derivations[]
  contradictions[]
  missing_coverage[]
  redaction_metadata
  token_budget
  provenance

The bundle is not a paste of every log line.

Selection must retain:
- chronology;
- rare/high-value signals;
- contradictory evidence;
- source diversity;
- boot boundaries;
- stable subject identity;
- references allowing drill-down.

Deterministic compression precedes semantic compression where possible.

  hypothesis_id
  failure_mode / concept
  statement
  supporting_evidence_ids[]
  contradicting_evidence_ids[]
  missing_evidence[]
  confidence_band
  causal_status
  alternatives[]

Every evidence ID returned by the model must exist in the supplied bundle or be rejected.

A model cannot create an observed fact by emitting a JSON object whose type says `fact`.

## Prompt / Context Construction Requirements

- [ ] Use a stable system contract that labels all evidence content as untrusted data.

- [ ] Separate instructions/schema from evidence using structural serialization.

- [ ] Never interpolate log text into privileged/tool instructions.

- [ ] Prefer typed JSON-like evidence serialization over freeform pasted transcript.

- [ ] Assign immutable evidence IDs before model invocation.

- [ ] Include boot/time/source/subject fields required for interpretation.

- [ ] Include contradictions and missing coverage rather than only evidence favoring one hypothesis.

- [ ] Bound records, bytes, tokens and time span.

- [ ] Preserve chronology after selection.

- [ ] Use deterministic deduplication from Phase 22.

- [ ] Do not let semantic summarization become the only retained representation.

- [ ] Record context-selection provenance.

- [ ] Use task-specific minimal context rather than universal giant prompt.

- [ ] Cap output tokens.

- [ ] Cap repair attempts.

- [ ] Cap evidence-request rounds.

- [ ] Treat malformed/truncated output as provider failure or bounded repair case.

- [ ] Do not recursively feed model prose back as new evidence.

- [ ] Do not hide provider/model/version from result provenance.
