# Phase 24.4 — Deterministic Upgrade Preflight Engine

## Objective

Implement a strictly read-only preflight engine for candidate platform changes.

Check package database consistency, repository availability, disk/boot space, dependencies/conflicts, held packages, DKMS, kernel/driver compatibility, initramfs tooling, known-good boot fallback, snapshot/backup capability, mounts, active failures, service constraints, and reboot requirements.

Return typed PASS / FAIL / UNKNOWN evidence. UNKNOWN must never silently become PASS. Semantic models may explain results but may not determine deterministic pass/fail facts.

## Mandatory invariants for every Phase 24.x task

- Read repository/project/AGENTS guidance first and inspect existing implementation extensively.
- Reuse, extend, migrate, and refactor before creating new modules.
- Never solve placement/architecture problems by simply deleting misplaced implementations.
- No destructive host action by default.
- No kernel removal, driver replacement, repository mutation, GRUB mutation, reboot, distribution upgrade, or destructive cleanup unless a later task explicitly requires it AND the user separately authorizes the concrete mutation.
- Preserve known-good recovery paths.
- UNKNOWN is not PASS.
- Preserve provenance and Rebuntu epistemic classes:
  OBSERVED_FACT, DETERMINISTIC_DERIVATION, SEMANTIC_ANNOTATION, HYPOTHESIS, RECOMMENDATION, UNKNOWN.
- BitNet/LLMs are advisory semantic providers only. They cannot authorize or execute actions, fabricate evidence, or mutate state.
- Never turn model text directly into shell authority.
- Runtime discovery is authoritative; do not hard-code the current development host as the universal Rebuntu machine.
- Integrate with Phases 21 Predictive System Health, 22 Log Analysis System, and 23 BitNet-Coupled Log Understanding where relevant.
- Add meaningful deterministic tests for new behavior and regressions.
- Update documentation and architectural inventories/tree metadata where the repository conventions require it.

## Completion requirement

Do not stop at scaffolding or TODO-only interfaces. Complete the repository inspection, integration, implementation, tests, and documentation that are legitimately in scope for this phase. Report discovered architectural conflicts and unresolved safety limitations explicitly rather than papering over them.
