# Phase 27.21 — Terminal Configuration Ownership & Drift

## Mission

Track terminal profile/config ownership, provenance and external/manual drift without fighting operator changes.

## Non-negotiable architecture and invariants

The project is always **Rebuntu**. Start with repository-first discovery and follow all applicable AGENTS.md/tree rules. Reuse, extend, refactor or migrate existing structures before creating parallel terminal abstractions. Apply **aggregational morphing**: mature existing shell/terminal/profile work into canonical ownership rather than bolting on another layer.

Keep these concepts strictly distinct:

```text
terminal emulator/provider
        !=
TTY / PTY
        !=
shell
        !=
console
        !=
Panel
        !=
OS login session
```

The intended interactive architecture remains:

```text
graphical terminal
      |
      +--> Fish + Oh My Fish + Zephyr     human interactive cockpit
      |
      `--> Fish `console`
               |
               `--> normal child Bash
                       |
                     exit
                       |
                       `--> Fish
```

The graphical terminal may explicitly launch Fish. Do **not** change the account login shell merely to implement this UX. Do not replace `/bin/sh`, `/bin/bash`, script shebangs, systemd/Docker interpreters or coding-agent Bash/POSIX behavior.

GNOME Terminal is the expected/current provider where discovered, not the architecture. Phase 27 must use provider adapters and runtime capability discovery. `$TERM` and `$COLORTERM` are evidence/hints, not sufficient proof of terminal capabilities.

Phase 27 owns terminal provider/profile/capability/TTY-PTY/terminal-session/terminal-visual configuration. Phase 26 owns Fish/Bash shell state, history, functions, aliases, environments and shell-facing tools. Phase 25 Panel is a frontend. Later generic configuration/secrets/identity phases remain their respective owners. Do not duplicate their semantics.

Powerline separators `   ` are abandoned and must not be restored, emulated or used as compatibility targets. If terminal/glyph validation needs a supported set, use only:

```text
FILES:              
NAVIGATION:                     ➜  ❯
SHELL/STATUS:             
SYSTEM:                       
DEV:                
GIT/STATE:      ↑  ↓  +  !  ?  ✘
```

Never redistribute or package font files as part of Phase 27. Store/configure font family references and validate availability through system/provider mechanisms. Do not invent a font installation path.

Terminal output, titles, OSC payloads, remote content and escape sequences may be untrusted. Clipboard contents are private data and must not be logged/captured as ordinary telemetry. Terminal management must not become surveillance.

All managed mutations follow:

```text
observe -> diff/plan -> validate -> backup -> authorize as required
        -> provider-native minimal apply -> verify -> record
```

No destructive profile cleanup, reset-to-default, broad dconf wipe or replacement of user configuration merely because it is unfamiliar. UNKNOWN is not PASS.

A broken Phase 27, custom profile, Fish launch, theme or font must not eliminate conventional Linux/Bash recovery. Recovery must not depend on Panel, semantic models or optional terminal integrations.


## Phase-specific implementation requirements

Fingerprint Phase 27-owned provider settings and detect manual/external changes. Show exact drift and ownership. Reconciliation must allow adopting operator changes or reapplying a planned state; never run a daemon that continuously fights manual profile edits.

## Required implementation method

### 1. Repository and live-state discovery
Inspect the repository for existing terminal abstractions, GNOME Terminal integration, launch configuration, shell-terminal coupling, profile code, font/palette settings, TTY/PTY utilities, capability checks, Panel APIs and recovery logic. Inspect relevant provider state non-destructively. Produce an ownership map before editing.

### 2. Canonical ownership
For each touched feature identify:
- native authority/provider;
- Phase 27 representation;
- configuration owner;
- read/query path;
- mutation path;
- shell/Panel consumers;
- fallback/recovery path.

Refactor overlapping terminal abstractions instead of creating another owner.

### 3. Typed provider-neutral contracts
Represent provider identity, profile identity, capabilities, terminal-side sessions and TTY/PTY context explicitly. Preserve provenance and UNKNOWN/unsupported state. Provider-specific IDs/settings may live in adapter payloads rather than contaminating the common domain.

### 4. Minimal provider-native mutation
Prefer supported provider-native APIs/settings. Plan exact changes, back up relevant state, preserve unrelated settings, apply the smallest change and verify by re-reading provider state. Do not use a full configuration reset as a repair strategy.

### 5. Shell boundary validation
Test terminal launch into Fish, `console` into child Bash, exit back to Fish, and direct conservative Bash recovery. Phase 27 must not own Fish prompt/history/config semantics.

### 6. Security and privacy
Treat terminal-delivered text/escape payloads as untrusted where appropriate. Do not log clipboard contents. Do not trust remote TERM values as authorization or local capability proof. Validate custom command/launch settings before enabling them.

### 7. Safe testing
Use temporary provider fixtures/profiles/config stores where feasible. Do not intentionally break the operator's only working graphical terminal profile. Failure-injection must preserve an independent recovery route.


## Global acceptance criteria

Complete only when:
- repository-first discovery and ownership mapping are documented;
- terminal, PTY/TTY, shell, console, Panel and login-session semantics remain distinct;
- GNOME Terminal is implemented as a provider adapter rather than hard-coded architecture;
- graphical launch can select Fish without changing the account login shell;
- `console` remains a normal child Bash path owned semantically by Phase 26;
- TERM/COLORTERM are not treated as sufficient capability proof;
- terminal profiles have stable provider-backed identity and provenance;
- font configuration stores references only; no font files are redistributed;
- only verified glyphs are relied upon and Powerline separators remain excluded;
- palette/visual management does not duplicate Fish/CLI semantic coloring;
- clipboard contents are not captured in ordinary logs/history;
- OSC/escape/custom-command/remote propagation risks are explicitly handled;
- provider changes are minimal, backed up and verified;
- manual profile changes are detected/reconciled rather than silently overwritten;
- degraded/provider-missing states are explicit;
- conventional Bash/TTY recovery remains possible;
- Panel and future frontends consume typed APIs rather than editing terminal config directly;
- tests cover provider loss, broken profiles, bad launch configuration and recovery;
- final reporting separates verified implementation from UNKNOWN/deferred behavior.

6. **Recovery** — backups, fallback paths and degraded/provider-missing behavior.
7. **Validation** — exact tests/checks and results, including failure cases.
8. **Performance** — launch/query/config overhead where relevant.
9. **Remaining UNKNOWNs** — unverified provider/capability behavior and concrete follow-up only.

Distinguish observed and verified behavior from assumptions or recommendations.
