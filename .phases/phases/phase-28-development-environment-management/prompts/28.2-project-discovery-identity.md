# Phase 28.2 — Project Discovery & Identity

## Mission

Discover development projects from deterministic repository/filesystem evidence and assign stable project identity without equating a directory basename with identity.

## Non-negotiable architecture and invariants

The project is always **Rebuntu**. Start with repository-first discovery and obey applicable AGENTS.md/tree rules. Reuse, extend, refactor or migrate existing structures before creating parallel project/runtime/toolchain abstractions. Apply **aggregational morphing**: converge existing development functionality into clear canonical ownership instead of adding a second development framework beside it.

Phase 28 is an **aggregator and manager of development context**, not a replacement for Git, Python, CMake, Meson, Ninja, npm/pnpm/yarn, test runners, linters, VS Code, Docker or coding agents. Native tools remain authoritative for their own semantics.

Preserve these boundaries:

```text
Phase 26 -> interactive shell, shell history, PATH/environment presentation
Phase 27 -> terminal provider/profile/TTY-PTY
Phase 28 -> project/repository/dev-environment/toolchain/task context
Phase 29 -> process/workload lifecycle
Phase 30 -> resource allocation/policy
Phase 34 -> GPU/accelerator runtime/topology
Phase 35 -> host packages/software
Phase 36 -> generic configuration semantics
Phase 37 -> secrets/credentials
Phase 39 -> temporal evidence
Phase 40 -> unified search/command
Phase 41 -> workflows
Phase 42 -> structural knowledge graph
Phase 45 -> unified control-plane contracts
```

Integrate with phases that exist in the repository; do not invent unavailable APIs merely because later architecture names are known.

The execution boundary remains:

```text
human interactive work -> Fish
`console`              -> child Bash
scripts/tasks          -> declared interpreter / Bash/POSIX where applicable
coding agents          -> Bash/POSIX execution boundary
```

Do not convert coding-agent automation to Fish. Do not change the account login shell.

Project identity is not a directory basename. Repository identity is not merely a remote URL. A project may contain multiple repositories; a repository may contain multiple logical projects; worktrees and monorepos must remain representable.

Agent/model prose is not execution evidence. A coding agent may report that a build passed, but Rebuntu should treat the actual command/tool result, exit status and artifacts as evidence. Semantic/model output must remain advisory unless independently validated.

Development fingerprints must be bounded and privacy-aware. Include selected technical facts useful for reproduction/diagnosis, but never dump complete environments, credentials, tokens, SSH material, secret `.env` values or arbitrary source contents. Secret material belongs to Phase 37.

No generic 'run arbitrary command as root' development capability. Project tasks execute under declared/native mechanisms and the current authorized user/context unless an owning subsystem explicitly defines otherwise.

No destructive repository cleanup, dependency purge, environment deletion, source rewriting, branch reset, `git clean`, lockfile regeneration or package removal merely as generic repair. UNKNOWN is not PASS.

All managed configuration mutations follow:

```text
observe -> diff/plan -> validate -> backup -> authorize as required
        -> minimal/provider-native apply -> verify -> record
```

A broken Phase 28 must not make repositories, compilers, editors, shells or ordinary Linux development tools unusable. Conventional manual development/recovery remains available.


## Phase-specific implementation requirements

Implement deterministic project discovery using explicit Rebuntu metadata if present, VCS roots, build/package manifests, workspace declarations and configured project roots. Record why a directory was classified as a project. Handle nested/ambiguous candidates explicitly. Never scan the entire filesystem unbounded by default.

## Required implementation method

### 1. Repository-first discovery
Search the actual Rebuntu repository for existing project/repository/environment/runtime/toolchain/task/editor/agent abstractions and integrations. Search configuration and AGENTS.md guidance before choosing locations. Produce an ownership/reuse/migration map before adding code.

### 2. Provider discovery, not assumptions
Detect providers and project declarations at runtime. Never assume Python/Node/CMake/VS Code/Docker/CUDA exists merely because Phase 28 supports adapters for them. Return unsupported/unavailable/UNKNOWN explicitly.

### 3. Canonical typed references
Use stable typed refs and provenance for project, repository/worktree, environment, runtime, toolchain, build system, task and editor/agent contexts. Provider-specific metadata belongs in bounded adapter payloads.

### 4. Deterministic selection
When resolving active runtime/toolchain/project/task, expose precedence and evidence. Ambiguity must remain ambiguity unless the operator or project configuration resolves it.

### 5. Native execution semantics
Invoke native build/test/task/package tools according to declared project semantics. Capture command, cwd, environment reference, exit status, duration and relevant artifacts/results. Do not infer success from agent/model text.

### 6. Configuration safety
Treat project-authored configuration as valuable source. Managed changes should be minimal, backed up and ownership-scoped. Do not normalize/reformat unrelated project files.

### 7. Secrets and privacy
Filter secret-bearing environment/config fields before fingerprints, logs, indexes, Panel output or model context. Store references/metadata where later Phase 37 integration is available.

### 8. Safe tests
Use fixture repositories, temporary HOME/workspaces/environments and mock/fake providers for mutation/failure testing. Never destroy or rewrite the user's real repositories as a test.


## Global acceptance criteria

Complete only when:
- repository-first discovery and ownership mapping were performed;
- existing development abstractions were reused/refactored/migrated before additions;
- project, repository, worktree and environment identities remain distinct;
- provider availability is discovered rather than assumed;
- runtime/toolchain selection is explainable with executable/path/version provenance;
- native Git/build/test/package/editor semantics remain authoritative;
- Phase 28 does not duplicate Phase 26 shell or Phase 27 terminal ownership;
- coding agents retain Bash/POSIX execution boundaries and no implicit root authority;
- actual command/tool results are evidence; agent/model narrative is not;
- project fingerprints exclude secret material and are explicitly bounded;
- tasks are typed/provider-backed rather than arbitrary privileged shell strings;
- project-authored configuration is not silently overwritten;
- no destructive source/repository/environment cleanup occurs as generic repair;
- Panel/CLI/future clients consume typed Phase 28 APIs;
- degraded/missing providers produce explicit unsupported/UNKNOWN states;
- manual development remains possible if Phase 28 is unavailable;
- tests use safe fixture projects/environments for destructive/failure scenarios;
- final reporting clearly separates verified implementation from deferred/UNKNOWN behavior.


## Required final report for Phase 28.2

Return an implementation report containing:

1. **Discovery** — existing repository structures, project/provider configuration and applicable AGENTS.md guidance.
2. **Ownership** — authoritative native providers, Phase 28-owned abstractions and cross-phase references.
3. **Implementation** — exact files changed/created/refactored/migrated.
4. **Selection & provenance** — how projects/runtimes/toolchains/tasks are resolved and what evidence supports them.
5. **Agent/tool boundary** — execution shell, privilege, task invocation and actual-result verification.
6. **Privacy & safety** — secret filtering, configuration protection and destructive-action review.
7. **Validation** — exact fixture/unit/integration checks and results, including missing/broken providers.
8. **Performance** — discovery/fingerprint/task-management overhead where relevant.
9. **Remaining UNKNOWNs** — unverified or deferred provider behavior and concrete follow-up.

Do not report agent/model narrative as proof of implementation. Distinguish observed tool/repository evidence, deterministic derivation, and recommendations.
