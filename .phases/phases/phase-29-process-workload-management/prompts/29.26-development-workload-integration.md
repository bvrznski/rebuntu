# Phase 29.26 — Development Workload Integration

## Mission

Integrate Phase 28 tasks/builds/tests/agents as workload context while preserving project/task ownership.

## Non-negotiable architecture and invariants

The project is always **Rebuntu**. Begin with repository-first discovery and obey applicable AGENTS.md/tree rules. Reuse, extend, refactor or migrate existing process/workload structures before creating parallel implementations. Apply **aggregational morphing**: converge generic lifecycle/grouping logic into canonical Phase 29 ownership rather than accumulating wrappers around `ps`, `pgrep` and `kill`.

The central distinction is:

```text
PROCESS != WORKLOAD
PID != DURABLE PROCESS IDENTITY
PROCESS TREE != WORKLOAD MEMBERSHIP
SERVICE != PROCESS
CONTAINER != PROCESS
PROJECT TASK != PROCESS
```

A Linux PID is transient and may be reused. Every consequential process action must bind to a richer `ProcessRef` and revalidate identity immediately before mutation. Never canonicalize `pkill <name>`, `killall`, `ps | grep | awk | xargs kill`, broad regex/name matching or stale PID lists as safe management mechanisms.

A **workload** is a Rebuntu/provider-backed grouping with explicit membership evidence and lifecycle semantics. It may correspond to a systemd unit/scope, container, development task, explicit cgroup or declared Rebuntu grouping, but Phase 29 must not invent membership merely because processes share a name, executable or parent.

Preserve domain ownership:

```text
Phase 26 -> shell/session/history context
Phase 27 -> terminal/TTY-PTY context
Phase 28 -> development project/task context
Phase 29 -> process/workload identity + lifecycle
Phase 30 -> resource capacity/pressure/allocation/policy
Phase 31 -> service semantics/lifecycle
Phase 34 -> accelerator identity/usage/control
Phase 38 -> user/account/session/authorization semantics
Phase 39 -> temporal events/history
Phase 41 -> durable multi-step workflows
Phase 42 -> structural relationships/impact
Phase 44 -> adaptive policy
Phase 45 -> shared control-plane contracts
```

Integrate only with APIs that actually exist in the repository; do not fabricate later-phase interfaces.

Graceful/provider-native lifecycle control is preferred. A service should normally be stopped through its service provider, a container through its container provider, and a managed workload through its workload owner rather than killing arbitrary member PIDs.

High resource usage is not itself a fault and never grants permission to kill/throttle a process. Resource policy belongs to Phase 30. Phase 29 may expose observations and lifecycle capabilities.

Protect the operator and machine control path. Generic lifecycle operations must detect/protect, where evidence exists:
- active desktop/display-critical workloads;
- current terminal/shell/operator session;
- SSH/remote maintenance path;
- Rebuntu control/recovery components;
- explicitly critical/protected services/workloads.

Protection is policy and evidence, not an absolute 'unkillable' bit. High-risk override requires explicit authorization and impact/recovery handling.

All consequential mutations follow:

```text
observe
 -> resolve exact ProcessRef / WorkloadRef
 -> impact + protection checks
 -> plan
 -> authorize as required
 -> immediate identity/membership revalidation
 -> provider-native action
 -> verify
 -> record
```

Execution success is not verification success. UNKNOWN is not PASS. Partial bulk action is explicit.

No generic broad process cleanup, 'kill hung processes', zombie purge, orphan purge or background-process termination. A zombie is already exited and generally cannot be repaired by sending it another signal.

Process inspection can expose sensitive information. Command lines, environment, open files, sockets and ownership data must be minimized, access-controlled/redacted where appropriate, and never dumped wholesale into semantic/model context. Secret values belong to Phase 37.

A broken Phase 29 must not prevent conventional `ps`, `systemctl`, container tooling, TTY/Bash or ordinary Linux recovery.


## Phase-specific implementation requirements

Associate Phase 28 build/test/agent task refs with workloads when actual execution evidence supports it. Preserve task result ownership. Stopping a development workload must not imply repository cleanup or source mutation.

## Required implementation method

### 1. Repository-first discovery
Search the repository for process models, PID wrappers, workload/task abstractions, process trees, signal/kill helpers, systemd/container integration, resource/GPU process mapping, Panel process views and recovery code. Produce an ownership/reuse/refactor/migration map before implementation.

### 2. Linux/provider evidence
Use authoritative Linux/provider interfaces appropriate to the repository. Preserve observation timestamps, boot identity/start-time evidence and permission errors. Do not scrape formatted human `ps` output when structured kernel/provider data is already available.

### 3. Stable identity and race discipline
Define process identity robustly enough to detect PID reuse. Bind plans to identity evidence and re-read it immediately before action. Treat disappearance between observe and execute as a normal race outcome, not necessarily an error.

### 4. Workload abstraction
Build workload membership from explicit provider/declaration evidence. Keep workload lifecycle separate from individual process signaling. Route actions to the owning provider when possible.

### 5. Protection and impact
Before lifecycle mutation, determine active-session/display/service/container/control-plane/dependency context to the extent available. If critical evidence is missing, expose UNKNOWN and require policy/authorization appropriate to the risk.

### 6. Safe mutation
Prefer graceful stop and native lifecycle APIs. Escalation is explicit and verified. Never implement a convenience bulk-kill path that bypasses stable identity and protection.

### 7. Safe testing
Use spawned disposable processes, isolated scopes/cgroups/containers or fakes. Intentionally create PID/member races in fixtures. Never kill arbitrary real user/system processes to prove functionality.


## Global acceptance criteria

Complete only when:
- repository-first discovery and ownership mapping were performed;
- ProcessRef is richer than PID and detects stale/reused identity;
- every consequential process action revalidates exact identity immediately before mutation;
- process ancestry, POSIX groups/sessions and workload membership remain distinct;
- workload membership has explicit provenance/evidence;
- service/container/task workloads route lifecycle actions to their owning provider where possible;
- graceful stop precedes escalation unless explicit semantics require otherwise;
- TERM/KILL escalation is explicit, bounded and verified;
- bulk actions cannot target processes by loose name/grep matching;
- current operator/terminal/display/maintenance/control-plane protections are implemented where evidence is available;
- high CPU/RAM/GPU use is not treated as permission to terminate;
- zombies/orphans are represented correctly rather than generically 'cleaned';
- resource allocation remains Phase 30 ownership;
- sensitive process metadata is minimized/redacted/access-controlled;
- Panel/CLI consume typed Phase 29 plans/capabilities;
- races, partial actions and provider loss produce explicit outcomes;
- conventional Linux recovery remains available without Phase 29;
- failure tests use disposable targets;
- final reporting separates verified facts from UNKNOWN/deferred behavior.


## Required final report for Phase 29.26

Return an implementation report containing:

1. **Discovery** — existing process/workload/PID/signal/provider structures and applicable repository guidance.
2. **Ownership** — what Phase 29 owns, what remains with service/container/resource/session/GPU providers, and what was migrated.
3. **Identity & race safety** — exact ProcessRef/WorkloadRef evidence and pre-mutation revalidation behavior.
4. **Implementation** — exact files changed/created/refactored and lifecycle/provider paths.
5. **Protection & impact** — operator/display/maintenance/control-plane protections and UNKNOWN dependencies.
6. **Mutation safety** — graceful stop, escalation, bulk-target discipline, authorization and verification.
7. **Privacy** — handling of argv/open-resource/session/user metadata and redaction/minimization.
8. **Validation** — exact disposable-process/fixture tests and results, especially PID/member races and partial failure.
9. **Performance** — enumeration/observation/query overhead and any bounded sampling strategy.
10. **Remaining UNKNOWNs** — concrete unverified/deferred behavior only.

Do not treat command output prose, semantic interpretation, PID alone or successful signal syscall as sufficient proof of the intended final state.
