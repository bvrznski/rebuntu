# Phase 30.9 — Swap & Virtual Memory Context

## Mission

Expose swap and virtual-memory context as resource evidence, not as simplistic health scores.

## Non-negotiable architecture

The project is always **Rebuntu**. Perform repository-first discovery and obey applicable AGENTS.md/tree rules. Reuse, refactor, migrate and generalize existing resource structures before adding new ones. Apply **aggregational morphing**; do not build a second resource manager beside existing canonical mechanisms.

The defining model is:

```text
CAPACITY
   !=
OBSERVED CONSUMPTION
   !=
PRESSURE
   !=
DEMAND
   !=
RESERVATION
   !=
ALLOCATION
   !=
POLICY
```

Never collapse these concepts into one percentage or generic `resource_usage` object. A machine may have high utilization without harmful pressure; a workload may demand resources it is not currently consuming; a reservation may exist without consumption; an allocation may be enforced without being fully used.

Phase boundaries:

```text
Phase 29 -> what processes/workloads are running + lifecycle
Phase 30 -> resource capacity/pressure/demand/reservation/allocation/policy
Phase 31 -> service semantics
Phase 33 -> network configuration/connectivity
Phase 34 -> accelerator hardware/runtime/topology/control
Phase 39 -> temporal evidence
Phase 42 -> structural relationships
Phase 44 -> cross-subsystem adaptive coordination
```

Phase 30 must not kill workloads as a generic reclamation primitive, reset GPUs, reconfigure networking, stop services or mutate project state. It requests typed actions from owning subsystems where architecture permits.

Runtime discovery is mandatory. Never hard-code the workstation's CPU count, RAM amount, number/type/order of GPUs, NUMA topology, interface names, link speeds or device ordinals. Provider-local ordinals are not durable resource identity.

Resource observations require timestamps, units, source, sampling/window semantics and freshness. Counter deltas must use valid intervals. Missing/stale evidence is UNKNOWN, not zero.

Policy must be deterministic and explainable. A policy records inputs, scope, precedence, constraints and proposed outputs. Semantic/model output may recommend a policy or explain evidence, but cannot become resource authority or directly execute allocation.

All consequential actions follow:

```text
observe -> resolve stable resource/workload refs -> evaluate policy
 -> plan -> constraints/impact/protection -> authorize as required
 -> revalidate -> provider-native apply -> verify effective state -> record
```

Control loops require hysteresis/cooldown/rate limits and stale-evidence handling. Do not create oscillating affinity, quota, GPU or workload policies.

Protect operator-facing, display-critical, maintenance and Rebuntu control/recovery paths. High CPU/GPU/RAM/I/O/network use is not permission to deprioritize, suspend or terminate them.

No broad cache deletion, swap destruction, process killing, filesystem cleanup or service stopping as generic 'free resources' behavior. Conventional Linux tools and recovery must remain usable if Phase 30 is unavailable.


## Phase-specific implementation requirements

Capture swap configured/used/activity and relevant VM context. Swap use is not automatically a fault. Never disable/recreate swap as diagnosis.

## Required implementation method

1. **Discover first.** Search the repository for resource monitors, schedulers, cgroup/systemd controls, CPU/NUMA logic, memory metrics, GPU/VRAM handling, I/O/network metrics, workload attribution and policy code. Produce an ownership/migration map.
2. **Typed evidence.** Every resource measurement carries ResourceRef, provider, units, timestamps/window and freshness. Preserve raw/native semantics where normalization would lose meaning.
3. **Stable references.** Bind workload consumers through Phase 29 refs and accelerators through Phase 34 refs when those APIs exist. Never persist remembered ordinals as semantic identity.
4. **Policy separation.** Keep observation, diagnosis, policy evaluation, planning and execution separate modules/interfaces. A diagnostic result must not mutate the host.
5. **Native enforcement.** Use cgroups/systemd/kernel/driver/provider mechanisms rather than bespoke polling enforcement where possible. Re-read effective state after apply.
6. **Safety.** Revalidate topology, targets, active protections and evidence freshness immediately before mutation. Partial enforcement is an explicit outcome.
7. **Testing.** Use fake providers, disposable cgroups/workloads/containers and bounded synthetic load. Never stress the real workstation to dangerous thermal/memory/I/O exhaustion merely to test the subsystem.


## Global acceptance gate

Phase work is complete only when the implementation:
- preserves all capacity/consumption/pressure/demand/reservation/allocation distinctions;
- discovers topology/capabilities at runtime;
- uses typed stable resource and workload references;
- records units, sampling windows, provenance and freshness;
- treats stale/missing data as UNKNOWN rather than zero/PASS;
- keeps Phase 29 lifecycle and Phase 34 hardware control outside Phase 30 ownership;
- makes policies deterministic, inspectable and explainable;
- provides plan-before-mutate behavior with revalidation and postcondition verification;
- includes hysteresis/cooldown/rate limiting for repeated control;
- protects operator/display/control-plane workloads;
- never uses generic kill/cleanup as resource reclamation;
- preserves native cgroup/systemd/kernel/provider semantics;
- exposes structured CLI/Panel APIs rather than UI-specific control logic;
- degrades safely when providers disappear or topology changes;
- uses safe disposable fixtures for pressure/contention/failure testing;
- documents exact verified behavior and leaves unsupported behavior as UNKNOWN/deferred.


## Required final report for Phase 30.9

Return:
1. **Discovery and ownership** — existing code/providers reused, migrated or intentionally left with another phase.
2. **Evidence model** — resource refs, units, timestamps/windows, provenance and freshness.
3. **Implementation** — exact files and provider/common-layer changes.
4. **Policy/plan behavior** — deterministic inputs, constraints, protection, authorization and revalidation.
5. **Safety** — anti-oscillation, stale-data handling, protected workloads and forbidden reclamation shortcuts.
6. **Verification** — exact effective-state checks after any mutation.
7. **Tests** — safe fixtures/failure cases and observed results.
8. **Performance** — sampling/controller overhead.
9. **Remaining UNKNOWNs** — unsupported/unverified behavior only.

Do not present utilization as pressure, consumption as demand, reservation as allocation, a model recommendation as policy authority, or successful provider invocation as proof of verified effective state.
