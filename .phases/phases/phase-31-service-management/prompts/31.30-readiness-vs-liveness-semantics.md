# Phase 31.30 — Readiness vs Liveness Semantics

## Mission

Distinguish readiness, liveness, successful activation and provider active state where the service/provider supports those concepts.

## Non-negotiable architecture and invariants

The project is always **Rebuntu**. Begin with repository-first discovery and obey applicable AGENTS.md/tree rules. Reuse, refactor, migrate and generalize existing service/systemd structures before creating new ones. Apply **aggregational morphing**: Phase 31 becomes canonical ownership for generic service semantics rather than another wrapper beside existing helpers.

The core distinctions are mandatory:

```text
SERVICE != PROCESS
SERVICE != WORKLOAD
LOADED != ENABLED
ENABLED != RUNNING
RUNNING != HEALTHY
ACTIVE != READY
RESTART != RELOAD
SERVICE RELOAD != SERVICE-MANAGER DAEMON-RELOAD
ORDERING != REQUIREMENT
UNIT FILE != EFFECTIVE CONFIGURATION
```

systemd is the expected primary provider on the current Linux environment when discovered, but **systemd is a provider, not the architecture**. Common contracts must not expose systemd-specific assumptions as universal service semantics.

Native service managers remain authoritative. Phase 31 does not implement its own init system, process supervisor or dependency solver. It observes, plans and invokes provider-native capabilities.

Preserve ownership boundaries:

```text
Phase 24 -> platform/kernel/driver/release evolution
Phase 29 -> process/workload identity + lifecycle
Phase 30 -> resource capacity/pressure/allocation/policy
Phase 31 -> service identity/state/lifecycle/dependencies/config-health
Phase 36 -> generic configuration model
Phase 37 -> secrets/credentials
Phase 38 -> users/identity/authorization context
Phase 39 -> temporal evidence
Phase 41 -> durable multi-step workflows
Phase 42 -> structural graph/impact
Phase 45 -> shared control-plane contracts
```

Integrate only with APIs actually present in the repository.

A service must normally be controlled as a service, not by killing its member PID. Phase 29 may expose process/workload evidence, but Phase 31 routes service lifecycle through the owning service provider.

System and user managers are separate authorities. Never silently substitute `systemctl --user` for system service control or vice versa.

Enablement and activation are separate. A disabled service may be active; an enabled service may be inactive; socket/timer/path activation may intentionally leave the service process absent until triggered. Do not label these combinations as faults without provider semantics.

All consequential operations follow:

```text
observe -> resolve exact ServiceRef -> dependency/impact/protection analysis
 -> plan -> validate -> backup if config changes -> authorize
 -> immediate target/config revalidation -> provider-native apply
 -> verify effective provider state + expected postconditions -> record
```

Do not use `systemctl reset-failed`, daemon-reload, enable/disable, mask/unmask, restart, kill or broad unit-file edits as generic troubleshooting shortcuts. Each operation needs a reason and exact scope.

Prefer provider-supported drop-ins/overrides over modifying packaged/vendor unit files. Preserve unknown directives, precedence and comments/files outside the managed patch. Never broadly delete `/etc/systemd` content or reset service configuration.

Health is evidence-backed and service-specific. `active (running)` is not proof that the application is healthy. Conversely, an inactive socket-activated service is not necessarily unhealthy.

Protect active desktop/display, operator terminal/remote maintenance, networking required for current access, Rebuntu control/recovery and explicitly critical services from unsafe generic actions. UNKNOWN dependency/protection evidence is not PASS.

Service environment and command metadata can contain secrets. Never copy secret values into general logs, Panel DTOs, fingerprints, semantic-model context or audit records. Phase 37 owns secret material.

A broken Phase 31 must not prevent conventional `systemctl`, journal inspection, Bash/TTY recovery or native service-manager operation.


## Phase-specific implementation requirements

Represent readiness/liveness only for services/providers with concrete checks/signals. Successful `start` command does not necessarily mean ready; readiness timeout is a distinct outcome.

## Required implementation method

1. **Repository-first discovery.** Find all service/systemd helpers, unit models, lifecycle wrappers, health checks, service configuration, Panel views and process/resource integrations. Produce an ownership/reuse/migration map before adding structures.
2. **Provider-native evidence.** Query structured provider state where possible. Preserve native active/sub/result/enablement states and timestamps instead of parsing human-formatted output into lossy booleans.
3. **Stable identity.** Bind actions to provider/scope/unit identity and revalidate immediately before mutation. PID is only member-process evidence.
4. **Dependency semantics.** Preserve relationship type and direction. Never collapse After/Before/Wants/Requires/BindsTo/PartOf/Triggers into a generic dependency edge.
5. **Configuration safety.** Resolve effective configuration/layering first. Prefer minimal drop-ins. Validate syntax/provider loadability, back up touched state, invoke daemon reload only when required, then verify.
6. **Lifecycle safety.** Use native start/stop/restart/reload operations with explicit expected transitions, timeouts and protection checks. No generic process kill fallback.
7. **Safe testing.** Use disposable test units, user-manager fixtures, transient units or isolated provider fakes. Never stop essential real workstation services to prove functionality.


## Global acceptance gate

Complete only when:
- repository-first discovery and ownership mapping were performed;
- service identity is provider/scope-backed and never reduced to PID;
- system and user service-manager scopes remain distinct;
- loaded/enabled/running/healthy/readiness concepts remain distinct;
- native unit types and activation mechanisms retain their semantics;
- dependency relationship types and ordering are not flattened;
- service lifecycle routes through the service provider, not generic process killing;
- configuration provenance and precedence are inspectable;
- managed systemd configuration prefers minimal drop-ins where appropriate;
- daemon-reload is used only when required by a validated unit configuration change;
- health is evidence-backed rather than inferred from active state alone;
- protection covers critical/operator/display/maintenance/control-plane dependencies where evidence exists;
- secrets are excluded/redacted from general service evidence;
- mutations are planned, authorized, revalidated and post-verified;
- provider loss/permission denial/stale state produce explicit UNKNOWN/unsupported outcomes;
- Panel/CLI consume typed Phase 31 APIs;
- failure tests use disposable service fixtures;
- conventional native service recovery remains possible without Phase 31;
- final reporting distinguishes verified provider facts from UNKNOWN/deferred behavior.


## Required final report for Phase 31.30

Return:
1. **Discovery & ownership** — existing service/systemd code and what was reused, migrated or left with another owner.
2. **Provider evidence** — manager scope, exact ServiceRef/unit identity, native states and provenance.
3. **Implementation** — exact files changed/created/refactored and common/provider split.
4. **Dependencies & configuration** — relation types, effective-config provenance, drop-ins and daemon-reload requirements.
5. **Lifecycle & protection** — exact plan, authorization, revalidation, affected services/operator paths and provider-native action.
6. **Health & verification** — active/readiness/liveness/health evidence and postconditions.
7. **Security & privacy** — privilege and service-environment/secret handling.
8. **Tests** — disposable unit/provider/failure tests and exact results.
9. **Performance** — inventory/query/health overhead where relevant.
10. **Remaining UNKNOWNs** — unsupported/unverified provider behavior only.

Never report `active`, `enabled`, a successful `systemctl` invocation, a process PID or a log message alone as proof that the intended service outcome is healthy and verified.
