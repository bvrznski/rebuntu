# Phase 32.18 — Storage I/O Integration

## Mission

Link storage resources to phase 30 i/o evidence without duplicating throughput/allocation policy.

## Non-negotiable architecture and invariants

The project is always **Rebuntu**. Begin with repository-first discovery and obey applicable AGENTS.md/tree rules. Search for existing device, mount, filesystem, fstab, encryption, RAID, migration and storage-health implementations before adding code. Reuse, refactor and migrate first. Apply **aggregational morphing** rather than building a parallel storage framework.

Preserve the actual layered topology. A common path is:

```text
physical device -> partition / RAID -> device-mapper / LUKS
                -> filesystem -> mount -> path/data
```

but layers may be omitted, repeated or composed differently. Represent observed typed relationships rather than forcing the diagram.

Mandatory distinctions:

```text
DEVICE != PARTITION
PARTITION != FILESYSTEM
FILESYSTEM != MOUNT
MOUNTPOINT != FILESYSTEM IDENTITY
DEVICE NODE != DURABLE DEVICE IDENTITY
MOUNTED != HEALTHY
FREE SPACE != DEVICE CAPACITY
SNAPSHOT != BACKUP
FILESYSTEM RESIZE != PARTITION RESIZE
ENCRYPTED VOLUME != SECRET KEY
```

Native Linux storage providers remain authoritative: kernel/sysfs/udev, util-linux/lsblk/blkid/mount, filesystem-native tools, device-mapper/LVM, cryptsetup, mdadm and systemd where present. Phase 32 does not implement a filesystem, RAID engine, encryption scheme, volume manager or backup engine.

Never hard-code `/dev/sdX`, `/dev/nvmeXnY`, `/dev/dm-X` or enumeration order as durable identity. Use stable provider-backed identifiers plus current topology evidence. Device nodes are locators.

Preserve ownership boundaries: Phase 29 owns process/workload lifecycle; Phase 30 I/O resource pressure/allocation; Phase 31 services; Phase 32 storage topology/filesystem/mount semantics; Phase 36 generic configuration transactions; Phase 37 secrets; Phase 39 temporal evidence; Phase 42 structural graph; Phase 45 shared control-plane contracts. Integrate only with APIs actually present.

**No destructive cleanup.** An unmounted disk, old-looking partition, duplicate-looking filesystem, stale mount directory, RAID member, snapshot or unknown volume is never presumed disposable.

Root, boot, EFI and active `/home` are high-value protected chains. `/home` may share a filesystem/device with unrelated data; never assume a drive is dedicated to `/home`.

Every consequential mutation follows:

```text
observe complete relevant stack
 -> resolve stable refs
 -> dependency + in-use + protection analysis
 -> exact plan
 -> validate prerequisites
 -> prepare real recovery evidence where applicable
 -> explicit authorization
 -> immediate identity/topology revalidation
 -> provider-native apply
 -> verify each affected layer and final postcondition
 -> record
```

Hotplug/topology change invalidates stale plans. UNKNOWN is not PASS.

Never format/repartition/shrink/overwrite signatures/remove RAID metadata/close an in-use encrypted mapping/force-unmount/run blind repair/delete migration source data/alter boot-critical storage as generic repair.

Keys, passphrases and keyfile contents never enter general logs, fingerprints, Panel output, audit or model context. Phase 37 owns secret custody.

A broken Phase 32 must leave conventional Bash/TTY and native Linux storage recovery usable.


## Phase-specific implementation requirements

Implement this phase around the following exact focus:

**Link storage resources to phase 30 i/o evidence without duplicating throughput/allocation policy.**

Inspect existing Rebuntu structures first and identify the canonical owner/provider boundaries affected by this focus. Implement the smallest coherent common abstraction plus provider adapters needed by the actual repository. Add deterministic tests for identity/provenance, stale-target behavior and provider failure where relevant. Any mutation path introduced by this phase must use stable refs, plan-first semantics, immediate revalidation and postcondition verification. Do not broaden the phase into unrelated storage management.

## Required implementation method

### 1. Repository-first discovery
Produce an ownership/reuse/migration map for all relevant existing storage code before implementation.

### 2. Structured provider evidence
Prefer structured native/provider interfaces over decorative human output. Preserve identifiers, raw state, provenance, timestamps and permission/unsupported errors.

### 3. Whole-stack resolution
Before mutation resolve the relevant lower and upper layers plus known consumers. Never execute a consequential operation from one remembered `/dev/*` string.

### 4. Stable target binding
Plans bind to typed stable refs and a current topology fingerprint. Revalidate immediately before mutation; abort/reconcile on mismatch.

### 5. Configuration safety
Persistent mount/encryption-related configuration uses minimal edits, syntax/provider validation, exact backups and effective-state verification.

### 6. Destructive safety
Destructive operations receive explicit risk classes, stronger authorization and recovery prerequisites. There is no convenience bypass.

### 7. Disposable validation
Use sparse files, loop devices, temporary mount namespaces, disposable mappings/filesystems/RAID fixtures and fake providers. Never destructively test on real user storage.

## Global acceptance gate

Complete only when:
- existing storage ownership was audited and reused/migrated before additions;
- device/partition/mapping/RAID/encryption/filesystem/mount identities remain distinct;
- durable identity never depends solely on `/dev/*` enumeration;
- relevant full-stack topology and consumers are inspected before mutation;
- root/boot/EFI/home/in-use protections are enforced;
- stale plans fail after topology/hotplug change;
- size/free/available/allocation semantics remain distinct;
- current mount state and persistent desired configuration remain distinct;
- fstab/provider edits are minimal, validated and backed up;
- filesystem and partition resize remain separate ordered operations;
- snapshot is never represented as equivalent to backup;
- encrypted storage contains only secret references, never credential material;
- destructive actions require exact stable targets and explicit strong authorization;
- migration verifies destination before cutover and never automatically deletes the source;
- rollback is claimed only where real recovery capability exists;
- CLI/Panel consume typed Phase 32 contracts;
- failure/destructive tests use disposable storage only;
- native manual recovery remains possible without Phase 32;
- unsupported/unverified behavior remains explicit UNKNOWN/deferred.

## Required final report

Return:
1. **Discovery & ownership** — existing code/providers and reuse/migration decisions.
2. **Topology & identity** — exact typed refs, relationships and stable identity evidence.
3. **Implementation** — exact files changed/created/refactored.
4. **Safety & protection** — consumers, boot/home protection, destructive classification and authorization.
5. **Configuration / recovery** — backups, validation and actual rollback/recovery capability.
6. **Verification** — provider state and postconditions after any mutation.
7. **Tests** — disposable fixtures/failure/race cases and exact results.
8. **Remaining UNKNOWNs** — unsupported or unverified behavior only.

Never report a device node, successful command invocation, snapshot existence, mount state or copied byte count alone as proof that a destructive or migration outcome is safe and verified.
