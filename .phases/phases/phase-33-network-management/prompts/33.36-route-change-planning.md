# Phase 33.36 — Route Change Planning

## Mission

Build route/policy-rule plans with reachability impact, exact table/rule identity and rollback preparation.

## Non-negotiable architecture and invariants

The project is always **Rebuntu**. Start with repository-first discovery and obey applicable AGENTS.md/tree rules. Search for existing networking, NetworkManager, route, DNS, firewall, socket and connectivity code before adding anything. Reuse/refactor/migrate first and apply **aggregational morphing**.

Mandatory distinctions:

```text
INTERFACE != INTERFACE NAME
ADMIN UP != CARRIER UP
LINK UP != IP CONFIGURED
IP CONFIGURED != ROUTABLE
DEFAULT ROUTE PRESENT != INTERNET CONNECTIVITY
DNS CONFIGURED != DNS WORKING
REACHABLE != HEALTHY
LISTENING != EXPOSED
FIREWALL RULE != PROVEN REACHABILITY
CONNECTION PROFILE != ACTIVE CONNECTION
NETWORK CONFIGURATION != NETWORK RESOURCE POLICY
```

NetworkManager is an expected current provider when discovered, not the architecture. Kernel/iproute2, resolver mechanisms, UFW/nftables/netfilter and other native providers remain authoritative.

Preserve ownership boundaries:

```text
Phase 29 -> process/workload/socket ownership context
Phase 30 -> network throughput/pressure/resource policy
Phase 31 -> network-related service lifecycle
Phase 33 -> network identity/configuration/connectivity/exposure
Phase 36 -> generic configuration transactions
Phase 37 -> credentials/secrets
Phase 38 -> actor/authorization context
Phase 39 -> temporal evidence
Phase 42 -> structural relationships
Phase 45 -> unified control-plane contracts
```

Interface names such as `eth0`, `enp...`, `wlan...` are current locators, not guaranteed durable identities. Resolve provider/stable identity and current namespace before consequential actions.

Exposure is evidence composed from at least relevant bind/listener state, namespace/address scope, routing/reachability context and firewall policy. Never report a socket as Internet-exposed merely because it listens on `0.0.0.0` or `::`.

Connectivity is layered evidence. Carrier, local address, gateway reachability, DNS resolution and endpoint/application connectivity must remain separately inspectable.

**Never disable the firewall as a generic diagnostic step.** Never flush nftables/iptables, delete all routes, reset NetworkManager profiles or drop active interfaces as broad repair.

The current operator access path is protected. Before address/route/DNS/firewall/link mutations, determine whether the target participates in the active graphical/local/SSH/remote maintenance path. Missing evidence is risk/UNKNOWN, not PASS.

All consequential changes follow:

```text
observe -> resolve stable refs + namespace/provider
 -> determine current access/dependency/exposure impact
 -> exact plan + recovery/timed rollback where appropriate
 -> validate -> authorize
 -> immediate state/identity revalidation
 -> provider-native apply
 -> verify link/address/route/DNS/connectivity/exposure postconditions
 -> commit/cancel rollback guard -> record
```

Remote-stranding changes require staged/timed rollback when technically available. A successful `nmcli`, `ip`, `resolvectl` or firewall command is not proof of connectivity.

Secret values for Wi-Fi, VPN and authentication never enter logs, Panel DTOs, audit, fingerprints or model context. Phase 37 owns secret custody.

A broken Phase 33 must leave ordinary Bash/TTY and native Linux networking tools usable for recovery.


## Phase-specific implementation requirements

Implement this phase around the following exact focus:

**Build route/policy-rule plans with reachability impact, exact table/rule identity and rollback preparation.**

Before coding, identify every existing Rebuntu implementation that overlaps this focus and decide whether to reuse, refactor, migrate or leave it under another phase owner. Keep common contracts provider-neutral and provider adapters native.

For every observation introduced here, preserve exact provider/namespace/reference provenance and freshness. For every mutation introduced here, define typed preconditions, exact stable targets, access-path impact, authorization requirements, immediate revalidation and deterministic postconditions. If a requested fact cannot be verified, return UNKNOWN rather than guessing.

Add tests specific to this focus, including stale identity/provider loss and access-protection cases where relevant. Use isolated network fixtures for mutation/failure testing.

## Required implementation method

1. **Repository-first discovery.** Produce an ownership/reuse/migration map for network code, providers and configuration.
2. **Structured evidence.** Prefer netlink/provider structured state over parsing decorative output. Preserve namespace, provider, timestamps and provenance.
3. **Stable targeting.** Resolve interface/connection/rule/route identity and revalidate immediately before mutation.
4. **Access protection.** Explicitly identify current access-path dependencies and define rollback before risky changes.
5. **Provider-native mutation.** Use NetworkManager/iproute2/resolver/firewall provider semantics; never create a shadow network stack.
6. **Postcondition verification.** Verify each relevant layer rather than equating command success with working connectivity.
7. **Disposable testing.** Use network namespaces, veth, dummy interfaces, fake providers and isolated rule tables where safe. Never intentionally sever the real workstation connection for tests.


## Global acceptance gate

Complete only when:
- existing network code was discovered and ownership reconciled;
- interface identity is not reduced to interface name;
- admin/link/address/route/DNS/connectivity states remain distinct;
- IPv4/IPv6 and namespace semantics are preserved;
- listeners and exposure remain distinct;
- exposure claims include sufficient deterministic network/firewall context;
- current operator/SSH access paths are protected;
- firewall disable/flush is never generic troubleshooting;
- risky network changes have explicit recovery/timed rollback where supported;
- provider configuration and current runtime state remain distinguishable;
- NetworkManager/UFW/systemd/etc. are providers rather than architecture assumptions;
- mutations use exact plans, authorization, revalidation and postcondition verification;
- credentials are represented only by secret references;
- Phase 30 retains resource arbitration and Phase 31 service lifecycle;
- CLI/Panel consume typed Phase 33 APIs;
- failure tests use isolated namespaces/interfaces/providers;
- native recovery remains possible without Phase 33;
- unsupported/unverified behavior is explicit UNKNOWN/deferred.
