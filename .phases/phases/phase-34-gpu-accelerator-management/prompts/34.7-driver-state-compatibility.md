# Phase 34.7 — Driver State & Compatibility

## Mission

Observe driver/provider state and compatibility facts while phase 24 remains owner of driver lifecycle.

## Non-negotiable architecture and invariants

The project is always **Rebuntu**. Begin with repository-first discovery and obey applicable AGENTS.md/tree rules. Search for all existing NVIDIA/CUDA/GPU/VRAM/topology/power/thermal/placement code before adding anything. Reuse, refactor and migrate first. Apply **aggregational morphing**.

NVIDIA is an expected current provider when discovered, not the architecture. The common model must remain capable of representing other accelerators/providers.

Mandatory distinctions:

```text
ACCELERATOR IDENTITY != GPU INDEX
PCI ADDRESS != NVIDIA ORDINAL
NVIDIA ORDINAL != CUDA ORDINAL
CUDA ORDINAL != CONTAINER ORDINAL

VRAM CAPACITY != VRAM PRESSURE
UTILIZATION != PRESSURE
TEMPERATURE != THROTTLING
POWER DRAW != POWER LIMIT
CLOCK STATE != CLOCK POLICY
P-STATE != HEALTH
DISPLAY ROLE != COMPUTE ROLE

DRIVER EVENT != ROOT CAUSE
XID != AUTOMATIC HARDWARE FAILURE
ECC UNSUPPORTED != ECC CLEAN

OBSERVATION != AUTHORIZATION
CAPABILITY != PERMISSION
SUCCESSFUL COMMAND != VERIFIED EFFECTIVE STATE
```

Never hard-code the workstation's number of GPUs, model, PCI addresses or provider indices. All topology and mappings are runtime-discovered.

Stable accelerator identity must survive provider ordinal reorder where the underlying device identity is unchanged. Every action binds to a stable AcceleratorRef and re-resolves the current provider locator immediately before execution.

Preserve ownership boundaries:

```text
Phase 24 -> kernel/driver/package/reboot evolution
Phase 29 -> process/workload identity + lifecycle
Phase 30 -> resource capacity/pressure/demand/reservation/allocation
Phase 31 -> service lifecycle
Phase 34 -> accelerator hardware/runtime/topology/device controls
Phase 39 -> temporal evidence
Phase 42 -> structural relationships
Phase 44 -> adaptive cross-subsystem policy
Phase 45 -> unified control-plane contracts
```

Display-critical accelerators are protected. Before reset, power, clock, visibility or placement mutations, resolve whether the device participates in the current graphical session/display stack. UNKNOWN dependency evidence is risk, not PASS.

No implicit overclocking, undervolting, clock locking, reset, persistence-mode mutation, visibility rewrite or power-limit change. Such operations require an exact typed plan, supported provider capability and explicit authorization appropriate to risk.

Do not infer hardware failure from one Xid, low PCIe speed at idle, a P8 state, high utilization, one thermal sample or a provider error string. Preserve raw evidence, temporal context and competing explanations.

All consequential operations follow:

```text
observe -> resolve stable AcceleratorRef
 -> current provider locator + topology + workload/display dependencies
 -> capability + impact + protection analysis
 -> exact plan -> validate -> authorize
 -> immediate identity/topology revalidation
 -> provider-native apply
 -> re-read effective state + postconditions
 -> record
```

Provider loss/reload/device reorder invalidates stale plans. UNKNOWN is not PASS.

Secret material is not expected in ordinary accelerator state, but container/environment/config evidence can contain sensitive values; redact through Phase 37 boundaries where applicable.

A broken Phase 34 must not prevent conventional Bash/TTY, native driver tools or Phase 24 driver recovery.


## Phase-specific implementation requirements

Implement this phase around the following exact focus:

**Observe driver/provider state and compatibility facts while phase 24 remains owner of driver lifecycle.**

Before coding, locate every existing Rebuntu implementation that overlaps this concern. Record whether each piece is reused, refactored, migrated into Phase 34, adapted through another phase, or intentionally retained under its current owner. Do not create duplicate NVIDIA/CUDA/device-control helpers.

Use stable AcceleratorRefs throughout common code. Provider-local PCI/index/CUDA/container locators must be explicit mappings with provenance and freshness. Any mutation introduced here must define its provider capability, supported bounds, exact stable target, current workload/display impact, authorization class, immediate revalidation and postcondition verification.

Add deterministic tests for this focus. Where disruptive/error states are needed, simulate them with provider fixtures rather than using the real workstation as a destructive GPU test bench.

## Required implementation method

1. **Repository-first discovery.** Produce an ownership/reuse/migration map for GPU, CUDA, NVIDIA, topology, power, thermal and placement code.
2. **Provider-neutral core.** Keep common refs/snapshots/plans vendor-neutral; isolate NVIDIA-specific fields and commands in provider adapters.
3. **Stable identity.** Persist semantic refs, not provider ordinals. Re-resolve current PCI/provider/CUDA/container mappings before action.
4. **Evidence quality.** Every observation carries exact device ref, provider, timestamp/window, units and provenance.
5. **Protection.** Determine display/workload dependencies before disruptive controls. Never use broad reset/kill as generic recovery.
6. **Native control + verification.** Use provider-supported controls within discovered limits and re-read effective state afterward.
7. **Safe testing.** Prefer fake providers and deterministic fixtures for reset/error/reorder/thermal/control paths. Do not intentionally overheat, reset display GPUs or destabilize real workloads to test the subsystem.


## Global acceptance gate

Complete only when:
- existing accelerator ownership was audited and reconciled;
- no durable semantic identity relies on GPU/provider/CUDA/container ordinal alone;
- provider ordinal translation is explicit and tested;
- topology/capabilities are discovered at runtime;
- NVIDIA-specific behavior remains behind provider boundaries;
- VRAM/utilization/pressure, temperature/throttling and draw/limit remain distinct;
- display-critical devices and current workloads are protected;
- Xid/ECC/driver evidence is not overinterpreted;
- reset/power/clock/visibility controls are explicit planned high-risk actions where appropriate;
- no implicit overclocking or guessed tuning exists;
- stale plans fail after provider/device reorder or topology change;
- Phase 24 owns driver lifecycle and Phase 30 owns resource arbitration;
- mutations use stable refs, authorization, revalidation and effective-state verification;
- CLI/Panel consume typed Phase 34 contracts;
- failure/control tests do not destabilize real GPUs;
- conventional native recovery remains possible without Phase 34;
- unsupported/unverified behavior remains explicit UNKNOWN/deferred.


## Required final report for Phase 34.7

Return:
1. **Discovery & ownership** — existing accelerator code/providers reused, migrated or retained elsewhere.
2. **Identity & mappings** — stable AcceleratorRefs and current PCI/provider/CUDA/container locators.
3. **Evidence** — exact units, timestamps/windows, provider provenance and freshness.
4. **Implementation** — exact files changed/created/refactored.
5. **Dependencies & protection** — workloads, display role, topology and affected services/resources.
6. **Plan & authorization** — exact capability, bounds, target, risk and immediate revalidation.
7. **Verification** — effective provider/device state after any mutation.
8. **Tests** — fake-provider/reorder/error/failure cases and exact results.
9. **Remaining UNKNOWNs** — unsupported or unverified behavior only.

Never report a GPU ordinal, successful `nvidia-smi` invocation, Xid line, P-state, utilization value, PCIe link state or temperature sample alone as proof of stable identity, hardware failure, safe control or successful final outcome.
