# Phase 35.7 — APT Source Configuration Provenance

## Mission

Track repository configuration source files and effective entries without flattening ownership or precedence.

## Non-negotiable architecture and invariants

The project is always **Rebuntu**. Begin with repository-first discovery and obey applicable AGENTS.md/tree rules. Search for all existing APT/dpkg/Flatpak/Snap/software inventory/update/install/remove helpers before adding code. Reuse, refactor and migrate first. Apply **aggregational morphing**.

Mandatory distinctions:

```text
PACKAGE != APPLICATION
PACKAGE != EXECUTABLE
APPLICATION != DESKTOP LAUNCHER
INSTALLED VERSION != CANDIDATE VERSION
PACKAGE PROVIDER != SOFTWARE ORIGIN
REMOVE != PURGE
CACHE != INSTALLED SOFTWARE
DUPLICATE-LOOKING != SAFE TO DELETE
TRANSACTION SUCCESS != VERIFIED FINAL STATE
```

APT/dpkg is the expected primary host package provider on the current Debian-family system when discovered, but it is a provider, not the architecture. Flatpak, Snap and standalone software retain their own semantics.

Native package managers remain authoritative for dependency solving, package database state, signature/trust verification and transaction mechanics. Phase 35 must not implement a second Debian dependency solver or edit package databases directly.

Preserve ownership boundaries:

```text
Phase 24 -> kernel/driver/boot/release evolution
Phase 28 -> project/runtime/development dependencies
Phase 29 -> running workload/process identity
Phase 31 -> service lifecycle
Phase 35 -> installed host software/package/repository lifecycle
Phase 36 -> generic configuration transactions
Phase 37 -> secrets/credentials
Phase 39 -> temporal evidence
Phase 45 -> unified control-plane contracts
```

Never silently weaken repository signatures, trust policy or TLS verification to make an installation succeed.

No implicit `autoremove`, purge, package-cache deletion, orphan deletion or cross-provider duplicate removal. Native tools may identify candidates, but candidate status is evidence, not authorization.

Kernel, bootloader, GPU driver and release-transition packages require Phase 24 protections rather than ordinary Phase 35 treatment.

Every consequential operation follows:

```text
observe provider state
 -> resolve exact typed package/software/repository refs
 -> native simulation/resolution
 -> dependency + reverse-dependency + workload/service/platform impact
 -> exact plan
 -> validate trust/network/disk/locks
 -> authorize
 -> immediate provider-state revalidation
 -> native transaction
 -> verify package database + versions + required postconditions
 -> record
```

Never bypass package-manager locks or repair native databases through ad-hoc deletion. Interrupted package state is diagnosed and recovered through supported provider mechanisms.

Conffile changes are operator data/configuration. Do not blindly overwrite locally modified conffiles. Preserve native conflict semantics and integrate Phase 36 where appropriate.

Repository credentials/tokens and other secrets must be represented through Phase 37 SecretRefs and structurally excluded from logs, Panel output, fingerprints, semantic context and audit.

A broken Phase 35 must not prevent conventional Bash/TTY and native apt/dpkg/flatpak/snap recovery.


## Phase-specific implementation requirements

Implement this phase around the following exact focus:

**Track repository configuration source files and effective entries without flattening ownership or precedence.**

Before implementation, locate every overlapping Rebuntu structure and document whether it will be reused, refactored, migrated into Phase 35, adapted through another owner, or intentionally retained elsewhere. Do not introduce a second package inventory, dependency solver, repository registry or software lifecycle path.

Preserve native provider identity and evidence in common abstractions. Any mutation introduced here must start from an exact typed target and current provider snapshot, consume native simulation/resolution where applicable, expose dependency/workload/service/platform impact, require appropriate authorization, revalidate locks/state immediately before execution and verify final provider state afterward.

Add deterministic tests specific to this focus. Simulate broken repositories, interrupted transactions, locks, conffile divergence and duplicate providers with isolated fixtures rather than damaging the real host.

## Required implementation method

1. **Repository-first discovery.** Produce an ownership/reuse/migration map for all software/package-management code.
2. **Provider-native evidence.** Query structured/native package state where possible and preserve provider-specific version/architecture/scope/origin semantics.
3. **Native resolution.** Use provider simulation/solver output for dependency plans. Do not recreate the solver in Rebuntu.
4. **Exact targeting.** Plans bind to typed provider/package/repository refs and observed-state fingerprints, then revalidate before mutation.
5. **Impact analysis.** Inspect reverse dependencies, running consumers, services, platform boundaries, conffiles and repository trust before change.
6. **Transaction verification.** Re-query provider/package state and required postconditions after mutation. Exit code alone is insufficient.
7. **Safe testing.** Prefer provider fakes, temporary roots/containers and disposable package fixtures. Never intentionally corrupt the workstation's real dpkg database.


## Global acceptance gate

Complete only when:
- existing package/software code was audited and ownership reconciled;
- package/application/executable/provider identities remain distinct;
- APT/dpkg dependency solving remains native;
- installed/candidate/available versions remain distinct;
- repository source/trust provenance is inspectable;
- signature/trust verification is never weakened automatically;
- remove/purge/autoremove/cache cleanup remain distinct explicit operations;
- no automatic duplicate-software deletion exists;
- conffile conflicts preserve administrator changes and native semantics;
- package-manager locking/concurrency is respected;
- kernel/driver/release package changes route through Phase 24 protections;
- running workload and service impact is explicit;
- transactions are planned, authorized, revalidated and post-verified;
- repository credentials are redacted/SecretRef-based;
- CLI/Panel consume typed Phase 35 APIs;
- recovery uses supported provider mechanisms;
- failure tests avoid damaging the real host package database;
- unsupported/unverified behavior remains explicit UNKNOWN/deferred.


## Required final report for Phase 35.7

Return:
1. **Discovery & ownership** — existing software/package code reused, migrated or retained elsewhere.
2. **Provider identity/evidence** — exact package/software/repository refs, versions, architecture/scope/origin and provenance.
3. **Native resolution** — solver/simulation evidence and dependency/reverse-dependency impact.
4. **Implementation** — exact files changed/created/refactored.
5. **Safety & authorization** — purge/autoremove/platform/conffile/trust/lock implications.
6. **Workload/service impact** — active consumers and explicit Phase 29/31 coordination.
7. **Verification** — provider/package database state and exact postconditions.
8. **Tests** — isolated provider/transaction/failure cases and results.
9. **Remaining UNKNOWNs** — unsupported or unverified behavior only.

Never report a package-manager exit code, candidate version, autoremove classification, duplicate-looking application, repository entry or downloaded package alone as proof that a software change is safe, authorized or fully verified.
