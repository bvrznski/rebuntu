# Phase 36.10 — Textual vs Semantic Configuration Model

## Mission

Distinguish textual file changes from semantic configuration changes and preserve both where meaningful.

## Non-negotiable architecture and invariants

The project is always **Rebuntu**. Begin with repository-first discovery and obey applicable AGENTS.md/tree rules. Search for existing configuration loaders, writers, serializers, validators, backup/rollback helpers, ownership registries and domain-specific config code before adding anything. Reuse, refactor and migrate first. Apply **aggregational morphing**.

Phase 36 owns **generic configuration mechanics**: identity, source/effective/desired distinctions, layering, provenance, diff, ChangeSets, transactions, bounded history and generic recovery mechanics. Domain phases continue to own the **meaning**, validation requirements and activation semantics of their configuration.

Mandatory distinctions:

```text
SOURCE CONFIG != EFFECTIVE CONFIG
OBSERVED CONFIG != DESIRED CONFIG
DEFAULT != DECLARED != INHERITED != OVERRIDDEN
FILESYSTEM OWNER != CONFIGURATION OWNER
TEXTUAL DIFF != SEMANTIC DIFF
FILE CONTENT != RUNTIME STATE
BACKUP != ROLLBACK
SNAPSHOT != GUARANTEED RECOVERY
SECRET REFERENCE != SECRET VALUE
WRITE SUCCESS != ACTIVATED STATE
ACTIVATED STATE != VERIFIED DOMAIN OUTCOME
```

Do not invent a universal configuration format. Native formats and providers remain authoritative: INI-like files, TOML, YAML, JSON, shell fragments, systemd drop-ins, GNOME settings, fstab, NetworkManager profiles and other formats retain their native semantics through adapters/owning phases.

Preserve comments, ordering, unknown keys, includes, fragments and unmanaged content where technically possible. Never normalize/rewrite an entire file merely because a parser can serialize it.

Configuration identity is not just a filesystem path. It includes semantic owner/domain, provider, scope and native identity. Symlinks/generated files/drop-ins/includes require explicit provenance.

All consequential changes follow:

```text
observe sources + effective state
 -> resolve ConfigRef + owner/provider/scope
 -> fingerprint exact base
 -> compute textual + semantic diff
 -> validate with owning domain/provider
 -> impact + activation + recovery analysis
 -> minimal ChangeSet
 -> backup exact touched material where applicable
 -> authorize
 -> immediate base/concurrency revalidation
 -> atomic/provider-native apply
 -> activate through owning domain if required
 -> re-read effective state + verify domain postconditions
 -> record
```

Concurrent/manual edits invalidate stale plans. Never silently overwrite them. Offer adopt/rebase/replan/reconcile behavior.

Generic Phase 36 must not hide `systemctl restart`, network reconnects, mount operations, package transactions, GPU controls or other domain mutations inside file writes. Activation belongs to owning capabilities and must be visible in the plan.

Secret values must be removed **before serialization/persistence**, not cosmetically hidden at display time. Phase 37 owns secret custody. Config diffs/history/snapshots/exports/Panel/model context contain SecretRefs or redacted structural placeholders only.

Do not broadly chmod/chown configuration trees, delete 'stale' files, erase unknown directives, reset configs to defaults or overwrite vendor/admin changes as generic repair.

A broken Phase 36 must not prevent conventional Bash/TTY/manual editor/provider-native recovery.


## Phase-specific implementation requirements

Implement this phase around the following exact focus:

**Distinguish textual file changes from semantic configuration changes and preserve both where meaningful.**

Before implementation, locate all overlapping Rebuntu configuration mechanisms and document whether each is reused, refactored, migrated into Phase 36, adapted through an owning domain, or intentionally retained elsewhere. Do not create a second configuration registry, writer, backup system or drift engine beside canonical structures.

Every configuration fact introduced here must retain owner/provider/scope/source provenance. Every ChangeSet must identify its exact base state and smallest intended semantic change. Every mutation path must validate through the owning provider/domain, detect concurrent edits immediately before apply, preserve unmanaged material, apply atomically/provider-natively where possible and verify both effective configuration and any explicitly activated domain outcome.

Add deterministic tests specific to this focus, including malformed input, unknown directives, concurrent modification, provider rejection and secret-redaction cases where relevant.

## Required implementation method

1. **Repository-first discovery.** Produce an ownership/reuse/migration map for generic and domain-specific configuration code.
2. **Provider/domain split.** Keep generic transaction/provenance/diff machinery in Phase 36; semantic validation and activation remain with owning domains.
3. **Loss-minimizing edits.** Prefer AST/CST/provider-native patching or targeted textual edits that preserve unmanaged material.
4. **Optimistic concurrency.** Bind ChangeSets to base fingerprints/versions and fail safely on concurrent edits.
5. **Two-level verification.** Verify both stored/effective configuration and, when activation occurs, the owning domain's actual postcondition.
6. **Secret-safe by construction.** Redact/extract SecretRefs before any generic serialization, persistence, indexing or semantic-model handoff.
7. **Disposable tests.** Use temporary configuration trees, fake providers and isolated domain fixtures. Never intentionally corrupt live system configuration to test rollback.


## Global acceptance gate

Complete only when:
- existing configuration code was audited and ownership reconciled;
- source/effective/desired/default/inherited/override states remain distinct;
- filesystem ownership and configuration ownership remain distinct;
- textual and semantic diffs are both available where meaningful;
- native formats/provider semantics remain authoritative;
- unknown/unmanaged content is preserved where technically possible;
- ChangeSets are minimal and bound to exact base versions/fingerprints;
- concurrent edits abort or reconcile instead of being overwritten;
- backup, snapshot and rollback remain distinct concepts;
- activation is explicit and delegated to owning domains;
- secrets are structurally excluded before persistence/diff/history/export/model context;
- drift does not trigger blind automatic overwrite;
- mutations are validated, authorized, revalidated, atomically/provider-natively applied and post-verified;
- CLI/Panel consume typed Phase 36 APIs;
- failure tests use disposable configuration fixtures;
- native manual recovery remains available without Phase 36;
- unsupported/unverified behavior remains explicit UNKNOWN/deferred.


## Required final report for Phase 36.10

Return:
1. **Discovery & ownership** — existing config code reused, migrated, adapted or retained under another owner.
2. **Identity & provenance** — ConfigRefs, scopes, sources, layers and effective-value origins.
3. **Diff / ChangeSet** — textual and semantic changes, exact base fingerprint and minimal patch.
4. **Implementation** — exact files changed/created/refactored.
5. **Validation & impact** — provider/domain validation, dependencies, activation requirements and blast radius.
6. **Concurrency & recovery** — revalidation, backups, rollback capability and conflict behavior.
7. **Secrets/privacy** — structural redaction and SecretRef handling.
8. **Verification** — effective configuration and activated domain postconditions where applicable.
9. **Tests** — disposable transaction/failure/concurrency cases and exact results.
10. **Remaining UNKNOWNs** — unsupported or unverified behavior only.

Never report a successful file write, parser round-trip, backup creation, reload command or textual equality alone as proof that the intended effective configuration and domain behavior are safely applied and verified.
