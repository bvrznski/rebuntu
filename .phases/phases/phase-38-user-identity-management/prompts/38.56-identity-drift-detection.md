# Phase 38.56 — Identity Drift Detection

## Mission

Detect account/group/privilege/session configuration drift without silently reverting manual changes.

## Non-negotiable architecture and invariants

The project is always **Rebuntu**. Begin with repository-first discovery and obey applicable AGENTS.md/tree rules. Search for existing user/group/session/sudo/polkit/PAM/NSS/account-management code before adding anything. Reuse, refactor and migrate first. Apply **aggregational morphing**.

Phase 38 does not replace NSS, PAM, systemd-logind, sudo, polkit, passwd/group databases or external identity providers. Native identity/authentication/authorization providers remain authoritative.

Mandatory distinctions:

```text
USERNAME != DURABLE IDENTITY
ACCOUNT != SESSION
SESSION != SHELL
TERMINAL != SHELL
LOGIN SHELL != GRAPHICAL TERMINAL'S INTERACTIVE SHELL
USER IDENTITY != PROCESS EFFECTIVE UID
AUTHENTICATION != AUTHORIZATION
GROUP MEMBERSHIP != CURRENT SESSION AUTHORITY
SUDO != POLKIT
ACCOUNT LOCK != ACCOUNT DELETE
ACCOUNT DELETE != HOME DELETE
FILESYSTEM OWNER != ACCOUNT SEMANTIC OWNER
```

Never ingest, persist, display, index or pass `/etc/shadow` password hashes or authentication secret material into ordinary Phase 38 evidence. Phase 37 owns credential custody.

Preserve the Rebuntu shell architecture:

```text
human graphical terminal -> Fish
console -> Bash child -> exit -> Fish
scripts / coding agents / system automation -> Bash/POSIX as appropriate
configured account login shell -> conservative/native boundary
```

Do not `chsh` the user's login shell to Fish as part of Phase 38 normalization.

The current operator identity, graphical session and administrative recovery path are protected. Never casually lock/delete/demote the current operator, remove their required admin group, invalidate their sudo/polkit access, terminate their active session or alter UID/GID underneath active ownership without explicit high-risk planning.

UID/GID mutation is not a simple metadata edit. It may affect filesystem ownership, processes, services, ACLs, containers, configs and external references. Never use broad `chown -R` as generic repair.

Account deletion never implies home-directory deletion. Data disposition is a separate explicit storage action with Phase 32 integration.

All consequential operations follow:

```text
observe provider identity/account/group/session/privilege state
 -> resolve stable refs
 -> collision + dependency + active-session + operator-access analysis
 -> exact plan
 -> validate provider/config/recovery prerequisites
 -> authorize
 -> immediate identity/session/provider revalidation
 -> provider-native apply
 -> verify account/group/session/privilege + affected-domain postconditions
 -> record
```

Existing sessions may retain old supplementary groups or credentials after account/group changes. Verification must distinguish persistent configuration from effective current-session state.

UNKNOWN is not PASS. A missing NSS/PAM/provider view or incomplete ownership scan increases risk rather than proving safety.

A broken Phase 38 must preserve conventional TTY/Bash/native account-management and recovery mechanisms.


## Phase-specific implementation requirements

Implement this phase around the following exact focus:

**Detect account/group/privilege/session configuration drift without silently reverting manual changes.**

Before coding, locate all overlapping Rebuntu identity/account/session/privilege implementations and document whether each is reused, refactored, migrated into Phase 38, adapted through another domain owner, or intentionally retained elsewhere. Do not create a shadow user database, authentication engine or privilege system.

Every observation introduced here must preserve provider, scope, stable identity, current mutable names and provenance. Every mutation introduced here must bind to exact typed refs and current provider state, analyze collisions/active sessions/processes/services/filesystem ownership/operator access, require appropriate authorization, immediately revalidate and verify both persistent and effective state afterward.

Add deterministic tests specific to this focus. Use synthetic/test identities and isolated environments only; never exercise destructive account/privilege paths against the real operator.

## Required implementation method

1. **Repository-first discovery.** Produce an ownership/reuse/migration map for identity/account/session/privilege code.
2. **Provider-native identity.** Use NSS/logind/sudo/polkit/PAM/local/external provider semantics rather than treating `/etc/passwd` as the whole identity system.
3. **Stable refs.** Separate mutable names from provider/native/numeric identity and revalidate immediately before mutation.
4. **Impact analysis.** Before account/group/UID/GID/privilege changes inspect sessions, processes, services, filesystems, configuration and recovery access.
5. **Secret boundary.** Never read/store password hashes or credential values in generic identity DTOs, logs or tests.
6. **Two-state verification.** Verify persistent identity configuration and current effective session/privilege state separately.
7. **Disposable testing.** Use containers/user namespaces/fake NSS-like providers/test accounts isolated from the real operator. Never lock/delete/demote the actual user to test safety.


## Global acceptance gate

Complete only when:
- existing identity code was audited and ownership reconciled;
- username and durable identity remain distinct;
- account/session/shell/process identity remain distinct;
- NSS/PAM/logind/sudo/polkit remain native authorities/providers;
- authentication and authorization remain separate;
- no shadow hashes or credential values enter ordinary evidence;
- current operator/session/admin/recovery paths are protected;
- login shell is not changed to Fish as normalization;
- UID/GID collision and ownership impact analysis precedes numeric identity changes;
- account deletion and home/data deletion remain separate;
- broad recursive ownership rewrites are not generic repair;
- persistent group/account state and effective existing-session state are verified separately;
- mutations are planned, authorized, revalidated and provider-verified;
- CLI/Panel consume typed Phase 38 APIs;
- failure tests use disposable identities/environments;
- native TTY/Bash recovery remains possible without Phase 38;
- unsupported/unverified behavior remains explicit UNKNOWN/deferred.


## Required final report for Phase 38.56

Return:
1. **Discovery & ownership** — existing identity code/providers reused, migrated or retained elsewhere.
2. **Identity model** — exact UserRef/GroupRef/AccountRef/SessionRef and mutable-name/numeric mappings.
3. **Provider evidence** — NSS/PAM/logind/sudo/polkit/local/external state and provenance as applicable.
4. **Implementation** — exact files changed/created/refactored.
5. **Impact & protection** — sessions, workloads, services, ownership, current operator and recovery path.
6. **Plan & authorization** — exact target, collision checks, privilege/data implications and revalidation.
7. **Verification** — persistent account/group state versus current effective session/privilege state.
8. **Secrets/privacy** — confirm no password hashes or credential material entered generic evidence.
9. **Tests** — disposable identity/provider/failure cases and exact results.
10. **Remaining UNKNOWNs** — unsupported or unverified behavior only.

Never report a username, successful `usermod`, group-file edit, sudo command or account record alone as proof of durable identity, current effective authorization, safe ownership migration or preserved operator access.
