# Phase 40.30 — Development Environment Search Provider

## Mission

Expose Phase 28 projects, workspaces, runtimes, toolchains, environments, tasks, VCS state, and development context.

## Global invariants

- **Repository-first.** Search for existing implementations, types, APIs, registries, providers, tests and contracts before creating anything.
- Apply **aggregational morphing**: extend/refactor/migrate existing structures rather than building a parallel subsystem.
- Follow the repository's post-migration **C++-first** architectural policy and all applicable `AGENTS.md` files. Runtime, state, concurrency, eventing, provider/control contracts, deterministic validation, IPC and control-plane logic belong in C++ unless the repository explicitly establishes another owner.
- Python is an explicit boundary for semantic/ML providers, experiments, research tooling and justified adapters; it is not a second control plane.
- Phase 40 owns **federated discovery/query/command-intent orchestration**, not the underlying domain state. Domain systems remain authoritative for their own state and mutations.
- Phase 39 remains the temporal/event authority. Phase 40 queries it; it does not create a competing timeline.
- Search results are references/evidence, not authority to mutate.
- Commands are typed intents/capabilities, **never arbitrary shell strings**.
- Consequential mutation follows `observe → plan → validate → authorize → execute → verify → record`.
- Semantic models may annotate, retrieve, rerank, or propose structured candidates, but cannot authorize or execute actions.
- Preserve epistemic classes: `OBSERVED_FACT`, `DETERMINISTIC_DERIVATION`, `SEMANTIC_ANNOTATION`, `HYPOTHESIS`, `RECOMMENDATION`, `UNKNOWN`.
- `UNKNOWN != PASS`; incomplete search != no matching state.
- Never leak Phase 37 secret material into indexes, logs, search results, semantic prompts, history, telemetry, or command previews.
- No destructive cleanup. Misplaced/obsolete code is migrated to the correct owner; retirement happens only after dependency/parity checks and according to repository safety policy.


## Required implementation work

1. **Discover first.** Inspect the repository, applicable `AGENTS.md`, prior phase contracts, existing C++ native runtime, tests, schemas and integration points relevant to this phase.
2. Produce or update an explicit ownership map: what Phase 40 owns, what remains owned by another phase/domain, and what is merely an adapter/provider.
3. Implement the capability through typed native interfaces. Reuse common result/error, identity, time, provenance, event, IPC, cancellation and authorization primitives already established by Rebuntu.
4. Preserve stable entity references and source provenance across boundaries. Never silently convert ambiguity, stale evidence or provider failure into certainty.
5. Add focused unit tests plus integration/contract tests against provider boundaries. Use fixtures/mocks for consequential host behavior.
6. Integrate with Phase 39 event/timeline contracts where this work produces operationally meaningful lifecycle events.
7. Audit for duplicate implementations and migrate callers to the canonical owner rather than leaving compatibility paths indefinitely.
8. Update architecture/ownership documentation and applicable repository guidance when this work establishes a durable contract.

## C++ implementation expectations

Prefer strong value types, RAII, bounded queues/work, explicit cancellation, deterministic parsing and typed errors. Avoid `std::any`/stringly-typed registries as the primary architecture. Do not invent a stable in-process C++ plugin ABI where a process/API boundary is safer. Linux-specific implementation is acceptable where Rebuntu is intentionally Linux-specific.

## Acceptance gate

This phase is complete only when **Development Environment Search Provider** is integrated into the existing Rebuntu architecture, exercised by tests, exposes explicit failure/UNKNOWN behavior, preserves domain ownership, and leaves no new permanent parallel search/control implementation.
