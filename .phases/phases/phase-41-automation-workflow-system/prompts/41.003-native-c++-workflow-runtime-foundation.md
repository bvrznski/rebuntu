# Phase 41.3 — Native C++ workflow runtime foundation

## Objective
Implement **Native C++ workflow runtime foundation** as a complete integrated workstream of Rebuntu Phase 41 — Automation & Workflow System.

## Mandatory repository-first execution
Before changing code, discover and read every applicable `AGENTS.md`, all Phase 41 architecture documents, relevant existing implementation/tests/build configuration, and the Phase 39/40 interfaces touched by this work. Recursively search for structures already implementing all or part of the responsibility. Integrate, migrate or refactor those structures; do not build a parallel subsystem.

`src/` is the canonical architecture-first implementation tree. Place implementation under the narrowest stable architectural owner and deepen the tree where real domain → subsystem → capability → component distinctions justify it. Never organize application ownership by implementation language.

Deterministic production functionality is C++-first. Python is permitted only at explicit justified semantic/ML, research/experimentation or narrow interoperability boundaries. Temporary coexistence is migration machinery, never permanent dual authority.

## System invariants
Phase 41 owns orchestration, not domain state. Use Phase 40 typed `CommandIntent`/capability interfaces and authoritative domain owners. Preserve the consequential-action lifecycle:

`observe → plan → validate → authorize → execute → verify → record`

A workflow, trigger, retry, schedule or semantic proposal never grants authorization. Phase 39 remains temporal/event authority. Preserve epistemic classes; `UNKNOWN != PASS`.

Use Phase 37 `SecretRef`; never place secret material in workflow definitions, persistence, logs, history, previews, semantic prompts, telemetry, timeline events or fixtures.

Native actions are typed commands/capabilities. Do not make arbitrary shell strings the workflow action vocabulary. Any legacy shell boundary must use explicit executable/argv plus constrained environment, cwd, timeout, output, authorization and audit policies.

Model state and recovery explicitly. Do not claim exactly-once external side effects. Use idempotency, deduplication, reconciliation and post-action domain verification. Bound concurrency, loops, fan-out, retries, queues and resource consumption.

## Implementation requirements
Define typed interfaces and state transitions, ownership, invariants, errors, cancellation, persistence/recovery behavior, provenance and observability appropriate to this workstream. Update callers, initialization, registration, CMake, packaging, documentation and tests so production actually reaches the new implementation.

Do not preserve legacy paths merely for convenience. Retire superseded implementation only after parity, caller migration and verification.

## Validation
Add focused unit, integration and adversarial tests. Exercise success, malformed input, denial, failure, cancellation, UNKNOWN/ambiguous outcomes, restart/recovery and relevant races. Never weaken tests to make the build green.

Configure/build the native code and run relevant test suites. Trace real production paths to prove authoritative integration.

## Recursive closure rule
After completing this workstream, search the entire repository again from scratch for missed callers/dependencies, duplicate authorities, legacy/fallback paths, stale imports/includes, obsolete documentation, migration scaffolding and related functionality that should be integrated. Resolve findings, rebuild/retest and repeat until rediscovery converges.

The inventory/checklist does not define scope; repository evidence does. If rediscovery exposes additional required work, perform it rather than labeling it future work.
