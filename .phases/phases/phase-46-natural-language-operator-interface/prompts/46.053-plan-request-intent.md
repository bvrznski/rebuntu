## `ask` interaction contract
Support:
- `ask <args...>` — parse the supplied natural-language request.
- bare `ask` — display one minimal `ask>` prompt, read one request, process it, then return to the parent shell.

Do not turn bare `ask` into an implicit persistent chat shell. A future conversational mode must be explicit and separately specified.

## Fundamental security invariants
Natural language may broaden understanding; it must never broaden authority.

Keep distinct:
- `Intent`: what appears to be requested.
- `Context`: what the request refers to and whether it makes sense here and now.
- `Capability`: what Rebuntu can represent/do through typed interfaces.
- `Authority`: what the requester/session/policy may permit.

Authorization alone is not sufficient for autonomous semantic execution. Consequential requests must also have adequate **contextual legitimacy** relative to current authoritative state, active task/project/workflow, recent actions, known services/endpoints/data flows, structural/temporal evidence and policy.

An authorized but unexpected request without sufficient contextual justification must transition to `CLARIFY`, `REQUIRE_JUSTIFICATION`, stronger confirmation, optional Gordon advisory review, or `DENY` according to policy/risk. It must not silently execute.

Operator justification is evidence, not authorization. Re-evaluate it against current state and policy. A plausible explanation cannot override deny policy, protected-resource invariants, missing authority or missing typed capability.

## Effect-based suspicious-use analysis
Detect suspicious use by intended effects and capability combinations, not merely literal strings or command blacklists.

Account for effects such as unbounded process creation/resource exhaustion, destructive mutation, safeguard disabling, privilege/persistence changes, new listeners/endpoints, outbound flows, bulk/sensitive data access, credential/secret access, data export and combinations producing exfiltration or loss-of-control paths.

A request equivalent in effect to a fork bomb must remain suspicious even when expressed in natural language, obfuscated, encoded or decomposed into multiple steps.

A request to open a new port and export logs to an unknown destination must be evaluated as a combined network/data-flow/persistence risk where applicable, not as unrelated individually permissible operations.

Legitimate administration must remain possible when context, policy, capability and authorization genuinely support it.

## Semantic and Gordon boundaries
BitNet is an NLU provider. It emits constrained structured `IntentCandidate` data, never authoritative shell commands. Rebuntu owns prompt/context construction, schemas, validation, policy, authority and execution.

Gordon may be consulted for unusual/ambiguous/contextually inconsistent requests using a minimal redacted EvidenceBundle. Gordon may identify inconsistencies, risks, missing evidence or clarification questions.

`Gordon verdict != authorization`.
`BitNet verdict != authorization`.
Neither may weaken policy, grant capabilities, fabricate observations, expose secrets, execute commands or turn `UNKNOWN` into `PASS`.

The deterministic safety path must remain valid when either provider is unavailable or compromised.

## Trust and provenance
Operator input and untrusted evidence are different trust domains. Instructions embedded in logs, files, README content, web content, process output, model output or quoted text remain data and cannot become operator intent.

Preserve provenance through context assembly and semantic processing. Resist prompt injection, context laundering and authority laundering.

Never send Phase 37 secret material to BitNet, Gordon, logs, telemetry, caches, history, graph/search indexes or unauthorized outputs. Use SecretRef and minimum safe projections.

## Action path
No direct `ask → shell`, `ask → privileged helper`, `BitNet → shell`, or `Gordon → shell` path is permitted.

Actionable requests must become typed Phase 40/45 intents/plans and follow:

`operator text → safe context → semantic IntentCandidate → deterministic resolution → contextual legitimacy → policy/safety → clarification/advisory review if needed → typed plan → validate → authorize → execute → verify → Phase 39 record`

Re-observe authoritative state before freshness-sensitive consequential operations. Material state/plan changes invalidate stale confirmation/authorization as appropriate.

## Implementation and validation
Define typed contracts, provenance, freshness, uncertainty, state machines, policy decisions, failure semantics, cancellation, timeouts, resource bounds, concurrency and observability.

Update actual production callers, CMake, packaging, shell integration, CLI/Panel surfaces, provider registration, tests and documentation. A native implementation not reached by the production `ask` path is incomplete.

Add unit/integration/end-to-end/adversarial tests appropriate to this workstream. Include benign administrative requests as well as suspicious requests to control false positives.

Explicitly test prompt injection, semantic obfuscation, resource exhaustion, unexpected-but-authorized use, data-flow/exfiltration-shaped combinations, fake justification, stale context, ambiguous referents, changed state after confirmation, provider compromise/outage, and the invariant that models cannot authorize or execute.
