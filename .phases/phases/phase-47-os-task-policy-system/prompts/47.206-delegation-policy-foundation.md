# Phase 47.206 — Delegation policy foundation

## Objective
Implement **Delegation policy foundation** as a complete production-integrated workstream of Rebuntu Phase 47 — OS Task Policy System.

## Repository-first execution
Before changing code, recursively discover/read every applicable `AGENTS.md`, all Phase 47 architecture documents, relevant source/tests/build/package/service definitions, and affected contracts from Phases 21–46. Search for existing task gates, authorization rules, workflow permissions, safety checks, resource limits, policy files, semantic guards, shell wrappers and direct domain execution paths.

Use aggregational morphing: converge existing policy behavior into one canonical task-policy architecture rather than adding a second gate or manager.

`src/` remains the canonical architecture-first tree. Deterministic task normalization, policy evaluation, capability/data-flow analysis, decision state, persistence and control-plane integration are C++-first. Python remains only at explicit semantic/ML/model, research/experimental or narrow justified interoperability boundaries.

## Task-policy invariants
An OS task is a typed unit of work, not a shell command.

Keep distinct:
`TaskIntent != TaskDefinition != TaskInstance != TaskPlan != PolicyDecision != Execution != Outcome`.

Preserve requester, origin/delegation chain, context, scope, targets, capabilities, data-flow effects, resource requirements, provenance, freshness, risk, reversibility and verification requirements.

Policy may narrow delegated authority but never amplify it.

`UNKNOWN != PASS`.
`missing context != allow`.
`semantic recommendation != policy decision`.
`policy allow != execution authorization`.
`execution success != verified outcome`.

## Policy lifecycle
Apply policy throughout the lifecycle:

`request → normalize → contextualize → classify → policy evaluate → plan → policy re-evaluate → authorize → execute → verify → outcome → record`

Bind decisions to the exact relevant requester, context, plan, targets, destinations, policy version and freshness window. Material changes invalidate stale decisions and require re-evaluation.

Use explicit effects such as ALLOW, DENY, CLARIFY, REQUIRE_JUSTIFICATION, REQUIRE_CONFIRMATION, REQUIRE_AUTHORIZATION, REQUIRE_STRONGER_AUTHORIZATION, REQUIRE_ADVISORY_REVIEW, RESTRICT_SCOPE, REQUIRE_SANDBOX, REQUIRE_BUDGET, REQUIRE_FRESH_OBSERVATION, REQUIRE_ROLLBACK and REQUIRE_VERIFICATION.

## Context, capabilities and data flow
Evaluate policy against authoritative current state and Phase 46 contextual legitimacy where relevant.

Analyze intended effects and combinations, not just command syntax. Represent capability composition, data sources/sinks, data classification, destination trust, persistence, privilege and resource amplification.

Detect policy evasion by splitting one prohibited effect across multiple tasks, workflow steps, automations or delegated agents. Cross-step composition such as sensitive data access followed by external egress must remain visible to policy.

Protect against unbounded process creation, retries, recursion, fan-out and other resource-exhaustion patterns.

## Cross-phase authority
Phase 47 does not replace:
- Phase 41 workflow orchestration,
- Phase 45 execution/authorization control path,
- Phase 46 natural-language interpretation,
- authoritative domain systems.

Taskwarrior records human tasks; a Taskwarrior task does not become executable merely by existing. Explicit bridging to a workflow/typed plan remains policy-governed.

BitNet and Gordon may explain, classify or advise only within their existing boundaries. They cannot create policy exceptions, grant authority, weaken deny rules or modify active policy autonomously.

## Policy representation and safety
Use typed, schema-validated, versioned policy with deterministic evaluation. Do not create an unrestricted executable policy language. Policy rules must never become arbitrary shell/code execution.

Protect bootability, storage integrity, network/SSH maintenance access, graphical session, identity/security controls, package trust, secrets and Rebuntu's own control plane.

Phase 37 secret material must not enter policy logs, traces, semantic prompts, history, fixtures or unauthorized outputs.

## Implementation requirements
Define typed contracts, state machines, precedence/conflict semantics, provenance, freshness, persistence/recovery, concurrency, cache invalidation, observability, versioning and failure behavior.

Update real production callers, Phase 45/46 hooks, Phase 41 workflows, Taskwarrior bridge, CMake, packaging, services, CLI/Panel, tests and documentation. Native code not reached by production task paths is incomplete.

## Validation
Add unit, integration, end-to-end and adversarial tests appropriate to this workstream. Test benign administration as well as denial paths to avoid a policy system that merely blocks everything.

Explicitly test task splitting, delegation/authority/context laundering, stale decisions, changed plans/destinations/requesters, resource exhaustion, sensitive-data egress, policy conflicts, semantic manipulation, crash/restart/reboot, concurrent reload/evaluation and fail-open attempts.
