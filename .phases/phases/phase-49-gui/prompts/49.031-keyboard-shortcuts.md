# Phase 49.31 — keyboard shortcuts

## Objective
Implement **keyboard shortcuts** as a complete production-integrated workstream of Rebuntu Phase 49 — GUI.

## Repository-first execution
Before changing code, recursively discover/read every applicable `AGENTS.md`, all Phase 49 architecture documents, relevant source/tests/build/package/desktop/service definitions, and affected contracts from Phases 21–48. Locate all existing Panel, TUI, dashboard, GUI, presentation-state and UI-to-action code.

Use aggregational morphing: migrate/refactor existing presentation capabilities—especially Phase 25 Panel work—into one canonical GUI rather than creating a parallel management application.

`src/` remains the canonical architecture-first tree. The GUI and deterministic UI/control integration are C++-first. Choose GUI technology based on repository/toolchain/runtime discovery and record the decision; do not force a framework merely because this specification exists.

## Fundamental architecture
The GUI is a presentation/interaction surface, not a second control plane.

`GUI gesture → typed intent → Phase 48 context where relevant → Phase 47 task policy → Phase 45 observe/plan/validate/authorize/execute/verify → Phase 39 record`

Never generate arbitrary shell strings from UI actions. Never execute the GUI as root merely to simplify privileged operations. Use existing typed IPC and narrow privilege boundaries.

Keep authoritative state distinct from presentation/cache state. Stale, partial, UNKNOWN, degraded and unavailable states must be visible and must not masquerade as current authoritative truth.

## Cross-phase ownership
Respect existing owners:
- Phases 21–24: health/log/platform foundations.
- Phases 26–38: system domains.
- Phase 39: temporal authority.
- Phase 40: unified search and typed commands.
- Phase 41: workflows/automation execution.
- Phase 42: structural graph.
- Phase 43: advisory intelligence.
- Phase 44: bounded adaptation.
- Phase 45: unified control plane.
- Phase 46: natural-language `ask`.
- Phase 47: OS task policy.
- Phase 48: OS task context awareness.

The GUI exposes these capabilities; it does not duplicate their logic.

## Operator experience
Design for a serious workstation/operator environment: fast keyboard navigation, high information density where useful, progressive disclosure, excellent diagnostics, clear provenance and precise action previews.

Use Rebuntu's retro-tech/ASCII sensibility as a restrained visual language, not as a novelty that harms legibility. Support Polish and English, accessibility, high contrast, keyboard-only use, HiDPI and multi-monitor operation.

Do not bundle or redistribute user font files. Prefer system-discovered/licensed fonts and robust fallbacks.

## `ask`, policy and context
Provide a first-class Phase 46 `ask` surface, but retain all semantic no-authority invariants.

Expose Phase 47 policy outcomes and Phase 48 contextual evidence when useful: why an action is unexpected, what context is stale, why justification is required, which exact plan is being confirmed, and what changed after confirmation.

Natural language, model output, context and recommendations never grant authority.

## Security
Treat logs, filenames, service descriptions, package metadata, remote text, model responses and other displayed content as untrusted data.

Sanitize terminal escapes/control characters and unsafe rich content. Prevent UI spoofing, confused-deputy behavior, stale-plan authorization, click-through confirmation, cross-session leakage and secret exposure.

Phase 37 secret material must not appear in GUI caches, diagnostics, telemetry, screenshots generated by Rebuntu, semantic prompts or ordinary history.

## Responsiveness and resilience
Use asynchronous bounded acquisition, incremental updates, cancellation, backpressure and virtualization for large/high-churn views. The UI must remain usable during event/log/process storms and provider/model outages.

A failed BitNet/Gordon provider must not disable deterministic system management. A GUI failure must not compromise the underlying Rebuntu control plane or maintenance access.

## Implementation and validation
Define typed UI models, IPC contracts, navigation, state invalidation, lifecycle, error semantics, accessibility metadata, localization, performance budgets and desktop integration.

Update real production callers, CMake/build/package/install definitions, desktop metadata, services where justified, tests, docs and `AGENTS.md`. Code that exists only as an unconnected mock/demo is incomplete.

Validate read-only and consequential workflows end-to-end, including plan preview, policy/context gates, authorization, execution progress, verification, rollback/partial failure and Phase 39 recording.

## Recursive fixed-point completion
After implementation, rediscover the entire repository for old Panel/UI paths, duplicate presentation state, direct UI-to-shell/domain/privilege paths, stale Python GUI ownership, duplicated ask/policy/context logic and obsolete launchers.

Resolve findings, rebuild/retest and repeat. Require a second clean rediscovery after the first zero-candidate pass, then adversarially audit authority boundaries, stale state, rendering security, accessibility, semantic output, IPC and privilege separation.

The repository, not this numbered inventory, defines completion.
