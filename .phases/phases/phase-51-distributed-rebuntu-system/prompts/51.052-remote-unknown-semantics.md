## System boundary
Phase 51 models one administratively coherent Rebuntu fabric composed of multiple nodes.

Do not implement this as SSH command fanout, arbitrary remote shell execution, a pile of scripts, or a second control plane.

Preserve the separation:
- authentication establishes identity;
- membership establishes participation in the fabric;
- context supplies evidence;
- policy constrains what may be requested;
- authorization permits a specific consequential operation;
- the authoritative target domain executes and verifies it.

`reachability != membership`
`membership != authorization`
`hostname != durable identity`
`IP address != identity`
`remote advertisement != authoritative fresh state`
`placement decision != execution authorization`
`UNKNOWN != PASS`

## Distributed execution invariant
Consequential remote work must remain typed and follow:

`intent -> resolve -> observe -> plan -> validate -> policy -> authorize -> dispatch -> target revalidate -> execute -> verify -> reconcile -> Phase 39 record`

The receiving node retains final local validation for its authoritative resources. A coordinator cannot force a target to bypass local safety, policy, capability applicability or freshness checks.

No model, semantic provider, workflow, graph path, search result, remote node claim or placement recommendation may grant execution authority.

## Failure model
Assume partitions, node loss, reboot, crash, duplicated/reordered/delayed messages, stale observations, clock skew and partial execution.

Never claim exactly-once execution. Use durable operation identities, idempotency where possible, bounded retries, explicit leases/fencing where justified, reconciliation and honest UNKNOWN/INDETERMINATE outcomes.

Do not interpret lost contact as proof that an operation failed or succeeded.
