# Phase 53.013 — one-level downward control

## Objective
Implement **one-level downward control** as a first-class part of Phase 53 — Dual-Flow Mandatory Security System.

## Execution contract
Perform repository-first discovery across the relevant Rebuntu tree. Find existing implementations,
partial implementations, types, providers, callers, tests and documentation. Reuse/refactor/migrate them;
never build a parallel security architecture. C++ owns deterministic authoritative enforcement.

Preserve these mandatory semantics:
- BLP confidentiality: JAWNY < POUFNY < TAJNY < SEKRETNY plus compartments; no-read-up/no-write-down baseline.
- Modified Biba control integrity: L0 UNTRUSTED < L1 CONSTRAINED < L2 TRUSTED < L3 AUTHORITATIVE.
- Upward reports may skip levels but convey no authority.
- Ordinary downward control is exactly one level.
- Any individual L3 authority may command L2.
- Individual L3→L1/L0 is forbidden.
- Direct L3→L1/L0 requires unanimous agreement of every independent admitted L3 authority, bound to the
  exact typed operation, targets, context, freshness, policy version and plan.
- Consensus never replaces capability checks, Phase47 policy, Phase45 authorization, validation or verification.
- DATA != CONTROL. Any data→control transition crosses an explicit deterministic gate.
- Clark–Wilson-style certified transformations protect consequential state.
- privilege != integrity; authentication != authorization; UNKNOWN != PASS.
- semantic/model output cannot self-promote integrity or directly execute commands.

## Implementation requirements
Define strong types, ownership, lifecycle, provenance, freshness, serialization/versioning, enforcement points,
error states, audit evidence, crash/restart/recovery behavior and adversarial cases relevant to this task.
Migrate all affected callers and schemas to a fixed point. Add unit, property, integration, negative, stale,
forged, replay, race and recovery tests as applicable. Preserve Phase37 secret discipline and Phase39 evidence.

Run a second clean repository rediscovery after implementation. Merge or retire obsolete duplicate logic only
when proven superseded; never perform destructive broad cleanup.

## Completion
Complete only when **one-level downward control** is enforced through canonical Rebuntu paths, relevant callers use it,
failure/recovery behavior is tested, and rediscovery finds no unjustified competing implementation.
