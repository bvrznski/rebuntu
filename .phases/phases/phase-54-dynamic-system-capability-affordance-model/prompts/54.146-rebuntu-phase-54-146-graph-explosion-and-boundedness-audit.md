# Rebuntu — Phase 54.146: Graph-explosion and boundedness audit

## Mission

Implement, migrate, audit and verify **Graph-explosion and boundedness audit** as part of Phase 54 — Dynamic System Capability & Affordance Model. The result must strengthen Rebuntu's runtime answer to what can be done, to which exact target, under which current conditions, with which prerequisites/blockers and evidence, without granting execution authority.

Execute this against the real repository produced by preceding phases. Discover before implementing. Compose existing capability, observation, policy, security, context, platform, resource, graph, distributed and control-plane contracts rather than duplicating them.

## Non-negotiable invariants

- THIS PROJECT IS REBUNTU; there is exactly one Rebuntu architecture.
- REBUNTU IS C++-NATIVE.
- Phase 54 composes existing phases; it does not create a second control plane.
- Capability != availability != applicability != feasibility != readiness != permission != authorization.
- AFFORDANCE != AUTHORIZATION.
- CAPABILITY != PERMISSION.
- AVAILABILITY != READINESS.
- FEASIBILITY != AUTHORIZATION.
- CONTEXT != AUTHORITY.
- TRUST != EXECUTION AUTHORITY.
- MODEL OUTPUT != AUTHORITY.
- DATA != CONTROL.
- UNKNOWN != PASS.
- Missing evidence does not prove absence.
- Stale evidence cannot justify a current affordance.
- Capability evaluation is read-side decision support until canonical authorization/execution gates are invoked.
- Phase 45 remains the unified control plane.
- Phase 47 remains task-policy authority.
- Phase 53 mandatory security remains non-bypassable.
- Phase 48 context supplies evidence and relevance, never authority.
- Phase 50 platform providers describe mechanisms/capabilities, not policy.
- Phase 51/52 remote association or reachability never implies permission.
- Phase 42 graph proximity never implies causality or permission.
- Phase 39 temporal ordering never implies causality.
- Phase 30 resource observations/reservations do not themselves authorize effects.
- Capability definitions are stable concepts; capability instances are contextual realizations.
- Affordances are target-, context-, time-, evidence- and policy-sensitive evaluations.
- Provider availability is not target applicability.
- Prerequisite satisfiability does not authorize prerequisite execution.
- A prerequisite graph is not an execution plan.
- Plan synthesis remains a separate bounded responsibility.
- Why-not explanations must be evidence-grounded and must not fabricate blockers.
- Alternatives must preserve exact target/scope/security constraints.
- Strong entity identity must survive index/name/path replacement hazards.
- Freshness and invalidation are first-class.
- TOCTOU is expected; consequential execution requires fresh revalidation.
- Remote capability advertisements are untrusted claims until validated under association/trust rules.
- No giant CapabilityManager/AffordanceManager/God Registry.
- One canonical capability identity model.
- One canonical affordance evaluation contract.
- C++ owns deterministic capability/affordance evaluation and graph mechanics.
- Python/model services may assist semantic discovery/explanation only.
- Python/model output cannot create permissions, capabilities or successful affordances.
- No shell command generation as capability execution architecture.
- No system(), popen(), sh -c or bash -c as canonical control path.
- Use typed operations and existing Phase 40/45 execution routes.
- Use C++20, RAII, strong types and explicit ownership.
- No raw owning pointers.
- No unbounded graph expansion, queues, recursion, retries or caches.
- Cycle detection is mandatory for prerequisite/dependency graphs.
- Evaluation has explicit deadlines/cancellation/resource bounds.
- Derived/cached affordances never become authoritative live state.
- SecretMaterial never enters generic capability graphs/explanations/logs.
- Capability queries must minimize sensitive topology disclosure.
- Production code must be build- and runtime-reachable.
- Caller migration must reach a fixed point before duplicate capability logic retires.
- Do not destructively modify the host merely to test capability evaluation.
- Documentation must describe implemented semantics, not aspirational intelligence.
- Rebuntu evolves through aggregational morphing: discover → extend → compose → refactor → migrate → remove obsolete duplication.
