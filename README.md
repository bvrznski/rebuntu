# Rebuntu

**Rebuntu** is a standalone, **C++-native Linux system-management, automation,
monitoring, coordination, verification, recovery, security, and
semantic-processing environment**. It lives *above* Linux while being
deliberately grounded *in* Linux: it composes the platform's own mechanisms
(systemd, D-Bus, journald, procfs, sysfs, cgroups v2, inotify/fanotify,
netlink, eBPF, …) into a coherent system rather than a collection of command
wrappers.

## What Rebuntu is (and is not)

Rebuntu is a **coherent system**, not a bag of aliases. It is intended to
eventually observe and operate on system state, declare desired state, detect
divergence, verify outcomes, preserve evidence, recover from failures, enforce
policies, and expose coherent interfaces to humans and software.

Rebuntu is **not**:

- a Linux distribution, or a replacement for the kernel or systemd;
- a giant Bash framework or an inventory of Linux objects;
- an unrestricted LLM-to-shell interface or an autonomous command generator;
- a synthetic mind / cognitive architecture / AGI framework.

Architecture uses **systems and software terminology** (observation, state,
event, condition, policy, coordination, operation, verification, evidence,
recovery, reconciliation, semantic processing) — not psychological or
cognitive categories. See [ARCHITECTURE.md](ARCHITECTURE.md).

## Engineering philosophy

- **Native first.** If Linux already provides the right primitive, use it.
  Use the *lowest appropriate* native abstraction; "kernel-first" does not mean
  bypassing mature userspace abstractions (e.g. use systemd, not raw PID
  bookkeeping).
- **C++-native.** Rebuntu is implemented in **C++20**. The primary structural
  package is `src/system/`; native implementation and the shared contracts live
  under `cpp/` (CMake + CTest, no external dependencies).
- **Verified outcomes, not exit codes.** `COMMAND SUCCESS != OPERATION
  SUCCESS`. Operations return explicit `Result`/`Outcome` with `Evidence`.
- **Evidence before mutation.** Establish observable state before changing it.
- **Maximalist structure, conservative implementation.** The tree is an
  *architectural hypothesis*, not a finished feature list. Empty structure is
  cheap; speculative runtime is not.
- **One Rebuntu.** Extend, compose, refactor — do not create parallel
  implementations. See [AGENTS.md](AGENTS.md).

## Quick start

```bash
# Build the native foundation (CMake + C++20) and run the test suite:
cd cpp
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build --output-on-failure

# Exercise the CLI:
./build/src/rebuntu version
./build/src/rebuntu components

# Lifecycle management (Phase 1.11):
./build/src/rebuntu reconfigure key=value
./build/src/rebuntu repair [path...]
./build/src/rebuntu upgrade target-version
./build/src/rebuntu uninstall [--dry-run] [--force]
./build/src/rebuntu purge [--dry-run]

# All lifecycle commands support --help:
./build/src/rebuntu reconfigure --help
./build/src/rebuntu repair --help
```

There is no Python runtime, no installed service, and no host-system change in
Phase 0.0. The C++ foundation is the only executable artifact, and it performs
no system mutation.
