# Discovery 0020 — Phase 0.19: Naming, Namespaces, Registries & Catalogs

## Observation / Problem

Phase 0.19 establishes how Rebuntu names, identifies, locates and discovers capabilities
without building registry bureaucracy or magical plugin loading.

Key questions to address:

1. **Name vs ID vs Path?** What is the semantic distinction between human name,
   stable identifier, filesystem path, import path, and systemd unit name?

2. **What is a namespace?** How do we avoid collisions while keeping the structure
   shallow and meaningful?

3. **Registry vs Catalog?** When should we have an authoritative mapping versus a
   discoverable inventory?

4. **Discovery vs Registration?** What mechanisms discover what exists, and when do
   we explicitly register implementations?

5. **How are providers identified?** How do we decouple capability identity from
   provider identity?

6. **How are collisions handled?** What happens when two components claim the same ID?

7. **How do aliases work?** Can a capability have alternate names that resolve to
   canonical identity?

8. **How do we safely discover capabilities?** How do agents search before implementing?

9. **How is shell namespace protected?** How do we avoid shadowing builtins/system commands?

## Architecture Decisions

### 1. Name vs ID vs Path

```
Human Name           : "Filesystem Copy"      (user-facing label)
Semantic ID          : "filesystem.copy"      (stable identifier, no spaces)
Filesystem Path      : "src/system/core/"     (physical location)
C++ Namespace        : "rebuntu::core"        (code organization)
Import Path          : "#include <...>"       (source include)
Systemd Unit Name    : "rebuntu-core.service" (deployment artifact)
Shell Verb           : "copy"                 (user command surface)
```

**Decision:** These must not be assumed identical. The system maintains explicit
mapping between semantic ID and all other representations.

### 2. Namespace Design

```
Rebuntu uses a single global namespace: rebuntu::
├── core/          - Foundational contracts
├── runtime/       - Runtime foundation  
├── cli/           - Command-line interface
├── automation/    - Automation definitions
└── ...            - Domain-specific modules
```

**Decision:** Namespaces are flat at first level (no deep nesting like
`rebuntu::system::core`). Directory structure encodes structural type,
not semantic domain.

### 3. Registry vs Catalog

| Aspect | Registry | Catalog |
|--------|----------|---------|
| Purpose | Authoritative resolution | Discoverable inventory |
| Usage | Runtime resolution | Documentation/search |
| Validation | Required (duplicate detection) | Optional |
| Authority | Deterministic C++ engine | Informational only |

**Decision:** 
- **Registry**: For components that must be resolved at runtime
  (`ComponentRegistry`, `OperationRegistry`, `ServiceRegistry`)
- **Catalog**: For discoverable but not necessarily authoritative info

### 4. Discovery vs Registration

**Discovery mechanisms:**
1. Source code inspection (grep, search)
2. Filesystem scan of `src/system/`
3. Registry lookup (C++ API)
4. Shell command help (`rebuntu components`)

**Registration requirements:**
- All structural components registered in `ComponentRegistry`
- Operations registered in `OperationRegistry`
- Services registered in `ServiceRegistry`

### 5. Provider Identity vs Capability Identity

```
Capability ID: "filesystem.copy"         (what can be done)
Provider IDs:  ["provider_posix_copy",
                "provider_python_shutil"]
```

**Decision:** Keep capability identity separate from provider identity.
A capability may have multiple providers; the registry tracks this mapping.

### 6. Collision Handling

| Collision Type | Resolution |
|----------------|------------|
| Duplicate semantic ID | Structural validation error |
| Shell verb collision | Reserved verb, must be explicitly assigned |
| Namespace collision | C++ compile-time error (language constraint) |

**Decision:** Duplicate semantic IDs are structural defects detected at
`ComponentRegistry::validate()` time.

### 7. Aliases

```
Alias: "filesystem.cp" → resolves to canonical ID "filesystem.copy"
```

**Decision:** Aliases are optional metadata on components/operations.
They do not change the authoritative behavior, only discoverability.

### 8. Safe Discovery

**Discovery safety rules:**
1. Never execute arbitrary files found during discovery
2. Validation is separate from discovery
3. Trust/registration is explicit (not automatic)

## Rejected Alternatives

| Alternative | Reason |
|-------------|--------|
| Deep namespace nesting (`rebuntu::system::core::...`) | Over-normalization; structural type already encoded in directory |
| Plugin-based dynamic loading | Complex lifecycle management; C++ static linking preferred |
| Import-time magic | Non-deterministic; hard to test and debug |
| Global registry for everything | Bureaucracy without consumers |
