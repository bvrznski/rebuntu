## Executive Summary

Phase 0.2 establishes Rebuntu's **operational grammar**: the precise vocabulary and relationships that describe how entities are instantiated, activated, executed, controlled, coordinated, communicate, change state, and produce results.

This is NOT an implementation phase. This is a definition/grammar phase.

## 1. Runtime

### Definition
**Runtime** is the infrastructure required to instantiate and execute Rebuntu entities.

### What Runtime Owns
- **Lifecycle management**: creation, initialization, activation, termination
- **Execution context**: timeouts, cancellation, environment variables
- **Dispatch**: routing requests to appropriate execution mechanisms
- **Active instances**: tracking runtime occurrences of specifications
- **Coordination**: making multiple components act consistently
- **Shutdown**: graceful and forced termination

### What Runtime Does NOT Own
- Domain-specific logic (that belongs in Units/Modules)
- State persistence (that belongs in state management)
- Policy enforcement (that belongs in policy engine)
- Security authorization (that belongs in security subsystem)

### Native Linux Mapping
| Rebuntu Runtime | Native Mechanism |
|-----------------|------------------|
| Lifecycle transitions | systemd unit lifecycle, process lifecycle |
| Execution context | cgroups v2, namespaces, env vars |
| Cancellation | signalfd, pidfd, SIGTERM/SIGINT |
| Dispatch | epoll, eventfd, timerfd |
| Shutdown coordination | systemd shutdown ordering |

### Implementation Status
**CURRENT**: Contracts in `src/runtime/contracts.hpp`, Runner/Executor/Dispatcher classes in `runner.hpp`, `executor.hpp`, `dispatcher.hpp`

## 2. Specification vs Instance

### Specification (Definition)
- Static declaration of what something is
- Immutable once created
- Reusable across multiple runtime occurrences
- Examples: Unit, Task, ServiceConfig, Workflow

### Runtime Instance
- Concrete occurrence of a specification in execution
- Has identity, lifecycle state, health status
- Temporal existence with creation and termination times
- Examples: Job (instance of Task), ServiceInstance, WorkflowRun

### Key Distinction
```
TaskDefinition (specification) + parameters → Job (runtime instance)
ServiceConfig (specification) → ServiceInstance (runtime instance)
WorkflowDefinition (specification) → WorkflowRun (runtime instance)
```

---

## 3. Execution

### Execution
- Concrete runtime occurrence of work being performed
- May have multiple attempts due to retries/failures
- Produces Result with verification status and evidence

### Runner
- Progresses one bounded execution according to an executable definition
- Maintains state machine: pending → running → waiting/finished
- Tracks progress stages: dispatched → executing → observing → verifying → completed
- Handles cancellation, timeouts, retries

### Executor
- Invokes concrete implementation/providers and returns structured observations/results
- Implements specific mechanisms: inline, subprocess, systemd unit, D-Bus method
- Returns Outcome (success/failure) with evidence

### Dispatcher
- Routes eligible work to appropriate execution mechanisms/providers
- Makes decisions based on task requirements, available mechanisms, system state
- May implement backpressure and scheduling

## 4. State Dimensions

Rebuntu uses **orthogonal state dimensions** that can be combined:

| Dimension | Values | Meaning |
|-----------|--------|---------|
| LifecycleState | created, initializing, ready, active, stopping, stopped, failed | Stage of existence/execution |
| WorkState | idle, processing, waiting, paused, jammed | Current activity type |
| ControlState | enabled, disabled, paused, frozen, locked | Administrative control state |
| ReadinessState | ready, not_ready | Can accept/perform work now? |
| HealthState | unknown, healthy, degraded, unhealthy | Sustained qualitative state |
| RecoveryState | none, retrying, rolling_back, restoring, repairing, failing_over | Corrective action in progress |

### State vs Status
- **State**: The complete set of runtime attributes across orthogonal dimensions
- **Status**: A simplified summary of state for display/monitoring

## 5. Result & Verification

### Result
A structured outcome with:
- Outcome (semantic conclusion)
- Evidence (provenance-bearing observations supporting claims)
- Timing information (duration, timeouts)
- Verification status

### Outcome
The semantic conclusion:
- SUCCESS: completed AND verified
- COMPLETED: completed but verification not applicable
- FAILURE: attempt ran but objective not met
- UNKNOWN: outcome could not be determined
- CANCELLED: explicitly cancelled before completion

### Execution Success vs Verification Success
```
Exit code 0 ≠ Semantic success
Execution may succeed but postconditions may fail verification

Example:
- Operation executes without error (exit 0)
- But desired state was not achieved
- Result = FAILURE with verification_status = FAILED
```

## 6. Request/Event/Signal/Trigger Distinctions

### Request
Semantic/system request for something to happen.
- Contains operation, target, parameters
- Has timeout, priority, origin context
- Distinct from Call (invocation mechanism) and Command (user representation)

### Event
Immutable statement that something occurred or was observed.
- Evidence-backed with provenance
- Originates from Rebuntu, systemd, kernel, filesystem, network, etc.
- Not a request for action

### Signal
Lightweight control/notification indication.
- Pauses, resumes, cancels, reconfigures execution
- Distinct from Event (which reports occurrences)

### Trigger
Activation decision produced because activation criteria were satisfied.
- Example: udev event + condition match → trigger workflow

## 7. Lifecycle Transitions

```
CREATED → INITIALIZING → READY → ACTIVE
    │              │          │        │
    └─failed───────┘          └─stop───→ STOPPED
                               failed ↓
                                    FAILED

READY → (readiness check) → can accept work
ACTIVE → health check → may become DEGRADED/UNHEALTHY
```

### Readiness Predicate
```
ready() = (readiness == kReady) AND (health == kHealthy)
```

An entity can be:
- Healthy but not ready (still initializing)
- Ready but unhealthy (degraded mode)
- Jammed (alive but making no forward progress)

## 9. Evidence

Evidence is a first-class architectural concept.

### What Evidence Includes
- Observed values
- Command/API results
- systemd state
- File metadata
- Kernel state
- Timestamps
- Hashes
- Before/after snapshots
- Verification measurements

### Evidence Principles
- **DATA, not CONTROL**: Evidence records facts but doesn't control behavior
- **Provenance-bearing**: Can trace evidence back to source
- **Bounded**: Not unbounded data streams
- **Secret-free**: Never contains plaintext secrets

## 10. Retry & Timeout Policy

### RetryPolicy
- max_attempts: total attempts including initial
- exponential_backoff: delay increases between attempts
- retryable_error_codes: filter which errors trigger retry
- compute_delay(): calculate delay with backoff and maximum cap

### TimeoutPolicy
- default_timeout: fallback timeout for operations
- operation_timeout: specific timeout for main execution
- verification_timeout: specific timeout for postcondition verification
- cancel_on_timeout: whether to cancel or continue on timeout
- retry_on_timeout: whether to attempt retry on timeout

## 11. Coordination & Dependencies

### Coordination
Making multiple components act consistently.
- Start B after A is ready
- Prevent C while D is active
- Synchronize workflow threads
- Arbitrate competing resource requests

### Dependency Types
- Structural dependency (code-level)
- Implementation dependency (runtime needs)
- Runtime dependency (lifecycle ordering)
- Ordering dependency (A must complete before B starts)
- Readiness dependency (B can start when A becomes ready)
- Resource dependency (shared lock/queue/buffer)

---

## 12. Automation vs Workflow

### Workflow
Describes how work progresses after activation.
- Phases → Stages → Steps hierarchy
- Threads for parallel execution
- Branch/join for conditional flow

### Automation
Describes when/why work becomes activated.
- Observes events/state/time
- Evaluates conditions
- Activates operations/workflows when criteria satisfied

**Distinction**: Workflow = "how"; Automation = "when why"

---

## 13. Reconciliation vs Recovery

### Reconciliation
Moves observed state toward desired state.
```
observed state + desired state → difference → corrective plan → operation → verification
```

### Recovery
Responds to failure/degradation and attempts to restore acceptable operation.
- Retry: attempt same operation again
- Rollback: return to prior known state
- Restore: recreate desired/known-good state from preserved source
- Repair: modify damaged/inconsistent state to become valid
- Failover: switch to alternate implementation/resource
- Degrade: continue with reduced functionality

---

## 14. Verification & Evidence Chain

```
PRECONDITIONS (evaluated before execution)
    ↓
EXECUTION
    ↓
OBSERVED RESULT
    ↓
POSTCONDITION VERIFICATION
    ↓
EVIDENCE GENERATED
    ↓
RESULT WITH VERIFICATION STATUS
```

**Key Principle**: Execution success ≠ Verification success. The operation may complete but postconditions may fail.
