## UNIT DEFINITION (Phase 0.7)

```
UNIT

A bounded, independently identifiable Rebuntu definition representing
a discrete piece of executable or operational functionality that may be invoked,
activated, composed, scheduled, inspected and verified.
```

A Unit should normally have:
- **identity** (stable semantic identifier like "filesystem.copy")
- **purpose** (what it does)
- **inputs** (explicit contract for parameters)
- **outputs** (structured result, not just stdout strings)
- **contract** (preconditions, postconditions, side effects)
- **execution semantics** (how it runs: in-process, subprocess, Service IPC)
- **dependencies** (what it needs to run)
- **result semantics** (outcome, verification status, evidence)

A Unit should NOT simply mean:
- any class
- any function  
- any file
- any directory
- any systemd unit (.service, .timer, etc.)
- any Service.

---

## KEY DISTINCTIONS

| Concept | Relation to Unit |
|---------|-----------------|
| **systemd Unit** | Deployment artifact (.service, .timer). Rebuntu Unit may be implemented through systemd but they are fundamentally different concepts. |
| **Module** | Structural boundary that may contain Units. Do not create one Unit per Module automatically. |
| **Service** | Managed functionality with lifecycle semantics. A Service may expose or invoke Units. |
| **Daemon** | Persistent process role. A daemon may execute Units, but process persistence is irrelevant to Unit identity. |
| **Script** | Executable artifact. A Script may implement a Unit, but Unit identity is not determined by file type. |
| **Operation** | Contractual system action. Unit = execution definition; Operation = semantic contract (likely relation). |
| **Task** | Parameterized work specification. Task refers to Unit as its implementation (Unit is reusable; Task is parameterized). |
| **Job** | Runtime execution/submission of Task. Job is concrete; Unit is reusable definition. |
| **Workflow** | Composed execution. A Workflow may invoke Units but is not itself a Unit. |

## UNIT VS SYSTEMD UNIT

| Concept | Definition | Relationship |
|---------|-----------|--------------|
| **Rebuntu Unit** | Semantic/operational definition (what can be done) | May be implemented through systemd |
| **systemd Unit** | Process lifecycle/deployment artifact (.service, .timer, etc.) | Deployment mechanism for Rebuntu Units |

A Rebuntu Unit may be implemented or activated through systemd, but they are
fundamentally different concepts.

---

## UNIT VS MODULE

| Concept | Definition | Relationship |
|---------|-----------|--------------|
| **Module** | Structural software boundary (reusable component) | May contain/ implement multiple Units |
| **Unit** | Executable operational definition | May depend on Modules for infrastructure |

Do not create one Unit per Module automatically.

---

## UNIT VS SERVICE

| Concept | Definition | Relationship |
|---------|-----------|--------------|
| **Service** | Managed functionality with availability/lifecycle semantics | May expose or invoke Units |
| **Unit** | Bounded executable/operational definition | May be invoked by Services |

A Unit may execute entirely in-process with no Service.

---

## UNIT VS DAEMON

| Concept | Definition | Relationship |
|---------|-----------|--------------|
| **Daemon** | Persistent process/runtime characteristic | A daemon may execute Units |
| **Unit** | Operational definition (what can be done) | Process persistence is irrelevant to Unit identity |

Process persistence is irrelevant to Unit identity.

---

## UNIT VS SCRIPT

| Concept | Definition | Relationship |
|---------|-----------|--------------|
| **Script** | Executable artifact (.sh, .py) | A Script may implement a Unit |
| **Unit** | Semantic/operational entity (stable identifier) | Identity not determined by file type |

Do not classify Unit identity by file type.

---

## UNIT VS OPERATION

| Concept | Definition | Relationship |
|---------|-----------|--------------|
| **Operation** | Contract describing a system action/query (what can be done) | Describes semantics |
| **Unit** | Executable container/definition (how it's done) | Implements the Operation |

A likely useful relation:
- Unit represents the executable container/definition
- Operation describes the semantic action exposed by it

---

## UNIT VS TASK

| Concept | Definition | Relationship |
|---------|-----------|--------------|
| **Task** | Parameterized work specification (copy /foo to /bar) | References a Unit for implementation |
| **Unit** | Reusable executable definition (filesystem.copy) | Provides the implementation |

A Task refers to a Unit as its implementation.

---

## UNIT VS JOB

| Concept | Definition | Relationship |
|---------|-----------|--------------|
| **Job** | Concrete submitted/executing realization | Runtime instance of work |
| **Unit** | Reusable definition (filesystem.copy) | What gets executed |

Potential chain:
```
Unit + parameters -> Task -> submit -> Job -> execute -> Result
```

---

## UNIT VS WORKFLOW

| Concept | Definition | Relationship |
|---------|-----------|--------------|
| **Workflow** | Composed execution (phases/steps invoking Units) | Orchestrates Units |
| **Unit** | Atomic/reusable executable definition | May form steps within Workflow |

Do not automatically make every Workflow a Unit.

---

## EXECUTION SEMANTICS

A Unit may execute through:
- Direct invocation (in-process)
- Subprocess execution
- Service IPC
- systemd activation

The execution mode is orthogonal to Unit identity.

---

## RESULT MODEL

Unit results include:
- **outcome** (SUCCESS/FAILURE/CANCELLED/TIMED_OUT)
- **output data**
- **verification status** (VERIFIED/UNVERIFIED/APPLICABLE)
- **evidence** (provenance-bearing observations)

Execution success ≠ Verification success:
- Exit code 0 proves only exit code, not desired state achieved
- Postcondition verification is required for consequential operations

---

## UNIT IDENTIFIERS

Stable semantic identifiers like "filesystem.copy" rather than implementation names.
Identifiers should describe semantic capability, not implementation.

Example patterns:
- `filesystem.copy`
- `service.ensure_available`  
- `text.normalize`
