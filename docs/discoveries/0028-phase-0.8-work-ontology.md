## Overview
This discovery documents the implementation of Rebuntu's work ontology - the model for bounded work and its runtime realization.

## The Core Distinction: Specification vs Instance

### Task (Specification)
A reusable, parameterized specification of bounded work.

**Answers:** What work is requested?

**Characteristics:**
- Declarative, not executable
- Reusable across multiple invocations
- May reference Units or Operations
- Contains parameter requirements

### Job (Managed Realization)
A concrete submitted, scheduled, or executing realization of a Task.

**Answers:** Which work is being managed? What's the current state?

**Characteristics:**
- Concrete instance of a Task
- Has its own lifecycle state
- Contains runtime parameters
- May have multiple attempts (for retry semantics)

### Execution (Runtime Attempt)
The runtime occurrence of performing work.

**Answers:** What is happening at runtime?

**Characteristics:**
- Actual execution activity
- May be implemented by subprocess, thread, D-Bus call, etc.
- Has unique identity independent from OS process

### Attempt (One Try)
One attempt to perform a Job.

**Answers:** Which try is this? What was the result?

**Characteristics:**
- Relevant for retry semantics
- Each attempt has unique ExecutionId
- Preserves failure history

## State Axes

Each concept uses orthogonal state dimensions:

### TaskState
- `kCreated` - defined but not ready
- `kReady` - ready for execution
- `kCancelled` - cancelled before execution
- `kDeprecated` - superseded by newer version

### JobState
- `kCreated` - submitted but not yet processed
- `kQueued` - waiting in queue
- `kReady` - ready to start
- `kRunning` - currently executing
- `kCompleted` - finished successfully
- `kFailed` - terminated with error
- `kCancelled` - cancelled during execution

### AttemptState
- `kCreated` - attempt created
- `kStarting` - initialization in progress
- `kRunning` - main work executing
- `kFinishing` - cleanup/verification phase
- `kFinished` - attempt complete

## Implementation Details

### Identifiers
- `TaskId` - unique identifier for Task specifications
- `JobId` - unique identifier for Job instances
- `ExecutionId` - unique identifier for Execution attempts
- `AttemptNumber` - ordinal number of attempt within a job

### Data Structures
- `Task` - specification with parameters, mode, required_parameters
- `Job` - instance with state, retry policy, timeout policy, priority
- `Attempt` - runtime record with PID, start/finish times, outcome
- `ExecutionRecord` - complete execution history
- `AttemptResult` - result with timing and retry metadata

## Key Distinctions Established

1. **Task != Job**: Task is specification; Job is managed instance
2. **Job != Execution**: Job may exist before execution; one job can have multiple executions
3. **Execution != Process**: Execution is semantic entity, process is OS entity

## Retry Semantics

Each Job can specify:
- `max_attempts`: Total attempts including initial
- `retry_policy`: Controls backoff and retry behavior
- Each attempt has unique ExecutionId
- Failure history is preserved across retries

## Cancellation

Jobs may be cancelled with reasons:
- `kExplicit` - explicit user/system request
- `kTimeout` - operation exceeded timeout
- `kDependencyFailed` - required dependency failed
- `kResourceExhausted` - insufficient resources

## Timeout Policy

Defined in `runtime::contracts.hpp`:
- `default_timeout`: General timeout for operations
- `operation_timeout`: Specific timeout for the operation itself
- `verification_timeout`: Time allowed for verification post-operation
- `cancel_on_timeout`: Whether to cancel on timeout

## Notes for Future Phases

1. **Execution Implementation**: This defines types, not execution logic. Later phases need to implement:
   - Job submission and queuing
   - Attempt scheduling and running
   - State persistence (if needed)

2. **Integration Points**:
   - Connect to Unit registry for task resolution
   - Connect to Operation system for semantic work
   - Connect to evidence system for outcome tracking

3. **Persistence Decision**: The work types define runtime state but do not mandate persistence. Implementers must decide:
   - Which jobs require persistence?
   - How long are completed jobs retained?
   - What happens after crash/restart?

4. **Thread Safety**: These are data structures only. Any shared access requires synchronization mechanisms.
