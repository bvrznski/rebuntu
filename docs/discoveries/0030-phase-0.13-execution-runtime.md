## Executive Summary

Phase 0.13 establishes the canonical execution-runtime grammar connecting validated Rebuntu
definitions to actual runtime work:

    REQUEST / ACTIVATION → RESOLVE → VALIDATE → AUTHORIZE → DISPATCH → EXECUTE → OBSERVE → VERIFY → EVIDENCE → RESULT

- Runner: State machine tracking execution lifecycle and progress

## Architecture Decisions

### 1. Semantic Separation of Concerns
```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│    Runner       │────▶│   Executor      │────▶│   Dispatcher    │
│ (State Machine) │     │(Execution Mgmt) │     │  (Routing)      │
└─────────────────┘     └─────────────────┘     └─────────────────┘

Runner:
- Tracks lifecycle: pending → running → finished
- Manages progress stages: dispatched → executing → observing → verifying → completed  
- Handles retry logic based on policy
- Propagates cancellation
- Collects evidence from all attempts
- Does NOT execute work directly

Executor:
- Executes ONE attempt of a task
- Returns Outcome with evidence
- Knows about execution mechanisms but not retry logic
- Does NOT track state progression (that's Runner)

Dispatcher:
- Evaluates Task requirements against available mechanisms
- Selects appropriate execution mode (inline, subprocess, systemd, etc.)
- Tracks pending work count for backpressure
- Enforces concurrency limits
- Does NOT execute tasks
```

### 2. ExecutionModeSelector
Five canonical execution modes:
- `kInline`: In-process function calls (no subprocess)
- `kSubprocess`: OS process with fork/execve
- `kSystemdUnit`: Managed systemd transient/managed unit
- `kDBusMethod`: D-Bus remote method invocation
- `kThread`: Thread-based parallel execution

### 3. RunnerState Machine
```
kPending → kRunning → [kWaiting] → kFinished

Progress Stages:
kDispatched → kExecuting → kObserving → kVerifying → kCompleted
```

### 4. InlineExecutor as Minimal Proof
Only `InlineExecutor` is implemented in Phase 0.13 for testing and lightweight operations.
Subprocess/systemd/dbus implementations are deferred to later phases.

## Implementation Details

### Runner (`src/runtime/runner.hpp`)
- State machine with `RunnerState` (pending, running, waiting, finished)
- Progress tracking with `ProgressStage`
- Context passed through execution stack via `RunnerContext`
- Retry logic uses `RetryPolicy` from Job
- Cancellation propagation to executor

### Executor (`src/runtime/executor.hpp`)
- Abstract `Executor` interface with virtual `execute()` method
- `InlineExecutor` for in-process execution (testing, read-only ops)
- Statistics: total_invocations_, successful_executions_, failed_executions_
- Execution context via `ExecutorInvocationContext`

### Dispatcher (`src/runtime/dispatcher.hpp`)
- Makes routing decisions based on task requirements and available mechanisms
- Backpressure tracking with `pending_work_count_` and `max_concurrent_executions_`
- `DispatcherRegistry` as DATA structure for mechanism registration
- Decision outcomes: `accept()` or `reject()`

## Rejected Alternatives

### 1. Single Executor Class with All Mechanisms
**Rejected**: Would create a god class mixing subprocess, systemd, D-Bus logic.

**Preferred**: Separate execution mechanisms via policy/strategy patterns deferred to later phases.

### 2. Global Execution Registry  
**Rejected**: Creates hidden global state, violates testability requirements.

**Preferred**: Local dispatcher instances passed as dependencies.

### 3. Unbounded Thread Pool
**Rejected**: Not required for minimal proof; could deadlock or consume resources unexpectedly.

**Preferred**: Bounded concurrency with explicit backpressure signals.

## Remaining Risks/Open Questions

1. **Cancellation propagation through OS processes**: Currently simulated via flag.
   - Deferred: pidfd/signalfd integration for proper process group handling

2. **Native timeout enforcement**: Currently simulated via clock polling
   - Deferred: timerfd integration for kernel-enforced timeouts

3. **Backpressure signaling**: Dispatcher tracks pending count but doesn't enforce limits yet
   - Deferred: Bounded work queue with caller blocking/rejection behavior
