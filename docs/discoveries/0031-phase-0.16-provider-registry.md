# Discovery 0031 — Provider Registry & System Boundaries (Phase 0.16)

- **Status:** ACCEPTED
- **Date:** 2026-09-24
- **Author:** Phase 0.16

## Summary

This discovery establishes Rebuntu's provider registry pattern for infrastructure tool
integration: how external providers (Docker, Ansible, etc.) can be discovered,
registered, selected, and invoked while maintaining stable contracts.

Three key relationships are established:

| Relationship | Direction | Example |
|--------------|-----------|---------|
| Interface → Consumer | Contract defines behavior | `ProviderRegistry` interface |
| Adapter → Interface | Implementation provides mechanism | `ProviderRegistryImpl` |
| Provider → Native Linux | Tool uses OS mechanisms | Docker CLI → fork/execve |

## Canonical Definitions

### Interface
An Interface is a declared contract that consumers depend on. It:
- Contains no implementation (what, not how)
- Is static: types, contracts, message formats
- Lives in `src/interfaces/`

### Adapter
An Adapter connects Rebuntu to a specific external/native mechanism. It:
- Isolates mechanism from semantics
- Implements Interface contracts declared elsewhere
- May depend on native Linux APIs

### Provider
A Provider is a concrete implementation of a capability that can be swapped.
It:
- Supplies interchangeable implementations
- Follows a stable interface contract
- May be selected by registry strategy

## Provider Registry Components

| Component | Purpose |
|-----------|---------|
| `ProviderId` | Unique string identifier for each provider |
| `ProviderAvailability` | State: unknown/available/unavailable/not_installed |
| `ProviderInfo` | Static metadata (name, description, version) |
| `ProviderSelector` | Strategy for selecting among providers |
| `ProviderRegistry` | Manager for registration and queries |

## Selection Policies

| Policy | Behavior |
|--------|----------|
| `kAny` | Any available provider is acceptable |
| `kFirst` | First registered that supports capability |
| `kPreferred` | Configurable preference with fallback |
| `kExplicit` | Caller specifies exact provider ID |

## Native Linux Mapping

| Rebuntu Concept | Native Mechanism |
|-----------------|------------------|
| Provider discovery | `std::filesystem::exists()` for executables |
| Process execution | `fork/execve` (via subprocess executor) |
| Availability assessment | Filesystem checks + version queries |

## Boundary Matrix

| Component | Owns | Delegates To |
|-----------|------|--------------|
| Interface | Contract definition | Native Linux mechanisms |
| Adapter | Implementation mechanism | Provider-specific tools |
| Registry | Provider selection strategy | Interface contracts |

## Ownership Boundaries

- **ProviderRegistry**: owns registration state and selector cache
- **ProviderSelector**: owns selection logic (not provider instances)
- **Native providers**: no Rebuntu ownership, external tools only

## Privilege Boundaries

- Registry operations: user-level access sufficient
- Provider availability checks: requires read access to PATH
- No privilege escalation in registry operations

## Persistence Requirements

- Registry state is transient (process lifetime)
- Provider info is re-assessed on each registration/selection

## Rejected Alternatives

### Giant Manager Class
Rejected: Single class combining registry, selector, and provider instances.

Reason: Violates separation of concerns; makes testing difficult.

### Global Registry
Rejected: Single global registry instance.

Reason: Creates hidden dependencies; hard to test in isolation.

### Dynamic Plugin Loading
Rejected: `dlopen`/plugin architecture for providers.

Reason: Overengineering; static linking suffices. Providers are optional.
