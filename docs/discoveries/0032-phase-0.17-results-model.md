# Discovery 0032 — Phase 0.17: Results, Outcomes, Errors, Verification & Evidence

**Status:** ACCEPTED  
**Date:** 2024-09-24  
**Author:** Agent Implementation  

## Executive Summary

This discovery establishes the canonical vocabulary for execution results, semantic outcomes,
errors, verification status, and evidence in Rebuntu. It resolves ambiguity between
execution success, semantic success, and verified success.

## Problem Statement

Historically, Rebuntu had fragmented result model definitions across multiple files:

1. `contracts.hpp` defined basic types: `SemanticStatus`, `Error`, minimal `Evidence`
2. `results.hpp` contained Phase 0.17 draft with overlapping/contradictory definitions
3. No clear distinction between:
   - Semantic outcome (what happened)
   - Verification status (was it checked against postconditions?)
   - Execution success (did the operation complete?)

The key invariant that needed to be formalized:

```
EXECUTED != SUCCEEDED != VERIFIED

EXIT STATUS 0 != VERIFIED SEMANTIC SUCCESS
```

## Canonical Definitions

### SemanticStatus (Phase 0.0, contracts.hpp)

Outcome classification independent of verification:

```cpp
enum class SemanticStatus {
    kSuccess,     // completed AND independently verified against postconditions
    kCompleted,   // completed the work, but verification was not performed/applicable
    kFailure,     // the attempt ran but the objective was not met
    kUnknown,     // the outcome could not be determined (NOT a negative observation)
    kCancelled,   // explicitly cancelled before completion
};
```

### VerificationStatus (Phase 0.17, results.hpp)

Postcondition verification result - orthogonal to semantic status:

```cpp
enum class VerificationStatus {
    kVerified,            // postconditions were independently verified and hold
    kNotVerified,         // verification was not performed
    kVerificationFailed,  // verification ran but postconditions did not hold
    kUnknown,             // could not determine verification status
};
```

### Evidence (Phase 0.17, results.hpp extension)

Provenance-bearing observation - DATA, not CONTROL:

```cpp
struct Evidence {
    std::string source;      // where this evidence came from (e.g., "procfs", "systemd")
    std::string value;       // the observed value / excerpt (bounded)
    std::string captured_at; // ISO-8601, UTC timestamp
};
```

Evidence is NEVER control authority. It never confers permission or authorization.

### FailureClassification (Phase 0.17)

Categorizes why execution failed:

```cpp
enum class FailureClassification {
    kExecution,
    kVerification,
    kValidation,
    kAuthorization,
    kResource,
    kTimeout,
    kCancelled,
    kUnknown,
};
```

## Core Distinctions

### 1. Execution vs Verification

```
EXECUTED SUCCESS + VERIFICATION FAILED = FAILURE (not SUCCEEDED)
EXECUTED SUCCESS + NO VERIFICATION = COMPLETED (not SUCCEEDED)
EXECUTED FAILURE = FAILURE
```

A process can exit with code 0 but have failed verification if postconditions don't hold.

### 2. UNKNOWN vs FALSE/FAILED

UNKNOWN is NOT the same as FALSE or FAILED:

- UNKNOWN means "could not determine"
- FALSE/FAILED means "determined to be false"

Acquisition failure (e.g., timeout, permission denied) produces UNKNOWN, not FAILURE.

### 3. DATA vs CONTROL

Evidence is DATA:
- Provenance-bearing observations
- Never confers authority
- Never bypasses authorization
- Cannot become control instructions

## Result Types

### ExecutionOutcome

For operations that don't return values:

```cpp
struct ExecutionOutcome {
    SemanticStatus status;
    
    static ExecutionOutcome success();
    static ExecutionOutcome completed_state();  // not verified
    static ExecutionOutcome failure();
    static ExecutionOutcome unknown(std::string message);
    static ExecutionOutcome cancelled(std::string reason);
};
```

### ExecutionResult<T>

For operations that return values:

```cpp
template <typename T>
struct ExecutionResult {
    SemanticStatus outcome;
    std::optional<T> value;
    bool verification_successful;
    std::vector<Evidence> evidence;
    
    bool succeeded() const {
        return outcome == SemanticStatus::kSuccess && verification_successful;
    }
};
```

### RetryAggregation

Preserves retry history:

```cpp
struct RetryAggregation {
    std::vector<RetryAttempt> attempts;
    std::chrono::system_clock::time_point first_attempt_at;
    std::chrono::system_clock::time_point last_attempt_at;
    SemanticStatus final_outcome;
};
```

A successful final result does NOT erase earlier failures.

### Key Design Decisions

1. **No evidence duplication**: Evidence struct defined once in contracts.hpp, extended via free functions
2. **Time-agnostic timestamps**: Use string format to avoid timezone issues
3. **Bounded values**: Evidence values are excerpts, not unbounded data
4. **Provenance tracking**: Optional provenance field records how evidence was obtained

## Verification Strategy

For an operation to be considered successful:

1. Execution completes (no crashes, timeout, or cancellation)
2. Postconditions are evaluated against observed state
3. Observed state matches expected postconditions
4. Evidence supports the verification conclusion

Example:

```cpp
// Package install operation
// 1. Execute: apt install foo (exit code 0)
// 2. Verify: dpkg -l foo | grep "^ii"
// 3. If grep succeeds, outcome = kSuccess, verified = true
// 4. If grep fails, outcome = kSuccess, verified = false -> overall FAILURE
```

## Known Limitations

1. Evidence retention policies not yet implemented (EvidenceRetention enum defined)
2. Secret redaction applied only at serialization boundaries (policy defined)
3. No automatic retry infrastructure (RetryAttempt/RetryAggregation types defined)

## Migration Notes

### Existing Code Patterns to Update

1. **Operations that check exit code only:**
   - Before: `if (exit_code == 0) return success;`
   - After: `return verify_postconditions() ? success : verification_failed;`

2. **Operations returning bool:**
   - Before: `bool installed = install_package();`
   - After: `ExecutionResult<void> result = install_package();`

3. **Error handling with strings:**
   - Before: `std::string error_msg;`
   - After: `std::optional<Error> error;` (structured)
