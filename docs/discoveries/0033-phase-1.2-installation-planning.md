# Discovery 0033 — Phase 1.2: Installation Planning & Environment Preparation

**Status:** ACCEPTED  
**Date:** 2026-09-24  
**Author:** Agent Implementation  

## Executive Summary

This discovery establishes the canonical C++ native installation planning module for Rebuntu Phase 1.2. It transforms validated installation intent and discovered host facts into an explicit, reviewable installation plan before any actual host mutation occurs.

## Problem Statement

Phase 1.0 established the bootstrap entry point but left planning incomplete:
- `planning.hpp/cpp` existed with stub implementations
- No build integration in CMakeLists.txt
- Evidence types referenced but not defined
- Discovery module had compilation issues (missing includes, namespace errors)

Key requirements from Phase 1.0 deferred to Phase 1.2:
1. Build install planning sources into the build system
2. Define `rebuntu::core::Evidence` for provenance-bearing observations
3. Fix discovery.hpp/cpp namespace and include issues
4. Integrate evidence chain from discovery to plan

## Canonical Architecture

### Installation Planning Flow

```
InstallationIntent (user declaration)
    ↓
Planner.produce_plan()
    ↓
InstallationPlan (reviewable, explicit steps)
    ↓
Bootstrap.authorize_execution() (privilege checks)
    ↓
Bootstrap.execute_steps() (plan execution)
    ↓
VerificationResult (independent verification)
```

### Core Types

```cpp
// InstallationIntent - User's declared intent for installation
struct InstallationIntent {
    std::string version;
    InstallationScope scope;  // kSystem or kUser
    bool skip_verification;
};

// InstallationPlan - Complete, reviewable plan with steps
struct InstallationPlan {
    enum class Status { kReady, kBlocked, kWarningOnly };
    
    std::vector<DependencyInfo> dependencies;
    std::vector<PreInstallationCheckResult> preflight_checks;
    std::vector<InstallationStep> steps;
};

// Planner - Produces plans from intent
class Planner {
    InstallationPlan produce_plan(const InstallationIntent&) const;
    bool has_blockers(const std::vector<PreInstallationCheckResult>&) const;
};
```

### Evidence Model

```cpp
struct Evidence {
    std::string subject;                    // What the evidence is about
    std::string source;                     // Where data came from (/etc/os-release, etc.)
    std::chrono::system_clock::time_point observed_at;
    std::string value;                      // "passed", "failed", version string, etc.
};

class EvidenceStore {
    void append(Evidence);
    const std::vector<Evidence>& records() const;
};
```

## Key Design Decisions

1. **C++20 Native**: Installation planning is implemented in native C++20, not Python or shell
2. **Planning First**: Plans are reviewable before execution - no implicit mutations
3. **Evidence Chain**: All preflight checks preserve provenance via `source` and `observed_at`
4. **Severity Levels**: kInfo/kWarning/kBlocker allows graceful degradation

## Verification Strategy

### Precondition Checks

1. **Supported Distribution**: ubuntu, debian, fedora, arch, centos (kBlocker if not supported in future)
2. **Root Privileges**: Required for kSystem scope (kWarning for user install)
3. **Bin Directory Writable**: /usr/bin or ~/.local/bin
4. **State Directory Writable**: /var/lib/rebuntu or ~/.local/state
5. **Package Manager Available**: apt, dnf, pacman (kWarning if none found)
6. **Home Directory Accessible**: Required for kUser scope
7. **Sufficient Free Space**: 50MB minimum

### Verification Order

```
1. Discovery → Host facts collected (read-only, no mutation)
2. Planning → InstallationPlan generated (reviewable, no mutation)
3. Authorization → Privilege checks passed
4. Execution → Steps applied (with dry_run protection)
5. Verification → Postconditions verified independently
```

## Migration Notes

### CMake Changes

Projects using the install module must now:
```cmake
# Build system must include rebuntu-install library
target_link_libraries(my_target PUBLIC rebuntu-install)
```

### API Changes

- `Bootstrap::execute_steps()` signature changed from `(InstallationPlan&)` to `(BootstrapResult&, InstallationPlan&)`
- This ensures steps can report their execution results properly
