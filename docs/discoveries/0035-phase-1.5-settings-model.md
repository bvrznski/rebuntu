## Summary

This document describes the implementation of Rebuntu's Phase 1.5 Settings Model, which establishes the canonical grammar for relatively stable explicit behavioral selections/toggles whose value is part of effective Rebuntu configuration.

## Architecture Overview

### Settings Model Components

| Component | Responsibility |
|-----------|----------------|
| `SettingKind` enum | Type of setting (Toggle, Selection, Choice) |
| `Scope` enum | Where setting applies (System, User, Session) |
| `SettingDefinition` struct | Setting specification with constraints |
| `SettingValue` struct | Concrete value with provenance tracking |
| `SettingChange` struct | Mutation request for a setting |
| `SettingsSchema` class | Collection of setting definitions forming a contract |
| `SettingsRegistry` class | Registry for managing schemas and values |
| `SettingsManager` class | High-level interface for managing settings |

### Core Principles

- **Setting ≠ State**: Setting = explicit behavioral toggle/selection (desired state); State = authoritative runtime-owned data (observed state)
- **Setting ≠ Option**: Setting = WHETHER an action occurs (boolean-like: on/off); Option = WHAT alternative to select
- **Setting ≠ Preference**: Setting = hard requirement or explicit toggle; Preference = soft choice that may be unsatisfied

## Rejected Alternatives

### Alternative 1: Separate Options Model
**Rejected**: Options are metadata on Settings (via `allowed_values`), not first-class objects.

### Alternative 2: Runtime Implementation Required
**Rejected**: The Settings model is a configuration contract grammar, not runtime implementation. Actual persistence (file I/O, systemd integration) belongs to later phases.
