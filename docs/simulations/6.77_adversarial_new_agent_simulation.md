## Repository State Analysis (Phase 6)

### Existing Architecture

1. **Core Contracts** (`src/system/core/`)
   - `contracts.hpp` defines: `SemanticStatus`, `Evidence`, `OperationDefinition`, `OperationResult`
   - Precondition/postcondition model with typed inputs/outputs
   - Verification semantics separate from execution success

2. **Command Model** (`src/system/command/`)
   - Typed command IR (not shell strings)
   - CommandIntent, CommandResolution, ExecutionPlan
   - SemanticKind: QUERY, OBSERVE, CONFIGURE, MANAGE, CREATE, UPDATE, REMOVE

3. **Environment Module** (`src/system/environment/`)
   - Authorization with `AuthorizationDecision`: ALLOW, DENY, REQUIRE_ELEVATION
   - Privilege system: UID/GID detection, elevation capability
   - Scope context: USER vs SYSTEM

4. **Operations Directory** (`src/operations/`)
   - Filesystem operations with full contract semantics
   - Pre/postconditions documented
   - Evidence collection for verification

5. **Adapters** (`src/adapters/`)
   - Native Linux mechanisms (procfs, sysfs, systemd D-Bus, netlink)
   - No shell command parsing for system state

6. **Build System** (`cpp/CMakeLists.txt`)
   - C++20 with proper compiler warnings
   - Unit tests via CTest
   - No Python dependencies in core libraries

### Architecture Flow (Phase 6)

```
User Request / CLI
    ↓
Shell parsing (C++) → CommandIntent IR
    ↓
Subject/target resolution → CapabilityReference
    ↓
Authorization check → Decision: ALLOW/DENY/REQUIRE_ELEVATION
    ↓
OperationRequest with typed parameters
    ↓

    ↓

```

## New-Agent Simulation Scenario

### Prompt Given to Agent

> You are a Rebuntu Phase 6 developer. Implement a new OS mutation: **create a user account**.
>
> Requirements:
> - User name must be specified as typed input (not shell string concatenation)
> - Precondition checks before mutation
> - Postcondition verification after mutation
> - Evidence collection for verification
> - No Python or shell commands
> - Use native Linux mechanisms only

### Expected Agent Behavior

1. **Discover existing patterns**
   - Look at `src/operations/filesystem.hpp` and `.cpp`
   - Look at `src/system/environment/user_identity.cpp` for user management
   - Check `src/system/command/model.hpp` for command model

2. **Identify location**
   - Add operation to `src/operations/users.hpp/.cpp`
   - Or extend `src/operations/filesystem.hpp` if user management fits there
   - NOT: create `python/user_manager.py`

3. **Implement typed contract**
```cpp
struct CreateUserInputs {
    std::string username;
    std::optional<int> uid;
    std::optional<std::string> home_dir;
    std::optional<std::string> shell;
    bool skip_if_exists = false;
};

struct CreateUserResult {
    core::SemanticStatus status;
    bool created;  // New user created vs already existed
    bool verified;
    std::vector<core::Evidence> evidence;
};
```

4. **Preconditions**
   - Caller must have elevated privilege (root)
   - Username must be valid (no special characters, not empty)
   - If UID specified, it must not already exist

5. **Native mechanism**
   - Use `useradd` via bounded subprocess with argv-style invocation
   - OR use native Linux APIs if available (NIS/LDAP integration)
   - NOT: `system("useradd " + username)` or shell concatenation

6. **Postconditions**
   - User exists in `/etc/passwd`
   - Home directory created (if requested)
   - Shell set correctly

7. **Evidence**
   - Observation of `/etc/passwd` after creation
   - Process exit result from useradd
   - Timestamp of operation

### Where Agent Might Go Wrong

1. **Option A: Python shell** ❌
```python

```

2. **Option B: Shell string concatenation** ❌
```cpp

system(cmd.c_str());
```
